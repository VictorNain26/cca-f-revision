1. Workflows vs. agents : le choix fondamental (Task 1.6 complement)

Le problème que cela resout

Quand on concoit un système base sur Claude, il faut choisir entre un workflow (séquence d'etapes predefinies, orchestree par le code) et un agent (séquence d'etapes decidees dynamiquement par le modèle). Le mauvais choix entraine soit un système rigide qui ne s'adapte pas, soit un système imprevisible difficile a tester.

WorkflowsAgents
EtapesPredéterminees par le développeurChoisies dynamiquement par le modèle
TestabilityFacile (séquence connue)Difficile (chemin imprevisible)
ReliabilityTaux de completion elevePlus bas (complexite déléguée au modèle)
Quand les utiliserLes etapes exactes sont connues a l'avanceLes details de la tache sont flous ou variables
Regle de decision : privilegiez les workflows pour la reliability. N'utilisez un agent que lorsque la flexibilite est reellement nécessaire. Les utilisateurs veulent des produits fiables, pas des agents impressionnants.

Les quatre workflow patterns

PatternPrincipeCas d'usage typique
ParallelizationSous-taches simultanees, puis agregationTaches decomposables sans dependances entre elles
ChainingEtapes sequentielles distinctesClaude ignore des contraintes dans les prompts longs → decouper en etapes
RoutingClassifier l'entree, puis dispatcher vers le bon pipelineDifferents types de requêtes necessitant un traitement different
Evaluator-optimizerProduire → evaluer → boucler jusqu'a satisfactionQualite variable necessitant un raffinement iteratif

Quand les subagents sont utiles — et quand ils nuisent

La question cle : est-ce que le travail intermediaire m'interesse ?

  • Non (seul le résultat compte) → déléguér a un subagent. Exemple : explorer comment l'authentification fonctionne dans un codebase inconnu.
  • Oui (je dois voir et reagir a chaque etape) → garder dans le thread principal. Exemple : executer des tests et analyser les erreurs.
Trois anti-patterns de subagents a connaitre :
  • Les « expert claims » : « You are a Python expert » n'ajoute aucune capacite reelle. Claude possede déjà ces connaissances. Preferer une description factuelle du role et du perimetre.
  • Les sequential pipelines : quand chaque etape depend des decouvertes de la precedente (reproduire → debugger → corriger), l'information se perd dans les transferts entre agents. Garder dans le thread principal.
  • Les test runners en subagent : un subagent qui retourne simplement « tests failed » cache les details de diagnostic dont on a besoin pour comprendre l'echec.

2. L'agentic loop — la boucle agentique (Task 1.1)

Le problème que cela resout

Un appel classique a l'API Claude produit une réponse en une seule fois. Mais dans un système agentique, la tache necessite souvent plusieurs actions successives : chercher un client, consulter sa commande, puis decider d'un remboursement. Il faut donc un mécanisme pour que Claude puisse agir, observer le résultat, puis agir a nouveau — en boucle — jusqu'a ce que le travail soit termine.

C'est exactement ce que fait l'agentic loop : un cycle request → response → tool execution → new request pilote par le modèle lui-même.

Le cycle observe — think — act — respond

Statut de l'acronyme OTAR : "observe-think-act-respond" est une mnemonique pedagogique communautaire, pas un terme officiel Anthropic. La doc officielle parle d'agentic loop lifecycle centre sur stop_reason et de phases gather context → take action → verify results. Connais le concept, mais ne cherche pas "OTAR" dans la doc Anthropic — tu ne le trouveras pas. C'est une grille de lecture utile pour raisonner autour des hooks et de l'API.

Chaque iteration de la boucle se décompose en quatre phases conceptuelles, exposees au modèle de maniere implicite :

PhaseCe que fait le modèleElement de l'API
ObserveLit le contexte courant : messages historiques, tool results recents, system promptTableau messages (avec tool_result blocks)
ThinkRaisonne sur l'etat (eventuellement via extended thinking, voir D4)thinking blocks (si actives) ou raisonnement implicite
ActDecide d'appeler un outil ou de produire une réponse finaletool_use block ou text block
RespondSoit attend le tool_result (boucle continue), soit terminestop_reason : "tool_use" ou "end_turn"
OTAR n'est pas un protocole de l'API — c'est une grille de lecture pour décrire le comportement de la boucle. L'examen utilise le vocabulaire "observe-think-act-respond" pour parler du fonctionnement standard d'un agent. Comprendre la grille permet de raisonner sur ou intervenir : un hook PreToolUse intercepte entre think et act, un hook PostToolUse intercepte au debut du prochain observe.

Comment ca fonctionne

A chaque iteration, votre code envoie l'historique complet a Claude (messages + tool results). Claude repond, et sa réponse contient un champ stop_reason qui détermine la suite :

Valeur de stop_reasonSignificationAction dans votre code
"tool_use"Claude veut appeler un outilExecuter l'outil, ajouter le tool_result a l'historique, relancer une iteration
"end_turn"Claude a termineAfficher le résultat a l'utilisateur, sortir de la boucle
"max_tokens"La limite de tokens est atteinteLa réponse est tronquee ; envisager d'augmenter max_tokens
L'approche est model-driven. C'est Claude qui choisit quel outil appeler a chaque etape, en s'appuyant sur le contexte accumule et les tool results precedents. Cela differe fondamentalement d'un arbre de decision code en dur (hardcoded), ou la séquence d'actions est figee a l'avance.

Exemple de code

while True:
    response = client.messages.create(
        model="claude-sonnet-4-6",
        messages=messages,
        tools=tools
    )
    # On ajoute la réponse complete a l'historique
    messages.append({"role": "assistant", "content": response.content})

    # Le SEUL signal fiable pour decider de la suite
    if response.stop_reason != "tool_use":
        break   # "end_turn" → la tache est terminee

    # On execute les outils demandes et on renvoie les tool_results
    tool_results = execute_tools(response.content)
    messages.append({"role": "user", "content": tool_results})

Les anti-patterns a connaitre

Trois erreurs classiques dans les systèmes agentiques mal concus :

  • Parser le texte de l'assistant pour y detecter des phrases comme « Task completed » ou « I'm done ». Le langage naturel n'est pas un signal fiable ; Claude peut écrire « done » tout en ayant encore un tool call en attente.
  • Utiliser une limite d'iterations arbitraire (max_iterations=5) comme condition d'arret principale. Cela peut interrompre une tache legitime en cours d'execution.
  • Verifier la presence de texte dans la réponse comme signal de fin. Claude peut generer du texte explicatif ET un tool_use block dans la même réponse.

Le seul signal fiable est stop_reason == "end_turn".

Pour l'examen : quand on vous demande comment déterminer si la boucle doit continuer ou s'arreter, la bonne réponse est toujours stop_reason. Les distracteurs proposeront du text parsing, des limites d'iterations ou la detection de contenu textuel.

3. L'architecture hub-and-spoke (Task 1.2)

Le problème que cela resout

Quand une tache est trop complexe pour un seul agent — par exemple, produire un rapport de recherche qui necessite a la fois de la recherche web, de l'analyse documentaire et de la synthese — il faut repartir le travail entre plusieurs agents spécialisés. Mais ces agents ont besoin d'etre coordonnes : qui fait quoi ? Qui agrege les résultats ? Qui gere les erreurs ?

L'architecture hub-and-spoke repond a ce besoin : un agent coordinateur (le hub) orchestre plusieurs subagents spécialisés (les spokes).

           Coordinator (hub)
           /     |     \
    Subagent 1   Subagent 2   Subagent 3
    (research)   (analysis)   (synthesis)

Les responsabilites du coordinateur

Le coordinateur est le chef d'orchestre. Il se charge de :

  1. Decomposer la tache principale en sous-taches cohérentes.
  2. Selectionner dynamiquement les subagents nécessaires.
  3. Deleguer en fournissant a chaque subagent le contexte dont il a besoin.
  4. Agreger et valider les résultats renvoyes par les subagents.
  5. Gerer les erreurs : decider de retry, d'adapter la requête ou de continuer avec des résultats partiels.
  6. Communiquer le résultat final a l'utilisateur.
Principe fondamental : le contexte des subagents est isole.

Les subagents n'heritent pas automatiquement de l'historique de conversation du coordinateur. Ils ne partagent pas non plus de memoire entre eux. Toute information nécessaire doit etre explicitement transmise dans le prompt du subagent. Et toute communication entre subagents transite par le coordinateur — jamais en direct — ce qui garantit l'observabilite et le controle des erreurs.

Le risque d'une décomposition trop etroite

Un piege frequent : le coordinateur décompose la tache de maniere trop restrictive, ce qui cree des angles morts.

Exemple concret : le coordinateur recoit « AI impact on creative industries » et cree trois sous-taches : « AI in digital art », « AI in graphic design » et « AI in photography ». Chaque subagent execute correctement sa mission, mais le rapport final ne couvre que l'art visuel — la musique, la litterature et le cinema sont totalement absents. Le problème n'est pas dans l'execution des subagents, mais dans la décomposition faite par le coordinateur.

Bonnes pratiques

  • Partitionner explicitement l'espace de recherche avant de déléguér, pour eviter les doublons et les angles morts.
  • Prevoir des boucles de raffinement : le coordinateur evalue la synthese, identifie les lacunes et relance des sous-taches si nécessaire.
  • Ne jamais court-circuiter le coordinateur : même si cela semble plus efficace qu'un subagent envoie directement ses résultats a un autre, le passage systematique par le hub assure la visibilite centralisee, la gestion uniforme des erreurs et le controle de ce que chaque subagent recoit.

4. Les strategies de décomposition (Task 1.6)

Le problème que cela resout

Toutes les taches ne se décomposent pas de la même maniere. Une code review suit toujours les mêmes etapes (lire, analyser, reporter), tandis qu'une investigation dans un codebase inconnu revele ses sous-taches au fur et a mesure. Choisir la mauvaise strategie entraine soit de la rigidite inutile, soit du chaos.

Fixed pipeline (prompt chaining)

Chaque etape est definie a l'avance et s'execute en séquence :

Document → Metadata extraction → Data extraction → Validation → Enrichment → Output

Quand l'utiliser : la structure de la tache est previsible, toutes les etapes sont connues, et on a besoin de stabilite et de reproductibilite.

Dynamic adaptive décomposition

Les sous-taches emergent en fonction des résultats intermediaires :

  1. Objectif : « Ajouter des tests pour un codebase legacy. »
  2. Premiere etape : mapper la structure (Glob, Grep).
  3. Decouverte : trois modules sans tests, deux avec une couverture partielle.
  4. Priorisation : commencer par le module de paiements (risque eleve).
  5. Surprise en cours de route : une dependance vers une API externe non mockee.
  6. Adaptation : creer le mock avant d'écrire les tests.

Quand l'utiliser : taches d'investigation ouvertes, perimetre inconnu au depart, chaque etape depend de ce que la precedente a revele.

La multi-pass review pour les grosses PR

Quand une pull request touche plus de dix fichiers, une analyse en une seule passe produit des résultats inconsistants : commentaires detailles sur certains fichiers, superficiels sur d'autres, et des contradictions (un pattern signale dans un fichier, approuve dans un autre).

La solution : decouper en deux passes :

PassePerimetreCe qu'elle detecte
Pass 1 — per-fileChaque fichier analyse individuellementBugs locaux, problèmes de qualite, vulnerabilites
Pass 2 — intégrationRelations entre les fichiersTypes inconsistants, dependances circulaires, flux de donnees casses
Pour l'examen : le prompt chaining convient aux taches previsibles et repetables (review, migration). La dynamic décomposition convient aux investigations ouvertes ou les sous-taches emergent en cours d'execution.

5. Le Task tool, context passing et spawning (Task 1.3)

Le problème que cela resout

Le coordinateur a besoin d'un mécanisme concret pour creer des subagents et leur transmettre leur mission. Dans le Claude Agent SDK, ce mécanisme s'appelle l'outil Task.

Comment ca fonctionne

Pour qu'un coordinateur puisse creer des subagents, son allowedTools doit inclure "Task". Chaque appel a Task cree un subagent avec son propre contexte isole.

coordinator = AgentDefinition(
    name="coordinator",
    allowed_tools=["Task", "get_customer", "lookup_order"]
)

Le context passing explicite

Les subagents ne recoivent rien automatiquement du coordinateur. Tout le contexte nécessaire doit figurer dans le prompt de la tache déléguée.

Mauvais : Task: "Analyse le document." — le subagent ne sait pas quel document, n'a aucun résultat anterieur et ignore le format de sortie attendu.
Bon : Task: "Analyse le document suivant. Document : [texte complet]. Resultats de recherche prealables : [donnees]. Format de sortie attendu : [schema]." — le subagent dispose de tout ce qu'il faut pour travailler de maniere autonome.

Lors du context passing, utilisez des formats structures qui separent clairement les donnees des metadonnees (source, date, type). Cela evite toute confusion et facilite l'agregation par le coordinateur. (Source : guide officiel, Task 1.3.)

Le parallel spawning

Le coordinateur peut emettre plusieurs appels Task dans une seule réponse. Les subagents s'executent alors en parallele, ce qui accelere considerablement le traitement :

# Une seule réponse du coordinateur contient :
Task 1 : "Rechercher des articles sur X"
Task 2 : "Analyser le document Y"
Task 3 : "Rechercher des articles sur Z"
# → Les trois s'executent simultanement (parallel execution).

La configuration AgentDefinition

agent = AgentDefinition(
    name="customer_support",
    description="Handles customer returns and order issues",
    system_prompt="You are a customer support agent...",
    allowed_tools=["get_customer", "lookup_order",
                   "process_refund", "escalate_to_human"]
)

La description joue un double role : elle détermine quand le coordinateur decide de lancer ce subagent, et elle influence la qualite du prompt que le coordinateur redige pour lui. Une description vague produit des delegations vagues.

Redigez les prompts du coordinateur en termes d'objectifs et de criteres de qualite (« le rapport doit couvrir au moins cinq secteurs avec des sources datees ») plutot qu'en instructions procedurales etape par etape.

Les subagents dans Claude Code

Dans Claude Code, les subagents personnalises se configurent dans .claude/agents/nom-du-subagent.md. Le frontmatter definit les metadonnees, et la suite constitue le system prompt :

---
name: code-quality-reviewer
description: Reviews code for quality, security, and best practices.
  You must tell the agent precisely which files to review.
tools: Bash, Glob, Grep, Read
model: sonnet
color: purple
---
You are an expert code reviewer. Provide your review in:
1. Summary  2. Critical Issues  3. Major Issues
4. Minor Issues  5. Recommendations  6. Approval Status
7. Obstacles Encountered

Les quatre caracteristiques d'un subagent efficace

#CaracteristiquePourquoi c'est important
1Une description spécifiqueElle controle quand le subagent est lance et influence la qualite du prompt d'entree.
2Un structured output formatC'est l'amelioration n° 1 : cela cree des points d'arret naturels et empeche le subagent de tourner trop longtemps.
3Le signalement des obstaclesSi le subagent decouvre un contournement (dependance manquante, flag special), cette information doit remonter pour eviter que le thread principal ne la redecouvre.
4Des outils limites au strict nécessaireUn subagent de recherche n'a besoin que de Glob, Grep, Read. Un reviewer y ajoute Bash. Trop d'outils (18 au lieu de 4-5) degrade la fiabilite de selection.

6. Programmatic enforcement et hooks (Tasks 1.4 & 1.5)

Le problème que cela resout

Dans un workflow de support client, il est critique de verifier l'identite du client avant de traiter un remboursement. On peut l'écrire dans le prompt… mais les instructions dans le prompt ont un taux de conformite de l'ordre de 90-95 %, pas 100 %. Sur des milliers d'interactions, même un faible taux d'echec peut causer des remboursements verses au mauvais client.

Le programmatic enforcement resout ce problème en rendant la violation impossible par le code, plutot qu'improbable par le prompt.

De même, les outils MCP tiers renvoient souvent des donnees dans des formats heterogenes : un outil retourne des timestamps Unix, un autre de l'ISO 8601, un troisieme des codes numeriques de statut. Si Claude recoit ces formats bruts, il peut mal les interpreter. Les hooks repondent a ces besoins en interceptant les tool calls a des points precis de l'agentic loop.

Note : cette section couvre les hooks de l'Agent SDK (niveau programmatique). Pour les hooks de Claude Code (niveau configuration), voir D3, section 7.

Exemple concret : les logs de production montrent que dans 12 % des cas, l'agent saute l'appel a get_customer et appelle directement lookup_order en se fiant au nom fourni par le client, ce qui entraine parfois des remboursements incorrects.

La solution : un prerequis programmatique qui bloque les appels a lookup_order et process_refund tant que get_customer n'a pas retourne un identifiant client verifie. Ni les few-shot examples ni un prompt renforce ne suffisent — les conséquences financieres exigent une garantie deterministe.

PreToolUse : bloquer les actions non conformes

Ce hook intercepte un tool call avant son execution et peut le bloquer ou le rediriger :

@hook("PreToolUse")
def enforce_refund_limit(tool_call):
    if tool_call.name == "process_refund" and tool_call.args.amount > 500:
        return redirect_to_escalation(tool_call)

PostToolUse : normaliser les donnees avant qu'elles n'atteignent Claude

Ce hook intercepte le tool result après l'execution de l'outil, mais avant que le modèle ne le traite :

@hook("PostToolUse")
def normalize_dates(tool_result):
    # Unix timestamp  →  ISO 8601
    # "Mar 5, 2025"   →  "2025-03-05"
    # Status code 2   →  "shipped"
    return normalized_result

Hooks vs. instructions dans le prompt

C'est l'une des distinctions les plus testees a l'examen. La regle est simple :

Hooks (programmatic enforcement)Prompt instructions
GarantieDeterministe (100 %)Probabiliste (> 90 %, mais pas 100 %)
Quand les utiliserBusiness rules critiques, operations financieres, conformite reglementairePreferences generales, formatting, recommandations
ExempleBloquer les remboursements superieurs a 500 $« Try to resolve the issue before escalating »

Le structured handoff lors d'une escalation

Quand l'agent decide d'escalader vers un operateur humain, celui-ci n'a pas accès au transcript complet de la conversation. Le resume transmis doit donc etre complet et autosuffisant :

{
  "customer_id": "CUST-12345",
  "issue_summary": "Refund request for damaged item",
  "order_id": "ORD-67890",
  "root_cause": "Item arrived damaged; photos attached",
  "actions_taken": [
    "Identity verified via get_customer",
    "Order confirmed via lookup_order",
    "Replacement offered — customer insists on refund"
  ],
  "refund_amount": "$89.99",
  "recommended_action": "Approve full refund",
  "escalation_reason": "Customer requested to speak with a manager"
}

Voir aussi : D5, section 2 pour les escalation patterns detailles et la calibration par criteres + few-shot.

Les requêtes multi-aspects

Quand un client inclut plusieurs problèmes dans un même message (« Je veux un remboursement pour la commande #1234 ET mettre a jour l'adresse de livraison de la commande #5678 »), la bonne approche consiste a décomposer en elements distincts, les traiter en parallele avec un contexte client partage, puis synthetiser une réponse unifiee.

La regle absolue : quand l'echec a des conséquences financieres, legales ou de securite → hooks. Les prompt instructions ne suffisent jamais pour ces cas-la.

Failure recovery patterns (retries, circuit breakers, partial results)

Au-dela du structured handoff (D5 §3 — propagation d'erreur), un agent doit decider quand reessayer, comment degrader, et quand abandonner. Cinq patterns standards.

Pattern 1 — Retry avec backoff exponentiel

Pour les erreurs transient (timeout, 503, rate limit). Une seule tentative supplementaire est rarement suffisante ; la plupart des SDK Anthropic retentent automatiquement avec un delai croissant.

// Backoff : 1s → 2s → 4s → 8s (max 4 tentatives en general)
attempts: 1 → wait 1s → 2 → wait 2s → 3 → wait 4s → 4 → fail

// Configuration cote SDK Anthropic
client = Anthropic(max_retries=3)
Type d'erreurRetry pertinent ?Strategie
503, timeout, networkOuiBackoff exponentiel, 3-4 tentatives
429 (rate limit)OuiRespecter Retry-After header
400 (validation)Oui après correctionModifier la requête (retry-with-feedback, voir D4 §4.4)
401, 403 (auth)NonEscalader, refresh token
500 (erreur serveur metier)Selon contexte1 retry max, sinon propager

Pattern 2 — Circuit breaker

Apres N echecs consecutifs sur un même outil ou serveur, arreter de tenter pendant une fenetre de temps. Evite de saturer un service déjà en panne et permet a l'agent de degrader proprement.

// Etats d'un circuit breaker
CLOSED   : tout passe normalement (etat initial)
OPEN     : echec persistant detecte, on bloque sans tenter (cooldown 30s-5min)
HALF-OPEN: cooldown ecoule, on laisse passer 1 requête test
           — succes → CLOSED ; echec → OPEN a nouveau
Quand l'utiliser : dans les systèmes multi-agents avec dependances externes (API tierces, MCP servers distants). Un circuit breaker par dependance evite l'effet domino — un service en panne ne fait pas tomber l'agent entier.

Pattern 3 — Partial results / graceful degradation

Plutot qu'echouer en bloc, livrer ce qui a fonctionne avec une annotation explicite de ce qui manque. C'est le cousin direct des coverage annotations de D5 §3.

// Resultat d'un agent multi-source qui a partiellement echoue
{
  "status": "partial_success",
  "completed": ["web_search", "doc_analysis"],
  "failed": ["patent_search"],
  "results": { ... },
  "missing_data": "Patent search timed out — patent landscape not covered",
  "confidence": 0.75
}
EXAM TIP : sur les questions de scenario Multi-Agent Research, la bonne réponse face a un echec partiel est presque toujours "continuer avec partial results et annoter les lacunes", pas "abandonner le workflow" ni "retry indefiniment".

Pattern 4 — Compensating actions (rollback)

Quand un workflow multi-etapes echoue au milieu (etape 3 sur 5), il faut defaire les effets des etapes déjà executees pour eviter un etat incohérent. Distinct des transactions DB classiques car les agents font souvent appel a des systèmes sans transactions distribuees.

// Saga pattern : a chaque action, definir sa compensation
def book_trip():
    flight = book_flight()       # action 1
    try:
        hotel = book_hotel()     # action 2
        try:
            car = book_car()     # action 3
        except:
            cancel_hotel(hotel)  # compensate action 2
            cancel_flight(flight) # compensate action 1
            raise

Pattern 5 — Idempotence et keys

Pour rendre les retries surs, chaque action doit etre idempotente : la repeter ne change pas le résultat. Les API exposent souvent un paramètre idempotency_key pour cela.

// Stripe-style : même key = même charge, jamais double
POST /v1/refunds
Idempotency-Key: refund-CUST-12345-ORDER-67890
Anti-pattern critique : retry sans idempotence sur une action a effet de bord. Exemple classique : retry de process_refund après un timeout reseau — sans idempotency key, vous avez peut-etre rembourse deux fois. Toujours verifier l'idempotence avant d'autoriser un retry sur une action transactionnelle.

Decision tree : quel pattern utiliser

SituationPattern
Erreur transient (timeout, 503)Retry + backoff exponentiel
Service externe en panne prolongeeCircuit breaker
Sous-tache d'une recherche multi-sourcePartial results + coverage annotation
Workflow transactionnel multi-etapesCompensating actions (saga)
Toute action a effet de bordIdempotency key
Cas critique financier/legalHook PreToolUse + idempotency + audit log

Human-in-the-loop comme pattern d'architecture

Le human-in-the-loop (HITL) n'est pas seulement l'escalation en fin de workflow (vue en D5 §2). C'est un pattern d'architecture ou un humain est integre dans la boucle decisionnelle de l'agent, pas seulement en sortie.

Quatre points d'insertion d'un humain dans la boucle

Pattern HITLOu l'humain intervientCas d'usage
1. Approval gateAvant l'execution d'une action sensibleOperations financieres, deploiements, suppressions
2. DisambiguationQuand l'agent detecte une ambiguiteMultiple matches client, intention floue
3. Quality reviewSur un echantillon de sortiesExtraction de donnees, classification, content moderation
4. Escalation handoffQuand l'agent ne peut pas resoudreSupport client (vu en D5 §2)

Pattern 1 — Approval gate (validation avant action)

L'agent prepare une action sensible et attend la validation humaine avant d'executer. Implementation typique :

// L'agent declare son intention via un tool dedie
<tool_use name="propose_refund">
  customer_id: CUST-12345
  amount: 489.99
  reason: "Defective item, customer has photos"
</tool_use>

// Le tool ne fait PAS le refund — il cree une demande d'approbation
// dans un dashboard humain et retourne :
<tool_result>
  status: "awaiting_approval"
  approval_id: "APR-2024-0042"
  timeout: "2024-12-15T18:00:00Z"
</tool_result>

// L'agent doit alors continuer son workflow (informer le client) ou
// boucler avec poll_approval(APR-2024-0042) selon la latence acceptable
Couplage avec les hooks : un approval gate est typiquement implemente via un hook PreToolUse qui intercepte les actions sensibles, declenche une notification humaine, et bloque l'execution jusqu'a réponse. Le hook offre la garantie deterministe que l'humain est consulte (vs. une simple instruction dans le prompt qui peut etre contournee).

Pattern 2 — Disambiguation

Quand l'agent detecte une ambiguite (3 clients avec le même nom de famille, requête avec plusieurs interpretations possibles), au lieu de deviner, il demande des informations supplementaires.

// L'agent detecte 3 matches et n'invente pas
"J'ai trouve 3 comptes au nom de Smith. Pour confirmer le votre,
 pouvez-vous fournir votre email ou les 4 derniers chiffres de
 votre numero de telephone enregistre ?"
Anti-pattern : deviner. Si plusieurs candidats matchent, l'agent ne doit jamais choisir le "plus probable" sur des criteres implicites. Le risque (mauvais client, mauvais ordre) excede largement le cout d'une interaction supplementaire.

Pattern 3 — Quality review (echantillonnage)

Pour les workflows automatises a grand volume (extraction de donnees, classification), un humain revoit periodiquement un echantillon stratifie (D5 §5) des sorties. Le but : detecter les derives, calibrer les seuils de confiance, ameliorer les prompts.

Strategie d'echantillonnageCas d'usage
Aleatoire stratifie par catégorieMesure du taux d'erreur global
Tous les cas low-confidence (< 0.7)Calibration des seuils
Cas a fort enjeu (montant > 1000$)Risk-weighted review
Nouveaux patterns detectesAdaptation aux donnees

Pattern 4 — Escalation handoff

Vu en detail en D5 §2 (escalation patterns + structured handoff). C'est le pattern HITL "fin de boucle" — l'agent passe la main quand il a epuise ses options ou rencontre un cas hors perimetre.

Architecture combinee : les 4 patterns dans un même système

+----------------------------------------------+
|  Agent de support client                     |
|                                              |
|  Disambiguation gate (Pattern 2)             |
|     - Multiple matches ? Ask user            |
|                                              |
|  Approval gate (Pattern 1, hook PreToolUse)  |

EXAM TIP : les questions de scenario Customer Support testent souvent la combinaison de plusieurs patterns HITL, pas un seul. Si une question oppose "ajouter une instruction dans le prompt" et "implementer un hook PreToolUse comme approval gate" pour une action critique, la bonne réponse est toujours le hook (deterministe). Voir aussi §6 sur le programmatic enforcement.

7. La gestion des sessions (Task 1.7)

Le problème que cela resout

Les investigations complexes s'etalent souvent sur plusieurs sessions de travail. Entre deux sessions, des fichiers peuvent etre modifies, et le contexte accumule peut devenir obsolete. Il faut des mécanismes pour reprendre intelligemment la ou l'on s'est arrete — ou choisir de repartir de zero avec un resume.

--resume : reprendre une session

claude --resume investigation-auth-bug

Continue la conversation avec le contexte sauvegarde. Utile quand le travail s'etale sur plusieurs heures ou jours, a condition que les fichiers n'aient pas trop change entre-temps.

fork_session : explorer deux pistes en parallele

     Investigation du codebase
              |
         fork_session
          /         \
     Approach A      Approach B
      (Redux)        (Context API)

Les deux branches heritent du contexte commun jusqu'au point de bifurcation, puis divergent independamment. Ideal pour comparer des strategies ou tester des hypotheses.

Quand choisir quoi

SituationChoix recommandé
Le contexte precedent est encore valide (fichiers inchanges)--resume
Les tool results sont obsoletes (fichiers modifies)Nouvelle session avec un resume structure injecte
On veut comparer deux approchesfork_session
Beaucoup de temps a passe et le contexte s'est degradeNouvelle session : « Here's a summary of our findings… »
Il est souvent plus fiable de demarrer une nouvelle session avec un resume structure que de reprendre avec des tool results potentiellement obsoletes. Un resume bien ecrit perd peu d'information et offre un contexte frais.

8. Synthese + questions d'auto-evaluation

Si vous ne deviez retenir que l'essentiel de ce domaine :

Workflows vs. agents

  • Privilegier les workflows (reliability) ; reserver les agents aux situations ou la flexibilite est indispensable.
  • 4 workflow patterns : parallelization, chaining, routing, evaluator-optimizer.

L'agentic loop

  • Cycle observe-think-act-respond (OTAR) — grille de lecture conceptuelle de chaque iteration.
  • stop_reason == "tool_use" → continuer. "end_turn" → terminer. C'est le seul signal fiable.
  • Ne jamais parser le texte de l'assistant, utiliser des limites d'iterations arbitraires ou verifier la presence de texte comme signal de fin.
  • Hooks PreToolUse = entre think et act ; PostToolUse = au debut de l'observe suivant.

Failure recovery

  • 5 patterns : retry+backoff exponentiel / circuit breaker / partial results / compensating actions (saga) / idempotency keys.
  • Retry pertinent : 503, timeout, rate limit (429), 400 après correction. Non pertinent : 401/403.
  • Circuit breaker (CLOSED/OPEN/HALF-OPEN) pour les dependances externes en panne prolongee.
  • Partial results + coverage annotations pour les workflows multi-source (lien D5 §3).
  • Anti-pattern critique : retry sans idempotency key sur action a effet de bord (double remboursement).

Human-in-the-loop (HITL)

  • 4 patterns : approval gate / disambiguation / quality review (echantillon) / escalation handoff.
  • Approval gate = hook PreToolUse + notification humaine + blocage jusqu'a réponse.
  • Disambiguation = demander des infos quand plusieurs candidats matchent ; ne jamais deviner.
  • Quality review = echantillonnage stratifie + calibration des seuils (lien D5 §5).
  • Escalation handoff = structured handoff (lien D5 §2).
  • Combinaison : les 4 patterns coexistent dans un système robuste, ils ne s'excluent pas.

L'architecture multi-agents (hub-and-spoke)

  • Le coordinateur (hub) gere toute la communication entre subagents (spokes).
  • Les subagents ont un contexte isole : le context passing doit etre explicite.
  • L'outil Task est le mécanisme de creation ; allowedTools doit inclure "Task".
  • Plusieurs appels Task dans une seule réponse = parallel execution.
  • Attention a la décomposition trop etroite → couverture incomplete.

Le programmatic enforcement et les hooks

  • Conséquences financieres, legales ou de securite → hooks (garantie a 100 %).
  • Preferences et recommandations → prompt instructions (probabiliste).
  • PostToolUse pour normaliser les donnees heterogenes. PreToolUse pour bloquer les actions non conformes.

La décomposition

  • Fixed pipeline (prompt chaining) pour les taches previsibles. Dynamic décomposition pour les investigations ouvertes.
  • Multi-pass review pour les grosses PR : pass per-file + pass intégration.

Les sessions

  • --resume si le contexte est encore valide, fork_session pour comparer, nouvelle session si les donnees sont obsoletes.
  • 4-5 outils maximum par subagent ; un structured output format est l'amelioration n° 1.

Questions d'auto-evaluation

Q1 : Situation : les logs montrent que dans 12% des cas, l'agent saute get_customer et appelle directement lookup_order, causant des remboursements incorrects. Quel changement est le plus efficace ? A) Ajouter un programmatic precondition qui bloque lookup_order et process_refund tant que get_customer n'a pas retourne un ID verifie. B) Ameliorer le system prompt. C) Ajouter des few-shot examples. D) Implementer un routing classifier.

Reponse : A

Les conséquences financieres (remboursements incorrects) exigent un programmatic enforcement deterministe, pas une amelioration probabiliste du prompt. B et C ameliorent la conformite mais ne la garantissent pas (toujours un risque residuel sur des milliers d'interactions). D (routing classifier) resout un problème de dispatch, pas un problème de sequencage obligatoire d'outils. Seul un precondition programmatique rend la violation impossible.

Q2 : Situation : le système de recherche sur 'AI impact on creative industries' ne couvre que l'art visuel. Le coordinateur a décompose en : 'AI in digital art', 'AI in graphic design', 'AI in photography'. Quelle est la cause ? A) Le synthesis agent ne detecte pas les lacunes. B) Le coordinateur a décompose trop etroitement. C) Le web search agent ne cherche pas assez. D) Le document analysis agent filtre les sources non-visuelles.

Reponse : B

Le coordinateur a décompose la tache en sous-taches toutes centrees sur l'art visuel, excluant la musique, la litterature et le cinema. Chaque subagent a correctement execute sa mission — le problème est en amont, dans la décomposition trop etroite. A est incorrect car le synthesis agent ne peut synthetiser que ce qu'il recoit. C et D sont incorrects car les subagents ont bien fait leur travail dans le perimetre qu'on leur a donne.

Q3 : Situation : un web-search subagent timeout. Comment propager l'erreur au coordinateur ? A) Retourner structured error context (failure type, query, partial results, alternatives). B) Retry automatique + status generique 'search unavailable'. C) Retourner un empty result set marque success. D) Propager l'exception au top-level handler qui termine tout le workflow.

Reponse : A

Un structured error context permet au coordinateur de prendre une decision intelligente : relancer avec une requête differente, utiliser les résultats partiels, ou déléguér a un autre subagent. B masque l'information utile derriere un retry aveugle et un message generique. C est dangereux car il fait croire que la recherche a reussi alors qu'elle a echoue. D est disproportionne — un timeout d'un subagent ne devrait pas tuer tout le workflow.

Q4 : Comment votre code détermine-t-il si l'agentic loop doit continuer ou s'arreter ? A) Verifier stop_reason : continuer si tool_use, arreter si end_turn. B) Parser le texte de l'assistant pour des phrases comme 'I'm done'. C) Utiliser une limite d'iterations (max_iterations=5). D) Verifier si la réponse contient du texte.

Reponse : A

stop_reason est le SEUL signal fiable pour déterminer si la boucle doit continuer. B est fragile car Claude peut écrire « done » tout en ayant un tool call en attente dans la même réponse. C peut interrompre prematurement une tache legitime. D est trompeur car Claude peut generer du texte explicatif ET un tool_use block simultanement.

Q5 : Situation : une investigation complexe s'etale sur plusieurs jours. Les fichiers ont change depuis la derniere session. Comment reprendre ? A) --resume pour continuer la session. B) fork_session pour explorer deux pistes. C) Nouvelle session avec un resume structure injecte. D) Relancer la même commande.

Reponse : C

Les fichiers ayant change, les tool results de la session precedente sont obsoletes (stale). --resume (A) chargerait ces résultats perimes, ce qui peut induire Claude en erreur. fork_session (B) sert a comparer deux approches, pas a gerer des donnees obsoletes. Relancer la même commande (D) perd tout le contexte accumule. Une nouvelle session avec un resume structure preserve les conclusions importantes tout en offrant un contexte frais base sur l'etat actuel des fichiers.

Q6 : Situation : votre agent appelle process_refund via une API tierce. Le premier appel timeout au bout de 30 secondes. L'agent retry automatiquement. Quel est le risque, et comment le neutraliser ? A) Aucun risque — un timeout signifie que la requête a echoue. B) Risque de double remboursement — passer un idempotency_key dans la requête pour que l'API reconnaisse les doublons. C) Augmenter le timeout a 60 secondes. D) Demander la confirmation a Claude avant de retry.

Reponse : B. Un timeout reseau ne signifie pas que la requête n'a pas atteint le serveur — elle a peut-etre ete traitee, mais la réponse n'est jamais revenue au client. Sans idempotency_key, le retry creerait un second remboursement sur la même commande. Avec une key (par exemple refund-CUST-12345-ORDER-67890), l'API reconnait que c'est la même operation et retourne le résultat de la premiere execution. C ne resout pas le problème de fond. D ne resout rien (Claude n'a pas plus d'info que le code).

Q7 : Situation : votre agent multi-source dependait de 4 APIs externes. L'API patents tombe en panne pour 30 minutes. L'agent retry chaque appel 4 fois avant d'echouer, multipliant la latence par 4 sur cette branche pendant toute la durée de la panne. Quel pattern resout proprement ce problème ? A) Reduire le nombre de retries. B) Implementer un circuit breaker sur l'API patents : après 3 echecs consecutifs, ouvrir le circuit pendant 5 min, puis tester en half-open. C) Supprimer la branche patents du workflow. D) Augmenter le nombre de subagents.

Reponse : B. Un circuit breaker arrete les appels vers une dependance en panne prolongee, evitant le gaspillage de latence et de tokens. Les autres branches du workflow continuent de fonctionner ; la branche patents est annotee comme "indisponible" via partial results. A est un compromis grossier (degradera la fiabilite quand l'API marche). C abandonne la fonctionnalite. D ajoute de la complexite sans traiter la cause.

Q8 : Situation : votre agent de support client peut emettre des remboursements jusqu'a 5000$. La direction veut une approbation humaine au-dela de 500$. Vous avez le choix entre : (1) ajouter "always ask for approval if amount > 500" dans le system prompt, (2) implementer un hook PreToolUse qui intercepte process_refund, ouvre une demande d'approbation et bloque jusqu'a réponse. Lequel et pourquoi ? A) Option 1 — c'est plus rapide a implementer. B) Option 1 — Claude est très fiable sur le suivi d'instructions. C) Option 2 — un approval gate via hook PreToolUse offre une garantie deterministe ; les instructions textuelles sont probabilistes (> 90 % mais pas 100 %), insuffisantes pour des decisions financieres. D) Les deux donnent le même résultat.

Reponse : C. C'est l'application directe du principe vu en §6 (programmatic enforcement) couplee au pattern HITL "approval gate". Pour toute action a conséquence financiere, legale ou de securite, l'enforcement doit etre deterministe via un hook. Une instruction prompt peut etre contournee, mal interpretee, ou oubliee dans un contexte long. Un hook PreToolUse rend la violation impossible. A et B reposent sur un raisonnement de risque inacceptable a 1 % d'echec sur des milliers de transactions.
