1. Workflows vs. agents : le cadrage (hors task statements)

Le problème que cela résout

Concevoir un système avec Claude impose un choix : workflow (étapes prédéfinies, orchestrées par le code) ou agent (étapes décidées dynamiquement par le modèle). Se tromper donne soit un système rigide, soit un système imprévisible et difficile à tester.

WorkflowsAgents
ÉtapesPrédéterminées par le développeurChoisies dynamiquement par le modèle
TestabilityFacile (séquence connue)Difficile (chemin imprévisible)
ReliabilityTaux de completion élevéPlus bas (complexité déléguée au modèle)
Quand les utiliserLes étapes exactes sont connues à l'avanceLes détails de la tâche sont flous ou variables
Règle de décision : privilégiez les workflows pour la reliability. N'utilisez un agent que lorsque la flexibilité est réellement nécessaire. Les utilisateurs veulent des produits fiables, pas des agents impressionnants.

L'essai Anthropic « Building effective agents » nomme cinq patterns de workflow (prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer). Le référentiel n'en retient que deux stratégies de décomposition, traitées en section 4, et le pattern coordinateur-subagents, traité en section 3 : les autres noms ne sont pas matière d'examen.

Quand les subagents sont utiles — et quand ils nuisent

La question clé : est-ce que le travail intermédiaire m'intéresse ?

  • Non (seul le résultat compte) → déléguer à un subagent. Exemple : explorer comment l'authentification fonctionne dans un codebase inconnu.
  • Oui (je dois voir et réagir à chaque étape) → garder dans le thread principal. Exemple : exécuter des tests et analyser les erreurs.

2. L'agentic loop — la boucle agentique (Task 1.1)

Le problème que cela résout

Un appel classique à l'API Claude produit une réponse en une seule fois. Mais dans un système agentique, la tâche nécessite souvent plusieurs actions successives : chercher un client, consulter sa commande, puis décider d'un remboursement. Il faut donc un mécanisme pour que Claude puisse agir, observer le résultat, puis agir à nouveau — en boucle — jusqu'à ce que le travail soit terminé.

C'est exactement ce que fait l'agentic loop : un cycle request → response → tool execution → new request piloté par le modèle lui-même.

Les phases d'une itération de la boucle

Cadre officiel : le guide décrit l'agentic loop lifecycle piloté par stop_reason — envoyer une requête à Claude, exécuter les outils demandés, renvoyer les tool_result, itérer jusqu'à "end_turn". Le découpage ci-dessous décrit ce qui se passe à chaque tour.

Chaque itération de la boucle se décompose en quatre phases conceptuelles, exposées au modèle de manière implicite :

PhaseCe que fait le modèleÉlément de l'API
Lecture du contexteLit le contexte courant : messages historiques, tool results récents, system promptTableau messages (avec tool_result blocks)
RaisonnementRaisonne sur l'état courant avant de décider de l'action suivanteraisonnement produit dans la génération
ActionDécide d'appeler un outil ou de produire une réponse finaletool_use block ou text block
Boucle ou finSoit attend le tool_result (la boucle continue), soit terminestop_reason : "tool_use" ou "end_turn"
Le cadrage d'examen passe par stop_reason ("tool_use" vs "end_turn"), pas par un découpage en phases nommées. Ce découpage reste utile pour situer les hooks : un hook PreToolUse intercepte entre la décision d'appel (le bloc tool_use est émis) et l'exécution de l'outil par ton code ; un hook PostToolUse intercepte une fois le tool_result obtenu, avant le tour suivant.

Comment ça fonctionne

Chaque réponse porte un champ stop_reason — les valeurs et leur signification sont détaillées en D0 §3. Ici, ce qui compte est ce que votre code en fait : deux valeurs suffisent à piloter la boucle.

stop_reason == "tool_use"  → exécuter les outils, ajouter les tool_result
                              à l'historique, relancer une itération
stop_reason == "end_turn"  → la tâche est terminée, sortir de la boucle
L'approche est model-driven. C'est Claude qui choisit quel outil appeler à chaque étape, en s'appuyant sur le contexte accumulé et les tool results précédents. Cela diffère fondamentalement d'un arbre de décision codé en dur (hardcoded), où la séquence d'actions est figée à l'avance.

Exemple de code

while True:
    response = client.messages.create(
        model="claude-sonnet-5",
        messages=messages,
        tools=tools
    )
    # On ajoute la réponse complète à l'historique
    messages.append({"role": "assistant", "content": response.content})

    # stop_reason est le signal fiable pour décider de la suite
    if response.stop_reason == "pause_turn":
        continue   # server tool interrompu par sa limite d'itérations : on relance tel quel

    if response.stop_reason != "tool_use":
        break   # "end_turn" (ou "refusal" / "model_context_window_exceeded") → la tâche est terminée

    # On exécute les outils demandés et on renvoie les tool_results
    tool_results = execute_tools(response.content)
    messages.append({"role": "user", "content": tool_results})

Les anti-patterns à connaître

Trois erreurs classiques dans les systèmes agentiques mal conçus :

  • Parser le texte de l'assistant pour y détecter des phrases comme « Task completed » ou « I'm done ». Le langage naturel n'est pas un signal fiable ; Claude peut écrire « done » tout en ayant encore un tool call en attente.
  • Utiliser une limite d'itérations arbitraire (max_iterations=5) comme condition d'arrêt principale. Cela peut interrompre une tâche légitime en cours d'exécution.
  • Vérifier la présence de texte dans la réponse comme signal de fin. Claude peut générer du texte explicatif ET un tool_use block dans la même réponse.

Le signal fiable reste stop_reason. À l'examen, deux valeurs suffisent : "tool_use" pour continuer, "end_turn" pour sortir — ce sont les seules que le guide nomme. En production vous rencontrerez aussi "pause_turn" (server tool interrompu, à relancer sans sortir de la boucle), "refusal" et "model_context_window_exceeded" ; utile à savoir, jamais demandé.

Pour l'examen : quand on vous demande comment déterminer si la boucle doit continuer ou s'arrêter, la bonne réponse est toujours stop_reason. Les distracteurs proposeront du text parsing, des limites d'itérations ou la détection de contenu textuel.

3. L'architecture hub-and-spoke (Task 1.2)

Le problème que cela résout

Quand une tâche est trop complexe pour un seul agent — par exemple, produire un rapport de recherche qui nécessite à la fois de la recherche web, de l'analyse documentaire et de la synthèse — il faut répartir le travail entre plusieurs agents spécialisés. Mais ces agents ont besoin d'être coordonnés : qui fait quoi ? Qui agrège les résultats ? Qui gère les erreurs ?

L'architecture hub-and-spoke répond à ce besoin : un agent coordinateur (le hub) orchestre plusieurs subagents spécialisés (les spokes).

           Coordinator (hub)
           /     |     \
    Subagent 1   Subagent 2   Subagent 3
    (research)   (analysis)   (synthesis)

Les responsabilités du coordinateur

Le coordinateur est le chef d'orchestre. Il se charge de :

  1. Décomposer la tâche principale en sous-tâches cohérentes.
  2. Sélectionner dynamiquement les subagents nécessaires.
  3. Déléguer en fournissant à chaque subagent le contexte dont il a besoin.
  4. Agréger et valider les résultats renvoyés par les subagents.
  5. Gérer les erreurs : décider de retry, d'adapter la requête ou de continuer avec des résultats partiels.
  6. Communiquer le résultat final à l'utilisateur.
Principe fondamental : le contexte des subagents est isolé.

Les subagents n'héritent pas automatiquement de l'historique de conversation du coordinateur. Ils ne partagent pas non plus de mémoire entre eux. Toute information nécessaire doit être explicitement transmise dans le prompt du subagent. Et toute communication entre subagents transite par le coordinateur — jamais en direct — ce qui garantit l'observabilité et le contrôle des erreurs.

Le risque d'une décomposition trop étroite

Un piège fréquent : le coordinateur décompose la tâche de manière trop restrictive, ce qui crée des angles morts.

Exemple concret : le coordinateur reçoit « AI impact on creative industries » et crée trois sous-tâches : « AI in digital art », « AI in graphic design » et « AI in photography ». Chaque subagent exécute correctement sa mission, mais le rapport final ne couvre que l'art visuel — la musique, la littérature et le cinéma sont totalement absents. Le problème n'est pas dans l'exécution des subagents, mais dans la décomposition faite par le coordinateur.

Bonnes pratiques

  • Partitionner explicitement l'espace de recherche avant de déléguer, pour éviter les doublons et les angles morts.
  • Prévoir des boucles de raffinement : le coordinateur évalue la synthèse, identifie les lacunes et relance des sous-tâches si nécessaire.
  • Ne jamais court-circuiter le coordinateur : même si cela semble plus efficace qu'un subagent envoie directement ses résultats à un autre, le passage systématique par le hub assure la visibilité centralisée, la gestion uniforme des erreurs et le contrôle de ce que chaque subagent reçoit.
Le réflexe : quand chaque subagent réussit sa mission mais que le rapport final rate des pans entiers du sujet, la cause est la décomposition du coordinateur, pas les agents en aval. Les distracteurs incriminent un agent réel : des requêtes pas assez larges chez l'agent de recherche, l'absence de détection de lacunes chez l'agent de synthèse, ou des critères de pertinence trop stricts chez l'agent d'analyse. Ils séduisent parce qu'ils nomment un composant du système — mais l'énoncé précise que chacun a correctement exécuté ce qui lui était assigné. Ce qui a été mal fait, c'est l'assignation.

4. Les stratégies de décomposition (Task 1.6)

Le problème que cela résout

Toutes les tâches ne se décomposent pas de la même manière. Une code review suit toujours les mêmes étapes (lire, analyser, reporter), tandis qu'une investigation dans un codebase inconnu révèle ses sous-tâches au fur et à mesure. Choisir la mauvaise stratégie entraîne soit de la rigidité inutile, soit du chaos.

Fixed pipeline (prompt chaining)

Chaque étape est définie à l'avance et s'exécute en séquence :

Document → Metadata extraction → Data extraction → Validation → Enrichment → Output

Quand l'utiliser : la structure de la tâche est prévisible, toutes les étapes sont connues, et on a besoin de stabilité et de reproductibilité.

Dynamic adaptive décomposition

Les sous-tâches émergent en fonction des résultats intermédiaires :

  1. Objectif : « Ajouter des tests pour un codebase legacy. »
  2. Première étape : mapper la structure (Glob, Grep).
  3. Découverte : trois modules sans tests, deux avec une couverture partielle.
  4. Priorisation : commencer par le module de paiements (risque élevé).
  5. Surprise en cours de route : une dépendance vers une API externe non mockée.
  6. Adaptation : créer le mock avant d'écrire les tests.

Quand l'utiliser : tâches d'investigation ouvertes, périmètre inconnu au départ, chaque étape dépend de ce que la précédente a révélé.

La multi-pass review pour les grosses PR

Quand une pull request touche plus de dix fichiers, une analyse en une seule passe produit des résultats inconsistants : commentaires détaillés sur certains fichiers, superficiels sur d'autres, et des contradictions (un pattern signalé dans un fichier, approuvé dans un autre).

La solution : découper en deux passes :

PassePérimètreCe qu'elle détecte
Pass 1 — per-fileChaque fichier analysé individuellementBugs locaux, problèmes de qualité, vulnérabilités
Pass 2 — intégrationRelations entre les fichiersTypes inconsistants, dépendances circulaires, flux de données cassés
Pour l'examen : le prompt chaining convient aux tâches prévisibles et répétables (review, migration). La dynamic décomposition convient aux investigations ouvertes où les sous-tâches émergent en cours d'exécution.
Les distracteurs qui visent le mauvais choix de décomposition :
  • La revue multi-passes proposée pour une investigation ouverte — elle est conçue pour un périmètre borné et énumérable, comme les fichiers d'une PR, pas pour un sujet dont on ignore l'étendue.
  • Un prompt exhaustif unique qui couvrirait tout d'un coup — il suppose de connaître le périmètre à l'avance, ce qui est précisément l'inconnue.
  • Un pipeline fixe sur un périmètre inconnu — il exige la liste des étapes avant de commencer, alors que chaque étape ne se révèle qu'avec les découvertes de la précédente.

5. Le Task tool, context passing et spawning (Task 1.3)

Le problème que cela résout

Le coordinateur a besoin d'un mécanisme concret pour créer des subagents et leur transmettre leur mission. Dans le Claude Agent SDK, ce mécanisme s'appelle l'outil Task.

Comment ça fonctionne

Pour qu'un coordinateur puisse créer des subagents, son allowedTools doit inclure "Task". Chaque appel à Task crée un subagent avec son propre contexte isolé.

Note : dans la CLI récente, l'outil peut apparaître sous le nom Agent, mais le référentiel et l'examen emploient le nom Task. Pour l'examen, retenez "Task" — c'est le terme utilisé par le guide officiel.

⚠️ Pseudocode illustratif — la syntaxe exacte varie selon la version du SDK ; les concepts (hooks PreToolUse/PostToolUse, définition d'agents) sont, eux, officiels.

coordinator = AgentDefinition(
    name="coordinator",
    allowed_tools=["Task", "get_customer", "lookup_order"]
)

Le context passing explicite

Les subagents ne reçoivent rien automatiquement du coordinateur. Tout le contexte nécessaire doit figurer dans le prompt de la tâche déléguée.

Mauvais : Task: "Analyse le document." — le subagent ne sait pas quel document, n'a aucun résultat antérieur et ignore le format de sortie attendu.
Bon : Task: "Analyse le document suivant. Document : [texte complet]. Résultats de recherche préalables : [données]. Format de sortie attendu : [schéma]." — le subagent dispose de tout ce qu'il faut pour travailler de manière autonome.

Lors du context passing, utilisez des formats structurés qui séparent clairement les données des métadonnées (source, date, type). Cela évite toute confusion et facilite l'agrégation par le coordinateur. En particulier, inclure explicitement dans le contexte transmis au subagent : l'URL source ou le nom du document, le type de contenu (web, local, API), et le numéro de page (si applicable). Ces métadonnées explicites préservent l'attribution des claims jusqu'au rapport final — essentielles pour la traçabilité, surtout en domaines réglementaires. (Source : guide officiel, Task 1.3, Skills.)

Le parallel spawning

Le coordinateur peut émettre plusieurs appels Task dans une seule réponse. Les subagents s'exécutent alors en parallèle, ce qui accélère considérablement le traitement :

# Une seule réponse du coordinateur contient :
Task 1 : "Rechercher des articles sur X"
Task 2 : "Analyser le document Y"
Task 3 : "Rechercher des articles sur Z"
# → Les trois s'exécutent simultanément (parallel execution).

La configuration AgentDefinition

⚠️ Pseudocode illustratif — la syntaxe exacte varie selon la version du SDK ; les concepts (hooks PreToolUse/PostToolUse, définition d'agents) sont, eux, officiels.

agent = AgentDefinition(
    name="customer_support",
    description="Handles customer returns and order issues",
    system_prompt="You are a customer support agent...",
    allowed_tools=["get_customer", "lookup_order",
                   "process_refund", "escalate_to_human"]
)

La description joue un double rôle : elle détermine quand le coordinateur décide de lancer ce subagent, et elle influence la qualité du prompt que le coordinateur rédige pour lui. Une description vague produit des délégations vagues.

Rédigez les prompts du coordinateur en termes d'objectifs et de critères de qualité (« le rapport doit couvrir au moins cinq secteurs avec des sources datées ») plutôt qu'en instructions procédurales étape par étape.

Les quatre caractéristiques d'un subagent efficace

#CaractéristiquePourquoi c'est important
1Une description spécifiqueElle contrôle quand le subagent est lancé et influence la qualité du prompt d'entrée.
2Un structured output formatC'est l'amélioration n° 1 : cela crée des points d'arrêt naturels et empêche le subagent de tourner trop longtemps.
3Le signalement des obstaclesSi le subagent découvre un contournement (dépendance manquante, flag spécial), cette information doit remonter pour éviter que le thread principal ne la redécouvre.
4Des outils limités au strict nécessaireUn subagent de recherche n'a besoin que de Glob, Grep, Read. Un reviewer y ajoute Bash. Trop d'outils (18 au lieu de 4-5) dégrade la fiabilité de sélection.
Le réflexe : trois faits décident de la bonne option. allowedTools doit contenir "Task" pour qu'un coordinateur puisse lancer des subagents ; les subagents n'héritent d'aucun contexte, tout ce dont ils ont besoin passe par le prompt ; le parallélisme s'obtient en émettant plusieurs appels Task dans une seule réponse du coordinateur. Les distracteurs : agrandir la fenêtre de contexte du subagent (rien ne lui a été transmis, la taille n'y change rien), laisser les subagents s'appeler entre eux (cela casse le hub-and-spoke et l'observabilité), ou émettre les appels sur des tours successifs (c'est du séquentiel avec des étapes en plus, pas du parallèle).

Voir aussi : D2, section 3 pour le paramètre tool_choice et D2, section 5 pour la référence complète des outils intégrés.

6. Programmatic enforcement et hooks (Task 1.4 & 1.5)

Le problème que cela résout

Dans un workflow de support client, il est critique de vérifier l'identité du client avant de traiter un remboursement. On peut l'écrire dans le prompt… mais les instructions dans le prompt ont un taux de conformité élevé, jamais garanti à 100 % — le guide officiel parle seulement d'un non-zero failure rate (le « 90-95 % » parfois cité en formation est illustratif, pas un chiffre officiel). Sur des milliers d'interactions, même un faible taux d'échec peut causer des remboursements versés au mauvais client.

Le programmatic enforcement résout ce problème en rendant la violation impossible par le code, plutôt qu'improbable par le prompt.

De même, les outils MCP tiers renvoient souvent des données dans des formats hétérogènes : un outil retourne des timestamps Unix, un autre de l'ISO 8601, un troisième des codes numériques de statut. Si Claude reçoit ces formats bruts, il peut mal les interpréter. Les hooks répondent à ces besoins en interceptant les tool calls à des points précis de l'agentic loop.

Note : cette section couvre les hooks de l'Agent SDK (niveau programmatique). Pour les hooks de Claude Code (niveau configuration), voir D3, section 7.

Exemple concret : les logs de production montrent que dans 12 % des cas, l'agent saute l'appel à get_customer et appelle directement lookup_order en se fiant au nom fourni par le client, ce qui entraîne parfois des remboursements incorrects.

La solution : un prérequis programmatique qui bloque les appels à lookup_order et process_refund tant que get_customer n'a pas retourné un identifiant client vérifié. Ni les few-shot examples ni un prompt renforcé ne suffisent — les conséquences financières exigent une garantie déterministe.

PreToolUse : bloquer les actions non conformes

Ce hook intercepte un tool call avant son exécution et peut le bloquer ou le rediriger :

⚠️ Pseudocode illustratif — la syntaxe exacte varie selon la version du SDK ; les concepts (hooks PreToolUse/PostToolUse, définition d'agents) sont, eux, officiels.

@hook("PreToolUse")
def enforce_refund_limit(tool_call):
    if tool_call.name == "process_refund" and tool_call.args.amount > 500:
        return redirect_to_escalation(tool_call)

PostToolUse : normaliser les données avant qu'elles n'atteignent Claude

Ce hook intercepte le tool result après l'exécution de l'outil, mais avant que le modèle ne le traite :

⚠️ Pseudocode illustratif — la syntaxe exacte varie selon la version du SDK ; les concepts (hooks PreToolUse/PostToolUse, définition d'agents) sont, eux, officiels.

@hook("PostToolUse")
def normalize_dates(tool_result):
    # Unix timestamp  →  ISO 8601
    # "Mar 5, 2025"   →  "2025-03-05"
    # Status code 2   →  "shipped"
    return normalized_result

Hooks vs. instructions dans le prompt

C'est l'une des distinctions les plus testées à l'examen. La règle est simple :

Hooks (programmatic enforcement)Prompt instructions
GarantieDéterministe (100 %)Probabiliste (non-zero failure rate — pas 100 % ; le guide ne donne pas de chiffre exact, le « > 90 % » est illustratif)
Quand les utiliserBusiness rules critiques, opérations financières, conformité réglementairePréférences générales, formatting, recommandations
ExempleBloquer les remboursements supérieurs à 500 $« Try to resolve the issue before escalating »

Le structured handoff lors d'une escalation

Quand l'agent décide d'escalader vers un opérateur humain, celui-ci n'a pas accès au transcript complet de la conversation. Le résumé transmis doit donc être complet et autosuffisant :

{
  "customer_id": "CUST-12345",
  "issue_summary": "Refund request for damaged item",
  "order_id": "ORD-67890",
  "root_cause": "Item arrived damaged; photos attached",
  "actions_taken": [
    "Identity verified via get_customer",
    "Order confirmed via lookup_order",
    "Replacement offered — customer insists on refund"
  ],
  "refund_amount": "$89.99",
  "recommended_action": "Approve full refund",
  "escalation_reason": "Customer requested to speak with a manager"
}

Voir aussi : D5, section 2 pour les escalation patterns détaillés et la calibration par critères + few-shot.

Les requêtes multi-aspects

Quand un client inclut plusieurs problèmes dans un même message (« Je veux un remboursement pour la commande #1234 ET mettre à jour l'adresse de livraison de la commande #5678 »), la bonne approche consiste à décomposer en éléments distincts, les traiter en parallèle avec un contexte client partagé, puis synthétiser une réponse unifiée.

La règle absolue : quand l'échec a des conséquences financières, légales ou de sécurité → hooks. Les prompt instructions ne suffisent jamais pour ces cas-là.
Les distracteurs qui visent l'enforcement programmatique :
  • Renforcer le system prompt (« la vérification est obligatoire »).
  • Ajouter des few-shot examples montrant l'agent appelant toujours l'outil de vérification en premier.
  • Auditer après coup les transactions pour repérer les violations.
  • Déployer un classifieur de routage qui n'active que le sous-ensemble d'outils pertinent pour chaque requête.

Les trois premiers séduisent parce qu'ils font réellement baisser le taux d'échec — mais l'énoncé demande une garantie, et un audit ne détecte la violation qu'une fois l'argent parti. Le quatrième traite la disponibilité des outils, pas leur ordre d'appel : ce n'est pas le problème posé.

7. La gestion des sessions (Task 1.7)

Le problème que cela résout

Les investigations complexes s'étalent souvent sur plusieurs sessions de travail. Entre deux sessions, des fichiers peuvent être modifiés, et le contexte accumulé peut devenir obsolète. Il faut des mécanismes pour reprendre intelligemment là où l'on s'est arrêté — ou choisir de repartir de zéro avec un résumé.

--resume : reprendre une session

claude --resume investigation-auth-bug

Continue la conversation avec le contexte sauvegardé. Utile quand le travail s'étale sur plusieurs heures ou jours, à condition que les fichiers n'aient pas trop changé entre-temps.

fork_session : explorer deux pistes en parallèle

     Investigation du codebase
              |
         fork_session
          /         \
     Approach A      Approach B
      (Redux)        (Context API)

Les deux branches héritent du contexte commun jusqu'au point de bifurcation, puis divergent indépendamment. Idéal pour comparer des stratégies ou tester des hypothèses.

Quand choisir quoi

SituationChoix recommandé
Le contexte précédent est encore valide (fichiers inchangés)--resume
Un nombre limité de fichiers précis ont changé, le reste du contexte reste valide--resume en informant explicitement l'agent des fichiers précisément modifiés, pour une ré-analyse ciblée (plutôt qu'une ré-exploration complète)
Les tool results sont obsolètes (fichiers modifiés de façon étendue ou incertaine)Nouvelle session avec un résumé structuré injecté
On veut comparer deux approchesfork_session
Beaucoup de temps a passé et le contexte s'est dégradéNouvelle session : « Here's a summary of our findings… »
Il est souvent plus fiable de démarrer une nouvelle session avec un résumé structuré que de reprendre avec des tool results potentiellement obsolètes. Un résumé bien écrit perd peu d'information et offre un contexte frais.
Le réflexe : trois situations, trois réponses. Le contexte antérieur reste majoritairement valide → --resume, en nommant les fichiers modifiés pour une ré-analyse ciblée. Les tool results sont largement périmés → session neuve avec un résumé structuré injecté. On veut explorer deux approches depuis une base d'analyse commune → fork_session. Les distracteurs : tout ré-explorer de zéro (cela jette du travail encore valide), reprendre sans signaler les changements (l'agent garde une vue fausse des fichiers et raisonne sur des tool results morts), ou forker pour comparer l'ancienne et la nouvelle version d'un fichier (le fork sert à explorer des approches divergentes, pas à réconcilier un état disque).

8. Synthèse + questions d'auto-évaluation

Si vous ne deviez retenir que l'essentiel de ce domaine :

Workflows vs. agents

  • Privilégier les workflows (reliability) ; réserver les agents aux situations où la flexibilité est indispensable.
  • 5 workflow patterns : prompt chaining, routing, parallelization, orchestrator-workers (voir section 3, hub-and-spoke), evaluator-optimizer.

L'agentic loop

  • Boucle agentique pilotée par stop_reason : "tool_use" → exécuter l'outil et itérer ; "end_turn" → terminer.
  • Les deux valeurs testées : "tool_use" → continuer, "end_turn" → terminer. Les autres ("pause_turn", "refusal", "model_context_window_exceeded") existent en production mais ne sont pas matière d'examen.
  • Ne jamais parser le texte de l'assistant, utiliser des limites d'itérations arbitraires ou vérifier la présence de texte comme signal de fin.
  • Hooks PreToolUse = entre la décision d'appel (bloc tool_use émis) et l'exécution de l'outil ; PostToolUse = au début de l'observe suivant.

L'architecture multi-agents (hub-and-spoke)

  • Le coordinateur (hub) gère toute la communication entre subagents (spokes).
  • Les subagents ont un contexte isolé : le context passing doit être explicite.
  • L'outil Task est le mécanisme de création ; allowedTools doit inclure "Task".
  • Plusieurs appels Task dans une seule réponse = parallel exécution.
  • Attention à la décomposition trop étroite → couverture incomplète.

Le programmatic enforcement et les hooks

  • Conséquences financières, légales ou de sécurité → hooks (garantie à 100 %).
  • Préférences et recommandations → prompt instructions (probabiliste).
  • PostToolUse pour normaliser les données hétérogènes. PreToolUse pour bloquer les actions non conformes.

La décomposition

  • Fixed pipeline (prompt chaining) pour les tâches prévisibles. Dynamic décomposition pour les investigations ouvertes.
  • Multi-pass review pour les grosses PR : pass per-file + pass intégration.

Les sessions

  • --resume si le contexte est encore valide, fork_session pour comparer, nouvelle session si les données sont obsolètes.
  • 4-5 outils maximum par subagent ; un structured output format est l'amélioration n° 1.

Questions d'auto-évaluation

Q1 (D1) — A dose released before the interaction check

Scenario: A pharmacy agent fills prescription requests through MCP tools (check_interactions, dispense, page_pharmacist). Reviewers pulled last month's transcripts and found doses released to patients whose interaction check never ran: in those requests the agent took the allergy list pasted into the ticket at face value and went straight to dispense.

Question: Which change makes the skipped check impossible?

A) Have the agent write out the sequence it intends to follow before its first call, so a skipped step shows up in the transcript.

B) Cache interaction results per patient so the check costs almost nothing and the agent has no reason to route around it.

C) Refuse dispense in code until check_interactions has returned for that patient.

D) Add a hook that rejects malformed prescription identifiers before the outgoing call leaves the agent.

Answer: refuse the downstream call in code until the upstream check has returned

Why: an ordering that guards a patient-safety boundary needs a guarantee, not a tendency. A prerequisite evaluated in code cannot be argued out of by a convincing-looking allergy list sitting in the ticket.

Why the others are wrong:

  • A stated plan is still the model's own output, nothing holds it to what it wrote, and the transcript gets read after the dose is out.
  • Cost was never the obstacle — the agent skipped a step it believed it already had the answer to.
  • Enforces a property of the arguments, not the fact that anything ran first. A well-formed identifier says nothing about the check.
Q2 (D1) — A clean audit that missed most of the rubric

Scenario: A multi-agent system was asked to audit a banking app for accessibility. Three auditor subagents ran, and each returned a clean, well-formed result. The coordinator's log preserves the assignments it wrote: color contrast on the login screen, color contrast on the transfer screen, color contrast on the statements screen. The delivered report says nothing about screen-reader labels, focus order, or touch-target size.

Question: Where does the gap come from?

A) The three screens sampled do not represent the app's surface, so entire flows were never opened by any auditor.

B) The report template offers one findings section per screen.

C) Running the three auditors in isolation left none of them able to notice which criteria the others were leaving untouched.

D) The coordinator wrote three assignments that all exercise a single criterion.

Answer: the assignments the coordinator wrote all exercise one criterion

Why: the log names the defect. Screen-reader labels, focus order and target size were handed to nobody, so no amount of careful work downstream could surface them. The auditors did what they were given; the giving was the fault.

Why the others are wrong:

  • Three screens is thin coverage, but what is missing here is criteria, not screens — those same three screens went unchecked for focus order too.
  • A template shapes where findings get written, not whether they exist, and there was nothing to place.
  • Isolation is the point of a subagent, and mutual awareness would have changed nothing: no auditor held the missing criteria to share.
Q3 (D1) — Two backlog items, two decomposition strategies

Scenario: Each quarter you audit the same six connector adapters against the same three concerns: retry policy, secret handling, schema versioning. Separately, you must make an undocumented ingestion pipeline observable; nobody knows how many stages it has or which already emit metrics.

Question: Which strategy fits each item?

A) Prompt chaining for the audit, dynamic adaptive decomposition for the observability work.

B) Dynamic adaptive decomposition for the audit, prompt chaining for the observability work.

C) Prompt chaining for both, because a fixed pipeline is always more reproducible.

D) Dynamic adaptive decomposition for both, because letting the model replan is always safer.

Answer: prompt chaining for the audit, adaptive decomposition for the pipeline

Why: the criterion is whether the scope is known before you start. The audit repeats a fixed set of targets, so a chained sequence of focused passes gives even depth and comparable results. The observability work is open-ended: each stage you uncover changes what to look at next.

Why the others are wrong:

  • Inverts the criterion: the fixed sequence lands on the item whose steps nobody knows, the adaptive one on the item that never varies.
  • A fixed pipeline presupposes knowing the stages and their order, precisely the unknown here.
  • Adaptivity buys nothing once targets are frozen, and it makes successive audits harder to compare.
Q4 (D1) — Who decides the next tool call

Scenario: A migration agent needs to run read_schema, then plan_changes, then apply_migration for each table. To keep the process predictable, the orchestrator pre-computes this exact call sequence before the first request and feeds each tool result into the next hardcoded step, never letting the model's own response decide what happens next. When a table turns out to need an extra validation step the sequence doesn't account for, the agent has no way to trigger it.

Question: What should change about how the loop is driven?

A) Keep the fixed sequence, but add a fourth hardcoded step for validation, since the gap that appeared today is now a known case.

B) Let the model decide the next action each turn from the latest tool_result, continuing while it requests tools and stopping when it signals completion.

C) Run all three tools on every turn regardless of need, so the missing step is always covered and no case can slip through.

D) Keep the fixed sequence, but let the orchestrator retry a failed step before moving to the next one.

Answer: hand control back to the model, turn by turn

Why: a sequence fixed in advance by the orchestrator is a hardcoded decision tree — it can only be as flexible as whoever wrote it anticipated. An agentic loop is model-driven: the model reads each tool result and decides the next action itself, which is what lets it insert a step nobody hardcoded.

Why the others are wrong:

  • Fixes this one gap but leaves the orchestrator guessing every future case in advance — the same limitation returns with the next table that needs something different.
  • Running every tool regardless of need does not add judgment, it just hides the missing decision behind unconditional execution.
  • A retry addresses a step failing, not a step nobody planned for.
Q5 (D1) — The vendor retired the version you probed

Scenario: A session named fx-integration spent a long afternoon probing a currency vendor's sandbox: sample payloads, error shapes, throttling behavior. The vendor has since shipped v3 and retired v2, so every recorded response describes an endpoint that now answers 410. What that session concluded about the vendor's pagination model and its throttling window still holds.

Question: How do you take the integration work forward?

A) Start a new session and seed it with a summary of what still holds.

B) Resume the session and let the agent re-probe each endpoint as it needs one, so the recorded v2 responses get corrected along the way.

C) Start a new session and replay the entire v2 transcript into it, so nothing observed that afternoon is lost.

D) Start a new session with only the vendor's v3 changelog.

Answer: a new session seeded with what survived the version change

Why: resumption pays off while the stored tool results still describe the system you are talking to. Here they describe endpoints that answer 410, so replaying them makes the agent reason about a vendor that no longer exists. A summary carries the pagination model and the throttling window forward and leaves the dead payloads behind.

Why the others are wrong:

  • Re-probing corrects the record only where the agent happens to look; everything it does not revisit sits in context as though it were still true.
  • Carries the obsolete payloads into the new session, which is the one thing a fresh start was meant to avoid.
  • A changelog says what moved on the vendor's side, not what you learned. Pagination and throttling would have to be rediscovered.
Q6 (D1) — Five hundred rows, and then a signature

Scenario: A retention agent trims expired records through purge_records. Policy lets it delete up to 500 rows in one call; a larger purge needs a data steward's sign-off. The rule is written in the system prompt, and last week a single call removed 40,000 rows from an audit table.

Question: What makes the ceiling hold?

A) Give the agent a request_signoff tool, with a description telling it when a purge has grown too large to run alone.

B) A hook that blocks the outgoing call when the row count passes the ceiling.

C) State the ceiling in the tool's own description, so the limit travels with the tool wherever it is used.

D) Have the agent announce the row count it is about to delete before it issues the call.

Answer: intercept the outgoing call and stop it above the ceiling

Why: a ceiling that must hold every time belongs in code that sees the actual argument. The hook runs before the tool does, so an oversized purge never reaches the database, and a deletion is not something an apology can undo.

Why the others are wrong:

  • Offers a way out that the agent still has to choose, and the incident was precisely a case where it did not.
  • Moves the rule closer to the call site without changing its nature: it stays text the model reads, not a condition anything evaluates.
  • An announcement is a claim about an intent, made by the same run that is about to ignore it.
Q7 (D1) — Delegating a contract review (Select the 2 correct answers.)

Scenario: A coordinator has a clause-extraction subagent read two vendor contracts while a pricing subagent prepares a quote, and both outputs must land in one report.

Question: Which two moves are correct?

A) Put the contract text, the clause types wanted, and the output schema into the delegation prompt itself.

B) Emit both delegations in one coordinator response so the subagents run at the same time.

C) Count on each subagent inheriting the coordinator's conversation history.

D) Let the clause subagent hand its output straight to the pricing subagent, saving a hop.

E) Give both subagents the coordinator's whole tool set so neither is ever blocked.

Answers: carry the needed context in the delegation prompt, and issue both delegations in one response

Why: a subagent starts from an isolated context, so whatever it needs — source text, target clause types, output shape — travels in the prompt. Parallelism comes from several delegations inside one coordinator response; spread over consecutive turns they just run one after another.

Why the others are wrong:

  • Nothing is inherited: an isolated context is the defining property of a subagent.
  • Every exchange goes through the hub, which keeps the run observable and error handling uniform.
  • A wider tool set degrades selection reliability; each spoke gets only the tools its role needs.
Q8 (D1) — Three trackers, three ways to say urgent

Scenario: A triage agent pulls open issues from three trackers. One reports priority as P1 through P4, one as critical, major or minor, the third as an integer from 1 to 5 where 5 is the most urgent. The agent forwards to the on-call queue whatever it reads as top priority, and cosmetic issues keep arriving there while real outages wait.

Question: Which fix addresses the cause?

A) Rewrite each connector to attach a priority_scale field naming the vocabulary it uses, and leave the mapping itself to the model.

B) Ask the model to reason step by step about which scale a label belongs to before it routes anything.

C) A PostToolUse hook that maps every returned label onto one scale.

D) Re-open each issue in its own tracker before routing it.

Answer: fold the three vocabularies into one in a hook that runs after the tool returns

Why: three fixed vocabularies collapse onto one scale by a fixed table, so the mapping belongs in code that runs on every result rather than in a habit the model keeps most of the time. The hook fires once the tool has returned, before the model reads anything.

Why the others are wrong:

  • Naming the scale still leaves the mapping to the model on every single issue, and now costs context to describe as well.
  • Deliberation raises the hit rate on something with one right answer. The misroutes get rarer, not impossible.
  • Adds a round trip per issue and hands back the same three vocabularies, unchanged.
