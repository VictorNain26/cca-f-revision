1. Préserver les informations critiques dans le contexte (Task 5.1)

Le problème que cela résout

L'API Claude ne conserve aucun état entre les requêtes : vous devez envoyer le full history à chaque appel. Au fil d'une conversation longue, cet historique grossit, et trois phénomènes menacent la qualité des réponses :

1. La perte lors de la compression progressive

Quand l'historique est résumé pour libérer du contexte, les valeurs numériques, les pourcentages et les dates sont condensés en termes vagues. Un remboursement de 89,99 $ discuté vingt turns plus tôt devient « a promotional pricing was discussed » dans le résumé.

Solution : le case facts block. Extraire les faits transactionnels (montants, dates, numéros de commande, statuts) dans un bloc structuré, inclus dans chaque prompt en dehors de l'historique résumé : 
=== CASE FACTS (mis à jour à chaque nouveau fait) ===
Customer ID : CUST-12345
Order ID    : ORD-67890
Order Date  : 2025-01-15
Amount      : $89.99
Issue       : Article endommagé à la livraison
Request     : Remboursement intégral
Status      : En attente d'approbation
===
Point clé : Le case facts block vit en dehors de l'historique résumé (summarized history). Il est inclus dans chaque prompt API, de sorte que même après un /compact, les faits critiques restent intacts.

2. L'effet lost-in-the-middle

Les modèles traitent de manière fiable les informations situées au début et à la fin des entrées longues, mais peuvent manquer des éléments placés au milieu. La parade : placer les conclusions clés en tête et les actions requises en fin de document.

[CONCLUSIONS CLÉS — en haut]
Trois vulnérabilités critiques identifiées...

[RÉSULTATS DÉTAILLÉS — au milieu]
=== auth.ts === ...
=== database.ts === ...

[ACTIONS REQUISES — en bas]
Priorité : corriger auth.ts avant le merge.

3. L'accumulation des tool results

Si lookup_order retourne 40 champs mais que seuls 5 sont pertinents pour la tâche en cours, le contexte se remplit d'informations inutiles. La solution : un hook PostToolUse qui intervient après l'exécution de l'outil et ne conserve que les champs nécessaires avant que le résultat n'entre dans le contexte du modèle.

En pratique, le hook PostToolUse reçoit l'événement complet (tool name, full result, metadata) et peut filtrer les champs avant retour. Pour un outil lookup_order, cela signifie sélectionner seulement order_id, status, total, items et return_eligible plutôt que les 40 champs bruts. Le résultat réduit est ensuite passé au modèle, économisant du contexte pour les turns suivants.

À retenir : Le trimming des tool results se fait via un hook PostToolUse (pas PreToolUse). Le hook s'exécute après l'outil, avant l'intégration du résultat au contexte, et peut réduire les données retournées en ne gardant que les champs pertinents.

Les autres techniques de gestion du contexte

  • /compact : compresse le contexte en résumant l'historique. Utile dans les longues sessions, mais avec le risque de perdre des détails exacts — d'où l'importance du case facts block.
  • Fichiers scratchpad : l'agent écrit ses découvertes clés dans un fichier (investigation-scratchpad.md) et le consulte quand le contexte se dégrade.
  • Délégation aux subagents : isoler les phases de découverte verbeuses dans un subagent qui ne retourne qu'un résumé concis au thread principal.
  • Budgets de contexte contraints : envoyer un contexte minimal aux subagents, exiger des résultats structurés (pas de dumps bruts), et limiter les outils disponibles pour réduire les distractions.
  • Métadonnées obligatoires dans les sorties des subagents : les subagents doivent inclure les dates, sources et attributions dans leurs résultats structurés, faute de quoi la synthèse en aval perd la provenance.

2. Les patterns d'escalation (Task 5.2)

Le problème que cela résout

Un agent de support client doit savoir quand résoudre un problème de manière autonome et quand passer la main à un humain. Une mauvaise calibration entraîne deux types d'échecs : l'agent escalade des cas simples (perte d'efficacité) ou tente de traiter des cas complexes hors de sa portée (erreurs, frustration client).

Les déclencheurs fiables d'escalation

SituationAction
Le client demande explicitement un humainEscalader immédiatement, sans tenter de résoudre d'abord
La politique ne couvre pas la demande (policy gap)Escalader (ex. : alignement de prix concurrent quand la politique ne couvre que le propre site)
L'agent ne fait plus de progrès (no progress)Escalader après un nombre raisonnable de tentatives
Plusieurs correspondances clientDemander des identifiants supplémentaires ; ne pas deviner

Les déclencheurs NON fiables

MéthodePourquoi elle échoue
Sentiment analysisL'humeur du client ne corrèle pas avec la complexité du cas. Un client frustré peut avoir un problème simple.
Self-rated confidence (1-10)Le modèle peut être confiant à tort. La confidence calibration est insuffisante.
Automatic classifierSur-ingénierie. Nécessite des données d'entraînement souvent indisponibles.

Les 3 patterns concrets d'escalation

PatternSituationComportement attendu
Immediate« I want a manager »Appeler escalate_to_human immédiatement. Ne pas tenter de résoudre.
After attemptClient insatisfait de la solution proposéeProposer d'abord une résolution, escalader si le client refuse.
Nuanced (acknowledge → resolve → escalate on reiteration)« This is outrageous! »Reconnaître la frustration → proposer une solution → escalader uniquement si le client réitère sa demande d'humain.
Piège classique : « This is outrageous, I'm very unhappy! » ne justifie pas une escalation immédiate. Le sentiment n'est pas un déclencheur fiable. Le bon pattern : acknowledge → resolve → escalate only on reiteration.

Calibrer l'escalation : critères explicites + few-shot examples

Quand un agent escalade trop (cas simples) ou pas assez (cas complexes), la solution la plus efficace combine deux éléments dans le system prompt :

  1. Des critères d'escalation explicites — les règles claires (quand escalader, quand résoudre).
  2. Des few-shot examples — qui montrent comment appliquer ces règles dans les cas ambigus.
/* Few-shot escalation examples dans le system prompt */
Request: "Get me a manager"
Action: Immediately call escalate_to_human.
Rationale: Explicit human request. Do not attempt to solve.

Request: "This is outrageous, I'm very unhappy!"
Action: Acknowledge frustration, propose resolution.
Rationale: Frustration ≠ human request. Escalate only on reiteration.
À retenir : la bonne réponse est toujours la combinaison critères explicites + few-shot examples. Jamais l'un sans l'autre. Les distracteurs classiques : self-rated confidence, automatic classifier, sentiment analysis.

Le structured handoff protocol

L'opérateur humain qui prend le relais n'a pas accès au transcript complet. Le résumé transmis doit donc être complet et autosuffisant pour l'humain :

{
  "customer_id": "CUST-12345",
  "issue_summary": "Demande de remboursement pour article endommagé",
  "order_id": "ORD-67890",
  "root_cause": "Article arrivé endommagé",
  "actions_taken": [
    "Identité vérifiée via get_customer",
    "Commande confirmée via lookup_order",
    "Remplacement proposé — client insiste pour un remboursement"
  ],
  "refund_amount": "$89.99",
  "recommended_action": "Approuver le remboursement intégral",
  "escalation_reason": "Le client a demandé un responsable"
}
Structured handoff : Le résumé transmis à l'opérateur humain doit inclure tout ce qui est nécessaire pour reprendre le cas sans relire le transcript. C'est un protocole complet, pas un simple message d'escalation.

3. La propagation d'erreurs dans les systèmes multi-agents (Task 5.3)

Ce sujet complète D1 (architecture hub-and-spoke) et D2 (erreurs structurées MCP). Ici, l'accent est mis sur la propagation entre agents et la synthèse avec coverage annotations.

Le problème que cela résout

Dans un système multi-agents, un subagent peut échouer (timeout, document corrompu, API indisponible). Le coordinateur a besoin d'informations structurées pour décider intelligemment de la suite : retry ? Modifier la requête ? Continuer avec des résultats partiels ? Abandonner cette branche et annoter le manque ?

Le contexte d'erreur structuré d'un subagent

Chaque erreur retournée au coordinateur doit inclure quatre éléments : failure_type, la requête tentée (query), les résultats partiels (partial_results), et les alternatives (alternatives).

{
  "status": "partial_failure",
  "failure_type": "timeout",
  "attempted_query": "AI impact on music industry 2024",
  "partial_results": [
    {"title": "AI Music Generation Report", "url": "...", "relevance": 0.8}
  ],
  "alternative_approaches": [
    "Requête plus ciblée : 'AI music composition tools'",
    "Source de données alternative"
  ],
  "coverage_impact": "Non couvert : impact de l'IA sur la production musicale"
}

Distinguer timeout et résultats vides

Distinction critique : Un timeout est un access failure — la requête n'a pas abouti, et un retry peut être pertinent. Des résultats vides (0 results) signifient que la requête a abouti mais n'a rien trouvé — c'est un valid query avec un résultat légitime. Les traiter de la même manière (comme des « failures ») est un anti-pattern.
SituationTypeAction du coordinateur
Connection timeoutAccess failureRetry décision (1-2 tentatives), puis propager si l'échec persiste
0 results retournésValid empty resultAccepter comme résultat légitime, annoter dans la synthèse

Les 4 anti-patterns de gestion d'erreur

Anti-patternPourquoi c'est un problèmeApproche correcte
Statut générique (« search unavailable »)Le coordinateur ne peut pas choisir sa stratégie de récupérationRetourner failure_type, query, partial_results, alternatives
Suppression silencieuse (silent suppression : résultat vide = succès)Le coordinateur croit qu'il n'y a pas de résultatsDistinguer « 0 results » (valid query) de « access failure »
Abandon du workflow entier (abort whole workflow)On perd tous les résultats partiels obtenusContinuer avec les résultats disponibles, annoter les lacunes
Retries infinis (infinite retries) dans le subagentLatence excessive et gaspillage de ressourcesRécupération locale (1-2 retries), puis propagation au coordinateur

Les coverage annotations dans la synthèse

Quand la synthèse est produite à partir de résultats incomplets, elle doit l'indiquer explicitement :

## Rapport : impact de l'IA sur les industries créatives
### Art visuel (FULL COVERAGE)
[résultats de recherche]

### Musique (PARTIAL COVERAGE — timeout du subagent de recherche)
[résultats partiels]
Note : la couverture de cette section est limitée.

### Littérature (FULL COVERAGE)
[résultats de recherche]

Persistance des findings au-delà des limites de contexte : fichiers scratchpad

Quand un subagent rencontre des erreurs ou des résultats partiels, les findings et les métadonnées doivent être sauvegardés dans un fichier scratchpad pour que le coordinateur puisse les consulter ultérieurement, même après que le contexte du subagent soit perdu. Ce pattern est crucial pour le crash recovery et la synthèse finale :

// agent-findings-scratchpad.md
## Recherche « AI music 2024 » — Status: Partial
- Queries exécutées : 2/3 (timeout sur requête #3)
- Résultats obtenus : 12 articles
- Clés trouvées : AI-generated music grew 300% on streaming
- Lacune identifiée : impact sur la production musicale
- Retry strategy : requête #3 à reformuler plus tard
Fichiers scratchpad et propagation d'erreur : Chaque subagent exporte ses findings critiques dans un fichier scratchpad nommé de manière stable. En cas d'erreur ou de timeout, le coordinateur a accès aux résultats partiels via ce fichier, évitant ainsi de perdre les découvertes au-delà des limites de contexte du subagent.

4. Gérer le contexte dans les grandes codebases (Task 5.4)

Le problème : la dégradation du contexte dans les longues sessions

Dans les sessions d'investigation longues, le modèle commence à produire des réponses instables et à se référer à des « patterns typiques » au lieu de citer des classes ou des fichiers spécifiques du codebase. C'est le signe d'une context degradation : le contexte utile a été noyé ou perdu.

Les solutions

1. Fichiers scratchpad

L'agent consigne ses découvertes clés dans un fichier qu'il peut consulter plus tard, quand le contexte se dégrade :

# investigation-scratchpad.md
## Découvertes clés
- PaymentProcessor dans src/payments/processor.ts hérite de BaseProcessor
- refund() est appelé depuis 3 endroits : OrderController, AdminPanel, CronJob
- L'API PaymentGateway externe a une limite de 100 req/min
- La migration n° 47 a ajouté refund_reason (NOT NULL) — 2024-12-01

2. Délégation aux subagents

L'agent principal demande à un subagent Explore d'investiguer les dépendances d'un module. Le subagent lit 15 fichiers dans son propre contexte et retourne un résumé concis au thread principal. Le contexte principal garde une ligne au lieu de 15 fichiers :

// Résultat du subagent Explore → résumé retourné au coordinateur
"Le module Payments dépend de AuthService, OrderModel
 et de l'API externe PaymentGateway."

3. /compact

La commande /compact compresse le contexte en résumant l'historique de la conversation. Utile quand le contexte approche de sa limite, mais les faits critiques doivent être protégés par un case facts block ou un fichier scratchpad.

4. Persistance d'état structurée avec manifest.json (crash recovery)

Quand un workflow multi-agents est long, chaque subagent exporte son état dans un fichier JSON connu. Le coordinateur maintient un fichier manifest.json qui résume l'état global du workflow. En cas de crash ou de redémarrage, le coordinateur charge ce manifeste et reprend là où il s'était arrêté.

Exemple : état d'un subagent 
// agent-state/web-search-agent.json
{
  "status": "completed",
  "queries_executed": ["AI music 2024", "AI music composition"],
  "results_count": 12,
  "key_findings": [
    "AI-generated music grew 300% on streaming platforms in 2024",
    "Major labels investing in AI composition tools"
  ],
  "coverage": ["music composition", "music production"],
  "gaps": ["music distribution", "music licensing"]
}
Exemple : manifest.json du coordinateur 
// agent-state/manifest.json
{
  "web-search": "completed",
  "doc-analysis": "in_progress",
  "synthesis": "not_started"
}

Au redémarrage, le coordinateur lit manifest.json, constate que web-search est terminé et que doc-analysis est en cours, et reprend le workflow sans relancer les tâches déjà complétées. Le fichier d'état de chaque subagent (ex. web-search-agent.json) contient le détail de ses résultats, ses lacunes (gaps), et sa couverture.

À retenir : La persistance d'état structurée via manifest.json est le pattern recommandé pour le crash recovery dans les workflows multi-agents longs. Chaque subagent écrit son propre fichier d'état ; le coordinateur maintient le manifeste global. Ce pattern est distinct du scratchpad (qui protège le contexte d'un agent unique).

5. Modifier les agents en amont

Quand les agents en aval ont des budgets de contexte limités, les agents en amont doivent retourner des données structurées (faits clés, citations, scores de pertinence) plutôt que du contenu verbeux et des chaînes de raisonnement.

5. Le contrôle humain et la confidence calibration (Task 5.5)

Le problème que cela résout

Un système d'extraction de données affiche une accuracy globale de 97 %. En apparence, tout va bien. Mais en creusant, on découvre que l'accuracy sur un type de document spécifique (les factures scannées) est de 60 %, et que certains champs (les numéros de TVA) ont un taux d'erreur de 40 %. Les métriques agrégées masquent des problèmes localisés.

Exemple concret : 97% aggregate accuracy peut masquer 40% d'erreurs sur un type de document spécifique. C'est pourquoi l'analyse doit toujours se faire par document type ET par field, pas en agrégé.

Le stratified random sampling

Même pour les extractions à haute confiance, il faut maintenir un stratified random sampling régulier pour mesurer les taux d'erreur réels et détecter de nouveaux patterns d'erreur. L'analyse doit se faire :

  • Par document type (factures, contrats, formulaires...)
  • Par field (montants, dates, noms, numéros de TVA...)
  • Pas seulement en agrégé

6. La provenance et la synthèse multi-sources (Task 5.6)

Le problème : attribution loss pendant la summarization

Quand un agent agrège des résultats provenant de plusieurs sources, la synthèse peut perdre le lien entre chaque affirmation et sa source (attribution loss). L'utilisateur final ne sait plus d'où viennent les chiffres, ce qui rend le rapport inutilisable pour la prise de décision.

Les claim-source mappings

Chaque affirmation dans la synthèse doit être liée à sa source via un mapping structuré incluant l'URL, le nom du document et des citations directes :

Mauvais : « Le marché de la musique IA est estimé à 3,2 milliards de dollars. » (Pas de source, pas de date — attribution perdue.)
Bon — claim-source mapping : 
{
  "claim": "Le marché de la musique IA est estimé à 3,2 Mds $",
  "source_url": "https://example.com/report",
  "source_name": "Global AI Music Report 2024",
  "quote": "The AI music market reached $3.2B in 2024",
  "publication_date": "2024-06-15",
  "confidence": 0.9
}

Gérer les données contradictoires

Quand deux sources crédibles donnent des statistiques différentes, il ne faut pas choisir arbitrairement l'une des deux. Il faut préserver les deux valeurs avec leur attribution et annoter le conflit. Le coordinateur (ou l'utilisateur) décide :

{
  "claim": "Part de la musique générée par IA sur le streaming",
  "values": [
    {"value": "12%", "source": "Spotify Annual Report 2024",
     "date": "2024-03", "methodology": "Classification automatisée"},
    {"value": "8%", "source": "Music Industry Association Survey",
     "date": "2024-07", "methodology": "Enquête auprès de 500 labels"}
  ],
  "conflict_detected": true,
  "possible_explanation": "Différence de méthodologie et de période"
}

Inclure les dates pour le contexte temporel

Sans les dates, des différences temporelles peuvent être interprétées à tort comme des contradictions :

  • Mauvais : « Source A dit 10 %, Source B dit 15 %. Contradiction. »
  • Bon : « Source A (2023) dit 10 %, Source B (2024) dit 15 %. Probable croissance de 5 % sur un an — pas une contradiction. »
À retenir : 10% en 2023 + 15% en 2024 = growth, pas contradiction. Les dates transforment un conflit apparent en tendance. Toujours inclure les dates dans les claim-source mappings.

7. Synthèse — les points clés

Gestion du contexte

  • L'API ne conserve rien entre les requêtes : envoyer le full history à chaque appel.
  • Le case facts block préserve les faits transactionnels en dehors du summarized history.
  • L'effet lost-in-the-middle : conclusions clés en tête, actions en fin.
  • Réduire les tool results aux champs pertinents via des hooks PostToolUse.
  • /compact pour compresser ; scratchpad pour persister ; subagents pour isoler.
  • Persistance d'état structurée via manifest.json pour le crash recovery.
  • Les subagents doivent inclure les métadonnées (dates, sources) dans leurs sorties structurées.

Escalation

  • Déclencheurs fiables : demande explicite d'humain, policy gap, no progress.
  • Déclencheurs NON fiables : sentiment analysis, self-rated confidence (1-10), automatic classifier.
  • 3 patterns : immediate, after attempt, nuanced (acknowledge → resolve → escalate on reiteration).
  • La calibration passe par la combinaison critères explicites + few-shot examples dans le system prompt.
  • Le structured handoff protocol doit être complet et autosuffisant (l'humain n'a pas le transcript).

Erreurs multi-agents

  • Retourner un contexte d'erreur structuré : failure_type, query, partial_results, alternatives.
  • Distinguer timeout (access failure → retry décision) de empty results (valid query → résultat légitime).
  • 4 anti-patterns : generic status, silent suppression, abort whole workflow, infinite retries.
  • Coverage annotations dans la synthèse : FULL COVERAGE / PARTIAL COVERAGE.

Confidence et provenance

  • 97% aggregate accuracy peut masquer 40% d'erreurs sur certains document types.
  • Analyser par document type et par field via stratified random sampling.
  • Préserver les claim-source mappings (URL, nom, quotes) à travers la synthèse.
  • Annoter les conflits avec attribution ; ne jamais choisir arbitrairement une valeur.
  • Inclure les dates pour le contexte temporel (éviter les faux conflits).

8. Auto-évaluation (7 questions)

7 questions pour tester votre compréhension

Q1. Situation : un remboursement de $89.99 discuté 20 turns plus tôt est devenu « a promotional pricing was discussed » dans le résumé. Comment prévenir cette perte ?

A) Augmenter le context window.
B) Extraire les faits transactionnels dans un case facts block inclus dans chaque prompt, en dehors du summarized history.
C) Utiliser /compact moins souvent.
D) Ajouter des few-shot examples.

Réponse : B. Le case facts block persiste les informations critiques (montants, dates, IDs) en dehors de l'historique résumé. Même après un /compact, ces faits restent intacts dans le prompt. Augmenter le context window (A) ne fait que retarder le problème ; utiliser /compact moins souvent (C) aussi. Les few-shot examples (D) ne concernent pas la préservation des faits.

Q2. Situation : le client dit « This is outrageous, I'm very unhappy! » L'agent doit-il escalader immédiatement ?

A) Oui, le sentiment négatif indique une escalation nécessaire.
B) Non — acknowledge l'émotion, proposer une résolution, et escalader seulement si le client réitère sa demande de parler à un humain.
C) Oui, utiliser sentiment analysis pour détecter la frustration.
D) Non, ignorer l'émotion et se concentrer sur le problème technique.

Réponse : B. Le pattern nuanced : acknowledge → resolve → escalate only on reiteration. La sentiment analysis n'est pas un déclencheur fiable d'escalation (A et C sont des pièges). Ignorer l'émotion (D) est une mauvaise pratique — il faut reconnaître la frustration avant de proposer une solution.

Q3. Situation : trois catégories de sources retournent des résultats différents : academic databases = 15 papers, industry reports = « 0 results », patent databases = « Connection timeout ». Comment propager au coordinateur ?

A) Agréger en « 67% source coverage ».
B) Reporter timeout et 0 results comme des failures.
C) Retry automatiquement les failures transitoires.
D) Distinguer les access failures (timeout = retry décision) des valid empty results (0 results = successful query).

Réponse : D. Un timeout est un access failure — la requête n'a pas abouti et un retry peut être pertinent. Des résultats vides (0 results) signifient que la requête a réussi mais n'a rien trouvé — c'est un résultat légitime. Les traiter de la même manière (B) ou les agréger en un pourcentage générique (A) masque cette distinction sémantique critique.

Q4. Situation : l'accuracy globale de votre système d'extraction est 97%. Faut-il s'en satisfaire ?

A) Oui, 97% est excellent.
B) Non — l'accuracy agrégée peut masquer 40% d'erreurs sur un document type spécifique. Analyser par document type et par field.
C) Oui, si les tests unitaires passent.
D) Non, implémenter un classifier pour détecter les erreurs.

Réponse : B. L'analyse par stratified random sampling — par document type ET par field — peut révéler que certains types de documents (factures scannées, formulaires manuscrits) ou certains champs (numéros de TVA, adresses) ont des taux d'erreur bien plus élevés que la moyenne. 97% en agrégé ne garantit rien sur les sous-catégories.

Q5. Situation : deux sources crédibles rapportent des chiffres différents sur la part de musique générée par IA sur le streaming : 12 % (Spotify Annual Report, mars 2024) et 8 % (enquête sectorielle, juillet 2024), avec des méthodologies différentes. Comment traiter cette divergence dans la synthèse ?

A) Choisir la source la plus récente et ignorer l'autre.
B) Faire la moyenne des deux valeurs.
C) Préserver les deux valeurs avec leur attribution complète (source, date, méthodologie), marquer conflict_detected: true, et laisser le coordinateur ou l'utilisateur trancher.
D) Retirer la statistique du rapport pour éviter toute ambiguïté.

Réponse : C. Quand deux sources crédibles divergent, il ne faut jamais choisir arbitrairement une valeur (A, B) ni supprimer l'information (D). Le claim-source mapping doit préserver les deux valeurs avec leur attribution, annoter le conflit, et inclure les dates : ici, la différence de méthodologie et de période explique probablement l'écart, ce qui est une information utile pour la décision en aval.

Q6. Votre agent multi-turn approche de la limite du context window après 80 turns d'investigation. Les premiers turns contiennent des décisions architecturales importantes que vous ne voulez pas perdre. Quelle est la meilleure stratégie ?

A) Lancer /compact immédiatement et continuer.
B) Combiner progressive summarization (résumé structuré des turns anciens) avec un case facts block extérieur qui contient les décisions architecturales clés.
C) Augmenter max_tokens.
D) Démarrer une nouvelle session et oublier l'historique.

Réponse : B. La progressive summarization compresse l'historique long (libère du budget), tandis que le case facts block protège les informations critiques en dehors du résumé. C'est la combinaison qui garantit à la fois longévité de session et préservation des faits. A seule risque de perdre les décisions architecturales (la summarization dilue les détails). C confond max_tokens (budget de réponse) et limite de contexte. D perd tout l'historique utile.

Q7 (Domaine 5) : Situation : après 50 turns d'investigation, votre agent approche du context limit. Le policy gap a été identifié, et l'agent découvre qu'il y a 3 correspondances client possibles pour le même ID de dossier. Quels sont les deux bons patterns d'escalation à appliquer immédiatement ? (Sélectionne les 2 réponses correctes.) A) Escalader immédiatement à cause du context limit qui approche B) Demander des identifiants supplémentaires pour clarifier les 3 correspondances client C) Lancer /compact pour libérer du contexte avant de continuer D) Escalader à cause du policy gap identifié E) Utiliser sentiment analysis pour évaluer si l'escalade est nécessaire

Réponses : B, D. B est correcte : quand il y a plusieurs correspondances client, l'agent doit demander des identifiants supplémentaires pour clarifier, c'est un déclencheur fiable. D est correcte : le policy gap est un déclencheur fiable d'escalation. A confond une limite technique (context) avec un déclencheur d'escalade — libérer du contexte via /compact ou subagents n'est pas une raison d'escalader à un humain. C est une technique valide de gestion contextuelle, mais ce n'est pas un pattern d'escalade. E est un anti-pattern : la sentiment analysis n'est pas un déclencheur fiable d'escalade.
