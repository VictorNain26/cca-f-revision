1. API Request Structure

L'API Claude suit un modèle request-response classique. Chaque appel est stateless : le modèle ne conserve aucun état entre les requêtes. C'est au développeur de renvoyer l'historique complet à chaque appel.

Champs principaux d'une requête

ChampRôleObligatoire
modelIdentifiant du modèle Claude à utiliser (les IDs de modèles précis ne sont pas matière d'examen)Oui
max_tokensNombre maximum de tokens dans la réponseOui
systemLe system prompt — définit le comportement du modèle. Passe séparément, PAS dans messagesNon
messagesHistorique de la conversation (DOIT contenir l'historique complet — API stateless)Oui
toolsDéfinitions des tools disponiblesNon
tool_choiceStratégie de sélection des toolsNon

Exemple complet de requête JSON

{
  "model": "claude-sonnet-5",
  "max_tokens": 1024,
  "system": "Tu es un assistant spécialisé en analyse financière. Réponds de manière concise.",
  "messages": [
    {
      "role": "user",
      "content": "Quel est le chiffre d'affaires de l'entreprise X au Q3 ?"
    }
  ],
  "tools": [
    {
      "name": "get_financial_data",
      "description": "Retrieves quarterly financial data for a company. Returns revenue, net income, and margins. Input: ticker symbol (e.g. 'AAPL') and quarter (e.g. 'Q3-2025').",
      "input_schema": {
        "type": "object",
        "properties": {
          "ticker": { "type": "string", "description": "Stock ticker symbol" },
          "quarter": { "type": "string", "description": "Quarter in format QN-YYYY" }
        },
        "required": ["ticker", "quarter"]
      }
    }
  ],
  "tool_choice": { "type": "auto" }
}
Concept clé : Le champ system est au même niveau que messages, jamais à l'intérieur. C'est une erreur courante de le placer comme premier message user.

2. Message Roles

Chaque message dans le tableau messages possède un role qui détermine son origine :

RoleDescriptionQuand l'utiliser
userMessages de l'utilisateurChaque nouvelle requête ou question
assistantRéponses du modèleInclus lors du renvoi de l'historique pour maintenir le contexte
user (avec tool_result)Résultats d'un appel toolAprès exécution d'un tool — renvoyé comme content block tool_result dans un message user
EXAM TIP : À chaque requête API, vous devez envoyer l'historique COMPLET de la conversation. L'API est stateless — le modèle ne conserve rien entre deux appels. Si un tool_result est omis, le modèle ne saura pas que le tool a été exécuté.

Exemple d'historique multi-turn

"messages": [
  { "role": "user", "content": "Recherche les ventes Q3 d'AAPL" },
  { "role": "assistant", "content": [
    { "type": "tool_use", "id": "toolu_01A", "name": "get_financial_data",
      "input": { "ticker": "AAPL", "quarter": "Q3-2025" } }
  ]},
  { "role": "user", "content": [
    { "type": "tool_result", "tool_use_id": "toolu_01A",
      "content": "Revenue: $94.8B, Net Income: $23.2B" }
  ]},
  { "role": "assistant", "content": "Le CA d'Apple au Q3 2025 est de 94,8 milliards $." },
  { "role": "user", "content": "Et pour MSFT ?" }
]
Anti-pattern : Envoyer uniquement le dernier message sans l'historique. Le modèle perd tout contexte et ne peut pas répondre correctement à des questions de suivi.

3. Le champ stop_reason

Chaque réponse de l'API contient un champ stop_reason qui indique pourquoi le modèle a arrêté de générer. Ce champ est essentiel pour contrôler le flux de votre application.

ValeurSignificationAction typique
"end_turn"Le modèle a terminé naturellement sa réponseAfficher la réponse à l'utilisateur
"tool_use"Le modèle demande l'exécution d'un toolExécuter le tool, renvoyer le résultat
"max_tokens"La limite max_tokens a été atteinte — réponse tronquéeAugmenter max_tokens ou demander de continuer
"stop_sequence"Une séquence d'arrêt personnalisée a été détectéeTraitement spécifique selon la séquence
"pause_turn"Un server tool (ex: web search) a atteint sa limite d'itérationsRe-envoyer la requête avec l'historique tel quel pour laisser le modèle continuer — ne pas traiter comme une fin de tâche
"refusal"Refus de sécurité du modèleVérifier stop_details pour la raison du refus
"model_context_window_exceeded"La fenêtre de contexte a été dépassée pendant la génération (modèles 4.5+)Réduire le contexte envoyé ou augmenter la marge disponible
Pour les systèmes agentiques : Les deux valeurs les plus importantes sont "tool_use" et "end_turn". Elles controlent la boucle agentique :
  • "tool_use" → exécuter le tool, renvoyer le résultat, re-appeler l'API
  • "end_turn" → le modèle a fini, sortir de la boucle
Voir D1 pour les détails sur la boucle agentique.

4. System Prompt

Le system prompt est passé via le champ system, séparé du tableau messages. Il définit le comportement global du modèle pour toute la conversation.

Caractéristiques clés

  • Priorité supérieure aux messages user — le modèle suit le system prompt en priorité
  • Défini une fois côté code, mais renvoyé (et refacturé) à chaque appel — l'API est stateless
  • Consomme des tokens dans le context window à chaque appel
EXAM TRAP : La formulation du system prompt peut créer des associations non intentionnelles avec les tools. Exemple classique : un system prompt qui dit "always verify the customer's identity" peut provoquer un appel systématique à get_customer, même quand ce n'est pas nécessaire. Le modèle interprète l'instruction comme un déclencheur pour utiliser le tool le plus sémantiquement proche.
Anti-pattern : Placer le system prompt comme premier message user dans messages. Cela réduit sa priorité et le mélange avec le contexte conversationnel.

5. Context Window

Le context window représente la quantité totale de tokens que le modèle peut traiter en une seule requête. Il inclut tout :

  • Le system prompt
  • L'historique complet des messages
  • Les tool définitions (schémas des tools)
  • Les tool results (retours d'exécution)

3 problèmes majeurs

1. L'effet lost-in-the-middle

Le modèle traite de manière fiable les informations en début et en fin du context window, mais a tendance à manquer les détails situés au milieu. Plus le contexte est long, plus cet effet est prononcé.

2. Accumulation des tool results

Un tool peut retourner un objet avec 40+ champs alors que seuls 5 sont pertinents. Chaque appel ajoute ces résultats volumineux au contexte, le saturant rapidement avec des informations inutiles.

3. Progressive summarization

Quand on demande au modèle de résumer l'historique pour libérer du contexte, les valeurs numériques, les dates et les détails spécifiques sont progressivement perdus au profit de reformulations vagues.

EXAM TIP : Les solutions de gestion du context window sont détaillées dans D5. Retenez ici les 3 problèmes — ils reviennent souvent dans les questions d'examen.

6. tool_use — le mécanisme

Point fondamental : Claude n'exécute PAS de code. Il génère une requête structurée d'appel tool (nom + paramètres). C'est votre code qui exécute le tool et renvoie le résultat.

Anatomie d'une tool définition

ChampRole
nameIdentifiant unique du tool
descriptionMécanisme principal de sélection — c'est sur cette description que le LLM se base pour choisir un tool
input_schemaSchéma JSON Schema définissant les paramètres attendus

Ecrire une bonne description

La description est le mécanisme principal de sélection. Un LLM choisit ses tools en se basant sur leurs descriptions. Une bonne description répond à 4 questions :

  1. Que fait le tool et que retourne-t-il ?
  2. Quels sont les formats des inputs ? (avec exemples)
  3. Quels sont les edge cases et les contraintes ?
  4. Quand l'utiliser par rapport aux alternatives similaires ?
Anti-pattern : Des descriptions ambiguës ou qui se chevauchent entre tools causent du misrouting — le modèle choisit le mauvais tool ou hésite entre plusieurs.

Built-in tools vs MCP tools

Dans un système agentique, le modèle peut avoir accès à des built-in tools (définis directement dans la requête) et des MCP tools (provenant de serveurs externes). Les agents ont tendance à préférer les built-in tools. Pour compenser, il faut renforcer les descriptions des MCP tools afin qu'elles soient plus précises et distinctives.

Voir D2 pour une étude approfondie du tool design.

7. Le paramètre tool_choice

Le paramètre tool_choice contrôle comment le modèle décide d'utiliser (ou non) un tool :

ValeurComportementCas d'usage
{"type": "auto"}Le modèle décide librement s'il appelle un tool ou non (valeur par défaut)Conversations générales avec tools optionnels
{"type": "any"}Le modèle DOIT appeler un tool (n'importe lequel) — un tool est toujours appelé, mais la conformité au schéma n'est garantie que si le tool utilise strict: trueQuand vous voulez forcer un output structuré sans imposer un tool spécifique
{"type": "tool", "name": "extract_metadata"}Le modèle DOIT appeler le tool specifie — exécution garantieForcer un ordre d'exécution précis dans un pipeline
{"type": "none"}Aucun tool n'est autorisé, même s'il y en a de disponiblesForcer une réponse texte pure malgré la présence de tools dans la requête

L'option disable_parallel_tool_use: true peut être combinée à tool_choice pour empêcher le modèle d'appeler plusieurs tools en parallèle dans une même réponse.

Concept clé : tool_choice: {"type": "any"} avec plusieurs tools disponibles → le modèle choisit le tool le plus pertinent. C'est le pattern historique du tool_use forcé pour obtenir du structured output ; la méthode recommandée aujourd'hui est output_config.format (Structured Outputs natifs, voir section 8).

Voir D2 section 3 pour les stratégies avancées de tool_choice.

8. JSON Schemas pour structured output

Point essentiel : La méthode recommandée pour obtenir du structured output de Claude est désormais les Structured Outputs natifs : passer output_config: {"format": {"type": "json_schema", "schema": {...}}} à messages.create (ou, côté SDK Python, utiliser client.messages.parse() avec un modèle Pydantic). Ce mécanisme garantit un JSON syntaxiquement valide et conforme au schéma.

Le pattern « tool_use forcé » (tool_choice: {"type": "any"} ou {"type": "tool", "name": "..."}, voir section 7) reste valable et fonctionne, mais c'est le pattern historique. Sans strict: true sur la définition du tool — qui impose additionalProperties: false et la liste required — la conformité au schéma n'est pas garantie : le modèle peut omettre des champs requis ou ajouter des champs non prévus.

Pour l'examen : la bonne réponse pour le structured output est le pattern tool_use forcé (tool_choice) — c'est le mécanisme couvert par le guide officiel CCA-F. Les Structured Outputs natifs (output_config.format) sont la méthode actuelle recommandée par la documentation Anthropic, mais n'apparaissent pas dans le guide : ne les proposez pas comme réponse à l'examen. Dans les deux cas, la garantie de conformité au schéma suppose strict: true sur la définition du tool (ou l'équivalent natif) — sans quoi le modèle peut omettre ou ajouter des champs.

Ce qui est garanti vs ce qui ne l'est pas

GarantiNON garanti
JSON syntaxiquement valideExactitude sémantique des valeurs
Respect de la structure du schéma (Structured Outputs natifs, ou tool_use avec strict: true)Cohérence entre les champs (ex: totaux qui s'additionnent)
Types de données correctsAbsence de valeurs fabriquées (hallucinations)

Règles de conception des schémas

1. Champs required — avec prudence

Ne marquer un champ comme required que si l'information est toujours disponible. Sinon, le modèle fabrique une valeur plutôt que de laisser le champ vide.

2. Champs nullable

"company_name": {
  "type": ["string", "null"],
  "description": "Company name if mentioned, null otherwise"
}

Permet au modèle de retourner null au lieu d'halluciner une valeur quand l'information n'est pas présente dans le texte source.

3. Enums avec "other" + champ détail

"category": {
  "type": "string",
  "enum": ["billing", "technical", "account", "other"]
},
"category_detail": {
  "type": ["string", "null"],
  "description": "Free-text detail when category is 'other'"
}

Évite de perdre des données qui ne rentrent pas dans les catégories prédéfinies.

4. Enum avec "unclear"

"sentiment": {
  "type": "string",
  "enum": ["positive", "negative", "neutral", "unclear"]
}

Permet au modèle d'exprimer son incertitude. Un "unclear" honnête vaut mieux qu'une catégorisation erronée.

Types d'erreurs

Type d'erreurCauseSolution
Erreur syntaxique (JSON invalide)Génération de texte libreÉliminée par tool_use
Erreur sémantique (valeurs incorrectes)Mauvaise interprétation, hallucinationValidation programmatique + retry

Voir D4 pour les patterns avances de structured output.

9. Questions d'auto-évaluation

Q1 (D0) — API stateless et perte de tool_result

Situation : votre pipeline CI appelle l'API Claude. Entre deux requêtes, un tool_result de l'appel précédent est perdu. Quelle est la cause la plus probable ?

A) L'API est stateless : le développeur n'a pas renvoyé l'historique complet (avec les tool_result) dans la requête suivante.

B) Le tool_result expire côté serveur Anthropic après quelques secondes.

C) Le max_tokens est trop bas pour conserver le tool_result.

D) Il manque un paramètre session_id pour persister l'état entre requêtes.

Réponse : A) L'API est stateless, l'historique complet n'a pas été renvoyé

Explication : l'API Claude ne conserve aucun état entre les requêtes. À chaque appel, le tableau messages doit contenir l'intégralité de l'historique, tool_result compris. C'est au client de le reconstituer.

Pourquoi les autres sont faux :

  • B) Rien n'expire côté serveur, puisque l'API ne stocke rien.
  • C) max_tokens borne la longueur de la sortie, pas la taille de l'historique envoyé.
  • D) Il n'existe pas de paramètre session_id sur l'API Messages.
Q2 (D0) — System prompt keyword-sensitive

Situation : le system prompt dit « always verify the customer's identity ». Vous constatez que get_customer est appelé même quand ce n'est pas nécessaire. Quelle est la cause racine ?

A) La description de get_customer est trop large.

B) La formulation du system prompt (« always verify ») crée une association non intentionnelle avec le tool get_customer.

C) tool_choice est réglé sur "any", forçant un appel d'outil.

D) Le modèle appelle get_customer par défaut au premier tour.

Réponse : B) La formulation du system prompt crée une association non intentionnelle

Explication : le modèle interprète « always verify the customer » comme une instruction déclenchant systématiquement le tool sémantiquement le plus proche — ici get_customer. C'est une instruction keyword-sensitive : elle prend le pas sur des descriptions d'outils pourtant bien écrites. La correction est de dire quand la vérification est nécessaire plutôt que « always ».

Pourquoi les autres sont faux :

  • A) C'est un symptôme plausible, pas la cause : rien dans l'énoncé n'indique une description trop large, et le déclencheur identifié est le mot always.
  • C) Aucun tool_choice forcé n'est mentionné ; par défaut il vaut "auto".
  • D) Le modèle n'a pas de tool par défaut au premier tour — il choisit sur la base des descriptions et du system prompt.
Q3 (D0) — Garantir qu'un tool soit appelé

Situation : vous avez besoin d'une sortie structurée garantie de Claude. Quelle valeur de tool_choice garantit qu'un tool est toujours appelé, sans en imposer un précis ?

A) {"type": "auto"}

B) {"type": "any"}

C) Omettre tool_choice

D) {"type": "none"}

Réponse : B) {"type": "any"}

Explication : "any" oblige le modèle à appeler au moins un tool tout en le laissant choisir lequel — c'est exactement le réglage quand plusieurs schémas d'extraction coexistent et que le type d'entrée n'est pas connu à l'avance. Pour imposer un outil précis, on utilise {"type": "tool", "name": "..."}.

Pourquoi les autres sont faux :

  • A) "auto" laisse le modèle répondre en texte libre sans appeler d'outil.
  • C) Omettre le champ revient à "auto", qui est le défaut dès que des tools sont fournis.
  • D) "none" fait l'inverse : il interdit tout appel d'outil.
Q4 (D0) — Champ required et fabrication de valeur

Situation : un tool d'extraction déclare company_name dans required, mais certains documents ne mentionnent aucune entreprise. Que se passe-t-il le plus souvent ?

A) L'API renvoie une erreur 400 de validation.

B) Le champ est automatiquement renvoyé à null.

C) Le modèle fabrique une valeur pour satisfaire la contrainte required.

D) Le tool n'est pas appelé du tout.

Réponse : C) Le modèle fabrique une valeur pour satisfaire la contrainte

Explication : un champ required place le modèle devant un choix entre violer le schéma et inventer — il invente. La correction est de rendre le champ nullable ("type": ["string", "null"]) et de le retirer de required : le modèle renvoie alors null honnêtement quand l'information est absente.

Pourquoi les autres sont faux :

  • A) L'API valide la conformité au schéma, jamais la véracité du contenu — une valeur inventée est conforme.
  • B) Rien ne renvoie automatiquement null tant que le champ reste required.
  • D) Le tool est bien appelé ; c'est son contenu qui est faux.
