1. API Request Structure

L'API Claude suit un modèle request-response classique. Chaque appel est stateless : le modèle ne conserve aucun état entre les requêtes. C'est au développeur de renvoyer l'historique complet à chaque appel.

Champs principaux d'une requête

ChampRoleObligatoire
modelSelection du modèle (claude-opus-4-6, claude-sonnet-4-6, claude-haiku-4-5)Oui
max_tokensNombre maximum de tokens dans la réponseOui
systemLe system prompt — définit le comportement du modèle. Passe séparément, PAS dans messagesNon
messagesHistorique de la conversation (DOIT contenir l'historique complet — API stateless)Oui
toolsDefinitions des tools disponiblesNon
tool_choiceStrategie de selection des toolsNon

Exemple complet de requête JSON

{
  "model": "claude-sonnet-4-6",
  "max_tokens": 1024,
  "system": "Tu es un assistant spécialisé en analyse financiere. Reponds de maniere concise.",
  "messages": [
    {
      "role": "user",
      "content": "Quel est le chiffre d'affaires de l'entreprise X au Q3 ?"
    }
  ],
  "tools": [
    {
      "name": "get_financial_data",
      "description": "Retrieves quarterly financial data for a company. Returns revenue, net income, and margins. Input: ticker symbol (e.g. 'AAPL') and quarter (e.g. 'Q3-2025').",
      "input_schema": {
        "type": "object",
        "properties": {
          "ticker": { "type": "string", "description": "Stock ticker symbol" },
          "quarter": { "type": "string", "description": "Quarter in format QN-YYYY" }
        },
        "required": ["ticker", "quarter"]
      }
    }
  ],
  "tool_choice": { "type": "auto" }
}
Concept clé : Le champ system est au même niveau que messages, jamais a l'interieur. C'est une erreur courante de le placer comme premier message user.

2. Message Roles

Chaque message dans le tableau messages possede un role qui détermine son origine :

RoleDescriptionQuand l'utiliser
userMessages de l'utilisateurChaque nouvelle requête ou question
assistantReponses du modèleInclus lors du renvoi de l'historique pour maintenir le contexte
user (avec tool_result)Resultats d'un appel toolApres exécution d'un tool — renvoye comme content block tool_result dans un message user
EXAM TIP : A chaque requête API, vous devez envoyer l'historique COMPLET de la conversation. L'API est stateless — le modèle ne conserve rien entre deux appels. Si un tool_result est omis, le modèle ne saura pas que le tool a ete execute.

Exemple d'historique multi-turn

"messages": [
  { "role": "user", "content": "Recherche les ventes Q3 d'AAPL" },
  { "role": "assistant", "content": [
    { "type": "tool_use", "id": "toolu_01A", "name": "get_financial_data",
      "input": { "ticker": "AAPL", "quarter": "Q3-2025" } }
  ]},
  { "role": "user", "content": [
    { "type": "tool_result", "tool_use_id": "toolu_01A",
      "content": "Revenue: $94.8B, Net Income: $23.2B" }
  ]},
  { "role": "assistant", "content": "Le CA d'Apple au Q3 2025 est de 94,8 milliards $." },
  { "role": "user", "content": "Et pour MSFT ?" }
]
Anti-pattern : Envoyer uniquement le dernier message sans l'historique. Le modèle perd tout contexte et ne peut pas répondre correctement a des questions de suivi.

3. Le champ stop_reason

Chaque réponse de l'API contient un champ stop_reason qui indique pourquoi le modèle a arrete de generer. Ce champ est essentiel pour contrôler le flux de votre application.

ValeurSignificationAction typique
"end_turn"Le modèle a termine naturellement sa réponseAfficher la réponse a l'utilisateur
"tool_use"Le modèle demande l'exécution d'un toolExecuter le tool, renvoyer le resultat
"max_tokens"La limite max_tokens a ete atteinte — réponse tronqueeAugmenter max_tokens ou demander de continuer
"stop_sequence"Une sequence d'arret personnalisee a ete detecteeTraitement spécifique selon la sequence
Pour les systèmes agentiques : Les deux valeurs les plus importantes sont "tool_use" et "end_turn". Elles controlent la boucle agentique :
  • "tool_use" → exécuter le tool, renvoyer le resultat, re-appeler l'API
  • "end_turn" → le modèle a fini, sortir de la boucle
Voir D1 pour les détails sur la boucle agentique.

4. System Prompt

Le system prompt est passe via le champ system, séparé du tableau messages. Il définit le comportement global du modèle pour toute la conversation.

Caracteristiques clés

  • Priorite supérieure aux messages user — le modèle suit le system prompt en priorite
  • Charge une seule fois, s'applique a toute la conversation
  • Consomme des tokens dans le context window à chaque appel
EXAM TRAP : La formulation du system prompt peut creer des associations non intentionnelles avec les tools. Exemple classique : un system prompt qui dit "always verify the customer's identity" peut provoquer un appel systematique a get_customer, même quand ce n'est pas nécessaire. Le modèle interprété l'instruction comme un déclencheur pour utiliser le tool le plus semantiquement proche.
Anti-pattern : Placer le system prompt comme premier message user dans messages. Cela reduit sa priorite et le melange avec le contexte conversationnel.

5. Context Window

Le context window représente la quantite totale de tokens que le modèle peut traiter en une seule requête. Il inclut tout :

  • Le system prompt
  • L'historique complet des messages
  • Les tool définitions (schémas des tools)
  • Les tool results (retours d'exécution)

3 problèmes majeurs

1. L'effet lost-in-the-middle

Le modèle traite de manière fiable les informations en debut et en fin du context window, mais a tendance a manquer les détails situes au milieu. Plus le contexte est long, plus cet effet est prononce.

2. Accumulation des tool results

Un tool peut retourner un objet avec 40+ champs alors que seuls 5 sont pertinents. Chaque appel ajoute ces resultats volumineux au contexte, le saturant rapidement avec des informations inutiles.

3. Progressive summarization

Quand on demande au modèle de resumer l'historique pour liberer du contexte, les valeurs numeriques, les dates et les détails spécifiques sont progressivement perdus au profit de reformulations vagues.

EXAM TIP : Les solutions de gestion du context window sont detaillees dans D5. Retenez ici les 3 problèmes — ils reviennent souvent dans les questions d'examen.

6. tool_use — le mécanisme

Point fondamental : Claude n'execute PAS de code. Il généré une requête structurée d'appel tool (nom + paramètres). C'est votre code qui execute le tool et renvoie le resultat.

Anatomie d'une tool définition

ChampRole
nameIdentifiant unique du tool
descriptionMecanisme principal de selection — c'est sur cette description que le LLM se base pour choisir un tool
input_schemaSchema JSON Schema definissant les paramètres attendus

Ecrire une bonne description

La description est le mécanisme principal de selection. Un LLM choisit ses tools en se basant sur leurs descriptions. Une bonne description répond a 4 questions :

  1. Que fait le tool et que retourné-t-il ?
  2. Quels sont les formats des inputs ? (avec exemples)
  3. Quels sont les edge cases et les contraintes ?
  4. Quand l'utiliser par rapport aux alternatives similaires ?
Anti-pattern : Des descriptions ambigues ou qui se chevauchent entre tools causent du misrouting — le modèle choisit le mauvais tool ou hesite entre plusieurs.

Built-in tools vs MCP tools

Dans un système agentique, le modèle peut avoir accès a des built-in tools (definis directement dans la requête) et des MCP tools (provenant de serveurs externes). Les agents ont tendance a preferer les built-in tools. Pour compenser, il faut renforcer les descriptions des MCP tools afin qu'elles soient plus précises et distinctives.

Voir D2 pour une etude approfondie du tool design.

7. Le paramètre tool_choice

Le paramètre tool_choice contrôle comment le modèle decide d'utiliser (ou non) un tool :

ValeurComportementCas d'usage
{"type": "auto"}Le modèle decide librement s'il appelle un tool ou non (valeur par defaut)Conversations generales avec tools optionnels
{"type": "any"}Le modèle DOIT appeler un tool (n'importe lequel) — structured output garantiQuand vous voulez forcer un output structure sans imposer un tool spécifique
{"type": "tool", "name": "extract_metadata"}Le modèle DOIT appeler le tool specifie — exécution garantieForcer un ordre d'exécution precis dans un pipeline
Concept clé : tool_choice: {"type": "any"} avec plusieurs tools disponibles → le modèle choisit le tool le plus pertinent, mais l'output structure est garanti. C'est la méthode recommandée pour obtenir du structured output quand plusieurs schémas sont possibles.

Voir D2 section 3 pour les stratégies avancees de tool_choice.

8. JSON Schemas pour structured output

Point essentiel : Utiliser tool_use avec des JSON schémas est la méthode la plus fiable pour obtenir du structured output de Claude. Le mécanisme garantit un JSON syntaxiquement valide.

Ce qui est garanti vs ce qui ne l'est pas

GarantiNON garanti
JSON syntaxiquement valideExactitude semantique des valeurs
Respect de la structure du schémaCoherence entre les champs (ex: totaux qui s'additionnent)
Types de données correctsAbsence de valeurs fabriquees (hallucinations)

Regles de conception des schémas

1. Champs required — avec prudence

Ne marquer un champ comme required que si l'information est toujours disponible. Sinon, le modèle fabrique une valeur plutot que de laisser le champ vide.

2. Champs nullable

"company_name": {
  "type": ["string", "null"],
  "description": "Company name if mentioned, null otherwise"
}

Permet au modèle de retourner null au lieu d'halluciner une valeur quand l'information n'est pas présente dans le texte source.

3. Enums avec "other" + champ détail

"category": {
  "type": "string",
  "enum": ["billing", "technical", "account", "other"]
},
"category_detail": {
  "type": ["string", "null"],
  "description": "Free-text detail when category is 'other'"
}

Evite de perdre des données qui ne rentrent pas dans les catégories predefinies.

4. Enum avec "unclear"

"sentiment": {
  "type": "string",
  "enum": ["positive", "negative", "neutral", "unclear"]
}

Permet au modèle d'exprimer son incertitude. Un "unclear" honnete vaut mieux qu'une categorisation erronee.

Types d'erreurs

Type d'erreurCauseSolution
Erreur syntaxique (JSON invalide)Generation de texte libreEliminee par tool_use
Erreur semantique (valeurs incorrectes)Mauvaise interpretation, hallucinationValidation programmatique + retry

Voir D4 pour les patterns avances de structured output.

9. Questions d'auto-évaluation

Q1 : Votre pipeline CI appelle l'API Claude. Entre deux requêtes, un tool result de l'appel précédent est perdu. Quelle est la cause la plus probable ?

A) L'API est stateless : le développeur n'a pas renvoyé l'historique complet (avec les tool_result) dans la requête suivante.

B) Le tool_result expire côté serveur Anthropic après quelques secondes.

C) Le max_tokens est trop bas pour conserver le tool_result.

D) Il manque un paramètre session_id pour persister l'état entre requêtes.

Réponse : A. L'API Claude est stateless : elle ne conserve aucun état entre les requêtes. À chaque appel, le tableau messages doit contenir l'intégralité de l'historique, y compris les tool_result précédents. B/C/D sont faux : rien n'expire côté serveur (l'API ne stocke rien), max_tokens borne la sortie pas l'historique, et il n'existe pas de session_id — c'est au client de renvoyer l'historique.

Q2 : Le system prompt dit "always verify the customer's identity". Vous constatez que get_customer est appelé même quand ce n'est pas nécessaire. Quelle est la cause racine ?

A) La description de get_customer est trop large.

B) La formulation du system prompt ("always verify") crée une association non intentionnelle avec le tool get_customer.

C) tool_choice est réglé sur "any", forçant un appel d'outil.

D) Le modèle appelle get_customer par défaut au premier tour.

Réponse : B. Le modèle interprète "always verify the customer" comme une instruction déclenchant systématiquement le tool le plus sémantiquement proche — ici get_customer : c'est une instruction keyword-sensitive. La solution : reformuler le system prompt en spécifiant quand la vérification est nécessaire plutôt que "always". (A est un symptôme, pas la cause racine : rien n'indique une description trop large ; le déclencheur est le mot always du system prompt. C est faux : aucun tool_choice n'est forcé ici.)

Q3 : Vous avez besoin d'un structured output garanti de Claude. Quelle valeur de tool_choice garantit qu'un tool est toujours appelé (sans en imposer un précis) ?

A) {"type": "auto"}

B) {"type": "any"}

C) Omettre tool_choice

D) temperature: 0

Réponse : B. {"type": "any"} force le modèle à appeler au moins un tool, mais le laisse choisir lequel → output structuré garanti. "auto" (A, et le défaut quand on omet le champ — C) laisse le modèle répondre en texte libre. temperature (D) n'a aucun rapport. Pour forcer un tool spécifique : {"type": "tool", "name": "..."} (plus restrictif que "any").

Q4 : Un tool d'extraction a un champ required "company_name", mais certains documents ne mentionnent aucune entreprise. Que se passe-t-il le plus souvent ?

A) L'API renvoie une erreur 400 de validation.

B) Le champ est automatiquement renvoyé à null.

C) Le modèle fabrique une valeur (hallucination) pour satisfaire la contrainte required.

D) Le tool n'est pas appelé du tout.

Réponse : C. Un champ required pousse le modèle à inventer une valeur plutôt que de violer le schéma (l'API ne valide pas la véracité, donc pas d'erreur 400). Correction : rendre le champ nullable avec "type": ["string", "null"] et le retirer de required → le modèle renvoie null quand l'information est absente au lieu d'inventer un nom.
