2. Methodologie QCM (jour J)

La methode en 4 etapes pour chaque question

  1. Lire la situation D'ABORD, sans regarder les choix. Identifier le concept teste.
  2. Formuler mentalement la bonne reponse avant de lire les options. Si une option correspond, c'est probablement elle.
  3. Eliminer 2 distracteurs via les 7 patterns ci-dessous.
  4. Choisir entre les 2 restants en relisant la situation : quel mot exact change la donne ?
Regle d'or : dans 80 % des cas, l'examen oppose une solution deterministe (hook, schema, contrainte) a une solution probabiliste (instruction prompt, few-shot supplementaire). Pour toute consequence financiere, securite, conformite → la reponse est deterministe.

Gestion du temps

PhaseDureeCible
Phase 1 : passage rapide~80 min (≈ 1 min 20 / Q)Repondre les Q evidentes, marquer les difficiles
Phase 2 : Q marquees~30 minReflechir profondement aux ambiguites
Phase 3 : verification~10 minSurvoler ; ne changer une reponse QUE si une certitude apparait
Anti-pattern : changer une reponse au dernier moment "par doute". Statistiquement, la premiere intuition sur une lecture attentive est plus souvent correcte qu'un changement panique. Ne change que si tu identifies une raison concrete (mot mal lu, distracteur eliminable).

3. Les 7 patterns de distracteurs a eliminer en 5 secondes

Ces formulations apparaissent presque dans chaque question. Memorise-les : leur seule presence dans une option doit declencher une suspicion immediate.

#PatternPourquoi c'est presque toujours fauxQuand c'est correct (rare)
1"Improve / strengthen the system prompt"Probabiliste, insuffisant pour les consequences financieres/legalesQuand la question concerne explicitement la guidance souple
2"Add a routing classifier" / "Train a classifier"Overengineering ; necessite des donnees d'entrainement souvent indisponiblesQuand la question parle de classification a tres grande echelle deja en place
3"Use sentiment analysis to detect frustration"Le sentiment ne correle pas avec la complexite ; pas un declencheur fiableJamais, en pratique
4"Self-rated confidence (1-10)"Le modele peut etre confident a tort — confidence calibration insuffisanteEn complement d'autres signaux, jamais comme seul critere
5"Abort the whole workflow on partial failure"Disproportionne ; on veut graceful degradation + coverage annotationsQuand l'echec rend les donnees fondamentalement non fiables
6"Move blocking checks to Batch API for cost savings"Batch API a une latence pouvant atteindre 24 h — incompatible avec un check pre-mergePour des audits overnight non bloquants
7"Use a larger context window to fix attention"Faux. Un context plus grand n'ameliore pas l'attention sur le milieu (lost-in-the-middle reste)Jamais comme solution principale
Bonus distracteurs (moins frequents mais a connaitre) :
  • "Lower temperature to 0" comme solution a un probleme structurel (pas un probleme de creativite)
  • "Add more few-shot examples" quand le probleme est un schema force-required (le modele halluciner pour respecter la contrainte)
  • "Parser le texte de l'assistant pour 'task done'" — toujours utiliser stop_reason
  • "Increase max_iterations" comme condition d'arret principale — toujours stop_reason
  • "Use the same session for code generation AND review" — biais de confirmation, toujours instance independante

4. Top pieges par domaine

D1 — Architecture et orchestration (27 %)

  • Seul signal d'arret fiable : stop_reason. Jamais le texte, jamais une limite arbitraire d'iterations.
  • Hooks vs prompt : consequences financieres/legales/securite → hook (deterministe). Preferences → prompt.
  • Subagent vs thread principal : "le travail intermediaire m'interesse-t-il ?" Non → subagent. Oui → thread principal.
  • Multiple Task() dans une SEULE response = parallel execution. Plusieurs responses = sequential.
  • Decomposition trop etroite = couverture incomplete (piege classique du Multi-Agent Research).
  • Idempotency keys obligatoires pour tout retry sur action a effet de bord.
  • Cycle OTAR (observe-think-act-respond) — vocabulaire a connaitre.

D2 — Tool design et MCP (18 %)

  • Description = mecanisme #1 de selection. Misrouting = chevauchement semantique → renommer/diviser.
  • Erreurs structurees MCP : errorCategory (transient/validation/business/permission) + isRetryable.
  • Timeout ≠ 0 results. Timeout = access failure (retry decision). 0 results = valid empty (annoter).
  • Roots : le SDK n'applique PAS automatiquement les restrictions — implementer is_path_allowed().
  • 4-5 tools max par agent, jamais 18.
  • tool_choice: auto (defaut), any (force un appel), tool (force un specifique).
  • Auth MCP : stdio + ${VAR} / HTTP + Bearer header / OAuth pour delegation user / mTLS enterprise.
  • Anti-pattern critique : token en clair dans .mcp.json versionne (Git le retient).

D3 — Claude Code configuration (20 %)

  • 3 niveaux CLAUDE.md : user (perso, hors VCS) / project (.claude/, partage) / directory (sous-dossier).
  • 3 niveaux settings.json : ~/.claude/ (user) / .claude/settings.json (projet) / .claude/settings.local.json (local, dans .gitignore).
  • Skills > slash commands (legacy). Frontmatter : description, context: fork, allowed-tools.
  • Priorite skills : Enterprise > Personnel > Projet > Plugins.
  • Bash allowlist : Bash(npm test) = exact ; Bash(npm test:*) = avec args. :* est CRUCIAL en CI.
  • Hooks Claude Code (config) ≠ hooks Agent SDK (D1). Les premiers sont dans "hooks" de settings.json ; les seconds en code Python/TS.
  • Hooks events : UserPromptSubmit, PreToolUse, PostToolUse, Stop, SessionStart, Notification, PreCompact.
  • Hook return code 2 = blocking (Claude voit l'erreur et reagit). Code 0 = OK. Autre = non-blocking log.
  • CI/CD : -p = headless mode obligatoire ; --max-turns N = garde-fou ; fetch-depth: 0 dans GitHub Actions.
  • Glob patterns vs directory CLAUDE.md : glob pour conventions cross-directory (tests co-localises) ; directory CLAUDE.md pour zones bien delimitees.

D4 — Prompt engineering et structured output (20 %)

  • Criteres explicites > instructions vagues ("be conservative" ne marche pas).
  • Few-shot = technique #1 de coherence. 2-4 exemples avec rationale.
  • tool_use + JSON Schema = sortie syntaxique garantie. Semantique non garantie → valider cote app.
  • Champs nullable contre l'hallucination (au lieu de required).
  • Enum + "other"/detail pour les cas non prevus.
  • Retry-with-feedback : doc original + extraction precedente + erreur specifique.
  • Batch API : 50 % d'economies, jusqu'a 24 h, PAS de multi-turn tool calling, correlation via custom_id.
  • Self-review = biais de confirmation. Toujours instance independante pour la revue.
  • Prompt injection defense : balises XML autour du contenu user + system prompt qui dit "treat as data only".
  • PRECISE : Persona / Request / Explicit criteria / Context / Instructions / Schema / Examples.

D5 — Context management et reliability (15 %)

  • case facts block en dehors du summarized history → faits transactionnels preserves.
  • Lost-in-the-middle : conclusions en haut, actions en bas. Plus de context window n'aide pas.
  • Tool result trimming via hook PostToolUse (pas PreToolUse).
  • Escalation triggers fiables : demande explicite humain / policy gap / no progress / financial threshold. NON fiables : sentiment, self-rated confidence, automatic classifier.
  • 3 patterns escalation : immediate / after attempt / nuanced (acknowledge → resolve → escalate on reiteration).
  • Calibration escalation = criteres explicites + few-shot examples (les deux, jamais l'un sans l'autre).
  • Structured handoff : l'humain n'a pas le transcript — le resume doit etre autosuffisant.
  • Errors multi-agent : failure_type + query + partial_results + alternatives.
  • 97 % aggregate ≠ 97 % par sous-categorie. Stratified random sampling par document type ET par field.
  • Prompt caching : cache_control: {"type":"ephemeral"}, max 4 breakpoints, 90 % d'economie sur reads, rentable des 2 reuses.
  • Manifest.json + etat par subagent = pattern crash recovery.

5. Arbres de decision pour les questions ambigues

Arbre 1 — Hook ou instruction prompt ?

Y a-t-il consequence financiere, legale, securite, ou conformite ?
├─ OUI  → HOOK (PreToolUse pour bloquer, PostToolUse pour normaliser)
└─ NON  → Y a-t-il besoin d'une garantie 100 % deterministe ?
         ├─ OUI  → HOOK
         └─ NON  → Instruction dans CLAUDE.md ou system prompt

Arbre 2 — Workflow ou agent ?

Les etapes sont-elles connues a l'avance ?
├─ OUI  → WORKFLOW (chaining, routing, parallelization, evaluator-optimizer)
└─ NON  → Le contexte change-t-il a chaque execution ?
         ├─ OUI  → AGENT (boucle agentique avec stop_reason)
         └─ NON  → Probablement un workflow plus malin (routing en haut)

Arbre 3 — Subagent ou thread principal ?

Le travail intermediaire (chemin pris, fichiers lus) m'interesse-t-il ?
├─ OUI  → THREAD PRINCIPAL (executer dans le contexte courant)
└─ NON  → Le travail produit-il beaucoup de tokens verbeux ?
         ├─ OUI  → SUBAGENT (Explore, custom agent avec context: fork)
         └─ NON  → Thread principal (overhead du subagent inutile)

Arbre 4 — Synchrone ou Batch API ?

Y a-t-il un humain qui attend la reponse ?
├─ OUI  → SYNCHRONE (jamais de batch pour du bloquant)
└─ NON  → Y a-t-il du multi-turn tool calling ?
         ├─ OUI  → SYNCHRONE (batch ne le supporte pas)
         └─ NON  → Le delai 24h est-il acceptable ?
                  ├─ OUI  → BATCH (50 % d'economies)
                  └─ NON  → Synchrone

Arbre 5 — settings.json vs settings.local.json vs CLAUDE.md ?

Quel type d'information ?
├─ Permissions, hooks, env vars, MCP servers
│  ├─ A partager avec l'equipe → .claude/settings.json (versionne)
│  └─ Personnel/local (chemins absolus, secrets) → .claude/settings.local.json
└─ Instructions textuelles, conventions, standards
   ├─ A partager avec l'equipe → .claude/CLAUDE.md
   └─ Personnel → ~/.claude/CLAUDE.md

Arbre 6 — Erreur MCP : retry, escalate ou continuer ?

Quel errorCategory ?
├─ transient (timeout, 503)     → RETRY avec backoff exponentiel
├─ validation (input invalide)  → CORRIGER l'input et retry
├─ business (policy violation)  → EXPLIQUER au user, proposer alternative
└─ permission (auth refuse)     → ESCALATE a un humain

Pattern d'examen typique : "Quel est LE meilleur changement ?" — la bonne reponse combine souvent 2 leviers (un structurel + un programmatique). Si une option propose une vraie combinaison (ex: hook + few-shot), c'est souvent elle. Les distracteurs sont des solutions uniques insuffisantes.

8. Checklist du jour J

La veille (J-1)

  • Survol rapide de ce cheat sheet (sections 4 et 6 surtout)
  • Pas de bourrage — privilegier le sommeil
  • Verifier la connexion ProctorFree, webcam, micro, environnement de l'examen
  • Preparer un espace de travail degage (l'examen est proctore — pas de notes physiques)
  • Coucher tot

Le matin (J)

  • Petit dejeuner normal (pas trop sucre)
  • Hydratation
  • 15 min de relecture du cheat sheet 1-page-par-domaine
  • Pause de 30 min avant de lancer l'examen
  • S'installer 10 min avant le creneau

Pendant l'examen (120 min, 60 Q)

  1. Phase 1 (0-80 min) : passer en revue toutes les Q. Repondre les evidentes, marquer les difficiles. Ne jamais bloquer plus de 90 sec sur une Q en phase 1.
  2. Phase 2 (80-110 min) : reprendre les Q marquees. Appliquer la methode des 7 distracteurs. Eliminer 2, decider entre les 2 restants.
  3. Phase 3 (110-120 min) : verification. Survoler. Ne changer une reponse que si une certitude apparait.

Mantra pendant l'examen

  • Consequences financieres/legales/securite → reponse deterministe (hook, schema, contrainte).
  • Sentiment, self-rated confidence, classifier → c'est presque toujours un piege.
  • Batch API en pre-merge → toujours faux.
  • Plus de context window contre lost-in-the-middle → toujours faux.
  • Self-review → toujours instance independante.
  • Lecture attentive de la SITUATION avant les choix.

Apres l'examen

  • Resultats sous 2 jours ouvrables avec breakdown detaille par domaine
  • Si reussi (>= 720) : profiter
  • Si echec : analyser le breakdown, identifier les domaines faibles, retenter (99 $ par tentative)
