1. La hiérarchie CLAUDE.md et l'organisation modulaire (Task 3.1)

Le problème que cela resout

Dans une équipe, chaque développeur a ses preferences, mais le projet impose aussi des standards communs. Il faut un mécanisme pour separer ces niveaux d'instruction et garantir que chaque membre reçoit les bonnes directives.

Les trois niveaux

NiveauEmplacementPartage ?Usage
User~/.claude/CLAUDE.mdNon (personnel, hors VCS)Preferences personnelles, style de travail
Project.claude/CLAUDE.md ou racineOui (versionne, partage via Git)Standards de code, conventions de test, architecture
DirectoryCLAUDE.md dans un sous-dossierOui (versionne)Conventions propres a cette partie du codebase
Erreur classique : trois développeurs experimentes beneficient de l'instruction "always include comprehensive error handling", mais un nouveau ne la reçoit pas. Cause : les instructions etaient dans ~/.claude/CLAUDE.md (user-level) au lieu de .claude/CLAUDE.md (project-level). Le nouveau n'a pas les fichiers personnels des anciens. Solution : deplacer vers le project-level pour que tout le monde en beneficie.

La syntaxe @path pour les imports

Plutot que de concentrer toutes les instructions dans un seul fichier, vous pouvez referencer des fichiers externes :

# Dans CLAUDE.md
Les standards de code sont decrits dans @./standards/coding-style.md
Les exigences de test sont dans @./standards/testing-requirements.md
La vue d'ensemble du projet est dans @README.md

Le @ se place immediatement avant le path (sans espace). Les paths relatifs sont resolus par rapport au fichier contenant l'import. La profondeur maximale d'imbrication est de 5 niveaux.

Le repertoire .claude/rules/

Une alternative au CLAUDE.md monolithique : des fichiers thematiques dont le chargement depend des fichiers en cours d'edition.

.claude/rules/
  testing.md          — conventions de test
  api-conventions.md  — conventions API
  deployment.md       — regles de deploiement
  react-patterns.md   — patterns React

Chaque fichier inclut un YAML frontmatter avec le champ paths qui specifie quand le charger :

---
paths: ["src/api/**/*"]
---
Pour les fichiers API, utiliser async/await avec une gestion d'erreurs explicite.
Chaque endpoint doit retourner un wrapper de reponse standard.
Quand utiliser .claude/rules/ vs. un directory CLAUDE.md : les fichiers .claude/rules/ avec glob patterns sont preferables quand les conventions s'appliquent a des fichiers disperses dans le codebase (tests co-localises, migrations cross-directory). Un CLAUDE.md dans un sous-dossier convient quand les regles sont spécifiques a un repertoire bien défini.

Les commandes /memory et /compact

(Source : guide officiel, sections 5.7 et 5.8.)

  • /memory affiche quels fichiers mémoire sont actuellement chargés et vous permet de les editer pour y ajouter des notes et preferences. Les fichiers chargés (ex. ~/.claude/projects/<id>/memory/*.md) persistent entre les sessions et sont appliques automatiquement au demarrage. C'est aussi la commande de diagnostic quand vous soupçonnez qu'une instruction n'a pas ete chargee correctement — verifiez que le fichier de mémoire attendu apparaît dans la liste des fichiers chargés.
  • /compact compresse le contexte en resumant l'historique. Utile dans les longues sessions d'investigation, mais avec un risque : les valeurs numeriques exactes, les dates et les détails precis peuvent être perdus lors de la compression.

settings.json vs settings.local.json et permissions Bash

Pourquoi cette distinction est critique : a cote de CLAUDE.md (qui contient des instructions en prose), Claude Code utilise des fichiers JSON de configuration qui controlent les permissions, les variables d'environnement, les hooks, et les serveurs MCP. Confondre les deux est une erreur classique a l'examen.

Les trois niveaux de settings.json

NiveauEmplacementVersionne ?Usage
User~/.claude/settings.jsonNon — personnelPreferences globales (theme, model par defaut)
Project (partage).claude/settings.jsonOui — commit dans GitStandards d'équipe : permissions, hooks, MCP partages
Project (local).claude/settings.local.jsonNon — dans .gitignoreSurcharges locales par développeur (chemins absolus, secrets)
Ordre de precedence (du plus haut au plus bas) : settings.local.json > settings.json (projet) > ~/.claude/settings.json (user) > defauts. Les valeurs sont fusionnees champ par champ : une autorisation ajoutee en local n'efface pas celles du projet.
Anti-pattern : commiter .claude/settings.local.json. Ce fichier doit être dans .gitignore par convention — il contient des chemins spécifiques a la machine, des clés d'API, ou des autorisations dangereuses (Bash(rm:*)) que vous ne voulez pas imposer a l'équipe.

Le bloc permissions : allowlist et denylist

Le mécanisme de permissions de Claude Code fonctionne par allowlist explicite. Sans entree dans permissions.allow, chaque appel d'outil déclenche une demande de confirmation utilisateur — bloquant pour les pipelines CI.

// .claude/settings.json
{
  "permissions": {
    "allow": [
      "Bash(npm test:*)",
      "Bash(npm run lint:*)",
      "Bash(git status)",
      "Bash(git diff:*)",
      "Read(./src/**)",
      "Edit(./src/**)",
      "WebFetch(domain:docs.anthropic.com)"
    ],
    "deny": [
      "Bash(rm:*)",
      "Bash(curl:*)",
      "Read(./.env)",
      "Read(./secrets/**)"
    ],
    "defaultMode": "acceptEdits"
  }
}

Syntaxe des allowlists Bash

PatternSignificationExemple
Bash(commande)Commande exacte uniquementBash(git status) autorisé uniquement git status
Bash(commande:*)Commande avec n'importe quels argumentsBash(npm test:*) autorisé npm test --watch, npm test src/foo, etc.
Bash(prefixe:*)Prefixe de mot suivi de toutBash(git diff:*) autorisé git diff main mais pas git push
EXAM TIP : Bash(npm test) sans :* n'autorisé que la commande exacte. Un npm test --coverage declencherait quand même une demande. Pour CI, utilisez systematiquement :* après le verbe.

Les modes de permission (defaultMode)

ModeComportementQuand l'utiliser
"default"Demande pour chaque outil non explicitement autoriséDeveloppement local interactif
"acceptEdits"Auto-accepte les editions de fichiers, demande pour Bash et reseauRefactor sur un dossier connu
"plan"Mode planification : aucune modification, lecture seuleInvestigation, audit
"bypassPermissions"Aucune demande — DANGEREUXSandbox isole uniquement (jamais en CI sur prod)

Le bloc env et les variables d'environnement

// .claude/settings.json
{
  "env": {
    "API_BASE_URL": "https://staging.example.com",
    "NODE_ENV": "development"
  }
}

Les variables ici sont injectees dans toutes les commandes Bash executees par Claude Code. Pour les secrets, utilisez settings.local.json (non versionne) ou des références aux variables shell : "API_KEY": "${ANTHROPIC_API_KEY}".

Scenario d'examen : un développeur a configure des autorisations dans .claude/settings.local.json et constate qu'elles ne s'appliquent pas sur la machine de son collegue. Cause : settings.local.json est explicitement non versionne. Solution : deplacer les regles partagees dans .claude/settings.json.

2. Les slash commands et les skills (Task 3.2)

Le problème que cela resout

Si vous repetez regulierement les mêmes instructions ("fais une revue en suivant ce format", "généré des tests selon nos conventions"), il est plus efficace de les encapsuler dans une commande reutilisable.

Les slash commands (format legacy)

Les slash commands sont le format historique, stocke dans .claude/commands/. Elles restent fonctionnelles mais sont considerees comme legacy.

PorteeEmplacementPartage
Projet.claude/commands/Versionne via VCS, disponible après clonage
Personnel~/.claude/commands/Personnel, non partage

Le nom du fichier détermine le nom de la commande : review.md devient /review. Le placeholder $ARGUMENTS accepte des paramètres positionnels 0-based : $0 = 1er argument, $1 = 2e, etc.

Les skills (format actuel)

Les skills sont le format actuel et recommandé, plus puissant que les slash commands. Chaque skill vit dans un repertoire contenant un fichier SKILL.md avec un YAML frontmatter :

---
name: pr-description
description: Writes pull request descriptions. Use when creating
  a PR or summarizing changes for a review.
context: fork
allowed-tools: Read, Grep, Glob, Bash
argument-hint: "Branch name to compare against main"
---
Quand tu rediges une description de PR :
1. Executer `git diff main...HEAD` pour voir les changements
2. Ecrire une description structuree : What / Why / Changes

Les paramètres du frontmatter

ParametreObligatoireRole
nameOptionnel — défaut = nom du dossier du skillDisplay name (identifiant optionnel). Par défaut, le nom du dossier du skill sert de nom de commande (ex. /review pour .claude/skills/review/SKILL.md).
descriptionOuiDetermine quand Claude active le skill (matching semantique) — description + when_to_use tronqués à ~1536 caractères dans le listing — et influence comment il redige le prompt. C'est le champ le plus determinant pour le declenchement.
context: forkNonExecute le skill dans un contexte isole de subagent. La sortie verbeuse ne pollue pas la session principale.
allowed-toolsNonRestreint les outils disponibles (ex. : lecture seule = ni Edit ni Write).
argument-hintNonDemande un paramètre quand le skill est invoque sans argument.
Scenario d'examen : après avoir execute un skill d'analyse lourde, Claude devient moins reactif et perd le fil de la tache originale. Solution : ajouter context: fork dans le frontmatter du SKILL.md pour isoler l'exécution dans un subagent separe.

Skills personnels vs. skills projet

PorteeEmplacementPartage
Projet.claude/skills/Versionne via VCS, partage avec l'équipe
Personnel~/.claude/skills/Local, non partage
Priorite en cas de conflit de nom : un skill personnel l'emporte sur un skill projet de même nom. Par exemple, si vous avez un skill /review dans ~/.claude/skills/review/SKILL.md et que le projet definit aussi un /review dans .claude/skills/review/SKILL.md, votre skill personnel sera utilise.

Hierarchie complète : Enterprise (la plus haute) > Personnel > Projet > Plugins (la plus basse). Note : les skills issus de plugins sont namespacés (plugin:skill-name) et n'entrent donc jamais en conflit direct de nom avec des skills non namespacés.

Skills et subagents

Les subagents ne voient pas automatiquement les skills. Les agents integres (Explore subagent, Plan) ne peuvent pas y acceder. Seuls les agents personnalises (dans .claude/agents/) peuvent utiliser des skills, a condition qu'ils soient listes dans le frontmatter de l'agent.

Custom agents (.claude/agents/)

Les custom agents sont des subagents spécialisés definis au niveau projet ou user, distincts des agents integres (Explore, Plan, etc.). Ils s'invoquent via le Task tool ou le slash /agents.

// .claude/agents/security-reviewer.md
---
name: security-reviewer
description: Reviews code changes for security issues — SQL injection,
  XSS, auth bypass, secrets in code. Use when reviewing PRs that touch
  authentication, data input handling, or external integrations.
tools: Read, Grep, Glob, Bash(git diff:*)
skills: ["sql-pattern-check", "secrets-scan"]
model: claude-opus-4-7
---
You are a security-focused code reviewer. For each file in the diff:
1. Identify auth checks (or their absence)
2. Look for direct SQL string concatenation
3. Flag any hardcoded credentials or tokens
4. Check input validation on external boundaries

Output JSON: { issues: [{severity, file, line, message}] }
ChampRole
nameIdentifiant pour invocation (/agents security-reviewer ou via Task tool)
descriptionDetermine quand l'agent est invoque automatiquement (matching semantique)
toolsRestreint les outils — typique : lecture seule pour un reviewer
skillsListe les skills accessibles a cet agent (sinon il n'en voit aucun)
modelOverride du modèle : opus pour les analyses complexes, haiku pour les taches mecaniques
Custom agents vs Skills vs Subagents integres :
  • Skills = workflow encapsule (instructions + tools + skill name)
  • Custom agents = persona avec son propre system prompt, modèle, et perimetre d'outils — peut utiliser des skills
  • Subagents integres (Explore, Plan) = primitives fournies par Claude Code, non-personnalisables
Les custom agents brillent quand vous voulez une persona (security-reviewer, refactor-architect, doc-writer) reutilisable avec ses propres outils et skills.

Output styles

Les output styles personnalisent le ton et le format des réponses de Claude Code sans modifier le system prompt principal. Configures dans ~/.claude/output-styles/ ou .claude/output-styles/.

// .claude/output-styles/concise.md
---
name: concise
description: Terse responses, minimal explanations
---
Be terse. No filler phrases. No "I'll do X" announcements before doing X.
Bullet points over paragraphs. Code over prose. Skip the closing summary.

Activation : /output-style concise ou via le bloc "outputStyle" dans settings.json. Cas d'usage typique : pair-programming pro (concise) vs pedagogique (verbose).

Statusline (configuration de la barre d'état)

La statusline affiche en bas de l'interface des informations contextuelles (branche Git, modèle actif, tokens consommes, etc.). Elle se configure via une commande shell qui produit la ligne :

// .claude/settings.json
{
  "statusLine": {
    "type": "command",
    "command": "echo \"$(git branch --show-current) | $(date +%H:%M)\""
  }
}
Note pour l'examen : output styles et statusline sont des sujets marginaux (peu probables mais pas impossibles). L'important est de savoir qu'ils existent et de ne pas les confondre avec les skills, hooks, ou settings de permissions. Si une question parle de "personnaliser le ton des réponses sans toucher au system prompt", c'est output-styles.

Permissions par tool avec patterns

En complement des allowlists Bash vues en §1 (settings.json), les permissions s'appliquent aussi aux outils Read, Edit, Write, WebFetch avec des glob patterns :

{
  "permissions": {
    "allow": [
      "Read(./src/**)",          // Lire src/, mais pas les autres dossiers
      "Edit(./src/**)",
      "Write(./tests/**)",       // N'ecrire QUE des tests
      "WebFetch(domain:docs.anthropic.com)",
      "WebFetch(domain:github.com)"
    ],
    "deny": [
      "Read(./.env)",            // Ne JAMAIS lire .env meme si dans src/
      "Read(./secrets/**)",
      "Edit(./.github/workflows/**)"  // Pas de modif des workflows CI
    ]
  }
}
Precedence : deny > allow (defense en profondeur). Une regle deny sur un sous-chemin l'emporte sur une regle allow plus large. Cela permet d'ouvrir Read(./src/**) tout en bloquant explicitement Read(./src/secrets/**).

Plugins Claude Code

Les plugins sont le mécanisme officiel de distribution et d'installation de bundles de fonctionnalites (skills, slash commands, hooks, agents, MCP servers) en une seule unite installable. Ils s'installent depuis des marketplaces publiques (officielle Anthropic ou communautaires) ou depuis n'importe quel repo Git.

Commandes principales

CommandeEffet
/plugin marketplace add <source>Ajoute une marketplace : owner/repo GitHub, URL Git, ou chemin local vers marketplace.json
/plugin install <name>@<marketplace>Installe un plugin spécifique (ex : /plugin install commit-commands@anthropics-claude-code)
/plugin listListe les plugins installes et leur état
/reload-pluginsRecharge les plugins après install ou modification
/plugin marketRaccourci pour /plugin marketplace

Marketplaces officielles vs communautaires

SourceAdresseContenu
Officielle Anthropicanthropics/claude-plugins-officialPlugins curated, qualite garantie (commit-commands, code-review, etc.)
Communautairesclaude-plugins.dev, claudemarketplaces.comPlugins tiers, varie en qualite
Repo priveURL Git de votre choixPlugins maison pour l'équipe
# Workflow typique
claude
> /plugin marketplace add anthropics/claude-plugins-official
> /plugin install commit-commands@anthropics-claude-code
> /reload-plugins
> /plugin list

# Le plugin est dispo dans VS Code et terminal Claude Code
Distinction importante :
  • Un skill est une unite individuelle (un fichier SKILL.md avec frontmatter)
  • Un plugin est un bundle distribuable contenant plusieurs skills + commands + hooks + agents
La hiérarchie de priorite rappelee : Enterprise > Personnel > Projet > Plugins. Les plugins ont la priorite la plus basse — un skill projet local de même nom ecrase le plugin.
Scenario d'examen : votre équipe veut standardiser les conventions de revue de code sans que chaque développeur reconfigure son installation. Solution canonique : creer un plugin custom dans un repo Git partage, demander a l'équipe de faire /plugin marketplace add <votre-repo> + /plugin install team-conventions. Mise a jour : push au repo, chaque dev fait /reload-plugins.

3. Les regles conditionnelles par chemin (Task 3.3)

Le problème que cela resout

Les conventions de test s'appliquent a des fichiers disperses dans tout le codebase (co-localises avec le code source). Un CLAUDE.md par sous-repertoire serait fastidieux ; un CLAUDE.md unique chargerait des regles non pertinentes en permanence. Les fichiers .claude/rules/ avec glob patterns resolvent ce problème.

Exemple concret

# .claude/rules/testing.md
---
paths:
  - "**/*.test.tsx"
  - "**/*.test.ts"
  - "**/*.spec.ts"
---
Conventions de test :
- Utiliser des blocs describe/it.
- Utiliser des data factories, pas de donnees codees en dur.
- Ne pas mocker la base de donnees — utiliser une base de test.
Chargement conditionnel : la regle ne se charge que lorsque Claude Code edite un fichier correspondant au glob pattern. Cela economise du contexte et des tokens : les conventions non pertinentes ne sont jamais chargees.

Glob patterns vs. directory CLAUDE.md : les glob patterns sont preferables pour les conventions cross-directory (tests co-localises, fichiers de migration disperses). Un directory CLAUDE.md convient pour les regles strictement locales a un sous-dossier.

4. Planning mode vs. direct exécution (Task 3.4)

Le problème que cela resout

Corriger un bug cible n'exige pas la même approche que restructurer un monolithe. Utiliser le même mode pour les deux mene soit a de la lenteur inutile, soit a des erreurs couteuses.

Planning modeDirect exécution
ActionsExplore et planifie, ne modifie rienApplique les changements immediatement
OutilsRead, Grep, GlobEdit, Write, Bash
Cas d'usageChangements importants, choix architecturaux, codebase inconnu, migrations (45+ fichiers), multiples approches possiblesCorrections ciblees sur un seul fichier, ajout d'une validation simple

La combinaison la plus courante : planning mode pour l'investigation, approbation du plan, puis direct exécution pour l'implementation.

Plan = largeur (explorer plus de fichiers). Thinking = profondeur (raisonnement approfondi sur un problème precis). Les deux se combinent pour les taches complexes.

Le Explore subagent isole la sortie verbeuse de la phase de découverte et retourne un résumé concis, préservant le contexte principal pour les phases suivantes.

5. Le raffinement iteratif (Task 3.5)

Le problème que cela resout

Meme avec des instructions detaillees en prose, Claude peut interpréter differemment vos attentes a chaque iteration. Il faut des méthodes plus precises pour converger.

Des exemples concrets d'entree/sortie (I/O examples)

La méthode la plus efficace. Si Claude produit des resultats différents de vos attentes malgre les descriptions textuelles, fournissez 2 a 3 paires input/output concretes montrant la transformation voulue.

L'iteration guidee par les tests (TDD iteration)

  1. Ecrire les tests d'abord (cas attendus, cas limites, exigences de performance).
  2. Demander a Claude d'implementer le code.
  3. Iterer sur les échecs jusqu'a ce que tous les tests passent.

Le interview pattern

Avant d'implementer, Claude pose des questions de clarification pour faire émerger des considerations non anticipees :

"Avant d'implementer le cache pour l'API, quelques questions :
1. Preferez-vous une invalidation par TTL ou par evenement ?
2. Les donnees perimees sont-elles acceptables si le cache tombe ?
3. Le cache doit-il etre par utilisateur ou global ?
4. Quel volume de donnees est attendu ?"
Quand utiliser le interview pattern : domaine peu familier (fintech, sante), implications non evidentes (stratégies de cache, modes de defaillance), ou multiples approches valides dont le meilleur choix depend du contexte.

Batch vs. sequential feedback

Deux stratégies pour fournir du feedback a Claude :

StrategieQuand l'utiliserExemple
Batch feedbackQuand les problèmes sont interdépendants ou interactifs : tout dans un seul message détaillé pour que le modèle voie les interactions et les réconcilie"Le module manque de gestion d'erreurs, ce qui affecte aussi la validation d'input : proposer une architecture unifiee"
Sequential feedbackQuand les problèmes sont indépendants : un par un, sans que chaque correction dépende de la précédente"1. Renomme la variable X. 2. Après validation, on passera au type de retour."
La clé : l'interdépendance. Si les problèmes s'influencent mutuellement (ex. erreur de gestion d'erreur + validation d'input), utilisez batch pour que le modèle voit les interactions et reconcilie. Si chaque problème est indépendant, utilisez sequential pour valider étape par étape. Le batch est plus efficace en tokens, le sequential offre plus de contrôle et de validation.

6. L'intégration dans les pipelines CI/CD (Task 3.6)

Le problème que cela resout

Claude Code est interactif par defaut. Sans configuration adaptee, un job CI se bloquera indefiniment en attente d'une saisie utilisateur.

Le flag -p (--print)

claude -p "Analyse cette pull request pour les problemes de securite"

Le flag -p (alias --print) active le mode non interactif : Claude traite le prompt, imprime le resultat sur la sortie standard, puis se termine. C'est la seule manière documentee d'executer Claude Code en CI/CD.

Les sorties structurées

claude -p "Revue de cette PR" --output-format json --json-schema '{...}'

Le resultat est un JSON conforme au schéma fourni via --json-schema, que vous pouvez parser pour poster automatiquement des commentaires inline via l'API GitHub.

L'isolation de session pour la revue

La même session Claude qui a généré le code est moins efficace pour le reviewer. Elle conserve son contexte de raisonnement et questionne moins ses propres décisions — un biais analogue a celui d'un développeur relisant son propre code. Utilisez une instance independante (session separee) pour la revue.

Bonnes pratiques CI/CD

  • Eviter les commentaires dupliques : quand vous relancez une revue après de nouveaux commits, incluez les resultats de la revue precedente dans le contexte et demandez a Claude de ne signaler que les problèmes nouveaux ou non resolus.
  • Ameliorer la generation de tests : documentez les standards de test et les fixtures dans CLAUDE.md, et incluez les fichiers de test existants en contexte pour garder un style cohérent.

Le mode headless (terminologie Anthropic)

Le mode non interactif active par -p / --print est designe officiellement comme headless mode dans la documentation Anthropic. Caracteristiques :

  • Pas de prompt interactif, pas d'attente de saisie
  • Sortie sur stdout, code de retour exploitable ($?)
  • Combinable avec --output-format json pour parsing programmatique
  • Combinable avec --max-turns N pour limiter les iterations agentiques
  • Nécessite des permissions explicites (sinon les demandes bloquent silencieusement)

Workflow GitHub Actions concret

name: Claude Code Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  claude-review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # historique complet pour git diff main...HEAD

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Run Claude review (headless)
        id: review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          claude -p "Review the diff git diff origin/main...HEAD \
            for security issues, bugs, and style violations. \
            Output JSON matching the schema." \
            --output-format json \
            --max-turns 10 \
            --json-schema '{
              "type":"object",
              "properties":{
                "issues":{"type":"array","items":{
                  "type":"object",
                  "properties":{
                    "severity":{"enum":["critical","major","minor"]},
                    "file":{"type":"string"},
                    "line":{"type":"integer"},
                    "message":{"type":"string"}
                  },
                  "required":["severity","file","message"]
                }}
              }
            }' > review.json

      - name: Post inline comments
        uses: actions/github-script@v7
        with:
          script: |
            const review = require('./review.json');
            for (const issue of review.issues) {
              await github.rest.pulls.createReviewComment({
                ...context.repo,
                pull_number: context.issue.number,
                body: `**[${issue.severity}]** ${issue.message}`,
                commit_id: context.payload.pull_request.head.sha,
                path: issue.file,
                line: issue.line
              });
            }
Points clés du workflow :
  • fetch-depth: 0 — sans ca, git diff origin/main...HEAD echoue (historique tronque)
  • ANTHROPIC_API_KEY dans les secrets du repo, pas dans le YAML
  • --max-turns évite une boucle agentique infinie qui consommerait du budget
  • Les permissions GitHub Actions doivent inclure pull-requests: write pour poster des commentaires
  • L'instance de revue est distincte de toute instance de generation : pas de biais self-review
Anti-pattern : executer Claude sans --max-turns en CI. Un agent peut entrer en boucle sur un edge case et consommer 50+ iterations, faisant exploser le temps et le cout du job. --max-turns 10 ou --max-turns 15 est un garde-fou raisonnable pour la plupart des taches de revue.

Les hooks Claude Code (au niveau config)

Anatomie d'un hook

// .claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npm run lint -- --fix",
            "timeout": 30000
          }
        ]
      }
    ],
    "UserPromptSubmit": [
      {
        "matcher": "*",
        "hooks": [
          {
            "type": "command",
            "command": "echo \"Branche actuelle : $(git branch --show-current)\"",
            "timeout": 5000
          }
        ]
      }
    ],
    "Stop": [
      {
        "matcher": "*",
        "hooks": [
          {
            "type": "command",
            "command": "./scripts/notify-done.sh"
          }
        ]
      }
    ]
  }
}
ChampRole
matcherFiltre regex sur le nom de l'outil (PreToolUse / PostToolUse) ou "*" pour tous
typeToujours "command" dans la config (les hooks programmatiques sont via le SDK)
commandCommande shell executee. Les hooks reçoivent les données en JSON sur stdin avec tool_name et tool_input. Variable d'env disponible : CLAUDE_PROJECT_DIR
timeoutMillisecondes avant kill (defaut : 60000). Important pour éviter de bloquer la session
Code de retour du hook :
  • 0 — succes, Claude continue normalement
  • 2 — erreur "blocking" : stderr est renvoye a Claude qui peut reagir (auto-correction, ajustement)
  • autre code non-zero — erreur "non-blocking" : log mais Claude continue
Pour PreToolUse, un code 2 annule l'appel d'outil et permet de forcer Claude a reformuler.
Scenario d'examen : votre équipe veut que tous les fichiers TypeScript soient automatiquement reformates après edition par Claude. Solution : un hook PostToolUse avec matcher: "Edit|Write" qui execute prettier --write "$CLAUDE_FILE_PATHS". Pas besoin d'instructions dans CLAUDE.md ni de skill — le hook est deterministe (toujours execute), contrairement aux instructions textuelles que Claude peut oublier.

Hooks vs. instructions vs. skills : quand utiliser quoi

BesoinSolutionPourquoi
"Toujours formater après edition"Hook PostToolUseDeterministe, pas dependant du raisonnement de Claude
"Suivre nos conventions de style"CLAUDE.mdGuidance souple appliquee par le modèle
"Generer un changelog selon notre format"SkillWorkflow structure, invocation a la demande
"Bloquer rm -rf sur des chemins critiques"Permissions deny + hook PreToolUseDefense en profondeur

Configuration des serveurs MCP via la CLI

Les serveurs MCP peuvent être declares de deux manières : dans un fichier .mcp.json a la racine du projet (versionne, partage équipe), ou via la CLI claude mcp add qui edite ~/.claude.json (user-level).

La commande claude mcp add

# Ajout d'un serveur stdio (transport local par sous-processus)
claude mcp add github -- npx -y @modelcontextprotocol/server-github

# Ajout avec variables d'env (token API, URL de base)
claude mcp add postgres \
  -e DATABASE_URL=postgres://... \
  -- npx -y @modelcontextprotocol/server-postgres

# Ajout d'un serveur HTTP/SSE distant
claude mcp add my-api --transport http https://api.example.com/mcp

# Lister les serveurs enregistres
claude mcp list

# Supprimer
claude mcp remove github

Structure du fichier .mcp.json (projet)

// .mcp.json a la racine du projet — versionne avec Git
{
  "mcpServers": {
    "github": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    "internal-docs": {
      "type": "http",
      "url": "https://docs.internal/mcp",
      "headers": {
        "Authorization": "Bearer ${DOCS_TOKEN}"
      }
    }
  }
}
EXAM TIP : les secrets ne doivent jamais être ecrits en clair dans .mcp.json (versionne). Utilisez la syntaxe ${VAR} pour referencer des variables d'environnement, ou definissez le serveur dans ~/.claude.json (user, non versionne) via claude mcp add -e.
Hierarchie de resolution MCP : au demarrage de Claude Code, les serveurs sont charges depuis (priorite croissante) : config user (~/.claude.json) → .mcp.json du projet → arguments CLI --mcp-config. Un même nom dans plusieurs sources entraine une fusion, l'entree de plus haute priorite l'emporte.

8. Synthese — les points clés

CLAUDE.md

  • Trois niveaux : user (personnel), project (équipe), directory (local).
  • Erreur classique : mettre les instructions au user-level au lieu du project-level.
  • Syntaxe @path pour les imports modulaires (profondeur max : 5 niveaux).
  • .claude/rules/ avec YAML frontmatter paths et glob patterns pour le chargement conditionnel.
  • Glob patterns preferables pour les conventions cross-directory ; directory CLAUDE.md pour les regles strictement locales.
  • /memory pour persister des notes entre sessions ; /compact pour compresser le contexte.

Skills et slash commands

  • Slash commands dans .claude/commands/ : format legacy, partage via VCS.
  • Skills dans .claude/skills/ : format actuel, SKILL.md avec YAML frontmatter.
  • Skills personnels dans ~/.claude/skills/ : doivent utiliser des noms différents des skills projet (le skill personnel prend la priorité pour un même nom).
  • context: fork pour l'isolation dans un subagent, allowed-tools pour restreindre les outils.
  • Priorite : Enterprise > Personnel > Projet > Plugins.

Modes de travail

  • Planning mode pour les taches complexes, codebase inconnu, migrations 45+ fichiers.
  • Direct exécution pour les corrections ciblees sur un seul fichier.
  • Combinaison : planning mode puis direct exécution après approbation.
  • Le Explore subagent isole la sortie verbeuse de la decouverte.
  • Le interview pattern fait émerger les considerations non anticipees avant implementation.
  • Batch feedback (un seul message) pour les problèmes interdépendants ; sequential feedback pour les problèmes indépendants.

CI/CD

  • Le flag -p (--print) active le headless mode, obligatoire en CI.
  • --output-format json + --json-schema pour des sorties structurées.
  • --max-turns N est un garde-fou contre les boucles agentiques infinies.
  • Instance independante pour la revue (pas la même session qui a généré le code).
  • Inclure les resultats de revue precedents pour éviter les commentaires dupliques.
  • fetch-depth: 0 obligatoire dans GitHub Actions pour git diff origin/main...HEAD.
  • ANTHROPIC_API_KEY dans les secrets, jamais en clair dans le YAML.

Configuration JSON et permissions

  • Trois niveaux : ~/.claude/settings.json (user) / .claude/settings.json (projet, versionne) / .claude/settings.local.json (local, dans .gitignore).
  • Precedence : settings.local.json > settings.json projet > user > defauts.
  • permissions.allow : allowlist explicite nécessaire en CI pour éviter les blocages.
  • Syntaxe Bash : Bash(npm test) = exact ; Bash(npm test:*) = avec arguments libres.
  • defaultMode : "default" / "acceptEdits" / "plan" / "bypassPermissions" (dangereux).
  • permissions.deny a precedence sur allow (defense en profondeur).

Hooks Claude Code (config-level)

  • Definis dans le bloc "hooks" de settings.json — distincts des hooks Agent SDK (D1).
  • Evenements : UserPromptSubmit, PreToolUse, PostToolUse, Stop, SessionStart, Notification, PreCompact.
  • Code de retour : 0 = OK, 2 = blocking (Claude reagit), autre = non-blocking.
  • Variables : $CLAUDE_FILE_PATHS, $CLAUDE_TOOL_NAME, $CLAUDE_TOOL_INPUT.
  • Hook = deterministe (toujours execute) ; CLAUDE.md = instruction souple ; skill = workflow invocable.

MCP dans Claude Code

  • .mcp.json au projet (versionne) ou ~/.claude.json (user, via claude mcp add).
  • Transports : stdio (sous-processus local) ou http (distant).
  • Secrets via ${VAR} ou via flag -e de claude mcp add.

9. Auto-evaluation

Q1 : Trois développeurs anciens beneficient de "always include comprehensive error handling", mais un nouveau qui vient de rejoindre ne l'a pas. Tous travaillent sur le même repo. Cause probable ? A) L'instruction est dans ~/.claude/CLAUDE.md (user-level) au lieu de .claude/CLAUDE.md (project-level). B) Le ~/.claude/CLAUDE.md du nouveau contient des instructions conflictuelles. C) Claude Code apprend les preferences par utilisateur au fil du temps. D) Le nouveau doit relancer Claude Code.

Reponse : A. Le fichier ~/.claude/CLAUDE.md est au user-level : il est personnel et non partage via VCS. Les trois anciens développeurs l'ont chacun dans leur propre configuration, mais le nouveau n'en dispose pas. La solution est de deplacer cette instruction dans .claude/CLAUDE.md (project-level), qui est versionne et partage avec toute l'équipe.

Q2 : Votre codebase a des conventions différentes pour React, API, et database. Les tests sont co-localises avec le code. Quelle approche ? A) Des fichiers .claude/rules/ avec YAML frontmatter et glob patterns. B) Tout mettre dans le root CLAUDE.md. C) Des skills dans .claude/skills/. D) Un CLAUDE.md dans chaque repertoire.

Reponse : A. Les fichiers .claude/rules/ avec YAML frontmatter paths et glob patterns permettent un chargement conditionnel : chaque convention n'est chargee que quand Claude edite un fichier correspondant. C'est l'approche preferee pour les conventions cross-directory (tests co-localises disperses dans le codebase). B gaspillerait du contexte en chargeant tout systematiquement. C est pour les taches, pas les conventions. D serait fastidieux a maintenir avec des tests disperses.

Q3 : Un skill /analyze-codebase fait du deep analysis. Apres l'avoir lance, Claude devient moins responsif et perd le contexte de la tache originale. Comment fixer ? A) Ajouter context: fork dans le frontmatter du skill. B) Utiliser /compact après le skill. C) Reduire les outils du skill avec allowed-tools. D) Decouper le skill en plus petits skills.

Reponse : A. Le paramètre context: fork dans le frontmatter du SKILL.md execute le skill dans un subagent isole. La sortie verbeuse ne pollue pas la session principale, et Claude conserve le contexte de la tache originale. B compresserait le contexte mais avec perte d'information. C limiterait les capacites du skill sans resoudre le problème de pollution du contexte. D ajouterait de la complexite sans isolation.

Q4 : Votre pipeline CI execute claude 'Analyze this PR for security issues' mais le job reste bloque indefiniment. Quel est le problème ? A) Ajouter --batch. B) Utiliser le flag -p. C) Rediriger stdin depuis /dev/null. D) Setter CLAUDE_HEADLESS=true.

Reponse : B. Le flag -p (alias --print) est la manière documentee d'executer Claude Code en mode non interactif (headless mode) pour les pipelines CI/CD. Sans ce flag, Claude Code attend une saisie utilisateur interactive, ce qui bloque le job. La commande correcte est claude -p 'Analyze this PR for security issues'.

Q5 : Une developpeuse a ajoute des autorisations dans .claude/settings.local.json. Son collegue clone le repo mais les autorisations ne s'appliquent pas. Cause ? A) Il faut redemarrer Claude Code pour recharger la config. B) settings.local.json est dans .gitignore, il n'est pas versionne ni partage. C) Les permissions sont stockees par utilisateur dans une base locale. D) Le collegue doit lancer claude --sync-permissions.

Reponse : B. Par convention (et habituellement par .gitignore), .claude/settings.local.json n'est pas versionne. Il sert aux surcharges locales par développeur (chemins absolus, secrets, autorisations dangereuses). Pour partager des autorisations avec l'équipe, elles doivent être dans .claude/settings.json (versionne). A est faux (la config est rechargee), C et D ne correspondent pas a des fonctionnalites Claude Code.

Q6 : Vous voulez autoriser npm test avec n'importe quels arguments en CI, mais bloquer toute autre commande npm. Quelle entree dans permissions.allow ? A) "Bash(npm test)". B) "Bash(npm test:*)". C) "Bash(npm:*)". D) "Bash(npm test --*)".

Reponse : B. "Bash(npm test:*)" autorisé npm test suivi de n'importe quels arguments (npm test --watch, npm test src/foo). A est trop restrictif : seul npm test exact passerait. C autoriserait toute commande npm (npm publish, npm install) — trop large. D n'est pas la syntaxe valide des allowlists Claude Code (:* est le suffixe officiel).

Q7 : Votre équipe veut que tous les fichiers TypeScript soient automatiquement formates par Prettier après edition par Claude. Quelle approche est la plus fiable ? A) Ajouter "Always run prettier after editing" dans CLAUDE.md. B) Creer un skill /format que les développeurs invoquent. C) Configurer un hook PostToolUse avec matcher: "Edit|Write" qui execute prettier --write. D) Demander a Claude d'inclure prettier dans chaque commit.

Reponse : C. Un hook PostToolUse est deterministe : il s'execute après chaque Edit ou Write, sans dependre du raisonnement du modèle. A repose sur la conformite du modèle aux instructions textuelles, qui peut être oubliee dans des contextes longs. B est manuel et fragile. D melange les responsabilites (formatage en commit). Le hook est l'option choisie pour les actions automatiques garanties — c'est precisement leur raison d'être.

Q8 : Votre workflow GitHub Actions execute claude -p mais Claude entre parfois dans une boucle qui consomme 50+ iterations agentiques avant de s'arreter. Comment limiter cela proprement ? A) Ajouter --max-turns 10 a la commande. B) Mettre un timeout-minutes: 5 sur le job GitHub Actions. C) Reduire le contexte initial. D) Utiliser --output-format json.

Reponse : A. --max-turns N est le garde-fou natif de Claude Code pour limiter le nombre d'iterations agentiques (cycles tool_use → tool_result). C'est l'option propre : Claude termine avec un resultat partiel exploitable. B (timeout du job) est un filet de securite mais coupe brutalement, sans output structure. C peut aider mais ne resout pas la cause. D contrôle le format de sortie, pas le nombre d'iterations. Combinez idealement A + B pour la defense en profondeur.

Q9 : Vous configurez un serveur MCP github qui necessite un GITHUB_TOKEN. Vous voulez le partager avec l'équipe sans exposer le token. Approche correcte ? A) Mettre GITHUB_TOKEN: "ghp_xxx" dans .mcp.json. B) Mettre GITHUB_TOKEN: "${GITHUB_TOKEN}" dans .mcp.json et chacun definit la variable d'env localement. C) Stocker le token dans .claude/settings.json. D) Encoder le token en base64 dans .mcp.json.

Reponse : B. La syntaxe ${VAR} dans .mcp.json est resolue au runtime depuis l'environnement. Le fichier reste versionne sans secret expose ; chaque développeur fournit son propre token via son shell (export GITHUB_TOKEN=...) ou via un gestionnaire de secrets local. A et D exposent le secret dans Git. C melange les responsabilites et expose toujours le secret si settings.json est versionne. Alternative legitime : utiliser claude mcp add github -e GITHUB_TOKEN=... qui écrit dans ~/.claude.json (user-level, non versionne).
