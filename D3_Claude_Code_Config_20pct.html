1. La hiérarchie CLAUDE.md et l'organisation modulaire (Task 3.1)

Le problème que cela résout

Dans une équipe, chaque développeur a ses préférences, mais le projet impose aussi des standards communs. Il faut un mécanisme pour séparer ces niveaux d'instruction et garantir que chaque membre reçoit les bonnes directives.

Les trois niveaux

NiveauEmplacementPartage ?Usage
User~/.claude/CLAUDE.mdNon (personnel, hors VCS)Préférences personnelles, style de travail
Project.claude/CLAUDE.md ou racineOui (versionné, partagé via Git)Standards de code, conventions de test, architecture
DirectoryCLAUDE.md dans un sous-dossierOui (versionné)Conventions propres à cette partie du codebase
Erreur classique : trois développeurs expérimentés bénéficient de l'instruction "always include comprehensive error handling", mais un nouveau ne la reçoit pas. Cause : les instructions étaient dans ~/.claude/CLAUDE.md (user-level) au lieu de .claude/CLAUDE.md (project-level). Le nouveau n'a pas les fichiers personnels des anciens. Solution : déplacer vers le project-level pour que tout le monde en bénéficie.

La syntaxe @path pour les imports

Plutôt que de concentrer toutes les instructions dans un seul fichier, vous pouvez référencer des fichiers externes :

# Dans CLAUDE.md
Les standards de code sont décrits dans @./standards/coding-style.md
Les exigences de test sont dans @./standards/testing-requirements.md
La vue d'ensemble du projet est dans @README.md

Le @ se place immédiatement avant le path (sans espace). Les paths relatifs sont résolus par rapport au fichier contenant l'import. La profondeur maximale d'imbrication est de 4 niveaux (« four hops »).

Le répertoire .claude/rules/

Une alternative au CLAUDE.md monolithique : des fichiers thématiques dont le chargement dépend des fichiers en cours d'édition.

.claude/rules/
  testing.md          — conventions de test
  api-conventions.md  — conventions API
  deployment.md       — règles de déploiement
  react-patterns.md   — patterns React

Chaque fichier inclut un YAML frontmatter avec le champ paths qui spécifie quand le charger :

---
paths: ["src/api/**/*"]
---
Pour les fichiers API, utiliser async/await avec une gestion d'erreurs explicite.
Chaque endpoint doit retourner un wrapper de réponse standard.
Quand utiliser .claude/rules/ vs. un directory CLAUDE.md : les fichiers .claude/rules/ avec glob patterns sont préférables quand les conventions s'appliquent à des fichiers dispersés dans le codebase (tests co-localisés, migrations cross-directory). Un CLAUDE.md dans un sous-dossier convient quand les règles sont spécifiques à un répertoire bien défini.

Les commandes /memory et /compact

(Source : guide officiel, sections 5.7 et 5.8.)

  • /memory affiche quels fichiers mémoire sont actuellement chargés et vous permet de les éditer pour y ajouter des notes et préférences. Les fichiers chargés (ex. ~/.claude/projects/<id>/memory/*.md) persistent entre les sessions et sont appliqués automatiquement au démarrage. C'est aussi la commande de diagnostic quand vous soupçonnez qu'une instruction n'a pas été chargée correctement — vérifiez que le fichier de mémoire attendu apparaît dans la liste des fichiers chargés.
  • /compact compresse le contexte en résumant l'historique. Utile dans les longues sessions d'investigation, mais avec un risque : les valeurs numériques exactes, les dates et les détails précis peuvent être perdus lors de la compression.

2. Les slash commands et les skills (Task 3.2)

Le problème que cela résout

Si vous répétez régulièrement les mêmes instructions ("fais une revue en suivant ce format", "génère des tests selon nos conventions"), il est plus efficace de les encapsuler dans une commande réutilisable.

Les slash commands

Les slash commands sont stockées dans .claude/commands/ (partagées via VCS) et restent un mécanisme pleinement valide, non déprécié. Skills et slash commands coexistent ; le skill est simplement mieux outillé pour les workflows complexes (isolation de contexte, matching sémantique).

PorteeEmplacementPartage
Projet.claude/commands/Versionne via VCS, disponible après clonage
Personnel~/.claude/commands/Personnel, non partagé

Le nom du fichier détermine le nom de la commande : review.md devient /review. Le placeholder $ARGUMENTS accepte des paramètres positionnels 0-based : $0 = 1er argument, $1 = 2e, etc.

Les skills (format actuel)

Les skills sont le format actuel et recommandé, plus puissant que les slash commands. Chaque skill vit dans un repertoire contenant un fichier SKILL.md avec un YAML frontmatter :

---
name: pr-description
description: Writes pull request descriptions. Use when creating
  a PR or summarizing changes for a review.
context: fork
allowed-tools: Read, Grep, Glob, Bash
argument-hint: "Branch name to compare against main"
---
Quand tu rédiges une description de PR :
1. Exécuter `git diff main...HEAD` pour voir les changements
2. Ecrire une description structurée : What / Why / Changes

Les paramètres du frontmatter

ParamètreObligatoireRôle
nameOptionnel — défaut = nom du dossier du skillDisplay name (identifiant optionnel). Par défaut, le nom du dossier du skill sert de nom de commande (ex. /review pour .claude/skills/review/SKILL.md).
descriptionRecommandée — si omise, le premier paragraphe du corps sert de descriptionDétermine quand Claude active le skill (matching sémantique) — description + when_to_use tronqués à ~1536 caractères dans le listing — et influence comment il rédige le prompt. C'est le champ le plus déterminant pour le déclenchement.
context: forkNonExécute le skill dans un contexte isolé de subagent. La sortie verbeuse ne pollue pas la session principale.
allowed-toolsNonPré-approbation de permissions : liste les outils utilisables sans demande de confirmation quand ce skill est actif (les autres outils restent disponibles, mais soumis au flux de permission normal). Pour retirer un outil du pool disponible, utiliser disallowed-tools. Pour l'examen, le guide parle de « restrict tool access » ; la doc actuelle distingue pré-approbation (allowed-tools) et retrait (disallowed-tools).
disallowed-toolsNonRetire des outils du pool disponible pour ce skill (ex. : bloquer AskUserQuestion dans un skill destiné à tourner en arrière-plan sans interaction).
argument-hintNonIndice affiché à l'autocomplétion pour suggérer le paramètre attendu quand le skill est invoqué en slash command.
variantsNonPermet de définir plusieurs variantes d'un même skill avec des paramétrages ou des comportements légèrement différents (ex. : /review --strict vs /review --relaxed). Chaque variante hérite des paramètres du skill de base sauf surcharge explicite.
Scénario d'examen : après avoir exécuté un skill d'analyse lourde, Claude devient moins réactif et perd le fil de la tâche originale. Solution : ajouter context: fork dans le frontmatter du SKILL.md pour isoler l'exécution dans un subagent séparé.

Skills personnels vs. skills projet

PorteeEmplacementPartage
Projet.claude/skills/Versionné via VCS, partagé avec l'équipe
Personnel~/.claude/skills/Local, non partagé
Priorité en cas de conflit de nom : un skill personnel l'emporte sur un skill projet de même nom. Par exemple, si vous avez un skill /review dans ~/.claude/skills/review/SKILL.md et que le projet définit aussi un /review dans .claude/skills/review/SKILL.md, votre skill personnel sera utilisé.

Hiérarchie complète : Enterprise (la plus haute) > Personnel > Projet > Plugins (la plus basse). Note : les skills issus de plugins sont namespacés (plugin:skill-name) et n'entrent donc jamais en conflit direct de nom avec des skills non namespacés.

Skills et subagents

Les subagents ne voient pas automatiquement les skills. Les agents intégrés (Explore subagent, Plan) ne peuvent pas y accéder ; un subagent disposant du Skill tool peut en revanche invoquer les skills (projet, user, plugin) à la demande.

3. Les regles conditionnelles par chemin (Task 3.3)

Le problème que cela résout

Les conventions de test s'appliquent à des fichiers dispersés dans tout le codebase (co-localisés avec le code source). Un CLAUDE.md par sous-répertoire serait fastidieux ; un CLAUDE.md unique chargerait des règles non pertinentes en permanence. Les fichiers .claude/rules/ avec glob patterns résolvent ce problème.

Exemple concret

# .claude/rules/testing.md
---
paths:
  - "**/*.test.tsx"
  - "**/*.test.ts"
  - "**/*.spec.ts"
---
Conventions de test :
- Utiliser des blocs describe/it.
- Utiliser des data factories, pas de données codées en dur.
- Ne pas mocker la base de données — utiliser une base de test.
Chargement conditionnel : la règle ne se charge que lorsque Claude Code édite un fichier correspondant au glob pattern. Cela économise du contexte et des tokens : les conventions non pertinentes ne sont jamais chargées.

Glob patterns vs. directory CLAUDE.md : les glob patterns sont préférables pour les conventions cross-directory (tests co-localisés, fichiers de migration dispersés). Un directory CLAUDE.md convient pour les règles strictement locales à un sous-dossier.

4. Planning mode vs. direct exécution (Task 3.4)

Le problème que cela résout

Corriger un bug ciblé n'exige pas la même approche que restructurer un monolithe. Utiliser le même mode pour les deux mène soit à de la lenteur inutile, soit à des erreurs coûteuses.

Planning modeDirect exécution
ActionsExplore et planifie, ne modifie rienApplique les changements immédiatement
OutilsRead, Grep, GlobEdit, Write, Bash
Cas d'usageChangements importants, choix architecturaux, codebase inconnu, migrations (45+ fichiers), multiples approches possiblesCorrections ciblées sur un seul fichier, ajout d'une validation simple

La combinaison la plus courante : planning mode pour l'investigation, approbation du plan, puis direct exécution pour l'implémentation.

Plan = largeur (explorer plus de fichiers). Thinking = profondeur (raisonnement approfondi sur un problème précis). Les deux se combinent pour les tâches complexes.

Le Explore subagent isole la sortie verbeuse de la phase de découverte et retourne un résumé concis, préservant le contexte principal pour les phases suivantes.

5. Le raffinement iteratif (Task 3.5)

Le problème que cela résout

Même avec des instructions détaillées en prose, Claude peut interpréter différemment vos attentes à chaque itération. Il faut des méthodes plus précises pour converger.

Des exemples concrets d'entree/sortie (I/O examples)

La méthode la plus efficace. Si Claude produit des résultats différents de vos attentes malgré les descriptions textuelles, fournissez 2 à 3 paires input/output concrètes montrant la transformation voulue.

L'iteration guidee par les tests (TDD iteration)

  1. Ecrire les tests d'abord (cas attendus, cas limites, exigences de performance).
  2. Demander à Claude d'implémenter le code.
  3. Itérer sur les échecs jusqu'à ce que tous les tests passent.

Le interview pattern

Avant d'implémenter, Claude pose des questions de clarification pour faire émerger des considérations non anticipées :

"Avant d'implémenter le cache pour l'API, quelques questions :
1. Préférez-vous une invalidation par TTL ou par événement ?
2. Les données périmées sont-elles acceptables si le cache tombe ?
3. Le cache doit-il être par utilisateur ou global ?
4. Quel volume de données est attendu ?"
Quand utiliser le interview pattern : domaine peu familier (fintech, santé), implications non évidentes (stratégies de cache, modes de défaillance), ou multiples approches valides dont le meilleur choix dépend du contexte.

Batch vs. sequential feedback

Deux stratégies pour fournir du feedback à Claude :

StratégieQuand l'utiliserExemple
Batch feedbackQuand les problèmes sont interdépendants ou interactifs : tout dans un seul message détaillé pour que le modèle voie les interactions et les réconcilie"Le module manque de gestion d'erreurs, ce qui affecte aussi la validation d'input : proposer une architecture unifiée"
Sequential feedbackQuand les problèmes sont indépendants : un par un, sans que chaque correction dépende de la précédente"1. Renomme la variable X. 2. Après validation, on passera au type de retour."
La clé : l'interdépendance. Si les problèmes s'influencent mutuellement (ex. erreur de gestion d'erreur + validation d'input), utilisez batch pour que le modèle voie les interactions et réconcilie. Si chaque problème est indépendant, utilisez sequential pour valider étape par étape. Le batch est plus efficace en tokens, le sequential offre plus de contrôle et de validation.

6. L'intégration dans les pipelines CI/CD (Task 3.6)

Le problème que cela résout

Claude Code est interactif par défaut. Sans configuration adaptée, un job CI se bloquera indéfiniment en attente d'une saisie utilisateur.

Le flag -p (--print)

claude -p "Analyse cette pull request pour les problèmes de sécurité"

Le flag -p (alias --print) active le mode non interactif : Claude traite le prompt, imprime le résultat sur la sortie standard, puis se termine. C'est la seule manière documentée d'exécuter Claude Code en CI/CD.

Les sorties structurées

claude -p "Revue de cette PR" --output-format json --json-schema '{...}'

Le résultat reste l'enveloppe JSON habituelle de --output-format json ; le contenu conforme au schéma fourni via --json-schema se trouve dans le champ structured_output, que vous pouvez parser pour poster automatiquement des commentaires inline via l'API GitHub.

L'isolation de session pour la revue

La même session Claude qui a généré le code est moins efficace pour le reviewer. Elle conserve son contexte de raisonnement et questionne moins ses propres décisions — un biais analogue à celui d'un développeur relisant son propre code. Utilisez une instance indépendante (session séparée) pour la revue.

Bonnes pratiques CI/CD

  • Eviter les commentaires dupliqués : quand vous relancez une revue après de nouveaux commits, incluez les résultats de la revue précédente dans le contexte et demandez à Claude de ne signaler que les problèmes nouveaux ou non résolus.
  • Améliorer la génération de tests : documentez les standards de test et les fixtures dans CLAUDE.md, et incluez les fichiers de test existants en contexte pour garder un style cohérent.

Le mode headless (terminologie Anthropic)

Le mode non interactif activé par -p / --print est désigné officiellement comme headless mode dans la documentation Anthropic. Caractéristiques :

  • Pas de prompt interactif, pas d'attente de saisie
  • Sortie sur stdout, code de retour exploitable ($?)
  • Combinable avec --output-format json pour parsing programmatique
  • Combinable avec --max-turns N pour limiter les itérations agentiques
  • Nécessite des permissions explicites (sinon les demandes bloquent silencieusement)

Workflow GitHub Actions concret

name: Claude Code Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  claude-review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # historique complet pour git diff main...HEAD

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Run Claude review (headless)
        id: review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          claude -p "Review the diff git diff origin/main...HEAD \
            for security issues, bugs, and style violations. \
            Output JSON matching the schema." \
            --output-format json \
            --max-turns 10 \
            --json-schema '{
              "type":"object",
              "properties":{
                "issues":{"type":"array","items":{
                  "type":"object",
                  "properties":{
                    "severity":{"enum":["critical","major","minor"]},
                    "file":{"type":"string"},
                    "line":{"type":"integer"},
                    "message":{"type":"string"}
                  },
                  "required":["severity","file","message"]
                }}
              }
            }' > review.json

      - name: Post inline comments
        uses: actions/github-script@v7
        with:
          script: |
            const review = require('./review.json');
            for (const issue of review.structured_output.issues) {
              await github.rest.pulls.createReviewComment({
                ...context.repo,
                pull_number: context.issue.number,
                body: `**[${issue.severity}]** ${issue.message}`,
                commit_id: context.payload.pull_request.head.sha,
                path: issue.file,
                line: issue.line
              });
            }
Points clés du workflow :
  • fetch-depth: 0 — sans ça, git diff origin/main...HEAD échoue (historique tronqué)
  • ANTHROPIC_API_KEY dans les secrets du repo, pas dans le YAML
  • --max-turns évite une boucle agentique infinie qui consommerait du budget
  • Les permissions GitHub Actions doivent inclure pull-requests: write pour poster des commentaires
  • L'instance de revue est distincte de toute instance de génération : pas de biais self-review
Anti-pattern : exécuter Claude sans --max-turns en CI. Un agent peut entrer en boucle sur un edge case et consommer 50+ itérations, faisant exploser le temps et le coût du job. --max-turns 10 ou --max-turns 15 est un garde-fou raisonnable pour la plupart des tâches de revue.

8. Synthèse — les points clés

CLAUDE.md

  • Trois niveaux : user (personnel), project (équipe), directory (local).
  • Erreur classique : mettre les instructions au user-level au lieu du project-level.
  • Syntaxe @path pour les imports modulaires (profondeur max : 4 niveaux).
  • .claude/rules/ avec YAML frontmatter paths et glob patterns pour le chargement conditionnel.
  • Glob patterns préférables pour les conventions cross-directory ; directory CLAUDE.md pour les règles strictement locales.
  • /memory pour persister des notes entre sessions ; /compact pour compresser le contexte.

Skills et slash commands

  • Slash commands dans .claude/commands/ : mécanisme valide, partage via VCS.
  • Skills dans .claude/skills/ : format actuel, SKILL.md avec YAML frontmatter.
  • Skills personnels dans ~/.claude/skills/ : doivent utiliser des noms différents des skills projet (le skill personnel prend la priorité pour un même nom).
  • context: fork pour l'isolation dans un subagent, allowed-tools pour la pré-approbation des outils (pas une restriction — disallowed-tools retire un outil du pool disponible).
  • Priorité : Enterprise > Personnel > Projet > Plugins.

Modes de travail

  • Planning mode pour les tâches complexes, codebase inconnu, migrations 45+ fichiers.
  • Direct exécution pour les corrections ciblées sur un seul fichier.
  • Combinaison : planning mode puis direct exécution après approbation.
  • Le Explore subagent isole la sortie verbeuse de la découverte.
  • Le interview pattern fait émerger les considérations non anticipées avant implémentation.
  • Batch feedback (un seul message) pour les problèmes interdépendants ; sequential feedback pour les problèmes indépendants.

CI/CD

  • Le flag -p (--print) active le headless mode, obligatoire en CI.
  • --output-format json + --json-schema pour des sorties structurées (résultat conforme dans structured_output).
  • --max-turns N est un garde-fou contre les boucles agentiques infinies.
  • Instance indépendante pour la revue (pas la même session qui a généré le code).
  • Inclure les résultats de revue précédents pour éviter les commentaires dupliqués.
  • fetch-depth: 0 obligatoire dans GitHub Actions pour git diff origin/main...HEAD.
  • ANTHROPIC_API_KEY dans les secrets, jamais en clair dans le YAML.

9. Auto-évaluation

Q1 : Trois développeurs anciens beneficient de "always include comprehensive error handling", mais un nouveau qui vient de rejoindre ne l'a pas. Tous travaillent sur le même repo. Cause probable ? A) L'instruction est dans ~/.claude/CLAUDE.md (user-level) au lieu de .claude/CLAUDE.md (project-level). B) Le ~/.claude/CLAUDE.md du nouveau contient des instructions conflictuelles. C) Claude Code apprend les préférences par utilisateur au fil du temps. D) Le nouveau doit relancer Claude Code.

Réponse : A. Le fichier ~/.claude/CLAUDE.md est au user-level : il est personnel et non partagé via VCS. Les trois anciens développeurs l'ont chacun dans leur propre configuration, mais le nouveau n'en dispose pas. La solution est de déplacer cette instruction dans .claude/CLAUDE.md (project-level), qui est versionné et partagé avec toute l'équipe.

Q2 : Votre codebase a des conventions différentes pour React, API, et database. Les tests sont co-localises avec le code. Quelle approche ? A) Des fichiers .claude/rules/ avec YAML frontmatter et glob patterns. B) Tout mettre dans le root CLAUDE.md. C) Des skills dans .claude/skills/. D) Un CLAUDE.md dans chaque repertoire.

Réponse : A. Les fichiers .claude/rules/ avec YAML frontmatter paths et glob patterns permettent un chargement conditionnel : chaque convention n'est chargée que quand Claude édite un fichier correspondant. C'est l'approche préférée pour les conventions cross-directory (tests co-localisés dispersés dans le codebase). B gaspillerait du contexte en chargeant tout systématiquement. C est pour les tâches, pas les conventions. D serait fastidieux à maintenir avec des tests dispersés.

Q3 : Un skill /analyze-codebase fait du deep analysis. Après l'avoir lancé, Claude devient moins responsif et perd le contexte de la tâche originale. Comment fixer ? A) Ajouter context: fork dans le frontmatter du skill. B) Utiliser /compact après le skill. C) Reduire les outils du skill avec allowed-tools. D) Decouper le skill en plus petits skills.

Réponse : A. Le paramètre context: fork dans le frontmatter du SKILL.md exécute le skill dans un subagent isolé. La sortie verbeuse ne pollue pas la session principale, et Claude conserve le contexte de la tâche originale. B compresserait le contexte mais avec perte d'information. C changerait le pool d'outils pré-approuvés du skill (allowed-tools) sans résoudre le problème de pollution du contexte. D ajouterait de la complexité sans isolation.

Q4 : Votre pipeline CI execute claude 'Analyze this PR for security issues' mais le job reste bloque indefiniment. Quel est le problème ? A) Ajouter --batch. B) Utiliser le flag -p. C) Rediriger stdin depuis /dev/null. D) Setter CLAUDE_HEADLESS=true.

Réponse : B. Le flag -p (alias --print) est la manière documentée d'exécuter Claude Code en mode non interactif (headless mode) pour les pipelines CI/CD. Sans ce flag, Claude Code attend une saisie utilisateur interactive, ce qui bloque le job. La commande correcte est claude -p 'Analyze this PR for security issues'.

Q5 : Votre workflow GitHub Actions execute claude -p mais Claude entre parfois dans une boucle qui consomme 50+ iterations agentiques avant de s'arreter. Comment limiter cela proprement ? A) Ajouter --max-turns 10 a la commande. B) Mettre un timeout-minutes: 5 sur le job GitHub Actions. C) Reduire le contexte initial. D) Utiliser --output-format json.

Réponse : A. --max-turns N est le garde-fou natif de Claude Code pour limiter le nombre d'itérations agentiques (cycles tool_use → tool_result). C'est l'option propre : Claude termine avec un résultat partiel exploitable. B (timeout du job) est un filet de sécurité mais coupe brutalement, sans output structuré. C peut aider mais ne résout pas la cause. D contrôle le format de sortie, pas le nombre d'itérations. Combinez idéalement A + B pour la défense en profondeur.

Q6 (Domaine 3) : Vous avez un workflow que votre équipe doit répéter régulièrement (analyse de performance, génération de rapport technique, revue de sécurité). Ce workflow doit être réutilisable, configurable via l'équipe, invocable en local ET en CI/CD. Quelles deux approches vous permettent cela ? (Sélectionne les 2 réponses correctes.) A) Créer un skill avec context: fork, le partager via .claude/skills/, et le documenter dans CLAUDE.md. B) Mettre uniquement un slash command dans .claude/commands/, c'est suffisant pour la réutilisabilité équipe. C) Invoquer le skill en local par matching sémantique, ou en CI via claude -p avec --max-turns pour limiter les itérations. D) Stocker l'instruction du workflow dans ~/.claude/CLAUDE.md pour que les développeurs la voient automatiquement. E) Utiliser un hook PostToolUse pour déclencher le workflow automatiquement après chaque édition.

Réponses : A, C. Un skill isolé via context: fork peut être partagé avec l'équipe via VCS (.claude/skills/), documenté dans CLAUDE.md, et invoqué aussi bien en local (matching sémantique ou slash command) qu'en CI via « claude -p /skill-name » avec un --max-turns raisonnable. B ignore le répertoire structuré des skills (le format actuel supérieur aux slash commands). D place l'instruction au user-level (personnel, non partagé) au lieu du project-level. E confond le rôle des hooks : ils automatisent les actions post-événement d'outil, pas les workflows métier invocables.
