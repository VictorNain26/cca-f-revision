1. La hiérarchie CLAUDE.md et l'organisation modulaire (Task 3.1)

Le problème que cela résout

Dans une équipe, chaque développeur a ses préférences, mais le projet impose aussi des standards communs. Il faut un mécanisme pour séparer ces niveaux d'instruction et garantir que chaque membre reçoit les bonnes directives.

Les trois niveaux

NiveauEmplacementPartage ?Usage
User~/.claude/CLAUDE.mdNon (personnel, hors VCS)Préférences personnelles, style de travail
Project.claude/CLAUDE.md ou racineOui (versionné, partagé via Git)Standards de code, conventions de test, architecture
DirectoryCLAUDE.md dans un sous-dossierOui (versionné)Conventions propres à cette partie du codebase
Erreur classique : trois développeurs expérimentés bénéficient de l'instruction "always include comprehensive error handling", mais un nouveau ne la reçoit pas. Cause : les instructions étaient dans ~/.claude/CLAUDE.md (user-level) au lieu de .claude/CLAUDE.md (project-level). Le nouveau n'a pas les fichiers personnels des anciens. Solution : déplacer vers le project-level pour que tout le monde en bénéficie.
Réflexe d'examen : le signe distinctif d'un problème de hiérarchie, c'est « ça marche pour tout le monde sauf le nouvel arrivant ». Une instruction que les anciens appliquent et que le dernier embauché n'a jamais reçue vit au niveau user — ~/.claude/CLAUDE.md, jamais partagé par le VCS. La réponse est le déplacement vers le niveau projet ; /memory sert à le confirmer en listant les fichiers réellement chargés. Trois distracteurs : une version de Claude Code différente, qui n'explique pas une instruction ciblée manquante ; un CLAUDE.md devenu trop long, qui produirait une dégradation partagée par toute l'équipe et pas par un seul poste ; et demander à chacun de recopier le fichier, qui reproduit à la main ce que le versionnage fait déjà et redivergera au premier changement.

La syntaxe @path pour les imports

Plutôt que de concentrer toutes les instructions dans un seul fichier, vous pouvez référencer des fichiers externes :

# Dans CLAUDE.md
Les standards de code sont décrits dans @./standards/coding-style.md
Les exigences de test sont dans @./standards/testing-requirements.md
La vue d'ensemble du projet est dans @README.md

Le @ se place immédiatement avant le path (sans espace). Les paths relatifs sont résolus par rapport au fichier contenant l'import. La profondeur maximale d'imbrication est de 4 niveaux (« four hops »).

Le répertoire .claude/rules/

Une alternative au CLAUDE.md monolithique : des fichiers thématiques dont le chargement dépend des fichiers en cours d'édition.

.claude/rules/
  testing.md          — conventions de test
  api-conventions.md  — conventions API
  deployment.md       — règles de déploiement
  react-patterns.md   — patterns React

Chaque fichier inclut un YAML frontmatter avec le champ paths qui spécifie quand le charger :

---
paths: ["src/api/**/*"]
---
Pour les fichiers API, utiliser async/await avec une gestion d'erreurs explicite.
Chaque endpoint doit retourner un wrapper de réponse standard.
Quand utiliser .claude/rules/ vs. un directory CLAUDE.md : les fichiers .claude/rules/ avec glob patterns sont préférables quand les conventions s'appliquent à des fichiers dispersés dans le codebase (tests co-localisés, migrations cross-directory). Un CLAUDE.md dans un sous-dossier convient quand les règles sont spécifiques à un répertoire bien défini.

Les commandes /memory et /compact

(Source : guide officiel — /memory en Task 3.1, /compact en Task 5.4.)

  • /memory affiche quels fichiers mémoire sont actuellement chargés et vous permet de les éditer pour y ajouter des notes et préférences. Les fichiers chargés (ex. ~/.claude/projects/<id>/memory/*.md) persistent entre les sessions et sont appliqués automatiquement au démarrage. C'est aussi la commande de diagnostic quand vous soupçonnez qu'une instruction n'a pas été chargée correctement — vérifiez que le fichier de mémoire attendu apparaît dans la liste des fichiers chargés.
  • /compact compresse le contexte en résumant l'historique. Utile dans les longues sessions d'investigation, mais avec un risque : les valeurs numériques exactes, les dates et les détails précis peuvent être perdus lors de la compression.

2. Les slash commands et les skills (Task 3.2)

Le problème que cela résout

Si vous répétez régulièrement les mêmes instructions ("fais une revue en suivant ce format", "génère des tests selon nos conventions"), il est plus efficace de les encapsuler dans une commande réutilisable.

Les slash commands

Le guide fait loi sur ce point. Le référentiel traite slash commands et skills comme deux mécanismes distincts, et désigne .claude/commands/ comme l'emplacement d'une commande partagée avec l'équipe — c'est la réponse attendue à la question officielle « où créer un /review que tout le monde obtient au clone ? ». La documentation actuelle a depuis fusionné les deux : un fichier .claude/commands/deploy.md et un skill .claude/skills/deploy/SKILL.md produisent la même commande /deploy. Révisez le découpage du guide ; gardez la fusion pour votre travail quotidien.

Les slash commands sont stockées dans .claude/commands/ (partagées via VCS). Le nom du fichier donne le nom de la commande, et le contenu est le prompt exécuté.

PortéeEmplacementPartage
Projet.claude/commands/Versionne via VCS, disponible après clonage
Personnel~/.claude/commands/Personnel, non partagé

Le nom du fichier détermine le nom de la commande : review.md devient /review. Le placeholder $ARGUMENTS accepte des paramètres positionnels 0-based : $0 = 1er argument, $1 = 2e, etc.

Réflexe d'examen : dès que l'énoncé dit qu'une commande doit être disponible pour toute l'équipe après un clone, la réponse du guide est .claude/commands/. Trois distracteurs : ~/.claude/commands/, qui produit bien la commande mais reste personnel et hors VCS — donc invisible pour les collègues ; le CLAUDE.md, qui porte des instructions permanentes et non des définitions de commande invocable ; et un tableau commands déclaré dans un .claude/config.json, qui séduit parce qu'il ressemble à une configuration d'outil mais désigne un mécanisme inexistant.

Les skills

Le skill est l'autre mécanisme : il porte un workflow invoqué à la demande, et il est mieux outillé que la slash command pour les cas complexes — isolation de contexte, restriction d'outils, indice d'argument. Chaque skill vit dans un répertoire contenant un fichier SKILL.md avec un YAML frontmatter :

---
name: pr-description
description: Writes pull request descriptions. Use when creating
  a PR or summarizing changes for a review.
context: fork
allowed-tools: Read, Grep, Glob, Bash
argument-hint: "Branch name to compare against main"
---
Quand tu rédiges une description de PR :
1. Exécuter `git diff main...HEAD` pour voir les changements
2. Écrire une description structurée : What / Why / Changes

Les paramètres du frontmatter

ParamètreObligatoireRôle
nameOptionnel — défaut = nom du dossier du skillDisplay name (identifiant optionnel). Par défaut, le nom du dossier du skill sert de nom de commande (ex. /review pour .claude/skills/review/SKILL.md).
descriptionRecommandée — si omise, le premier paragraphe du corps sert de descriptionDétermine quand Claude active le skill (matching sémantique) — description + when_to_use tronqués à ~1536 caractères dans le listing — et influence comment il rédige le prompt. C'est le champ le plus déterminant pour le déclenchement.
context: forkNonExécute le skill dans un contexte isolé de subagent. La sortie verbeuse ne pollue pas la session principale.
allowed-toolsNonRestreint l'accès aux outils pendant l'exécution du skill — par exemple limiter aux opérations d'écriture de fichiers pour empêcher toute action destructrice. C'est la formulation du référentiel, et celle à retenir pour l'examen. Nuance terrain : la doc actuelle décrit ce champ comme une pré-approbation de permissions plutôt qu'une restriction stricte. À l'examen, répondez « restriction d'accès aux outils ».
argument-hintNonIndice affiché à l'autocomplétion pour réclamer le paramètre attendu quand le développeur invoque le skill sans argument.
Scénario d'examen : après avoir exécuté un skill d'analyse lourde, Claude devient moins réactif et perd le fil de la tâche originale. Solution : ajouter context: fork dans le frontmatter du SKILL.md pour isoler l'exécution dans un subagent séparé. Deux distracteurs accompagnent presque toujours cette question : allowed-tools, qui restreint les outils accessibles mais ne change rien à la destination de la sortie produite ; et une consigne « sois concis » ajoutée au corps du skill, qui demande au modèle de moins écrire au lieu d'écrire ailleurs — la sortie, même réduite, atterrit toujours dans la session principale.

Skills personnels vs. skills projet

PortéeEmplacementPartage
Projet.claude/skills/Versionné via VCS, partagé avec l'équipe
Personnel~/.claude/skills/Local, non partagé
Priorité en cas de conflit de nom : un skill personnel l'emporte sur un skill projet de même nom. Par exemple, si vous avez un skill /review dans ~/.claude/skills/review/SKILL.md et que le projet définit aussi un /review dans .claude/skills/review/SKILL.md, votre skill personnel sera utilisé.

C'est exactement pour cette raison que le référentiel recommande de donner un nom différent à votre variante personnelle : sans cela, vous masquez silencieusement le skill de l'équipe pour vous seul, et vous divergez de vos collègues sans le savoir.

Skills et subagents

Les subagents ne voient pas automatiquement les skills. Les agents intégrés (Explore subagent, Plan) ne peuvent pas y accéder ; un subagent disposant du Skill tool peut en revanche invoquer les skills (projet, user, plugin) à la demande.

3. Les règles conditionnelles par chemin (Task 3.3)

Le problème que cela résout

Les conventions de test s'appliquent à des fichiers dispersés dans tout le codebase (co-localisés avec le code source). Un CLAUDE.md par sous-répertoire serait fastidieux ; un CLAUDE.md unique chargerait des règles non pertinentes en permanence. Les fichiers .claude/rules/ avec glob patterns résolvent ce problème.

Exemple concret

# .claude/rules/testing.md
---
paths:
  - "**/*.test.tsx"
  - "**/*.test.ts"
  - "**/*.spec.ts"
---
Conventions de test :
- Utiliser des blocs describe/it.
- Utiliser des data factories, pas de données codées en dur.
- Ne pas mocker la base de données — utiliser une base de test.

L'anatomie du frontmatter

Le champ paths accepte une liste de globs. Le fichier ne se charge que si le fichier en cours d'édition correspond à l'un d'eux ; le corps est alors injecté tel quel dans le contexte, sans reformulation ni résumé. Un second exemple, scopé cette fois par répertoire :

# .claude/rules/terraform.md
---
paths: ["terraform/**/*"]
---
Toute ressource porte les tags obligatoires : owner, cost-center, environment.
Les backends d'état sont déclarés en S3 avec verrouillage DynamoDB.
Réflexe d'examen : quand un scénario dit que des conventions doivent s'appliquer à des fichiers dispersés dans l'arborescence — les tests co-localisés en sont l'exemple canonique — la réponse est .claude/rules/ avec un glob dans le frontmatter. Trois distracteurs reviennent : un CLAUDE.md par sous-répertoire, qui séduit parce qu'il est « plus local » mais reste lié au dossier et ne suit pas les fichiers dispersés ; tout consolider dans le CLAUDE.md racine sous des titres de section, qui repose sur l'inférence du modèle au lieu d'un appariement explicite ; et un skill par type de code, qui échoue sur le mot automatiquement de l'énoncé, puisqu'un skill s'invoque.
Chargement conditionnel : la règle ne se charge que lorsque Claude Code édite un fichier correspondant au glob pattern. Cela économise du contexte et des tokens : les conventions non pertinentes ne sont jamais chargées.

Glob patterns vs. directory CLAUDE.md : les glob patterns sont préférables pour les conventions cross-directory (tests co-localisés, fichiers de migration dispersés). Un directory CLAUDE.md convient pour les règles strictement locales à un sous-dossier.

4. Planning mode vs. direct exécution (Task 3.4)

Le problème que cela résout

Corriger un bug ciblé n'exige pas la même approche que restructurer un monolithe. Utiliser le même mode pour les deux mène soit à de la lenteur inutile, soit à des erreurs coûteuses.

Planning modeDirect exécution
ActionsExplore et planifie, ne modifie rienApplique les changements immédiatement
OutilsRead, Grep, GlobEdit, Write, Bash
Cas d'usageChangements importants, choix architecturaux, codebase inconnu, migrations (45+ fichiers), multiples approches possiblesCorrections ciblées sur un seul fichier, ajout d'une validation simple

Les cas contrastés du guide

Plan mode
  Restructurer un monolithe en microservices
    → frontières de service à décider, dizaines de fichiers
  Migrer une bibliothèque sur 45+ fichiers
    → périmètre large, approches concurrentes
  Choisir entre deux approches d'intégration
    → prérequis d'infrastructure différents

Exécution directe
  Corriger une déréférence null localisée par une stack trace
    → un fichier, une garde, périmètre déjà établi
  Ajouter une validation de date à un endpoint
    → changement compris, aucun arbitrage

La combinaison la plus courante : planning mode pour l'investigation, approbation du plan, puis direct exécution pour l'implémentation. Le plan approuvé sert alors de périmètre à la phase d'écriture : les décisions ont été tranchées avant qu'un seul fichier ne soit modifié.

Le Explore subagent isole la sortie verbeuse de la phase de découverte — les fichiers lus, les recherches infructueuses, les chemins abandonnés — et ne remonte qu'un résumé à la session principale. Le contexte principal reste disponible pour la planification puis l'implémentation, au lieu d'être consommé par la lecture exploratoire. C'est le complément naturel du plan mode sur un codebase inconnu : explorer via le subagent, planifier avec le résumé, exécuter ensuite.
Réflexe d'examen : la complexité est énoncée dans le scénario, elle ne se devine pas. « Dizaines de fichiers », « décisions d'architecture », « plusieurs approches valides » → plan mode. « Stack trace claire », « un seul fichier », « changement bien compris » → exécution directe. Le distracteur le plus fin propose de commencer en exécution directe et de basculer en plan mode si la complexité se révèle : il séduit parce qu'il a l'air prudent, mais il ignore que l'énoncé a déjà établi la complexité. Deux autres : appliquer le plan mode partout par principe, et donner des instructions exhaustives en exécution directe — ce qui suppose de connaître la bonne structure avant d'avoir exploré le code.

5. Le raffinement itératif (Task 3.5)

Le problème que cela résout

Même avec des instructions détaillées en prose, Claude peut interpréter différemment vos attentes à chaque itération. Il faut des méthodes plus précises pour converger.

Des exemples concrets d'entrée/sortie (I/O examples)

La méthode la plus efficace. Si Claude produit des résultats différents de vos attentes malgré les descriptions textuelles, fournissez 2 à 3 paires input/output concrètes montrant la transformation voulue.

Les distracteurs face à des exemples entrée/sortie. Trois options concurrentes reviennent quand une consigne en prose est interprétée différemment à chaque exécution. Réécrire la consigne encore plus précisément : c'est la démarche qui a déjà échoué, et ajouter des mots sur une ambiguïté ne la tranche pas. Demander au modèle d'expliquer son interprétation avant chaque exécution : cela transforme chaque lancement en négociation au lieu de figer la spécification une fois pour toutes. Découper la transformation en une commande par champ : cela multiplie les invocations sans jamais définir ce que le terme ambigu recouvre. L'exemple travaillé, lui, montre le résultat attendu au lieu de le décrire.

L'itération guidée par les tests (TDD iteration)

  1. Écrire les tests d'abord (cas attendus, cas limites, exigences de performance).
  2. Demander à Claude d'implémenter le code.
  3. Itérer sur les échecs jusqu'à ce que tous les tests passent.

Le interview pattern

Avant d'implémenter, Claude pose des questions de clarification pour faire émerger des considérations non anticipées :

"Avant d'implémenter le cache pour l'API, quelques questions :
1. Préférez-vous une invalidation par TTL ou par événement ?
2. Les données périmées sont-elles acceptables si le cache tombe ?
3. Le cache doit-il être par utilisateur ou global ?
4. Quel volume de données est attendu ?"
Quand utiliser le interview pattern : domaine peu familier (fintech, santé), implications non évidentes (stratégies de cache, modes de défaillance), ou multiples approches valides dont le meilleur choix dépend du contexte.

Batch vs. sequential feedback

Deux stratégies pour fournir du feedback à Claude :

StratégieQuand l'utiliserExemple
Batch feedbackQuand les problèmes sont interdépendants ou interactifs : tout dans un seul message détaillé pour que le modèle voie les interactions et les réconcilie"Le module manque de gestion d'erreurs, ce qui affecte aussi la validation d'input : proposer une architecture unifiée"
Sequential feedbackQuand les problèmes sont indépendants : un par un, sans que chaque correction dépende de la précédente"1. Renomme la variable X. 2. Après validation, on passera au type de retour."
La clé : l'interdépendance. Si les problèmes s'influencent mutuellement (ex. erreur de gestion d'erreur + validation d'input), utilisez batch pour que le modèle voie les interactions et réconcilie. Si chaque problème est indépendant, utilisez sequential pour valider étape par étape. Le batch est plus efficace en tokens, le sequential offre plus de contrôle et de validation.

6. L'intégration dans les pipelines CI/CD (Task 3.6)

Le problème que cela résout

Claude Code est interactif par défaut. Sans configuration adaptée, un job CI se bloquera indéfiniment en attente d'une saisie utilisateur.

Le flag -p (--print)

claude -p "Analyse cette pull request pour les problèmes de sécurité"

Le flag -p (alias --print) active le mode non interactif : Claude traite le prompt, imprime le résultat sur la sortie standard, puis se termine. C'est la seule manière documentée d'exécuter Claude Code en CI/CD.

Les sorties structurées

claude -p "Revue de cette PR" --output-format json --json-schema '{...}'

Le résultat reste l'enveloppe JSON habituelle de --output-format json ; le contenu conforme au schéma fourni via --json-schema se trouve dans le champ structured_output, que vous pouvez parser pour poster automatiquement des commentaires inline via l'API GitHub.

L'isolation de session pour la revue

La même session Claude qui a généré le code est moins efficace pour le reviewer. Elle conserve son contexte de raisonnement et questionne moins ses propres décisions — un biais analogue à celui d'un développeur relisant son propre code. Utilisez une instance indépendante (session séparée) pour la revue.

Bonnes pratiques CI/CD

  • Éviter les commentaires dupliqués : quand vous relancez une revue après de nouveaux commits, incluez les résultats de la revue précédente dans le contexte et demandez à Claude de ne signaler que les problèmes nouveaux ou non résolus.
  • Améliorer la génération de tests : documentez les standards de test et les fixtures dans CLAUDE.md, et incluez les fichiers de test existants en contexte pour garder un style cohérent.

Le mode headless (terminologie Anthropic)

Le mode non interactif activé par -p / --print est désigné officiellement comme headless mode dans la documentation Anthropic. Caractéristiques :

  • Pas de prompt interactif, pas d'attente de saisie
  • Sortie sur stdout, code de retour exploitable ($?)
  • Combinable avec --output-format json pour parsing programmatique
  • Combinable avec --json-schema pour contraindre la forme de cette sortie

Workflow GitHub Actions concret

name: Claude Code Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  claude-review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - run: npm install -g @anthropic-ai/claude-code

      - name: Run Claude review (non interactif)
        id: review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          claude -p "Review the diff git diff origin/main...HEAD \
            for security issues, bugs, and style violations. \
            Output JSON matching the schema." \
            --output-format json \
            --json-schema '{
              "type":"object",
              "properties":{
                "issues":{"type":"array","items":{
                  "type":"object",
                  "properties":{
                    "severity":{"enum":["critical","major","minor"]},
                    "file":{"type":"string"},
                    "line":{"type":"integer"},
                    "message":{"type":"string"}
                  },
                  "required":["severity","file","message"]
                }}
              }
            }' > review.json

      - name: Post inline comments
        uses: actions/github-script@v7
        with:
          script: |
            const review = require('./review.json');
            for (const issue of review.structured_output.issues) {
              await github.rest.pulls.createReviewComment({
                ...context.repo,
                pull_number: context.issue.number,
                body: `**[${issue.severity}]** ${issue.message}`,
                commit_id: context.payload.pull_request.head.sha,
                path: issue.file,
                line: issue.line
              });
            }
Points clés du workflow :
  • -p est ce qui empêche le job de se bloquer en attente d'une saisie interactive
  • --output-format json + --json-schema : la sortie devient exploitable par l'étape suivante sans parsing fragile
  • ANTHROPIC_API_KEY dans les secrets du repo, pas dans le YAML
  • Le CLAUDE.md du projet fournit à cette instance CI les standards de test, les fixtures disponibles et les critères de revue
  • L'instance de revue est distincte de toute instance de génération : pas de biais self-review
Anti-pattern : relancer la revue à chaque nouveau commit sans lui donner les findings des passes précédentes. Claude re-signale les mêmes problèmes, la PR se couvre de commentaires dupliqués et les développeurs cessent de les lire. Le correctif : inclure les findings antérieurs dans le contexte et demander explicitement de ne rapporter que les problèmes nouveaux ou non encore traités.
Réflexe d'examen : quatre associations suffisent à trancher la plupart des questions CI/CD. Un job qui se bloque en attente de saisie → -p. Une pipeline qui doit parser des findings → --output-format json avec --json-schema. Une instance CI qui ignore les conventions de test du projet → le CLAUDE.md versionné les lui porte. Une revue à faire sur du code que Claude vient de produire → une instance indépendante. Les distracteurs sont de deux familles. Les mécanismes inventés d'abord : une variable CLAUDE_HEADLESS et un flag --batch, plausibles parce que « headless » et « batch » sont bien le vocabulaire du domaine, mais aucun des deux n'existe. Les contournements ensuite : rediriger stdin depuis /dev/null, qui traite le symptôme sans activer le mode documenté, et parser la prose à coups de regex, qui déplace la fragilité du format dans votre code au lieu de contraindre la sortie.

Pour les hooks de l'Agent SDK (PostToolUse, PreToolUse) au niveau programmatique, voir D1, section 6.

CLAUDE.md

  • Trois niveaux : user (personnel), project (équipe), directory (local).
  • Erreur classique : mettre les instructions au user-level au lieu du project-level.
  • Syntaxe @path pour les imports modulaires (profondeur max : 4 niveaux).
  • .claude/rules/ avec YAML frontmatter paths et glob patterns pour le chargement conditionnel.
  • Glob patterns préférables pour les conventions cross-directory ; directory CLAUDE.md pour les règles strictement locales.
  • /memory pour persister des notes entre sessions ; /compact pour compresser le contexte.

Skills et slash commands

  • Slash commands dans .claude/commands/ : mécanisme valide, partage via VCS.
  • Skills dans .claude/skills/ : format actuel, SKILL.md avec YAML frontmatter.
  • Skills personnels dans ~/.claude/skills/ : doivent utiliser des noms différents des skills projet (le skill personnel prend la priorité pour un même nom).
  • context: fork pour l'isolation dans un subagent, allowed-tools pour restreindre l'accès aux outils pendant l'exécution du skill, argument-hint pour réclamer les paramètres attendus.

Modes de travail

  • Planning mode pour les tâches complexes, codebase inconnu, migrations 45+ fichiers.
  • Direct exécution pour les corrections ciblées sur un seul fichier.
  • Combinaison : planning mode puis direct exécution après approbation.
  • Le Explore subagent isole la sortie verbeuse de la découverte.
  • Le interview pattern fait émerger les considérations non anticipées avant implémentation.
  • Batch feedback (un seul message) pour les problèmes interdépendants ; sequential feedback pour les problèmes indépendants.

CI/CD

  • Le flag -p (--print) active le headless mode, obligatoire en CI.
  • --output-format json + --json-schema pour des sorties structurées (résultat conforme dans structured_output).
  • Instance indépendante pour la revue (pas la même session qui a généré le code).
  • Inclure les résultats de revue précédents pour éviter les commentaires dupliqués.
  • Fournir les fichiers de test existants pour que la génération de tests ne duplique pas la couverture.
  • CLAUDE.md porte les standards de test, les fixtures et les critères de revue jusqu'à l'instance CI.
  • ANTHROPIC_API_KEY dans les secrets, jamais en clair dans le YAML.

8. Auto-évaluation

Q1 (D3) — An instruction that never reaches the new contractor

Scenario: Every backend engineer gets Claude Code to register a new route in openapi.yaml before writing its handler. A contractor who cloned the repository this morning gets none of that. The rule was written by the platform lead in her own ~/.claude/CLAUDE.md.

Question: What is the diagnosis and the fix?

A) The rule sits at user scope and never travels with the repository; move it into a committed .claude/CLAUDE.md.

B) The contractor runs a newer build of Claude Code; align everyone on one version.

C) The rule file has grown past what gets loaded; split it first.

D) Send the contractor a copy of the lead's file to drop into their own home directory.

Answer: the rule lives at user scope instead of project scope

Why: a user-scope file belongs to one machine and never travels through version control, so only the people who wrote it hold it. Team-wide rules belong at project scope; /memory then confirms what a session actually loaded.

Why the others are wrong:

  • A version gap would not knock out one targeted instruction while everything else behaves.
  • Excess length would degrade the whole team's sessions, not one newcomer's.
  • Copying by hand reproduces what version control already does, and the copies drift apart at the first edit.
Q2 (D3) — Conventions for migration files nobody keeps in one place

Scenario: Each service owns its migration folder, so the files matching services/*/migrations/*.sql sit all over the tree. Every migration must be reversible and wrapped in a transaction, and you want that enforced whenever one is edited, without anyone having to ask for it.

Question: Which setup does that?

A) A rule file .claude/rules/migrations.md whose frontmatter paths field lists the migration glob.

B) A "Migrations" heading inside the root .claude/CLAUDE.md, left for the model to match against the file at hand.

C) A .claude/skills/migration/SKILL.md that engineers run before writing a migration.

D) One directory file per service, such as services/billing/migrations/CLAUDE.md.

Answer: a path-scoped rule file carrying the glob in its frontmatter

Why: the glob follows a file type wherever it sits, and the body loads only while a matching file is open — exactly the shape of a convention that crosses directories.

Why the others are wrong:

  • Leans on the model picking the right heading rather than on an explicit path match.
  • A skill waits to be invoked, and the requirement is that it apply on its own.
  • Directory-bound files mean the same rules copied into every service, drifting one folder at a time.
Q3 (D3) — A skill whose output crowds out the session

Scenario: Your /license-audit skill walks the dependency tree and prints every package it inspects before reaching its verdict. Reviewers want the verdict, but once the skill has run the main session drifts off the work it was doing.

Question: What fixes it?

A) context: fork, so the skill runs in an isolated subagent and only its result comes back.

B) An added line in the skill body telling it to stay brief.

C) A follow-up /compact after every audit.

D) One skill per package manager, replacing the single .claude/skills/license-audit/SKILL.md.

Answer: run the skill in a forked context

Why: the intermediate output is worth producing, it simply belongs somewhere other than the main conversation. A forked context keeps it inside the subagent and returns only the conclusion.

Why the others are wrong:

  • Asks the model to write less rather than to write elsewhere, with no guarantee either way.
  • Compacts after the damage is done, and compaction drops details.
  • Several verbose skills crowd the session just as one did, and nothing is isolated.
Q4 (D3) — A nightly job the runner has to kill

Scenario: A nightly job runs claude "Summarize the changes merged today" and the runner kills it at the step timeout. The log shows Claude Code sitting at an interactive prompt.

Question: What makes the command usable in an unattended job?

A) Export CLAUDE_CI=1 in the job environment.

B) Add --no-tty to the invocation.

C) Add -p (spelled out as --print) to the invocation.

D) Wrap the call in timeout 600 so the runner is never the one to kill it.

Answer: the print flag, which is the documented non-interactive mode

Why: it processes the prompt, writes the result to stdout and exits without waiting on input — which is what an unattended job needs.

Why the others are wrong:

  • No such environment variable exists, so the command runs unchanged and still waits.
  • No such flag exists either, and an unrecognized option does not switch the mode.
  • Turns a long hang into a shorter one; the job still produces nothing.
Q5 (D3) — Release notes the publisher cannot read

Scenario: A release job runs claude -p to draft release notes into changelog.json, and publish_notes.mjs reads an entries array out of it. Some runs come back as prose, some as a Markdown list, and the field names move around, so the publish step fails more often than it works.

Question: What is the correct fix?

A) Append "reply with valid JSON only, nothing around it" to the prompt.

B) Run with --output-format json and --json-schema, then read the conforming payload from structured_output.

C) Make the publisher tolerant: try jq first, fall back to a regular-expression sweep over the prose.

D) Pin the job to one model version so the shape stops moving.

Answer: constrain the shape with the two structured-output flags

Why: those flags exist for this case: one makes the reply machine-readable, the other imposes the expected fields, and the conforming payload lands in a known place for the next step to consume.

Why the others are wrong:

  • Rests on the model complying, which is the very thing already failing.
  • Moves the fragility into your own script and leaves it there.
  • Version drift is not what varies here; an unconstrained format varies within a single version.
Q6 (D3) — Packaging a workflow the whole team reuses (Select the 2 correct answers.)

Scenario: Your team runs the same accessibility audit over and over. It has to reach everyone, keep its verbose trace out of the working session, and run both at a developer's terminal and from the pipeline.

Question: Which two moves deliver that?

A) Commit it as .claude/skills/a11y-audit/SKILL.md with context: fork in its frontmatter.

B) Keep it as a personal ~/.claude/skills/a11y-audit/SKILL.md so you can iterate without disturbing anyone.

C) Invoke it by name at the terminal, and from the pipeline through claude -p with --output-format json so the next step can act on the result.

D) Paste the audit steps into ~/.claude/CLAUDE.md so every session carries them.

E) Fire it from a PostToolUse hook after each file write.

Answers: commit the forked skill with the repository, and invoke it by name locally or headless from the pipeline

Why: a committed skill meets all three requirements at once — versioned, so everyone gets it at clone time; forked, so its trace stays out of the session; and reachable from both sides, by name at the terminal and headless in the pipeline.

Why the others are wrong:

  • User scope is private and outside version control, which is the one requirement it cannot meet.
  • User scope again, and that file carries standing instructions rather than an invocable workflow.
  • A hook reacts to a tool event; it does not package a workflow somebody chooses to run.
Q7 (D3) — Two tickets, two modes

Scenario: Ticket one: a crash report pins a null dereference in renderShippingLabel() when carrier_code comes back empty — one guard, one file, scope already settled. Ticket two: split the shared database into one schema per service, which means deciding where ownership boundaries fall and touching dozens of files.

Question: Which mode for each?

A) Plan mode for both, since anything reaching production deserves a design pass first.

B) Direct execution for the crash, plan mode for the split.

C) Plan mode for the crash so the postmortem is documented, direct execution for the split.

D) Direct execution for both, taking the split one small step at a time.

Answer: execute the crash fix directly, plan the split

Why: planning earns its cost where boundaries are still open and many files move together. A one-file guard behind a crash report has nothing left to decide, and the scenario states as much.

Why the others are wrong:

  • Applies a heavy process by policy to a change that holds no design decision.
  • Inverts both criteria at once.
  • Small steps without a plan surface the dependencies late, when unwinding them costs most.
Q8 (D3) — One instruction, a different result every run

Scenario: You ask for supplier catalog rows to be "cleaned up before import". One run strips the unit off net_weight and the next leaves it; one run merges rows sharing a sku and the next keeps both. You have rewritten the written spec twice without converging.

Question: What is the most effective next move?

A) Rewrite the spec a third time, longer and more specific.

B) Have the model state its reading of "cleaned up" before each run, and correct it every time.

C) Supply two or three before/after row pairs showing exactly what a cleaned row looks like.

D) Split the cleanup into one instruction per column.

Answer: worked before/after pairs

Why: a worked example settles the cases the prose left open by showing the expected result rather than describing it again.

Why the others are wrong:

  • This is the move that has already failed twice; more words about an ambiguity do not resolve it.
  • Turns every run into a negotiation instead of fixing the specification once.
  • Multiplies invocations without ever defining what the ambiguous word covers.
