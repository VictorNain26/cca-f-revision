1. Strategies d'examen

Format et regles

  • Format : QCM, 4 choix, 1 seule réponse correcte. Score de 100 a 1000, seuil de reussite : 720.
  • Pas de penalite → répondre a TOUTES les questions, ne jamais laisser de blanc.
  • Methode de lecture : lire la situation d'abord, identifier le concept teste, PUIS regarder les choix.

Distracteurs recurrents a eliminer

  • "Improve/strengthen the system prompt" → insuffisant quand il y a des consequences financieres ou legales (il faut du programmatic enforcement).
  • "Add a routing classifier" / "trained classifier" → overengineering par rapport a la solution demandee.
  • "Sentiment analysis" / "self-rated confidence" → unreliable proxy (le modèle peut être confident a tort).
  • "Abort the whole workflow" → disproportionne, on veut de la graceful degradation.
  • "Move blocking checks to Batch API" → latence inacceptable (jusqu'a 24h).
  • "Larger context window fixes attention" → faux, un context window plus grand n'ameliore pas l'attention sur les sections centrales.

2. Questions expliquées (Guide officiel)

Q1 (Customer Support Agent) — Programmatic enforcement

Situation : Les donnees montrent que dans 12% des cas, l'agent saute l'appel a get_customer et appelle lookup_order en utilisant uniquement le nom du client, ce qui provoque des remboursements incorrects.

Question : Quelle approche resout le mieux ce problème ?

A) Ajouter une precondition programmatique bloquant lookup_order et process_refund tant que get_customer n'a pas retourné un verified ID

B) Ameliorer le system prompt pour insister sur l'importance de vérifier le client

C) Ajouter des few-shot examples montrant le bon ordre d'appel

D) Implementer un routing classifier pour diriger les requêtes

Reponse : A) Ajouter une precondition programmatique bloquant lookup_order et process_refund tant que get_customer n'a pas retourné un verified ID

Explication : Quand il y a des consequences financieres (remboursements incorrects), une solution deterministic est requise. Un contrôle programmatique garantit a 100% que l'ordre est respecte.

Pourquoi les autres sont faux :

  • B) Le system prompt est probabiliste — le modèle peut toujours l'ignorer dans 12% des cas.
  • C) Les few-shot examples ajoutent des tokens sans garantir le respect de l'ordre.
  • D) Un routing classifier adresse la disponibilite des outils, pas l'ordre d'exécution.
Q2 (Customer Support Agent) — Tool descriptions

Situation : L'agent appelle souvent get_customer au lieu de lookup_order. Les descriptions des outils sont minimales et similaires.

Question : Quelle est la meilleure facon de corriger la selection d'outils ?

A) Ajouter des few-shot examples

B) Enrichir la description de chaque outil avec les formats d'entree, des exemples et les limites d'utilisation

C) Ajouter une couche de routing

D) Fusionner les deux outils en un seul

Reponse : B) Enrichir la description de chaque outil avec les formats d'entree, des exemples et les limites d'utilisation

Explication : Les tool descriptions sont le mécanisme principal de selection d'outils. Des descriptions claires avec input formats, examples et boundaries permettent au modèle de distinguer precisement quand utiliser chaque outil.

Pourquoi les autres sont faux :

  • A) Les few-shot examples ajoutent des tokens sans corriger la cause racine (descriptions ambigues).
  • C) Un routing layer est du overengineering pour un problème de description.
  • D) Fusionner les outils demande plus d'effort que justifie et reduit la granularite.
Q3 (Customer Support Agent) — Escalation calibration

Situation : L'agent ne resout que 55% des cas (objectif : 80%). Il escalade les cas simples mais tente de gérer les cas complexes de manière autonome.

Question : Comment corriger la calibration de l'escalation ?

A) Ajouter des critères d'escalation explicites avec des few-shot examples

B) Utiliser un self-rated confidence score (1-10) avec escalation automatique sous un seuil

C) Entrainer un classifier separe sur les donnees historiques

D) Utiliser le sentiment analysis pour detecter la frustration

Reponse : A) Ajouter des critères d'escalation explicites avec des few-shot examples

Explication : Le problème est que les frontieres de décision sont floues. Des critères explicites + des exemples montrant quand escalader et quand resoudre corrigent directement ce problème.

Pourquoi les autres sont faux :

  • B) Le self-rated confidence est un unreliable proxy — le modèle peut être confidemment faux.
  • C) Un classifier entraine est du overengineering pour ce problème.
  • D) Le sentiment analysis resout un problème différent (detection de frustration, pas calibration d'escalation).

  • C) Le CLAUDE.md racine sert aux instructions, pas a definir des commandes.

Q5 (Claude Code) — Planning mode

Situation : Il faut restructurer un monolithe en microservices (dizaines de fichiers, décisions sur les frontieres de services).

Question : Quelle approche est la plus appropriee ?

A) Planning mode : explorer le codebase, comprendre les dependances, concevoir l'approche

B) Execution directe, incrementalement

C) Execution directe avec des instructions detaillees en amont

D) Execution directe et basculer en planning mode quand ca devient difficile

Reponse : A) Planning mode : explorer le codebase, comprendre les dependances, concevoir l'approche

Explication : Les changements a grande échelle + multiples approches possibles + décisions architecturales = planning mode. Il faut comprendre avant d'agir.

Pourquoi les autres sont faux :

  • B) L'exécution directe incrementale risque du rework massif sans vision d'ensemble.
  • C) Presuppose que la structure est connue a l'avance — ce n'est pas le cas.
  • D) Approche reactive : on decouvre les problèmes trop tard.

  • C) Les skills sont manuelles / on-demand, pas automatiques.
  • D) Un CLAUDE.md par repertoire ne fonctionne pas pour les fichiers disperses (ex: tests co-localises).

Q8 (Multi-Agent Research) — Error propagation

Situation : Le subagent de web search fait un timeout. Il faut concevoir la propagation d'erreur vers le coordinator.

Question : Quelle stratégie de gestion d'erreur est optimale ?

A) Retourner un contexte d'erreur structure : type de failure, query, resultats partiels, alternatives

B) Retries automatiques avec exponential backoff puis message generique "search unavailable"

C) Intercepter le timeout et retourner un ensemble de resultats vide marque comme succes

D) Propager l'exception au handler de niveau supérieur, terminant tout le workflow

Reponse : A) Retourner un contexte d'erreur structure : type de failure, query, resultats partiels, alternatives

Explication : Un structured error context donne au coordinator toute l'information nécessaire pour une intelligent recovery (retry partiel, source alternative, etc.).

Pourquoi les autres sont faux :

  • B) Les retries masquent le contexte — le coordinator ne sait pas pourquoi ca a echoue.
  • C) Masquer l'échec en succes est dangereux — la synthese travaillera avec des donnees incompletes sans le savoir.
  • D) Terminer tout le workflow est disproportionne pour un timeout partiel.
Q9 (Multi-Agent Research) — Synthesis vérification overhead

Situation : L'agent de synthese doit souvent vérifier des affirmations. Le circuit actuel passe par coordinator → web-search → re-synthese = 2-3 allers-retours supplémentaires, +40% de latence. 85% sont de simples fact checks, 15% necessitent une investigation approfondie.

Question : Comment reduire cette latence ?

A) Donner a l'agent de synthese un outil limite verify_fact pour les checks simples, router les complexes via le coordinator

B) Grouper toutes les verifications a la fin

C) Donner a la synthese un accès complet au web search

D) Mettre en cache proactivement du contexte supplémentaire

Reponse : A) Donner a l'agent de synthese un outil limite verify_fact pour les checks simples, router les complexes via le coordinator

Explication : Principe de least privilege : 85% des cas sont simples → un outil direct et limite suffit. Les 15% complexes passent par le coordinator pour maintenir le contrôle.

Pourquoi les autres sont faux :

  • B) Grouper a la fin retarde la detection d'erreurs et peut necessiter de refaire la synthese.
  • C) Un accès complet au web search viole le principe de least privilege.
  • D) Le caching proactif est imprecis — on ne sait pas a l'avance quelles verifications seront nécessaires.

Q11 (Claude Code for CI) — Batch API cost optimization

Situation : Deux workflows : un pre-merge check bloquant + un rapport de tech-debt nocturne. Le manager propose de mettre les deux sur la Batch API pour economiser 50%.

Question : Quelle est la bonne stratégie ?

A) Batch uniquement pour le tech-debt ; garder le pre-merge en synchrone

B) Les deux en batch avec polling

C) Les deux en synchrone

D) Les deux en batch avec fallback synchrone

Reponse : A) Batch uniquement pour le tech-debt ; garder le pre-merge en synchrone

Explication : La Batch API peut prendre jusqu'a 24h — c'est inacceptable pour un pre-merge check bloquant. Le rapport nocturne, lui, tolere cette latence.

Pourquoi les autres sont faux :

  • B) Le pre-merge bloquant ne peut pas attendre jusqu'a 24h.
  • C) Garder les deux en synchrone gaspille 50% d'economies sur le tech-debt.
  • D) Le fallback ne resout pas le problème de latence pour le pre-merge.
Q12 (Multi-file Code Review) — Multi-pass review

Situation : Une PR modifie 14 fichiers. La review en single-pass est inconsistante : détaillée pour certains fichiers, superficielle pour d'autres, avec des commentaires contradictoires.

Question : Comment obtenir une review consistante ?

A) Separer en passes par fichier pour les problèmes locaux, puis une passe d'intégration pour les enjeux cross-file

B) Demander aux développeurs de decouper les PRs en 3-4 fichiers

C) Passer a un modèle avec un context window plus grand

D) Trois passes independantes sur toute la PR, reporter le consensus

Reponse : A) Separer en passes par fichier pour les problèmes locaux, puis une passe d'intégration pour les enjeux cross-file

Explication : Le multi-pass corrigé la cause racine : l'attention dilution. Chaque passe se concentre sur un scope limite, puis la passe d'intégration couvre les interactions.

Pourquoi les autres sont faux :

  • B) Transfere la charge aux développeurs — ne resout pas le problème technique.
  • C) Un context window plus grand n'ameliore pas l'attention — c'est une misconception.
  • D) Trois passes identiques sur 14 fichiers vont reproduire les mêmes biais et supprimer les vrais bugs par vote majoritaire.

Q13 (Multi-Agent Research) — Statistiques contradictoires

Situation : Deux sources credibles rapportent des statistiques contradictoires (40% vs 12%) sur le même phenomene.

Question : Comment l'agent de synthese doit-il traiter cette contradiction ?

A) Choisir la valeur la plus probable et ajouter une footnote

B) Presenter les deux sans signaler le conflit

C) S'arreter et escalader au coordinator

D) Presenter les deux avec une conflict annotation et laisser le coordinator decider

Reponse : D) Presenter les deux avec une conflict annotation et laisser le coordinator decider

Explication : L'agent de synthese ne doit pas prendre de décision editoriale sur les donnees. Annoter le conflit et remonter au coordinator permet une décision informee.

Pourquoi les autres sont faux :

  • A) Choisir une valeur est une décision editoriale qui depasse le role de la synthese.
  • B) Presenter sans signaler le conflit produit un rapport incohérent.
  • C) S'arreter completement est disproportionne — le travail peut continuer avec l'annotation.
Q14 (Multi-Agent Research) — Etape suivante après collecte

Situation : Les agents de web search et de doc analysis ont termine leur travail. Quelle est l'étape suivante ?

Question : Comment les resultats doivent-ils être traites ?

A) Les agents envoient directement au report-writing

B) Le doc analysis fusionne les resultats en interne

C) Le coordinator transmet les deux ensembles de resultats a la synthese

D) Concatener les sorties brutes

Reponse : C) Le coordinator transmet les deux ensembles de resultats a la synthese

Explication : Le coordinator est le point central de l'orchestration. Il collecte les resultats de chaque subagent et les transmet a la synthese pour intégration.

Pourquoi les autres sont faux :

  • A) La communication directe entre subagents contourne le coordinator et reduit l'observability.
  • B) Le doc analysis n'a pas la responsabilite de fusionner des resultats d'autres agents.
  • D) La concatenation brute ne produit pas une synthese cohérente.
Q15 (Multi-Agent Research) — Recovery locale vs escalation

Situation : Le subagent de doc analysis echoue frequemment sur les PDFs. Toute exception termine le subagent, ce qui implique une intervention excessive du coordinator.

Question : Quelle stratégie de gestion d'erreur adopter ?

A) Un agent dedie a la gestion d'erreurs

B) Toujours retourner un succes partiel

C) Le coordinator valide tous les documents en amont

D) Recovery locale pour les erreurs transitoires, escalation uniquement pour les erreurs irrecuperables

Reponse : D) Recovery locale pour les erreurs transitoires, escalation uniquement pour les erreurs irrecuperables

Explication : La distinction entre erreurs transitoires (retry local) et irrecuperables (escalation) reduit l'implication du coordinator aux cas qui le necessitent vraiment.

Pourquoi les autres sont faux :

  • A) Un agent dedie aux erreurs est du overengineering.
  • B) Retourner toujours un succes partiel masque les vrais échecs.
  • C) Le coordinator ne devrait pas pre-valider chaque document — c'est le role du subagent.

Q24 (Multi-Agent Research) — Categories de sources

Situation : Trois catégories de sources : academic (15 articles), industry (0 resultats), patents (timeout).

Question : Comment interpréter ces resultats ?

A) Agreger comme 67% de couverture

B) Les deux échecs necessitent une intervention

C) Retenter uniquement les transitoires

D) Distinguer le timeout (access failure) de l'ensemble vide (resultat valide)

Reponse : D) Distinguer le timeout (access failure) de l'ensemble vide (resultat valide)

Pourquoi les autres sont faux :

  • B) L'ensemble vide n'est pas un échec — c'est un resultat valide.
  • C) Retenter uniquement les transitoires est partiellement correct mais ne répond pas a comment interpréter les resultats.

  • B) max_tokens contrôle la longueur de la réponse, pas le nombre de tool calls.
  • C) Un composite tool fusionne des responsabilites distinctes.

7. Practice Test — Developer Productivity Tools (Q65-Q71)

Contexte du scénario : votre équipe d'ingenierie veut outiller les développeurs avec un agent qui les aide a naviguer le codebase, automatiser les taches repetitives, et integrer des serveurs MCP pour acceder aux outils internes (Jira, GitHub, base de donnees). L'objectif est de reduire le temps passe sur les taches a faible valeur ajoutee.
Q65 (Developer Productivity Tools) — Strategie d'investigation incrementale

Situation : un développeur demande a Claude Code "Comment fonctionne l'authentification dans ce monorepo ?". Le codebase contient 1200 fichiers. Quelle stratégie est la plus efficace pour Claude ?

A) Lire tous les fichiers du repertoire src/ avant de répondre

B) Utiliser Grep pour trouver les points d'entree (auth, login, session), puis Read les fichiers identifiés, puis Grep les usages, puis Read les consommateurs (incremental investigation)

C) Demander au développeur de lister les fichiers pertinents

D) Charger le projet entier en context window et synthetiser

Reponse : B) Investigation incrementale Grep -> Read -> Grep -> Read

Explication : c'est la stratégie recommandée dans D2 §5. Elle minimise le contexte consomme en ne lisant que les fichiers pertinents. Grep identifié les points d'entree, Read les charge, puis on cherche les usages — la comprehension se construit par couches.

Pourquoi les autres sont faux :

  • A) Lire 1200 fichiers sature le contexte et noie l'information utile (lost-in-the-middle).
  • C) Le développeur a demande a Claude precisement parce qu'il ne sait pas — c'est une non-réponse.
  • D) Meme avec un grand context window, charger 1200 fichiers degrade la qualite du raisonnement.
Q66 (Developer Productivity Tools) — Subagent Explore vs lecture directe

Situation : votre senior dev veut que Claude lui resume les dependances du module Payments avant de planifier une refonte. La sortie verbeuse de l'investigation (lecture de 18 fichiers) pollue le contexte de la session principale. Comment proceder ?

A) Faire la lecture en thread principal et accepter la pollution.

B) Deleguer l'investigation a un Explore subagent qui retourne un résumé concis ; le contexte principal reste libre pour la phase de planification.

C) Demander au dev de faire la lecture lui-même.

D) Lancer /compact après chaque fichier lu.

Reponse : B) Deleguer a un Explore subagent qui retourne un résumé

Explication : l'Explore subagent (D3 §4) isole la sortie verbeuse de la phase de decouverte. Le subagent lit les 18 fichiers dans son propre contexte et retourne un résumé concis ("Le module Payments depend de AuthService, OrderModel et de PaymentGateway"). Le contexte principal garde une ligne au lieu de 18 fichiers.

Pourquoi les autres sont faux :

  • A) La pollution du contexte degrade la phase de planification qui suit.
  • C) On annule l'intérêt de l'outil productivite.
  • D) /compact compresse mais perd les détails ; un subagent isole sans perte.
Q67 (Developer Productivity Tools) — Custom skill vs slash command

Situation : votre équipe execute reguliereent une revue de PR avec un format spécifique : analyse securite + analyse performance + vérification de la couverture de tests. Vous voulez encapsuler ce workflow. Quelle approche choisir ?

A) Slash command legacy dans .claude/commands/review.md

B) Skill projet dans .claude/skills/pr-review/SKILL.md avec frontmatter (description pour matching semantique, context: fork pour isolation, allowed-tools pour limiter les outils)

C) Instruction dans CLAUDE.md qui liste les étapes

D) Hook PostToolUse qui s'execute après chaque PR

Reponse : B) Skill projet avec SKILL.md frontmatter

Explication : les skills sont le format actuel et recommandé (D3 §2). Le frontmatter description permet le matching semantique (Claude active le skill quand il detecte le besoin), context: fork isole la verbosite de la revue dans un subagent, et allowed-tools restreint a Read/Grep/Glob/Bash.

Pourquoi les autres sont faux :

  • A) Slash commands sont legacy. Skills sont plus puissants.
  • C) CLAUDE.md est pour les standards permanents, pas pour les workflows invocables.
  • D) Un hook ne fait pas de revue — il execute des commandes deterministes après une action.
Q68 (Developer Productivity Tools) — Configuration MCP partagee équipe

Situation : votre équipe veut que tous les développeurs aient accès aux mêmes serveurs MCP (Jira interne, GitHub, base PostgreSQL de dev). Chaque développeur doit utiliser ses propres credentials. Quelle approche ?

A) Mettre les tokens en clair dans .mcp.json versionne

B) Mettre la config des serveurs dans .mcp.json versionne avec syntaxe ${VAR} pour les credentials, chaque développeur fournit ses variables d'environnement localement

C) Demander a chaque développeur de lancer claude mcp add pour chaque serveur (config user dans ~/.claude.json)

D) Stocker les credentials dans .claude/settings.json

Reponse : B) .mcp.json versionne + ${VAR} pour les credentials

Explication : .mcp.json a la racine du projet est versionne et partage la config des serveurs avec l'équipe (D2 §4 et D3 §6 (HITL ou MCP CLI)). La syntaxe ${VAR} resout les credentials au runtime depuis l'environnement de chaque développeur — chacun fournit son propre token, jamais commit.

Pourquoi les autres sont faux :

  • A) Anti-pattern absolu — l'historique Git retient les secrets même après suppression.
  • C) Ne mutualise pas la config (chaque dev doit re-faire la setup, divergence des configs).
  • D) settings.json est pour les permissions/hooks, pas pour la config MCP.
Q69 (Developer Productivity Tools) — Permissions Bash en CI dev

Situation : votre équipe veut que les développeurs utilisent Claude Code en mode "acceptEdits" sur leur poste, mais les tests doivent toujours passer (npm test) sans demande. Quelle config dans .claude/settings.json ?

A) {"permissions": {"allow": ["Bash(npm test)"]}}

B) {"permissions": {"allow": ["Bash(npm test:*)", "Bash(npm run test:*)"], "defaultMode": "acceptEdits"}}

C) {"permissions": {"defaultMode": "bypassPermissions"}}

D) {"permissions": {"deny": ["Bash(rm:*)"]}}

Reponse : B) Bash(npm test:*) + Bash(npm run test:*) + acceptEdits

Explication : la syntaxe :* autorisé npm test avec n'importe quels arguments (--watch, --coverage, etc.). On ajoute npm run test:* car certains projets exposent des scripts comme npm run test:unit. defaultMode: acceptEdits auto-accepte les editions sans toucher aux Bash.

Pourquoi les autres sont faux :

  • A) Sans :*, seul npm test exact passe — npm test --watch declencherait une demande.
  • C) bypassPermissions est dangereux — autorisé toute commande y compris destructrice.
  • D) Bloque rm mais ne resout pas le problème des tests.
Q70 (Developer Productivity Tools) — Outils Built-in vs MCP : disambiguation

Situation : vous avez configure un serveur MCP "internal-search" qui indexe les wikis et docs internes. Mais Claude appelle systematiquement WebFetch pour rechercher de l'info, ignorant le serveur MCP. Pourquoi et comment fixer ?

A) Le serveur MCP est mal configure — vérifier .mcp.json

B) Les agents preferent les built-in tools — renforcer la description du tool MCP en soulignant les avantages concrets (donnees internes, contexte équipe) que les built-in ne couvrent pas

C) Supprimer WebFetch de l'allowlist

D) Ajouter une instruction dans CLAUDE.md "always use internal-search first"

Reponse : B) Renforcer la description MCP avec les differentiateurs

Explication : les agents ont une preference connue pour les built-in tools (D2 §1). La parade est au niveau de la description du tool MCP : la rendre plus precise et distinctive, souligner les donnees exclusives ("indexe les wikis internes incluant les décisions architecturales, post-mortems et knowledge base — pas accessibles via le web"). Cette differenciation aide le LLM a faire le bon choix.

Pourquoi les autres sont faux :

  • A) Si la config etait fausse, le tool ne serait pas du tout disponible.
  • C) Supprime un outil utile au lieu de resoudre la selection.
  • D) Instruction prompt = probabiliste. La description du tool est la source primaire de selection.
Q71 (Developer Productivity Tools) — Hook PostToolUse pour formater après edition

Situation : votre équipe TypeScript veut que tous les fichiers .ts soient automatiquement formates par Prettier après chaque edition par Claude. Solution la plus fiable ?

A) Ajouter "Always run prettier after editing TypeScript files" dans CLAUDE.md

B) Configurer un hook PostToolUse dans .claude/settings.json avec matcher: "Edit|Write" et command prettier --write "$CLAUDE_FILE_PATHS"

C) Creer un skill /format que les devs invoquent manuellement

D) Demander a Claude de toujours faire le formatage dans le même commit

Reponse : B) Hook PostToolUse

Explication : un hook PostToolUse est deterministe — il s'execute après chaque Edit ou Write, sans dependre du raisonnement du modèle (D3 §6 (hooks Claude Code)). La variable $CLAUDE_FILE_PATHS contient les chemins des fichiers edites. Pas de risque d'oubli, pas de dependance aux instructions textuelles.

Pourquoi les autres sont faux :

  • A) Instruction prompt = probabiliste, peut être oubliee dans des contextes longs.
  • C) Manuel = fragile et ralentit le workflow.
  • D) Melange formatage et commit, et reste probabiliste.

8. Practice Test — Structured Data Extraction (Q72-Q78)

Contexte du scénario : votre entreprise traite quotidiennement 50 000 documents PDF (factures, contrats, formulaires) provenant de fournisseurs heterogenes. Vous construisez un pipeline d'extraction structurée avec Claude qui doit produire du JSON exploitable par les systèmes en aval (ERP, comptabilite). Les enjeux : fiabilite, cout, latence, gestion des cas ambigus.
Q72 (Structured Data Extraction) — Garantir un output JSON valide

Situation : votre extraction produit du JSON avec des erreurs syntaxiques (virgules trainantes, guillemets manquants) dans 3% des cas. Comment eliminer ces erreurs ?

A) Augmenter la temperature pour plus de creativite

B) Utiliser tool_use avec un input_schema JSON Schema — la syntaxe valide est garantie par construction

C) Demander a Claude de relire son output avant de le retourner

D) Post-processer avec un parseur JSON tolerant

Reponse : B) tool_use + JSON Schema

Explication : le mécanisme tool_use garantit que la sortie respecte la syntaxe JSON et la structure du schéma (D0 §8, D2 §4 (JSON Schema)). Le modèle ne peut plus produire un JSON syntaxiquement invalide. La semantique (valeurs correctes) reste a valider cote app.

Pourquoi les autres sont faux :

  • A) Temperature plus haute = plus d'erreurs, pas moins.
  • C) La self-review augmente le cout et reste probabiliste.
  • D) Patcher le symptome, pas la cause. Et certaines erreurs (champs manquants) ne sont pas reparables.
Q73 (Structured Data Extraction) — Champs nullable contre l'hallucination

Situation : votre schéma a "company_name" en required. Pour 8% des documents (factures de freelancers), aucune entreprise n'est mentionnee. Le modèle invente un nom plausible. Comment fixer ?

A) Ajouter des few-shot examples

B) Rendre le champ nullable : {"type": ["string", "null"]} et le retirer de required

C) Ajouter une validation post-extraction qui rejette les noms suspects

D) Preprocesser les documents pour exclure les freelancers

Reponse : B) Nullable + retirer de required

Explication : un champ required force le modèle a fournir une valeur, qui est alors fabriquee si l'info est absente (D0 §8). Le pattern correct : nullable + retrait de required. Le modèle retourné null honnetement quand l'info manque, au lieu d'inventer.

Pourquoi les autres sont faux :

  • A) Few-shot peut aider mais ne resout pas la contrainte schéma qui force l'hallucination.
  • C) Detecter "noms suspects" est fragile et arbitraire.
  • D) Modifie le perimetre metier pour contourner un problème technique.
Q74 (Structured Data Extraction) — Enum avec "other" + champ détail

Situation : votre schéma categorise les depenses : enum: ["travel", "meals", "supplies", "software"]. Mais 12% des factures ne rentrent dans aucune catégorie (gym, formation, sponsoring). Comment faire sans casser la structure ?

A) Ajouter chaque nouvelle catégorie a l'enum au fil du temps

B) Etendre l'enum avec "other" + un champ détail nullable : {"category": "other", "category_detail": "Sponsoring sportif"}

C) Mettre type: "string" sans enum

D) Filtrer les documents non-conformes en amont

Reponse : B) Enum avec "other" + champ détail

Explication : ce pattern (D0 §8, D2 §4 (JSON Schema)) capture les cas inattendus sans perte d'information ni hallucination. Le modèle utilise "other" + le champ détail texte libre quand le cas ne rentre pas dans les catégories predefinies. Vous gardez la structure pour 88% des cas et collectez les nouvelles catégories pour decider plus tard de les officialiser.

Pourquoi les autres sont faux :

  • A) Etendre l'enum a chaque nouveau cas est ingerable a long terme.
  • C) Sans enum, perte totale de la structure contrôlée.
  • D) Meme erreur que Q73D — modifier le metier pour contourner.
Q75 (Structured Data Extraction) — Batch API pour traitement nocturne

Situation : vous traitez 50 000 factures par jour. Le SLA accepte une latence de 24h. Vous cherchez a reduire le cout. Quelle approche ?

A) Continuer en API synchrone, le cout est secondaire

B) Utiliser la Message Batches API (50% d'economies, jusqu'a 24h de traitement, correlation via custom_id)

C) Utiliser un modèle moins capable

D) Reduire max_tokens

Reponse : B) Message Batches API

Explication : 50 000 docs/jour avec un SLA de 24h est le cas d'usage parfait du Batch API (D4 §5) : 50% d'economies, traitement asynchrone, custom_id pour correler chaque réponse au document source. Pour les échecs, on resoumet uniquement les custom_id en échec.

Pourquoi les autres sont faux :

  • A) Ignore l'opportunite d'economie de 50%.
  • C) Degrade la qualite — les economies sur le modèle peuvent être annulees par les retries d'erreurs.
  • D) Tronque les réponses, ne reduit pas significativement le cout.
Q76 (Structured Data Extraction) — Retry-with-feedback sur erreur de validation

Situation : votre extraction sort un JSON valide syntaxiquement, mais la somme des line_items ne correspond pas au total annonce sur la facture. Que faire ?

A) Accepter le JSON et corriger en aval

B) Retry avec un nouveau prompt incluant : le document original + l'extraction precedente + l'erreur spécifique ("la somme des line_items est 487$ mais le total annonce est 512$")

C) Ignorer l'incohérence et logger

D) Retry avec une temperature plus haute

Reponse : B) Retry-with-feedback

Explication : le pattern retry-with-feedback (D4 §4.4) est efficace pour les erreurs de cohérence interne : on renvoie a Claude le document, sa premiere extraction, et l'erreur precise. Claude comprend ce qu'il a manque (ligne oubliee, frais cache) et corrigé. C'est l'usage canonique de la self-correction.

Pourquoi les autres sont faux :

  • A) Disperse la vérification semantique partout en aval — anti-pattern.
  • C) Laisse passer des donnees fausses qui contamineront l'ERP.
  • D) Temperature aleatoire ne corrigé pas une erreur de raisonnement.
Q77 (Structured Data Extraction) — Stratified sampling pour mesurer l'accuracy

Situation : votre rapport mensuel indique 97% d'accuracy globale. La direction veut deployer en production. Quelle precaution prendre avant ?

A) 97% est suffisant, deployer

B) Faire du stratified random sampling : analyser l'accuracy par document type ET par field. 97% global peut masquer 40% d'erreurs sur certains types (factures scannees) ou certains champs (numeros TVA)

C) Augmenter le seuil a 99% sans changer la mesure

D) Demander aux utilisateurs de rapporter les erreurs

Reponse : B) Stratified random sampling

Explication : les metriques agregees masquent des problèmes localises (D5 §5). Une accuracy de 97% en moyenne peut cacher des sous-catégories a 60% (factures manuscrites, champs date format US vs EU). L'analyse stratifiee par type ET par field detecte ces poches d'erreur avant qu'elles ne contaminent un cas critique en prod.

Pourquoi les autres sont faux :

  • A) Deploiement aveugle, risque eleve.
  • C) Rehausser le seuil sans diagnostic ne change pas le problème sous-jacent.
  • D) Detection reactive après impact, pas avant.
Q78 (Structured Data Extraction) — Validation conditionnelle JSON Schema

Situation : votre schéma extrait des transactions. Si type == "refund", alors les champs refund_reason et original_transaction_id sont obligatoires. Si type == "payment", ils ne servent a rien. Comment exprimer cela proprement ?

A) Mettre tous les champs dans required

B) Utiliser JSON Schema if/then : si type == "refund", alors required: ["refund_reason", "original_transaction_id"]

C) Documenter la regle dans la description du tool

D) Creer deux tools separes : extract_refund et extract_payment

Reponse : B) JSON Schema if/then

Explication : JSON Schema draft-07 supporte la validation conditionnelle if/then/else (D2 §4 (JSON Schema)). C'est le pattern propre quand des champs deviennent obligatoires selon une autre valeur. La contrainte est imposee par le schéma, donc deterministe.

Pourquoi les autres sont faux :

  • A) Force le modèle a fournir refund_reason même pour les payments — il l'inventera.
  • C) La description du tool guide le choix d'outil mais ne contraint pas la validation interne du schéma.
  • D) Acceptable si la logique etait plus complexe, mais ajoute un risque de misrouting (D2 §1) pour 2 schémas très proches. if/then reste plus simple ici.
