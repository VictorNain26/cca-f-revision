1. Stratégies d'examen

Format et règles

  • Format : QCM, 4 choix, 1 seule réponse correcte. Score de 100 à 1000, seuil de réussite : 720.
  • Pas de pénalité → répondre à TOUTES les questions, ne jamais laisser de blanc.
  • Méthode de lecture : lire la situation d'abord, identifier le concept testé, PUIS regarder les choix.

Distracteurs récurrents à éliminer

  • "Improve/strengthen the system prompt" → insuffisant quand il y a des conséquences financières ou légales (il faut du programmatic enforcement).
  • "Add a routing classifier" / "trained classifier" → overengineering par rapport à la solution demandée.
  • "Sentiment analysis" / "self-rated confidence" → unreliable proxy (le modèle peut être confident à tort).
  • "Abort the whole workflow" → disproportionné, on veut de la graceful degradation.
  • "Move blocking checks to Batch API" → latence inacceptable (jusqu'à 24h).
  • "Larger context window fixes attention" → faux, un context window plus grand n'améliore pas l'attention sur les sections centrales.

Q1 (Customer Support Agent) — Programmatic enforcement

Situation : Les données montrent que dans 12% des cas, l'agent saute l'appel à get_customer et appelle lookup_order en utilisant uniquement le nom du client, ce qui provoque des remboursements incorrects.

Question : Quelle approche résout le mieux ce problème ?

A) Ajouter une précondition programmatique avant lookup_order et process_refund

B) Ameliorer le system prompt pour insister sur l'importance de vérifier le client

C) Ajouter des few-shot examples montrant le bon ordre d'appel

D) Implementer un routing classifier pour diriger les requêtes

Réponse : A) Ajouter une précondition programmatique avant lookup_order et process_refund

Explication : Quand il y a des conséquences financières (remboursements incorrects), une solution deterministic est requise. Un contrôle programmatique — bloquant lookup_order et process_refund tant que get_customer n'a pas retourné un ID vérifié — garantit à 100% que l'ordre est respecté.

Pourquoi les autres sont faux :

  • B) Le system prompt est probabiliste — le modèle peut toujours l'ignorer dans 12% des cas.
  • C) Les few-shot examples ajoutent des tokens sans garantir le respect de l'ordre.
  • D) Un routing classifier adresse la disponibilite des outils, pas l'ordre d'exécution.
Q2 (Customer Support Agent) — Tool descriptions

Situation : L'agent appelle souvent get_customer au lieu de lookup_order. Les descriptions des outils sont minimales et similaires.

Question : Quelle est la meilleure façon de corriger la selection d'outils ?

A) Ajouter des few-shot examples

B) Enrichir la description de chaque outil avec les formats d'entree, des exemples et les limites d'utilisation

C) Ajouter une couche de routing

D) Fusionner les deux outils en un seul

Réponse : B) Enrichir la description de chaque outil avec les formats d'entree, des exemples et les limites d'utilisation

Explication : Les tool descriptions sont le mécanisme principal de selection d'outils. Des descriptions claires avec input formats, examples et boundaries permettent au modèle de distinguer précisement quand utiliser chaque outil.

Pourquoi les autres sont faux :

  • A) Les few-shot examples ajoutent des tokens sans corriger la cause racine (descriptions ambigues).
  • C) Un routing layer est du overengineering pour un problème de description.
  • D) Fusionner les outils demande plus d'effort que justifie et réduit la granularite.
Q3 (Customer Support Agent) — Escalation calibration

Situation : L'agent ne résout que 55% des cas (objectif : 80%). Il escalade les cas simples mais tente de gérer les cas complexes de manière autonome.

Question : Comment corriger la calibration de l'escalation ?

A) Ajouter des critères d'escalation explicites avec des few-shot examples

B) Utiliser un self-rated confidence score (1-10) avec escalation automatique sous un seuil

C) Entrainer un classifier séparé sur les données historiques

D) Utiliser le sentiment analysis pour détecter la frustration

Réponse : A) Ajouter des critères d'escalation explicites avec des few-shot examples

Explication : Le problème est que les frontières de décision sont floues. Des critères explicites + des exemples montrant quand escalader et quand résoudre corrigent directement ce problème.

Pourquoi les autres sont faux :

  • B) Le self-rated confidence est un unreliable proxy — le modèle peut être confidemment faux.
  • C) Un classifier entraîné est du overengineering pour ce problème.
  • D) Le sentiment analysis résout un problème différent (detection de frustration, pas calibration d'escalation).

C) Dans le fichier CLAUDE.md à la racine

Réponse : A) .claude/commands/ dans le repository du projet

Explication : Les project commands dans .claude/commands/ sont versionnées dans le VCS et automatiquement disponibles pour toute l'équipe. C'est l'emplacement prévu pour les commandes partagées.

Pourquoi les autres sont faux :

  • B) ~/.claude/commands/ est pour les commandes personnelles, pas partagées avec l'équipe.
  • C) Le CLAUDE.md racine sert aux instructions, pas à définir des commandes.
  • D) .claude/config.json n'est pas le mécanisme pour définir des commandes.
Q5 (Claude Code) — Planning mode

Situation : Il faut restructurer un monolithe en microservices (dizaines de fichiers, décisions sur les frontières de services).

Question : Quelle approche est la plus appropriée ?

A) Planning mode : explorer le codebase, comprendre les dépendances, concevoir l'approche

B) Execution directe, incrémentalement

C) Execution directe avec des instructions détaillées en amont

D) Execution directe et basculer en planning mode quand ça devient difficile

Réponse : A) Planning mode : explorer le codebase, comprendre les dépendances, concevoir l'approche

Explication : Les changements à grande échelle + multiples approches possibles + décisions architecturales = planning mode. Il faut comprendre avant d'agir.

Pourquoi les autres sont faux :

  • B) L'exécution directe incrémentale risque du rework massif sans vision d'ensemble.
  • C) Présuppose que la structure est connue à l'avance — ce n'est pas le cas.
  • D) Approche réactive : on découvre les problèmes trop tard.

A) Des fichiers dans .claude/rules/ avec YAML frontmatter et glob patterns

Explication : Les glob patterns dans le YAML frontmatter permettent un chargement conditionnel automatique selon les fichiers touchés. C'est le mécanisme conçu pour des règles cross-directory.

Pourquoi les autres sont faux :

  • B) Mettre tout dans le CLAUDE.md racine force le modèle à inférer quel contexte s'applique.
  • C) Les skills sont manuelles / on-demand, pas automatiques.
  • D) Un CLAUDE.md par répertoire ne fonctionne pas pour les fichiers dispersés (ex: tests co-localisés).

Pourquoi les autres sont faux :

  • A) La synthèse travaille sur ce qu'elle reçoit — elle ne peut pas inventer des domaines non recherchés.
  • C) Le web search a trouvé du contenu pour les sous-tâches assignées.
  • D) Il n'y a pas d'indication d'un filtrage excessif par le document analysis.
Q8 (Multi-Agent Research) — Error propagation

Situation : Le subagent de web search fait un timeout. Il faut concevoir la propagation d'erreur vers le coordinator.

Question : Quelle stratégie de gestion d'erreur est optimale ?

A) Retourner un contexte d'erreur structuré au coordinator

B) Retries automatiques avec exponential backoff puis message générique "search unavailable"

C) Intercepter le timeout et retourner un ensemble de résultats vide marqué comme succès

D) Propager l'exception au handler de niveau supérieur, terminant tout le workflow

Réponse : A) Retourner un contexte d'erreur structuré au coordinator

Explication : Un structured error context — incluant le type de failure, la query, les résultats partiels et des alternatives — donne au coordinator toute l'information nécessaire pour une intelligent recovery (retry partiel, source alternative, etc.).

Pourquoi les autres sont faux :

  • B) Les retries masquent le contexte — le coordinator ne sait pas pourquoi ça a échoué.
  • C) Masquer l'échec en succès est dangereux — la synthèse travaillera avec des données incomplètes sans le savoir.
  • D) Terminer tout le workflow est disproportionné pour un timeout partiel.
Q9 (Multi-Agent Research) — Synthesis vérification overhead

Situation : L'agent de synthèse doit souvent vérifier des affirmations. Le circuit actuel passe par coordinator → web-search → re-synthèse = 2-3 allers-retours supplémentaires, +40% de latence. 85% sont de simples fact checks, 15% nécessitent une investigation approfondie.

Question : Comment réduire cette latence ?

A) Donner à l'agent de synthèse un outil limité verify_fact pour les checks simples, router les complexes via le coordinator

B) Grouper toutes les vérifications à la fin

C) Donner à la synthèse un accès complet au web search

D) Mettre en cache proactivement du contexte supplémentaire

Réponse : A) Donner à l'agent de synthèse un outil limité verify_fact pour les checks simples, router les complexes via le coordinator

Explication : Principe de least privilege : 85% des cas sont simples → un outil direct et limité suffit. Les 15% complexes passent par le coordinator pour maintenir le contrôle.

Pourquoi les autres sont faux :

  • B) Grouper à la fin retarde la détection d'erreurs et peut nécessiter de refaire la synthèse.
  • C) Un accès complet au web search viole le principe de least privilege.
  • D) Le caching proactif est imprécis — on ne sait pas à l'avance quelles vérifications seront nécessaires.

Q11 (Claude Code for CI) — Batch API cost optimization

Situation : Deux workflows : un pre-merge check bloquant + un rapport de tech-debt nocturne. Le manager propose de mettre les deux sur la Batch API pour économiser 50%.

Question : Quelle est la bonne stratégie ?

A) Batch uniquement pour le tech-debt ; garder le pre-merge en synchrone

B) Les deux en batch avec polling

C) Les deux en synchrone

D) Les deux en batch avec fallback synchrone

Réponse : A) Batch uniquement pour le tech-debt ; garder le pre-merge en synchrone

Explication : La Batch API peut prendre jusqu'à 24h — c'est inacceptable pour un pre-merge check bloquant. Le rapport nocturne, lui, tolère cette latence.

Pourquoi les autres sont faux :

  • B) Le pre-merge bloquant ne peut pas attendre jusqu'à 24h.
  • C) Garder les deux en synchrone gaspille 50% d'économies sur le tech-debt.
  • D) Le fallback ne résout pas le problème de latence pour le pre-merge.
Q12 (Multi-file Code Review) — Multi-pass review

Situation : Une PR modifie 14 fichiers. La review en single-pass est inconsistante : détaillée pour certains fichiers, superficielle pour d'autres, avec des commentaires contradictoires.

Question : Comment obtenir une review consistante ?

A) Séparer en passes par fichier pour les problèmes locaux, puis une passe d'intégration pour les enjeux cross-file

B) Demander aux développeurs de découper les PRs en 3-4 fichiers

C) Passer à un modèle avec un context window plus grand

D) Trois passes indépendantes sur toute la PR, reporter le consensus

Réponse : A) Séparer en passes par fichier pour les problèmes locaux, puis une passe d'intégration pour les enjeux cross-file

Explication : Le multi-pass corrige la cause racine : l'attention dilution. Chaque passe se concentre sur un scope limité, puis la passe d'intégration couvre les interactions.

Pourquoi les autres sont faux :

  • B) Transfère la charge aux développeurs — ne résout pas le problème technique.
  • C) Un context window plus grand n'améliore pas l'attention — c'est une misconception.
  • D) Trois passes identiques sur 14 fichiers vont reproduire les mêmes biais et supprimer les vrais bugs par vote majoritaire.

3. Practice Test — Multi-Agent Research System (Q13-Q27)

Q13 (Multi-Agent Research) — Statistiques contradictoires

Situation : Deux sources crédibles rapportent des statistiques contradictoires (40% vs 12%) sur le même phénomène.

Question : Comment l'agent de synthèse doit-il traiter cette contradiction ?

A) Choisir la valeur la plus probable et ajouter une footnote

B) Présenter les deux sans signaler le conflit

C) S'arrêter et escalader au coordinator

D) Présenter les deux avec une conflict annotation et laisser le coordinator décider

Réponse : D) Présenter les deux avec une conflict annotation et laisser le coordinator décider

Explication : L'agent de synthèse ne doit pas prendre de décision éditoriale sur les données. Annoter le conflit et remonter au coordinator permet une décision informée.

Pourquoi les autres sont faux :

  • A) Choisir une valeur est une décision éditoriale qui dépasse le rôle de la synthèse.
  • B) Présenter sans signaler le conflit produit un rapport incohérent.
  • C) S'arrêter complètement est disproportionné — le travail peut continuer avec l'annotation.
Q14 (Multi-Agent Research) — Étape suivante après collecte

Situation : Les agents de web search et de doc analysis ont terminé leur travail. Quelle est l'étape suivante ?

Question : Comment les résultats doivent-ils être traités ?

A) Les agents envoient directement au report-writing

B) Le doc analysis fusionne les résultats en interne

C) Le coordinator transmet les deux ensembles de résultats à la synthèse

D) Concatener les sorties brutes

Réponse : C) Le coordinator transmet les deux ensembles de résultats à la synthèse

Explication : Le coordinator est le point central de l'orchestration. Il collecte les résultats de chaque subagent et les transmet à la synthèse pour intégration.

Pourquoi les autres sont faux :

  • A) La communication directe entre subagents contourne le coordinator et réduit l'observability.
  • B) Le doc analysis n'a pas la responsabilité de fusionner des résultats d'autres agents.
  • D) La concatenation brute ne produit pas une synthèse cohérente.
Q15 (Multi-Agent Research) — Recovery locale vs escalation

Situation : Le subagent de doc analysis échoue fréquemment sur les PDFs. Toute exception termine le subagent, ce qui implique une intervention excessive du coordinator.

Question : Quelle stratégie de gestion d'erreur adopter ?

A) Un agent dédié à la gestion d'erreurs

B) Toujours retourner un succès partiel

C) Le coordinator valide tous les documents en amont

D) Recovery locale pour les erreurs transitoires, escalation uniquement pour les erreurs irrécupérables

Réponse : D) Recovery locale pour les erreurs transitoires, escalation uniquement pour les erreurs irrécupérables

Explication : La distinction entre erreurs transitoires (retry local) et irrécupérables (escalation) réduit l'implication du coordinator aux cas qui le nécessitent vraiment.

Pourquoi les autres sont faux :

  • A) Un agent dédié aux erreurs est du overengineering.
  • B) Retourner toujours un succès partiel masque les vrais échecs.
  • C) Le coordinator ne devrait pas pré-valider chaque document — c'est le rôle du subagent.

Pourquoi les autres sont faux :

  • C) La logique de retry peut exister sans coordinator centralisé.
  • D) La sérialisation de mémoire est un détail d'implémentation, pas un avantage architectural.

B) Supprimer fetch_url et router via le coordinator

Pourquoi les autres sont faux :

  • B) Supprimer l'outil et passer par le coordinator ajoute de la latence inutile.

Q23 (Multi-Agent Research) — Duplication entre agents

Situation : Le web search et le doc analysis investigent les mêmes sous-thèmes, produisant des duplications.

A) Dedupliquer après coup

Réponse : B) Le coordinator partitionne l'espace de recherche avant de déléguer

Pourquoi les autres sont faux :

  • C) Un shared state entre subagents est complexe et réduit l'isolation.
  • D) L'exécution séquentielle augmente la latence sans résoudre la duplication.
Q24 (Multi-Agent Research) — Categories de sources

Situation : Trois catégories de sources : academic (15 articles), industry (0 résultats), patents (timeout).

Question : Comment interpréter ces résultats ?

A) Agréger comme 67% de couverture

B) Les deux échecs nécessitent une intervention

C) Retenter uniquement les transitoires

D) Distinguer le timeout (access failure) de l'ensemble vide (résultat valide)

Réponse : D) Distinguer le timeout (access failure) de l'ensemble vide (résultat valide)

Explication : Un timeout (patents) signifie que les données existent peut-être mais n'ont pas pu être récupérées — c'est un access failure. Un ensemble vide (industry) est un résultat valide : il n'y a pas de données. Les deux situations demandent des réponses différentes.

B) Continuer en API synchrone — le coût est secondaire ici

C) Utiliser un modèle moins capable

D) Réduire max_tokens

Réponse : A) Message Batches API

Explication : 50 000 docs/jour avec un SLA de 24h est le cas d'usage parfait du Batch API (D4 §5) : 50% d'économies, traitement asynchrone, custom_id pour corréler chaque réponse au document source. Pour les échecs, on resoumet uniquement les custom_id en échec.

Pourquoi les autres sont faux :

  • B) Ignore l'opportunité d'économie de 50% alors que la latence de 24h est déjà acceptée par le SLA.
  • C) Dégrade la qualité — les économies sur le modèle peuvent être annulées par les retries d'erreurs.
  • D) Tronque les réponses, ne réduit pas significativement le coût.
Q76 (Structured Data Extraction) — Retry-with-feedback sur erreur de validation

Situation : votre extraction sort un JSON valide syntaxiquement, mais la somme des line_items ne correspond pas au total annoncé sur la facture. Que faire ?

A) Accepter le JSON et corriger en aval

B) Retry avec une temperature plus haute

C) Ignorer l'incohérence et logger

D) Retry avec un nouveau prompt incluant : le document original + l'extraction précédente + l'erreur spécifique ("la somme des line_items est 487$ mais le total annoncé est 512$")

Réponse : D) Retry-with-feedback

Explication : le pattern retry-with-feedback (D4 §4.4) est efficace pour les erreurs de cohérence interne : on renvoie à Claude le document, sa première extraction, et l'erreur précise. Claude comprend ce qu'il a manqué (ligne oubliée, frais cachés) et corrige. C'est l'usage canonique de la self-correction.

Pourquoi les autres sont faux :

  • A) Disperse la vérification sémantique partout en aval — anti-pattern.
  • B) Une température aléatoire ne corrige pas une erreur de raisonnement — le modèle referait probablement la même erreur.
  • C) Laisse passer des données fausses qui contamineront l'ERP.
Q77 (Structured Data Extraction) — Stratified sampling pour mesurer l'accuracy

Situation : votre rapport mensuel indique 97% d'accuracy globale. La direction veut déployer en production. Quelle précaution prendre avant ?

A) 97% est suffisant, déployer

B) Demander aux utilisateurs de rapporter les erreurs qu'ils rencontrent

C) Augmenter le seuil à 99% sans changer la mesure

D) Faire du stratified random sampling : analyser l'accuracy par document type ET par field

Réponse : D) Stratified random sampling

Explication : les métriques agrégées masquent des problèmes localisés (D5 §5). Une accuracy de 97% en moyenne peut cacher des sous-catégories à 60% (factures manuscrites, champs date format US vs EU, numéros TVA). L'analyse stratifiée par type ET par field détecte ces poches d'erreur avant qu'elles ne contaminent un cas critique en prod.

Pourquoi les autres sont faux :

  • A) Déploiement aveugle, risque élevé.
  • B) Détection réactive après impact, pas avant — les utilisateurs ne remontent qu'une fraction des erreurs.
  • C) Rehausser le seuil sans diagnostic ne change pas le problème sous-jacent.
Q78 (Structured Data Extraction) — Validation conditionnelle JSON Schema

Situation : votre schéma extrait des transactions. Si type == "refund", alors les champs refund_reason et original_transaction_id sont obligatoires. Si type == "payment", ils ne servent à rien. Comment exprimer cela proprement ?

A) Mettre tous les champs dans required

B) Documenter la règle dans la description du tool

C) Utiliser JSON Schema if/then : si type == "refund", alors required: ["refund_reason", "original_transaction_id"]

D) Créer deux tools séparés : extract_refund et extract_payment

Réponse : C) JSON Schema if/then

Explication : JSON Schema draft-07 supporte la validation conditionnelle `if`/`then`/`else` (D2 §4 (JSON Schema)). C'est le pattern propre quand des champs deviennent obligatoires selon une autre valeur. JSON Schema `if/then/else` exprime l'intention, mais l'API **ne l'applique pas** (validation conditionnelle à faire côté application).

Pourquoi les autres sont faux :

  • A) Force le modèle à fournir refund_reason même pour les payments — il l'inventera.
  • B) La description du tool guide le choix d'outil mais ne contraint pas la validation interne du schéma.
  • D) Acceptable si la logique était plus complexe, mais ajoute un risque de misrouting (D2 §1) pour 2 schémas très proches. if/then reste plus simple ici.

9. Practice Test — Questions transversales (Q79-Q87)

Q79 (D1) — Task tool, allowedTools et context passing

Situation : le coordinateur d'un système multi-agents doit lancer trois recherches en parallèle sur des sujets différents, chacune confiée à un subagent de recherche isolé.

Question : quelle configuration respecte les bonnes pratiques du Task tool pour ce besoin ?

A) Émettre les trois appels Task l'un après l'autre dans des réponses séparées, pour garder le contrôle du flux

B) Donner à chaque subagent le même ensemble complet d'outils que le coordinateur, par simplicité

C) Laisser chaque subagent hériter implicitement du contexte de la conversation du coordinateur

D) Inclure "Task" dans allowedTools, émettre les trois appels Task dans une seule réponse, et transmettre à chaque subagent un contexte structuré (source, type de contenu, sujet)

Réponse : D) Task dans allowedTools + appels parallèles + contexte structuré

Explication : l'outil Task est le mécanisme de création de subagents ; allowedTools doit l'inclure. Plusieurs appels Task dans une seule réponse s'exécutent en parallèle. Le context passing doit utiliser des formats structurés séparant les données des métadonnées (D1 §5, Task 1.3).

Pourquoi les autres sont faux :

  • A) Des appels séquentiels fonctionnent mais perdent le bénéfice de l'exécution parallèle.
  • B) Chaque subagent doit avoir un accès scoped aux seuls outils pertinents à son rôle (principe du moindre privilège, D2 §3) — pas hérité du coordinateur.
  • C) Les subagents ont un contexte isolé : rien n'est hérité automatiquement, le context passing doit toujours être explicite.
Q80 (D1) — Prompt chaining vs dynamic decomposition

Situation : vous devez concevoir un agent qui explore un codebase legacy inconnu pour identifier les modules sans tests et proposer un plan de couverture, sans savoir à l'avance combien de modules existent ni leurs dépendances.

Question : quelle stratégie de décomposition est la mieux adaptée ?

A) La multi-pass review en deux passes (per-file puis intégration), pensée pour les grosses pull requests

B) Fixed pipeline (prompt chaining) avec des étapes définies et exécutées dans un ordre fixe à l'avance

C) Dynamic adaptive decomposition : mapper la structure via Glob/Grep, découvrir les modules non testés, puis adapter les priorités et les étapes suivantes selon les découvertes

D) Un unique prompt exhaustif qui énumère par avance toutes les étapes possibles de l'investigation

Réponse : C) Dynamic adaptive decomposition

Explication : le prompt chaining convient aux tâches prévisibles et répétables (review, migration) ; la dynamic decomposition convient aux investigations ouvertes où les sous-tâches émergent des résultats intermédiaires — exactement le cas d'un codebase legacy inconnu (D1 §4, Task 1.6).

Pourquoi les autres sont faux :

  • A) La multi-pass review est une technique différente, conçue pour les grosses PR (per-file + intégration), pas pour explorer un codebase legacy.
  • B) Le prompt chaining convient aux tâches prévisibles et répétables, pas à une investigation dont le périmètre est inconnu au départ.
  • D) Un plan figé à l'avance ne peut pas anticiper les surprises (dépendances non mockées, couverture partielle) découvertes en cours d'investigation.
Q81 (D1) — --resume vs fork_session vs nouvelle session

Situation : vous reprenez une investigation démarrée hier. Depuis, exactement deux fichiers du module concerné ont été modifiés, le reste du codebase est inchangé.

Question : quelle est l'approche recommandée ?

A) Nouvelle session, avec un résumé structuré injecté résumant les découvertes précédentes

B) --resume, en informant explicitement l'agent des fichiers précisément modifiés pour une ré-analyse ciblée

C) fork_session, pour comparer deux approches d'investigation en parallèle

D) --resume sans mention des fichiers modifiés, en laissant l'agent redécouvrir seul les changements

Réponse : B) --resume en informant des fichiers modifiés

Explication : quand un nombre limité de fichiers précis ont changé et que le reste du contexte reste valide, la recommandation est --resume en informant explicitement l'agent des fichiers modifiés, pour une ré-analyse ciblée plutôt qu'une ré-exploration complète (D1 §7, Task 1.7).

Pourquoi les autres sont faux :

  • A) Une nouvelle session est recommandée quand les tool results sont obsolètes de façon étendue ou incertaine, ou quand le contexte s'est dégradé avec le temps — pas ici, où seuls deux fichiers précis ont changé.
  • C) fork_session sert à comparer deux approches divergentes à partir d'un point commun, pas à reprendre après une modification ciblée.
  • D) Reprendre sans préciser les fichiers modifiés force l'agent à redécouvrir seul les changements, ce qui gaspille des tokens alors que l'information est déjà connue.
Q82 (D2) — tool_choice : auto, any, forced selection

Situation : un pipeline d'extraction doit toujours appeler extract_metadata en premier, avant tout autre traitement, quel que soit le document.

Question : quelle configuration de tool_choice impose ce comportement ?

A) {"type": "auto"} — Claude décide librement d'appeler un outil ou de répondre en texte

B) {"type": "any"} — Claude doit appeler un outil, mais choisit lequel

C) {"type": "tool", "name": "extract_metadata"} — Claude doit appeler précisément cet outil

D) {"type": "none"} — Claude ne peut appeler aucun outil

Réponse : C) Forced selection sur extract_metadata

Explication : la forced selection ({"type": "tool", "name": "..."}) garantit une première action spécifique avant le reste du workflow — utile pour imposer un ordre d'exécution, exactement l'exemple extract_metadata avant l'enrichissement donné dans le guide (D2 §3, Task 2.3).

Pourquoi les autres sont faux :

  • A) auto laisse Claude libre de choisir un autre outil en premier, ou aucun.
  • B) any garantit qu'un outil sera appelé, mais pas lequel — n'impose pas extract_metadata spécifiquement.
  • D) none désactive tout appel d'outil, ce qui empêche même extract_metadata d'être appelé.
Q83 (D2) — MCP resources vs tools vs prompts

Situation : votre application a besoin d'afficher dans l'interface la liste des tables d'une base de données pour que l'utilisateur choisisse la bonne avant de lancer une requête. Cette liste ne doit pas nécessiter d'action de la part du modèle.

Question : quelle primitive MCP est adaptée à ce besoin ?

A) tools, car c'est la primitive qui expose le plus de fonctionnalités

B) prompts, en définissant un workflow prédéfini déclenché par une commande slash

C) sampling, en demandant au client de générer la liste via son LLM

D) resources, car cette primitive est contrôlée par l'application et fournit des données en lecture comme un content catalog

Réponse : D) resources

Explication : les resources sont contrôlées par l'application (pas le modèle) et servent à fournir des données en lecture ; elles sont particulièrement utiles pour exposer des catalogues de contenu comme des schémas de base de données (D2 §4, Task 2.4).

Pourquoi les autres sont faux :

  • A) tools est contrôlé par le modèle et sert à exécuter des actions (CRUD, appel API) — pas à fournir un catalogue en lecture piloté par l'application.
  • B) prompts est contrôlé par l'utilisateur et sert à définir des workflows prédéfinis, pas à afficher des données de contexte.
  • C) sampling permet au serveur de demander une génération de texte au client, sans rapport avec l'exposition d'un catalogue de données.
Q84 (D2) — Glob vs Grep pour tracer des appelants ré-exportés

Situation : vous devez retrouver tous les appelants d'une fonction analyzeDocument qui est ré-exportée sous plusieurs alias à travers le codebase.

Question : quelle méthode est correcte ?

A) D'abord Grep tous les noms exportés de la fonction (alias et re-exports), puis Grep chacun de ces noms pour retrouver les appelants

B) Un seul Grep du nom d'origine analyzeDocument

C) Glob **/*.ts pour lister tous les fichiers du projet, puis les lire un par un avec Read

D) Glob avec analyzeDocument comme pattern de recherche de fichier

Réponse : A) Grep exports puis Grep chaque alias

Explication : un seul Grep du nom d'origine rate les appels indirects faits via un alias importé. La méthode correcte : d'abord Grep tous les noms exportés (alias et re-exports), puis Grep chacun de ces noms pour retrouver les appelants (D2 §5, Task 2.5).

Pourquoi les autres sont faux :

  • B) Rate les appels effectués via un alias importé — c'est exactement le piège identifié par le guide.
  • C) Glob trouve des fichiers par nom/pattern, pas du contenu ; lire tous les fichiers un par un surcharge le contexte inutilement.
  • D) Glob ne cherche pas dans le contenu des fichiers — il ne retournera aucun fichier nommé analyzeDocument, sauf coïncidence de nom de fichier.
Q85 (D5) — Structured handoff vers un opérateur humain

Situation : un agent de support client escalade un cas vers un opérateur humain qui n'a pas accès au transcript complet de la conversation.

Question : que doit contenir le message transmis à l'opérateur ?

A) Un message court : "Ce client demande à parler à un responsable."

B) Un structured handoff complet : identifiant client, résumé du problème, actions déjà tentées, raison de l'escalade — tout ce qu'il faut pour reprendre le cas sans relire le transcript

C) Le transcript brut intégral de la conversation, sans mise en forme

D) Rien de spécifique — l'opérateur rappelle le client pour reconstituer le contexte

Réponse : B) Structured handoff complet

Explication : le résumé transmis à l'opérateur humain doit inclure tout ce qui est nécessaire pour reprendre le cas sans relire le transcript — un protocole complet (customer_id, issue_summary, actions_taken, escalation_reason...), pas un simple message d'escalation (D5 §2, Task 5.2 ; D1 §6, Tasks 1.4/1.5).

Pourquoi les autres sont faux :

  • A) Un message minimal ne transmet ni le contexte ni les actions déjà tentées — l'opérateur devra tout redemander au client.
  • C) Le transcript brut n'est pas structuré ; l'opérateur doit le relire en entier pour en extraire les informations utiles, ce que le structured handoff évite justement.
  • D) Rappeler le client pour reconstituer le contexte dégrade l'expérience et fait perdre le travail déjà réalisé par l'agent.
Q86 (D5) — scratchpad, /compact et manifest.json

Situation : un système multi-agents tourne depuis plusieurs heures. Chaque subagent maintient son propre état, et vous voulez pouvoir reprendre le workflow exactement là où il s'est arrêté en cas de crash, sans relancer les tâches déjà terminées.

Question : quel mécanisme est spécifiquement conçu pour ce besoin de crash recovery ?

A) Un fichier scratchpad, dans lequel chaque subagent note ses découvertes clés

B) La commande /compact, pour résumer l'historique de conversation avant le crash

C) manifest.json, maintenu par le coordinateur, qui résume l'état global (completed / in_progress / not_started) de chaque subagent

D) Relancer l'intégralité du workflow depuis le début après chaque crash

Réponse : C) manifest.json

Explication : manifest.json est le pattern recommandé pour le crash recovery dans les workflows multi-agents longs. Chaque subagent écrit son propre fichier d'état ; le coordinateur maintient le manifeste global. Ce pattern est distinct du scratchpad, qui protège le contexte d'un agent unique (D5 §4, Task 5.4).

Pourquoi les autres sont faux :

  • A) Le scratchpad protège le contexte d'un agent unique contre la dégradation — ce n'est pas un mécanisme de coordination multi-agents ni de crash recovery.
  • B) /compact résume l'historique de conversation pour libérer du contexte, mais ne persiste pas d'état structuré permettant de savoir où en est chaque subagent.
  • D) Relancer tout le workflow gaspille les tâches déjà complétées — exactement ce que manifest.json permet d'éviter.
Q87 (D5) — Données temporelles dans le claim-source mapping

Situation : un agent de synthèse multi-sources rapporte : « Source A dit que la part de musique générée par IA sur le streaming est de 10%. Source B dit 15%. Contradiction. » Source A date de 2023, Source B de 2024, mais ces dates n'apparaissent pas dans le rapport.

Question : quel est le problème et comment le corriger ?

A) Choisir arbitrairement la valeur de la source la plus récente (Source B, 15%) et ignorer Source A

B) Ne rien changer : une divergence de 5 points est de toute façon dans la marge d'erreur habituelle

C) Fusionner les deux valeurs en une moyenne (12,5%) pour présenter un chiffre unique au lecteur

D) Inclure la date de chaque source dans le claim-source mapping — "Source A (2023) dit 10%, Source B (2024) dit 15%" peut révéler une croissance plutôt qu'une contradiction

Réponse : D) Inclure les dates dans le claim-source mapping

Explication : sans les dates, des différences temporelles peuvent être interprétées à tort comme des contradictions. "10% en 2023 + 15% en 2024 = growth, pas contradiction." Toujours inclure les dates dans les claim-source mappings (D5 §6, Task 5.6).

Pourquoi les autres sont faux :

  • A) Choisir arbitrairement une source revient à perdre l'attribution de l'autre — le guide recommande de préserver les deux valeurs avec leur date, pas de trancher au hasard.
  • B) Une marge d'erreur « habituelle » n'est pas un concept du guide — sans date, on ne peut même pas savoir si c'est une erreur ou une évolution réelle.
  • C) Fusionner en une moyenne invente une donnée qui n'existe dans aucune source et détruit l'attribution individuelle de chaque claim.
