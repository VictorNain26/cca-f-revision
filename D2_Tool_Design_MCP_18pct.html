1. Concevoir des interfaces d'outils claires (Task 2.1)

Le problème que cela résout

Quand Claude dispose de plusieurs outils aux fonctions proches, il choisit lequel appeler en se basant principalement sur la description de chaque outil. Si deux descriptions se ressemblent trop, Claude confond les outils — c'est le misrouting. Par exemple, si analyze_content est décrit comme "analyzes content and extracts key information" et analyze_document comme "analyzes documents and extracts key information", Claude les confondra fréquemment — dans le scénario d'examen associé, 45 % des requêtes étaient mal routées (chiffre illustratif propre à ce scénario, pas une constante générale du taux de misrouting).

Règle fondamentale : la description d'un outil est le mécanisme principal de sélection qu'un LLM utilise pour décider quel outil appeler. Des descriptions vagues ou redondantes entraînent un misrouting systématique.

L'anatomie d'une bonne description

Une description efficace répond à quatre questions :

  • Que fait l'outil et que retourne-t-il ?
  • Quels formats d'entrée accepte-t-il ? (avec des valeurs d'exemple dans input_schema)
  • Quels sont les edge cases et les contraintes ?
  • Quand utiliser cet outil plutôt qu'un autre similaire ?

Exemple concret

{
  "name": "get_customer",
  "description": "Finds a customer by email or ID. Returns the customer
    profile including name, email, order history, and account status.
    Use this tool BEFORE lookup_order to verify the customer's identity.
    Accepts an email (format: user@domain.com) or a numeric customer_id.",
  "input_schema": {
    "type": "object",
    "properties": {
      "email": {"type": "string", "description": "Customer email"},
      "customer_id": {"type": "integer", "description": "Numeric customer ID"}
    },
    "required": []
  }
}

Comment résoudre le misrouting

ProblèmeSolution
Deux outils aux descriptions similaires (chevauchement sémantique)Renommer pour lever l'ambiguïté : analyze_content → extract_web_results, et mettre à jour la description
Un outil générique utilisé hors de son périmètreRemplacer par un outil contraint : fetch_url → load_document (qui valide le format de l'URL)
Un outil « fourre-tout » trop largeDiviser en outils spécialisés : analyze_document → extract_data_points + summarize_content
Piège courant — system prompt et associations involontaires : le system prompt peut créer des associations non désirées avec les outils. Par exemple, l'instruction "always verify the customer" dans le system prompt pousse Claude à appeler get_customer même pour des requêtes qui ne nécessitent pas de vérification d'identité. L'examen teste votre capacité à identifier cette cause racine : un wording mal calibré dans le system prompt peut provoquer du misrouting autant que des descriptions vagues.

Outils intégrés vs outils MCP

Les agents ont tendance à préférer les outils intégrés (Read, Grep) aux outils MCP offrant des fonctionnalités proches. Pour contrer cette tendance, renforcez les descriptions des outils MCP en soulignant les avantages concrets qu'ils offrent par rapport aux outils intégrés : données exclusives, contexte spécifique, ou fonctionnalités que les outils intégrés ne couvrent pas.

2. Les réponses d'erreur structurées en MCP (Task 2.2)

Le problème que cela résout

Quand un outil MCP échoue, l'agent doit prendre une décision de récupération : faut-il faire un retry ? Modifier la requête ? Escalader vers un humain ? Si l'erreur retournée est un simple "Operation failed", l'agent ne dispose d'aucune information pour faire ce choix. Il faut donc des erreurs structurées qui indiquent le type d'erreur, sa cause probable et les actions possibles.

Ce que doit contenir une bonne erreur

{
  "isError": true,
  "content": [
    {
      "type": "text",
      "text": "errorCategory: transient | isRetryable: true | Service temporairement indisponible. Timeout sur l'API commandes. | attempted_query: order_id=12345"
    }
  ]
}

Dans un CallToolResult MCP, content est toujours un tableau de content blocks (jamais un objet ni une string). Les champs errorCategory/isRetryable ne font pas partie de la spécification MCP : c'est une convention de conception applicative, à encoder dans le texte du bloc text (ou en JSON stringifié dans ce texte), pas des champs officiels du protocole.

Anti-pattern — erreur générique : {"isError": true, "content": "Operation failed"}. L'agent ne peut pas décider s'il doit faire un retry, reformuler la requête ou escalader. Ce type d'erreur générique empêche toute récupération intelligente. C'est le principal anti-pattern testé à l'examen.

Les quatre catégories d'erreurs

errorCategoryExemplesisRetryableAction de l'agent
transientTimeout, erreur 503, panne réseautrueRetry avec backoff exponentiel
validationEntrée invalide, champ requis manquanttrue (après correction)Corriger l'entrée et retenter
businessViolation de politique, seuil dépasséfalseExpliquer à l'utilisateur, proposer une alternative
permissionAccès refusé, privilège insuffisantfalseEscalader à un humain
Distinction fondamentale : un échec d'accès (timeout — le serveur n'a pas répondu) est très différent d'un résultat vide valide (la requête a réussi, mais il n'y a aucune correspondance). Le premier nécessite une décision de retry ; le second est une information utile en soi. Les deux doivent être clairement distingués dans la réponse du tool_use.
Pattern complémentaire — local error recovery dans les subagents : un subagent ne doit pas propager au coordinateur chaque erreur MCP individuelle. Il tente une récupération locale (1-2 retries sur les erreurs transient), et ne remonte que les erreurs irrécupérables — avec les résultats partiels déjà obtenus et la requête tentée (attempted_query). Détail complet et exemple de payload : voir D5 §3 (Task 5.3, « La propagation d'erreurs dans les systèmes multi-agents »), qui traite explicitement ce pattern comme complément de D1 (hub-and-spoke) et D2 (erreurs structurées MCP).

3. Distribuer les outils entre agents et configurer tool_choice (Task 2.3)

Le problème que cela résout

Si vous donnez 18 outils à un seul agent, sa capacité à choisir le bon outil chute significativement. Pire : un agent disposant d'outils hors de sa spécialisation aura tendance à les utiliser à mauvais escient. Le principe est simple : chaque agent ne reçoit que les outils pertinents pour son rôle, idéalement 4 à 5 maximum, plus un ensemble restreint d'utilitaires transversaux si nécessaire.

Scoped tool access et principe du moindre privilège

Chaque subagent dans une architecture hub-and-spoke doit disposer d'un accès limité aux outils (scoped tool access). Cela évite qu'un agent utilise un outil hors de son périmètre. Exemple classique : un document analysis subagent qui dispose d'un outil générique fetch_url finit par télécharger des pages de moteurs de recherche au lieu de documents. La solution : remplacer fetch_url par load_document, un outil contraint qui valide que les URLs pointent vers des formats document.

Principe clé : plutôt que de restreindre le comportement via des instructions dans le prompt, remplacez les outils génériques par des alternatives contraintes au niveau de l'interface. Les contraintes au niveau de l'outil sont plus fiables que les instructions textuelles.

Le paramètre tool_choice

Ce paramètre contrôle la manière dont Claude sélectionne les outils :

ValeurComportementQuand l'utiliser
{"type": "auto"}Claude décide librement : texte ou appel d'outilMode par défaut, convient à la majorité des cas
{"type": "any"}Claude doit appeler un outil (mais choisit lequel)Pour garantir un appel d'outil quand plusieurs schémas existent
{"type": "tool", "name": "..."}Claude doit appeler un outil précis (forced selection)Pour forcer un ordre d'exécution (ex. : extract_metadata avant l'enrichissement)
{"type": "none"}Claude ne peut appeler aucun outil, réponse texte uniquementPour désactiver temporairement l'usage d'outils sans retirer leur définition

disable_parallel_tool_use: true (au sein de l'objet tool_choice) force Claude à n'appeler qu'un seul outil à la fois, quel que soit le type choisi.

Pour l'examen : tool_choice avec {"type": "any"} garantit qu'un outil sera appelé, pas que sa sortie respecte le schéma (il faut strict: true pour ça, cf. §4b). La forced selection ({"type": "tool", "name": "..."}) garantit une première action spécifique avant le reste du workflow — utile pour imposer un ordre d'exécution.

4. Intégrer des MCP servers dans Claude Code (Task 2.4)

Le problème que cela résout

L'approche traditionnelle d'intégration d'outils oblige les développeurs à écrire manuellement des schémas et des fonctions pour chaque outil. Le Model Context Protocol (MCP) résout ce problème en déplaçant la définition et l'exécution des outils vers des serveurs dédiés. Quelqu'un d'autre crée les outils, les empaquète dans un MCP server, et votre application s'y connecte automatiquement.

La portée des MCP servers

PortéeFichier de configurationPartageUsage
Projet.mcp.json (à la racine du projet)Versionné dans le VCS, partagé avec l'équipeIntégrations standards du projet
Utilisateur~/.claude.jsonPersonnel, non versionnéExpérimentations, serveurs personnels

La gestion des secrets par substitution de variables d'environnement

Les tokens d'accès ne doivent jamais être commités dans le dépôt. Utilisez la substitution de variables d'environnement dans .mcp.json :

{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}

La syntaxe ${VARIABLE_NAME} est résolue au lancement. Chaque développeur fournit ses propres credentials via ses variables d'environnement locales, ce qui permet de versionner .mcp.json sans exposer de secrets.

Anti-pattern (in-scope) : stocker un token en clair dans .mcp.json versionne. Même si vous le supprimez plus tard, l'historique Git le conserve indéfiniment. Toujours passer par ${VAR} ou par le user-level ~/.claude.json non versionne.

Les trois primitives MCP

MCP expose trois types de primitives, chacune contrôlée par un acteur différent :

PrimitiveContrôlée parObjectifQuand l'utiliser
toolsLe modèle (Claude)Ajouter des capacités d'actionClaude doit exécuter une opération (CRUD, appel API)
resourcesL'applicationFournir des données en lectureL'application a besoin de données pour l'interface ou le prompt
promptsL'utilisateurDéfinir des workflows prédéfinisL'utilisateur déclenche une action (bouton, commande slash)
resources comme « content catalogs » : les resources sont particulièrement utiles pour exposer des catalogues de contenu (schémas de base de données, listes de tâches, hiérarchies de navigation). Elles réduisent le nombre d'appels de tools exploratoires en fournissant directement les données de contexte dont l'application a besoin.

Choix entre community servers et custom servers

Pour les intégrations standards (Jira, GitHub, Slack), préférez les community servers existants. Ne construisez un custom server que pour les workflows spécifiques à votre équipe que personne d'autre n'a implémentés. Tous les tools de tous les serveurs connectés sont découverts à la connexion et disponibles simultanément.

JSON Schema en profondeur (input_schema)

Le input_schema d'un outil utilise un sous-ensemble standard de JSON Schema — la documentation Anthropic ne s'engage sur aucun draft par défaut précis (elle ne mentionne ni 2020-12 ni draft-07, seulement « standard JSON Schema with limitations »). Au-delà de type, properties et required déjà vus en D0, plusieurs constructions avancées apparaissent dans les questions d'examen.

Types complexes (oneOf, anyOf, allOf)

OpérateurSémantiqueCas d'usage
oneOfDoit valider exactement un sous-schémaDiscriminated union : email OU id_client, jamais les deux
anyOfDoit valider au moins un sous-schémaAcceptation flexible : string OU array de strings
allOfDoit valider tous les sous-schémasComposition de contraintes (extension de schéma de base)
// Exemple oneOf : recherche par email OU par ID, pas les deux
{
  "name": "find_customer",
  "description": "Find a customer by email or numeric ID. Provide exactly one.",
  "input_schema": {
    "type": "object",
    "oneOf": [
      {
        "properties": { "email": { "type": "string", "format": "email" } },
        "required": ["email"]
      },
      {
        "properties": { "customer_id": { "type": "integer", "minimum": 1 } },
        "required": ["customer_id"]
      }
    ]
  }
}

Validation conditionnelle (if/then/else)

// Si type == "refund", alors amount et reason sont obligatoires
{
  "type": "object",
  "properties": {
    "type": { "enum": ["refund", "info_only"] },
    "amount": { "type": "number" },
    "reason": { "type": "string" }
  },
  "required": ["type"],
  "if":   { "properties": { "type": { "const": "refund" } } },
  "then": { "required": ["amount", "reason"] }
}

Contraintes par type

TypeContraintesExemple
stringminLength, maxLength, pattern (regex), format (email, uri, date, date-time, uuid)"format": "email" rejette les strings invalides
number / integerminimum, maximum, exclusiveMinimum, multipleOf"minimum": 0, "maximum": 1000
arrayitems (schéma des éléments), minItems, maxItems, uniqueItemsListe non vide d'IDs uniques
objectrequired, additionalProperties (false pour rejeter champs inconnus)"additionalProperties": false = strict
EXAM TIP : "additionalProperties": false sur un objet rejette tout champ non déclaré dans properties — mais seulement si le tool est déclaré avec strict: true (top-level). strict: true exige additionalProperties: false sur chaque objet, mais pas que toutes les propriétés soient listées dans required — les propriétés optionnelles restent autorisées. En revanche, plusieurs contraintes du tableau ci-dessus sont incompatibles avec strict: true (erreur 400 si présentes) : minLength, maxLength, minimum, maximum, multipleOf, ainsi que maxItems (seul minItems avec la valeur 0 ou 1 est supporté) ; pattern n'est que partiellement supporté (regex simple, sans lookahead ni backreference). Sans strict: true, l'API Claude ne garantit pas la conformité au JSON Schema : le modèle peut techniquement produire des champs hallucinés. Pour du JSON structuré fiable, préférer output_config: {"format": {"type": "json_schema", ...}}.

Champs nullable et enums avec fallback (rappel D0 + extension)

{
  "company_name": {
    "type": ["string", "null"],
    "description": "Company name if mentioned, null otherwise"
  },
  "category": {
    "type": "string",
    "enum": ["billing", "technical", "account", "other"]
  },
  "category_detail": {
    "type": ["string", "null"],
    "description": "Free-text detail when category is 'other'"
  },
  "sentiment": {
    "type": "string",
    "enum": ["positive", "negative", "neutral", "unclear"]
  }
}
3 piliers d'un input_schema robuste :
  1. Nullable sur les champs non garantis (au lieu de required) — évite l'hallucination
  2. Enum avec "other" + champ détail — capture les cas inattendus sans perte d'information
  3. Enum avec "unclear" — permet au modèle d'exprimer son incertitude honnêtement
Ces 3 patterns transforment un schéma rigide en interface tolérante à l'incertitude.

Validation côté application (après réception)

Sans strict: true, l'API Claude ne garantit même pas la conformité syntaxique stricte au JSON Schema (respect d'additionalProperties: false compris) — encore moins la cohérence sémantique. Après réception, valider dans tous les cas :

  • Cohérence inter-champs : totaux qui s'additionnent, dates dans l'ordre chronologique
  • Existence des références : les IDs pointent vers des entités réelles
  • Plages métier : un montant négatif est syntaxiquement valide mais business-invalide

Voir D4 §4 pour le pattern retry-with-feedback : en cas d'échec de validation, renvoyer l'erreur à Claude pour qu'il corrige.

5. Les outils intégrés de Claude Code (Task 2.5)

Le problème que cela résout

Claude Code dispose d'outils intégrés pour interagir avec le système de fichiers et le terminal. Bien les connaître évite de créer des outils MCP redondants et permet une investigation efficace du code.

Référence de sélection

TâcheOutilExemple
Trouver des fichiers par nom ou patternGlob**/*.test.tsx, src/components/**/*.ts
Chercher dans le contenu des fichiersGrepUn nom de fonction, un message d'erreur, un import
Lire un fichier en entierReadCharger un fichier pour l'analyser
Créer un nouveau fichierWriteEcrire un fichier depuis zéro
Modifier précisément un fichier existantEditRemplacer un extrait via une correspondance de texte unique
Exécuter une commande shellBashgit, npm, tests, build
Fallback Read + Write : quand Edit échoue parce que le texte à remplacer n'est pas unique dans le fichier, la solution de repli est Read (charger le fichier complet) → modifier le contenu → Write (réécrire le fichier entier).

Tracer les ré-exports : la bonne approche Grep

Quand vous cherchez tous les appelants d'une fonction qui est ré-exportée à travers plusieurs wrappers (alias), un seul Grep du nom d'origine rate les appels indirects. Méthode correcte : d'abord Grep tous les noms exportés de la fonction (les aliases et re-exports) dans le codebase, puis Grep chacun de ces noms pour retrouver les appelants. (Source : guide officiel, Task 2.5, Skills.)

// Mauvais : un seul Grep du nom original
Grep "analyzeDocument"  // rate les appels via l'alias importé

// Bon : 2 passes
1. Grep "export.*analyzeDocument"      // trouve tous les noms exportés
   → "export { analyzeDocument }"      → "export { analyzeDocument as analyze }"
   → "export { analyzeDocument as doc }"
2. Grep chaque alias : "analyzeDocument | analyze | doc"  // capture tous les appelants

La stratégie d'investigation incrémentale

Plutôt que de lire tous les fichiers d'un coup, construisez votre compréhension progressivement :

  1. Grep : identifier les points d'entrée (définitions de fonctions, exports).
  2. Read : lire les fichiers identifiés.
  3. Grep : trouver les usages (imports, appels).
  4. Read : lire les fichiers consommateurs.
  5. Répéter jusqu'à avoir une vue complète.
Pour l'examen : cette stratégie incrémentale (Grep → Read → Grep → Read) est la méthode recommandée pour explorer un codebase inconnu. Elle évite de surcharger le contexte en ne lisant que les fichiers pertinents.

6. Synthèse — les points clés

Conception d'outils

  • La description est le mécanisme n° 1 de sélection par le LLM. Des descriptions vagues = misrouting.
  • Renommer, diviser ou remplacer les outils pour éliminer les chevauchements sémantiques.
  • Attention aux associations involontaires créées par le system prompt.
  • Spécifier les formats d'entrée dans input_schema avec des exemples et documenter les edge cases.

Erreurs structurées

  • Toujours retourner isError (champ de la spec) et, en convention applicative encodée dans le bloc text, errorCategory (transient / validation / business / permission) et isRetryable.
  • Distinguer un échec d'accès (timeout) d'un résultat vide valide (zéro correspondance).
  • Les erreurs génériques ("Operation failed") empêchent toute récupération intelligente — c'est l'anti-pattern principal.

Distribution et tool_choice

  • 4 à 5 outils max par agent, pas 18. Chaque agent ne reçoit que les outils pertinents pour son rôle (scoped tool access).
  • Remplacer les outils génériques par des alternatives contraintes (fetch_url → load_document).
  • auto (par défaut) / any (garantir un appel d'outil) / forced selection (imposer un outil précis).

MCP

  • .mcp.json pour le projet (versionne dans le VCS), ~/.claude.json pour l'utilisateur (personnel).
  • Substitution de variables d'environnement (${GITHUB_TOKEN}) pour les secrets.
  • Trois primitives : tools (modèle), resources (application), prompts (utilisateur).
  • resources = « content catalogs » qui réduisent les appels exploratoires.
  • Préférer les community servers pour les intégrations standards ; custom servers pour les workflows spécifiques.

JSON Schema (input_schema)

  • oneOf (exactement un sous-schéma) / anyOf (au moins un) / allOf (tous).
  • Validation conditionnelle if/then/else pour les exigences contextuelles.
  • Contraintes : format (email, uri, uuid), minLength/maxLength, minimum/maximum, pattern (regex).
  • "additionalProperties": false pour rejeter les champs hallucinés.
  • Sous strict: true : additionalProperties: false obligatoire, propriétés optionnelles permises (pas besoin que tout soit dans required) — mais minLength/maxLength/minimum/maximum/multipleOf/maxItems non supportés (400), seul minItems (0/1) l'est.
  • 3 piliers anti-hallucination : nullable, enum + "other"/détail, enum + "unclear".
  • Sans strict: true, le tool_use ne garantit ni la conformité syntaxique stricte au schéma ni la sémantique ; valider les deux côté app (retry-with-feedback, voir D4).

Authentification MCP

  • In-scope : variables d'env (${VAR} dans env, stdio) — seul pattern couvert par le guide.
  • Anti-pattern absolu (in-scope) : token en clair dans .mcp.json versionné (l'historique Git le retient).

Outils intégrés

  • Glob (fichiers par pattern), Grep (contenu), Read/Write (fichier entier), Edit (modification ciblée), Bash (commandes).
  • Edit échoue → fallback Read + Write.
  • Investigation incrémentale : Grep → Read → Grep usages → Read consommateurs.

7. Questions d'auto-evaluation

Q1 : Les logs montrent que les requêtes "analyze the uploaded quarterly report" sont routées vers le web-search agent 45 % du temps au lieu du document analysis agent. Les outils disponibles sont analyze_content (agent web-search) et analyze_document (agent document analysis). Leurs descriptions sont "analyzes content and extracts key information" et "analyzes documents and extracts key information". Comment corriger ?
A) Ajouter un pre-routing classifier.
B) Renommer le web-search tool en extract_web_results et mettre à jour sa description.
C) Ajouter des few-shot examples au coordinateur.
D) Enrichir seulement la description du document analysis tool.

Réponse : B

Le problème est un chevauchement sémantique entre les deux descriptions. Renommer le web-search tool en extract_web_results avec une description différenciée élimine l'ambiguïté à la racine. Les options A et C ajoutent de la complexité sans traiter la cause. L'option D n'élimine pas le chevauchement côté web-search.

Q2 : Un document analysis subagent a un outil générique fetch_url. Les logs montrent qu'il télécharge des pages de moteurs de recherche au lieu de documents. Quel fix appliquer ?
A) Remplacer fetch_url par load_document qui valide les URLs vers des formats document.
B) Retirer fetch_url et router via le coordinateur.
C) Filtrer les domaines de moteurs de recherche.
D) Ajouter des instructions dans le prompt.

Réponse : A

C'est le principe du moindre privilège appliqué au niveau de l'interface : contraindre l'outil lui-même plutôt que de compter sur des instructions textuelles (option D, peu fiable) ou d'ajouter de la complexité architecturale (option B). L'option C est un filtre fragile qui ne couvre pas tous les cas.

Q3 : Un outil MCP echoue avec {"isError": true, "content": "Operation failed"}. Pourquoi c'est un anti-pattern ?
A) L'agent ne peut pas décider s'il faut faire un retry, modifier la requête, ou escalader.
B) Le format JSON est incorrect.
C) isError devrait être false.
D) Le message est trop court.

Réponse : A

Une erreur générique ne fournit aucune information pour la prise de décision. Sans errorCategory ni isRetryable encodés dans le texte du bloc content, l'agent ne sait pas si l'erreur est transient (retry), validation (corriger l'entrée), business (expliquer à l'utilisateur) ou permission (escalader). isError: true est correct (C est faux), et la longueur du message n'est pas le problème central (D est faux). Sur B : content devrait être un tableau de content blocks (cf. §2), donc cet exemple est en réalité non conforme sur la forme — mais ce n'est pas le point testé : même reformaté en [{"type": "text", "text": "Operation failed"}], le message resterait trop générique pour permettre une récupération intelligente. C'est cette généricité, pas la validité de forme, qui fait l'anti-pattern.

Q4 : Vous voulez que Claude appelle toujours extract_metadata en premier avant tout autre traitement. Quelle valeur de tool_choice utiliser ?
A) {"type": "auto"}
B) {"type": "any"}
C) {"type": "tool", "name": "extract_metadata"}
D) Ajouter "always call this first" dans la description.

Réponse : C

La forced selection ({"type": "tool", "name": "extract_metadata"}) garantit que Claude appellera exactement cet outil. auto (A) laisse Claude libre de ne pas appeler d'outil. any (B) force un appel mais sans garantir lequel. L'option D repose sur une instruction textuelle dans la description, ce qui est moins fiable qu'une contrainte programmatique.

Q5 : Vous concevez un outil create_refund. La logique metier exige que amount et reason soient obligatoires seulement si type == "refund". Si type == "info_only", ces champs ne servent a rien. Comment exprimer cela proprement dans le input_schema ?
A) Mettre tous les champs dans required.
B) Utiliser if/then : si type == "refund", alors required: ["amount", "reason"].
C) Documenter la regle uniquement dans la description.
D) Creer deux outils séparés.

Réponse : B. JSON Schema supporte if/then/else pour la validation conditionnelle (introduit en draft-07, disponible dans les drafts suivants). C'est le pattern propre quand des champs deviennent obligatoires selon une autre valeur. A force le modèle à fournir amount même pour info_only (et il l'inventera). C déplace la responsabilité sur le modèle (peu fiable). D est correct mais ajoute de la complexité et du misrouting potentiel — préférer if/then si la logique est simple.

Q6 : Votre extracteur de métadonnées produit un JSON valide mais Claude ajoute parfois des champs inattendus comme "notes": "..." qui ne sont pas dans votre schéma. Comment empêcher cela côté schéma ?
A) Ajouter "notes" dans properties.
B) Mettre "additionalProperties": false au niveau de l'objet.
C) Lister les champs interdits dans une enum.
D) Utiliser tool_choice: any.

Réponse : B. "additionalProperties": false rejette tout champ non declare dans properties — à condition d'activer strict: true sur la définition du tool, sans quoi l'API Claude ne garantit pas la conformité au schéma. A le rendrait acceptable mais ne résout pas la question (le modèle continuerait à inventer d'autres champs). C n'a pas de sens sémantique. D ne contraint pas la structure du résultat.
