1. Concevoir des interfaces d'outils claires (Task 2.1)

Le problème que cela résout

Quand Claude dispose de plusieurs outils aux fonctions proches, il choisit lequel appeler en se basant principalement sur la description de chaque outil. Si deux descriptions se ressemblent trop, Claude confond les outils — c'est le misrouting. Par exemple, si analyze_content est décrit comme "analyzes content and extracts key information" et analyze_document comme "analyzes documents and extracts key information", Claude les confondra fréquemment — dans le scénario d'examen associé, 45 % des requêtes étaient mal routées (chiffre illustratif propre à ce scénario, pas une constante générale du taux de misrouting).

Règle fondamentale : la description d'un outil est le mécanisme principal de sélection qu'un LLM utilise pour décider quel outil appeler. Des descriptions vagues ou redondantes entraînent un misrouting systématique.

L'anatomie d'une bonne description

Une description efficace répond à quatre questions :

  • Que fait l'outil et que retourne-t-il ?
  • Quels formats d'entrée accepte-t-il ? (avec des valeurs d'exemple dans input_schema)
  • Quels sont les edge cases et les contraintes ?
  • Quand utiliser cet outil plutôt qu'un autre similaire ?

Exemple concret

{
  "name": "get_customer",
  "description": "Finds a customer by email or ID. Returns the customer
    profile including name, email, order history, and account status.
    Use this tool BEFORE lookup_order to verify the customer's identity.
    Accepts an email (format: user@domain.com) or a numeric customer_id.",
  "input_schema": {
    "type": "object",
    "properties": {
      "email": {"type": "string", "description": "Customer email"},
      "customer_id": {"type": "integer", "description": "Numeric customer ID"}
    },
    "required": []
  }
}

Comment résoudre le misrouting

ProblèmeSolution
Deux outils aux descriptions similaires (chevauchement sémantique)Renommer pour lever l'ambiguïté : analyze_content → extract_web_results, et mettre à jour la description
Un outil générique utilisé hors de son périmètreRemplacer par un outil contraint : fetch_url → load_document (qui valide le format de l'URL)
Un outil « fourre-tout » trop largeDiviser en outils spécialisés : analyze_document → extract_data_points + summarize_content + verify_claim_against_source
Piège courant — system prompt et associations involontaires : le system prompt peut créer des associations non désirées avec les outils. Par exemple, l'instruction "always verify the customer" dans le system prompt pousse Claude à appeler get_customer même pour des requêtes qui ne nécessitent pas de vérification d'identité. L'examen teste votre capacité à identifier cette cause racine : un wording mal calibré dans le system prompt peut provoquer du misrouting autant que des descriptions vagues.

Outils intégrés vs outils MCP

Les agents ont tendance à préférer les outils intégrés (Read, Grep) aux outils MCP offrant des fonctionnalités proches. Pour contrer cette tendance, renforcez les descriptions des outils MCP en soulignant les avantages concrets qu'ils offrent par rapport aux outils intégrés : données exclusives, contexte spécifique, ou fonctionnalités que les outils intégrés ne couvrent pas.

Les distracteurs classiques face au misrouting par description pauvre.
  • Ajouter des few-shot examples au system prompt — coûte des tokens à chaque appel sans lever l'ambiguïté sémantique des descriptions elles-mêmes.
  • Construire une couche de routage qui analyse l'entrée avant chaque tour — sur-ingénierie qui court-circuite la compréhension du langage naturel que le modèle fait déjà à partir des descriptions.
  • Fusionner les deux outils en un lookup_entity générique (par exemple get_customer et lookup_order) — un choix d'architecture défendable en soi, mais bien plus lourd qu'un premier pas quand le problème immédiat est simplement la pauvreté des descriptions existantes.
  • N'enrichir que l'une des deux descriptions — l'autre reste tout aussi attirante pour les mêmes requêtes, le misrouting persiste dans l'autre sens.

2. Les réponses d'erreur structurées en MCP (Task 2.2)

Le problème que cela résout

Quand un outil MCP échoue, l'agent doit prendre une décision de récupération : faut-il faire un retry ? Modifier la requête ? Escalader vers un humain ? Si l'erreur retournée est un simple "Operation failed", l'agent ne dispose d'aucune information pour faire ce choix. Il faut donc des erreurs structurées qui indiquent le type d'erreur, sa cause probable et les actions possibles.

Ce que doit contenir une bonne erreur

{
  "isError": true,
  "content": [
    {
      "type": "text",
      "text": "errorCategory: transient | isRetryable: true | Service temporairement indisponible. Timeout sur l'API commandes. | attempted_query: order_id=12345"
    }
  ]
}

Dans un CallToolResult MCP, content est toujours un tableau de content blocks (jamais un objet ni une string). Les champs errorCategory/isRetryable ne font pas partie de la spécification MCP : c'est une convention de conception applicative, à encoder dans le texte du bloc text (ou en JSON stringifié dans ce texte), pas des champs officiels du protocole.

Anti-pattern — erreur générique : {"isError": true, "content": "Operation failed"}. L'agent ne peut pas décider s'il doit faire un retry, reformuler la requête ou escalader. Ce type d'erreur générique empêche toute récupération intelligente. C'est le principal anti-pattern testé à l'examen.

Les quatre catégories d'erreurs

errorCategoryExemplesisRetryableAction de l'agent
transientTimeout, erreur 503, panne réseautrueRetry avec backoff exponentiel
validationEntrée invalide, champ requis manquanttrue (après correction)Corriger l'entrée et retenter
businessViolation de politique, seuil dépasséfalseExpliquer à l'utilisateur, proposer une alternative
permissionAccès refusé, privilège insuffisantfalseEscalader à un humain
Distinction fondamentale : un échec d'accès (timeout — le serveur n'a pas répondu) est très différent d'un résultat vide valide (la requête a réussi, mais il n'y a aucune correspondance). Le premier nécessite une décision de retry ; le second est une information utile en soi. Les deux doivent être clairement distingués dans la réponse du tool_use.
Pattern complémentaire — local error recovery dans les subagents : un subagent ne doit pas propager au coordinateur chaque erreur MCP individuelle. Il tente une récupération locale (1-2 retries sur les erreurs transient), et ne remonte que les erreurs irrécupérables — avec les résultats partiels déjà obtenus et la requête tentée (attempted_query). Détail complet et exemple de payload : voir D5 §3 (Task 5.3, « La propagation d'erreurs dans les systèmes multi-agents »), qui traite explicitement ce pattern comme complément de D1 (hub-and-spoke) et D2 (erreurs structurées MCP).

3. tool_choice, distribution et restriction des outils (Task 2.3)

Le problème que cela résout

Si vous donnez 18 outils à un seul agent, sa capacité à choisir le bon outil chute significativement. Pire : un agent disposant d'outils hors de sa spécialisation aura tendance à les utiliser à mauvais escient. Le principe est simple : chaque agent ne reçoit que les outils pertinents pour son rôle, idéalement 4 à 5 maximum, plus un ensemble restreint d'utilitaires transversaux si nécessaire.

Scoped tool access et principe du moindre privilège

Chaque subagent dans une architecture hub-and-spoke doit disposer d'un accès limité aux outils (scoped tool access). Cela évite qu'un agent utilise un outil hors de son périmètre. Exemple classique : un document analysis subagent qui dispose d'un outil générique fetch_url finit par télécharger des pages de moteurs de recherche au lieu de documents. La solution : remplacer fetch_url par load_document, un outil contraint qui valide que les URLs pointent vers des formats document.

Principe clé : plutôt que de restreindre le comportement via des instructions dans le prompt, remplacez les outils génériques par des alternatives contraintes au niveau de l'interface. Les contraintes au niveau de l'outil sont plus fiables que les instructions textuelles.

Le paramètre tool_choice

Ce paramètre contrôle la manière dont Claude sélectionne les outils :

ValeurComportementQuand l'utiliser
{"type": "auto"}Claude décide librement : texte ou appel d'outilMode par défaut, convient à la majorité des cas
{"type": "any"}Claude doit appeler un outil (mais choisit lequel)Pour garantir un appel d'outil quand plusieurs schémas existent
{"type": "tool", "name": "..."}Claude doit appeler un outil précis (forced selection)Pour forcer un ordre d'exécution (ex. : extract_metadata avant l'enrichissement)
Pour l'examen : tool_choice avec {"type": "any"} garantit qu'un outil sera appelé, pas que sa sortie respecte le schéma. La forced selection ({"type": "tool", "name": "..."}) garantit une première action spécifique avant le reste du workflow — utile pour imposer un ordre d'exécution.

Outils cross-role scoped : l'exemple de verify_fact

Certains outils sont pertinents pour plusieurs agents mais doivent rester restreints en capacité. Exemple : un outil verify_fact qui vérifie une affirmation contre une source documentaire. Un research agent et un document analysis agent ont tous deux besoin de cet outil — mais avec des restrictions différentes (ex. : le research agent y accède toujours, le document analysis agent seulement s'il la requête inclut explicitement la vérification). La solution : un outil partagé restreint, fourni aux deux via leur tools respectif avec une description précise du contexte d'utilisation.

{
  "name": "verify_fact",
  "description": "Verifies a claim against source documents or references. Returns confidence level (high/medium/low) and the source excerpt. Use this cross-role tool only when a specific claim needs verification, not for general information retrieval.",
  "input_schema": {
    "type": "object",
    "properties": {
      "claim": {"type": "string", "description": "The specific claim to verify"},
      "source_id": {"type": "string", "description": "ID of the source document to check against"}
    },
    "required": ["claim", "source_id"]
  }
}
Les distracteurs classiques face à la distribution d'outils et à tool_choice.
  • Fusionner les outils en un outil générique à paramètre mode — déplace la décision dans un argument, où la description ne peut plus la guider aussi efficacement que via des outils distincts.
  • Régler tool_choice: "any" pour corriger un mauvais choix d'outil — garantit qu'un outil est appelé, pas que ce soit le bon.
  • Réécrire les descriptions encore une fois — inutile quand le vrai problème est le nombre d'outils exposés à l'agent, pas leur formulation.
  • Donner tous les outils à un agent « au cas où » — un agent doté d'outils hors de sa spécialité les emploie à mauvais escient, comme le montre l'exemple fetch_url plus haut.

4. MCP Integration — primitives et configuration (Task 2.4)

Le problème que cela résout

L'approche traditionnelle d'intégration d'outils oblige les développeurs à écrire manuellement des schémas et des fonctions pour chaque outil. Le Model Context Protocol (MCP) résout ce problème en déplaçant la définition et l'exécution des outils vers des serveurs dédiés. Quelqu'un d'autre crée les outils, les empaquète dans un MCP server, et votre application s'y connecte automatiquement.

Les deux portées de configuration MCP

Un serveur MCP se déclare à l'une de deux portées, et le choix dépend d'une seule question : est-ce que toute l'équipe doit l'avoir ?

PortéeFichierPartagé ?Pour quoi
Projet.mcp.json à la racine du dépôtOui — versionné dans le VCS, disponible après un cloneOutillage d'équipe : Jira, GitHub, la base de connaissances interne
Utilisateur~/.claude.jsonNon — local à la machineServeurs personnels ou expérimentaux : vos notes, un prototype, un serveur que vous testez
Les deux coexistent. Les outils de tous les serveurs configurés, quelle que soit leur portée, sont découverts à la connexion et disponibles simultanément à l'agent. Déclarer un serveur personnel dans ~/.claude.json ne vous prive pas des serveurs projet — vous avez l'union des deux.
Réflexe d'examen : « tout le monde doit l'avoir » → .mcp.json projet. « moi seul, et je ne veux pas l'imposer à l'équipe » → ~/.claude.json utilisateur. Le distracteur classique consiste à proposer de mettre le serveur expérimental dans le fichier projet en le désactivant, ou à demander à chaque coéquipier d'ajouter le serveur d'équipe à la main : les deux inversent la logique des portées.

La gestion des secrets par substitution de variables d'environnement

Les tokens d'accès ne doivent jamais être commités dans le dépôt. Utilisez la substitution de variables d'environnement dans .mcp.json :

{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}

La syntaxe ${VARIABLE_NAME} est résolue au lancement. Chaque développeur fournit ses propres credentials via ses variables d'environnement locales, ce qui permet de versionner .mcp.json sans exposer de secrets.

Anti-pattern (in-scope) : stocker un token en clair dans un .mcp.json versionné. Même si vous le supprimez plus tard, l'historique Git le conserve indéfiniment. Toujours passer par ${VAR} ou par le user-level ~/.claude.json, non versionné.

Les primitives MCP

MCP expose trois types de primitives, chacune contrôlée par un acteur différent. Deux seulement sont au programme : l'appendice du guide cite les tools et les resources (avec isError et la configuration .mcp.json), et l'in-scope parle de « MCP tool and resource design ». Les prompts figurent ici pour que le tableau soit complet et que vous les reconnaissiez comme distracteur — aucune question ne portera dessus.

PrimitiveContrôlée parObjectifQuand l'utiliser
toolsLe modèle (Claude)Ajouter des capacités d'actionClaude doit exécuter une opération (CRUD, appel API)
resourcesL'applicationFournir des données en lectureL'application a besoin de données pour l'interface ou le prompt
promptsL'utilisateurDéfinir des workflows prédéfinisL'utilisateur déclenche une action (bouton, commande slash)
resources comme « content catalogs » : les resources sont particulièrement utiles pour exposer des catalogues de contenu (schémas de base de données, listes de tâches, hiérarchies de navigation). Elles réduisent le nombre d'appels de tools exploratoires en fournissant directement les données de contexte dont l'application a besoin.

Quand l'agent ignore votre outil MCP au profit d'un outil intégré

Vous branchez un serveur MCP qui expose un outil de recherche bien plus capable que Grep — il comprend la structure du code, suit les imports, renvoie du contexte. Et pourtant l'agent continue d'appeler Grep. Le serveur fonctionne, l'outil est bien connecté : ce n'est pas un problème de configuration.

La cause est la même qu'en section 1 : l'agent choisit sur la foi des descriptions. Les outils intégrés arrivent avec des descriptions détaillées et éprouvées. Beaucoup d'outils MCP, eux, se contentent d'une ligne générée à partir du nom de la fonction. Face à « Search files » d'un côté et à la description complète de Grep de l'autre, le modèle prend celle qu'il comprend.

Le correctif : enrichir la description de l'outil MCP pour qu'elle explique ce qu'il sait faire et ce qu'il renvoie — types d'entrée acceptés, forme exacte de la sortie, et surtout ce qu'il apporte que l'outil intégré n'a pas. Pas « recherche dans les fichiers », mais « recherche sémantique dans le code indexé : renvoie la définition, tous les appelants et la chaîne d'imports, là où une recherche textuelle ne renvoie que les lignes correspondantes ».

Réflexe d'examen : quand un scénario décrit un agent qui préfère un outil intégré à un outil MCP plus capable, la réponse n'est ni de retirer l'outil intégré, ni d'ajouter des instructions dans le system prompt, ni de construire une couche de routage. C'est de réparer la description — c'est le levier le moins coûteux et celui qui traite la cause.

Choix entre community servers et custom servers

Pour les intégrations standards (Jira, GitHub, Slack), préférez les community servers existants. Ne construisez un custom server que pour les workflows spécifiques à votre équipe que personne d'autre n'a implémentés. Tous les tools de tous les serveurs connectés sont découverts à la connexion et disponibles simultanément.

5. Les outils intégrés de Claude Code (Task 2.5)

Le problème que cela résout

Claude Code dispose d'outils intégrés pour interagir avec le système de fichiers et le terminal. Bien les connaître évite de créer des outils MCP redondants et permet une investigation efficace du code.

Référence de sélection

TâcheOutilExemple
Trouver des fichiers par nom ou patternGlob**/*.test.tsx, src/components/**/*.ts
Chercher dans le contenu des fichiersGrepUn nom de fonction, un message d'erreur, un import
Lire un fichier en entierReadCharger un fichier pour l'analyser
Créer un nouveau fichierWriteÉcrire un fichier depuis zéro
Modifier précisément un fichier existantEditRemplacer un extrait via une correspondance de texte unique
Exécuter une commande shellBashgit, npm, tests, build
Fallback Read + Write : quand Edit échoue parce que le texte à remplacer n'est pas unique dans le fichier, la solution de repli est Read (charger le fichier complet) → modifier le contenu → Write (réécrire le fichier entier).

Tracer les ré-exports : la bonne approche Grep

Quand vous cherchez tous les appelants d'une fonction qui est ré-exportée à travers plusieurs wrappers (alias), un seul Grep du nom d'origine rate les appels indirects. Méthode correcte : d'abord Grep tous les noms exportés de la fonction (les aliases et re-exports) dans le codebase, puis Grep chacun de ces noms pour retrouver les appelants. (Source : guide officiel, Task 2.5, Skills.)

// Mauvais : un seul Grep du nom original
Grep "analyzeDocument"  // rate les appels via l'alias importé

// Bon : 2 passes
1. Grep "export.*analyzeDocument"      // trouve tous les noms exportés
   → "export { analyzeDocument }"      → "export { analyzeDocument as analyze }"
   → "export { analyzeDocument as doc }"
2. Grep chaque alias : "analyzeDocument | analyze | doc"  // capture tous les appelants

La stratégie d'investigation incrémentale

Plutôt que de lire tous les fichiers d'un coup, construisez votre compréhension progressivement :

  1. Grep : identifier les points d'entrée (définitions de fonctions, exports).
  2. Read : lire les fichiers identifiés.
  3. Grep : trouver les usages (imports, appels).
  4. Read : lire les fichiers consommateurs.
  5. Répéter jusqu'à avoir une vue complète.
Pour l'examen : cette stratégie incrémentale (Grep → Read → Grep → Read) est la méthode recommandée pour explorer un codebase inconnu. Elle évite de surcharger le contexte en ne lisant que les fichiers pertinents.
Les distracteurs classiques face au choix d'un outil intégré.
  • Confondre Grep (contenu) et Glob (chemins) — le piège tient à ce que les deux « cherchent » ; l'un lit dans les fichiers, l'autre ne regarde que les chemins.
  • Relancer Edit avec la même ancre ambiguë — l'outil est déterministe et échouera à l'identique ; la correspondance non unique ne devient pas unique en réessayant.
  • Lire tous les fichiers d'emblée au lieu d'explorer par Grep puis Read — surcharge le contexte avec des fichiers non pertinents dès le départ.
  • Passer par Bash et find — là où Glob répond directement, sans dépendre d'une commande shell.

6. Synthèse — les points clés

Conception d'outils

  • La description est le mécanisme n° 1 de sélection par le LLM. Des descriptions vagues = misrouting.
  • Renommer, diviser ou remplacer les outils pour éliminer les chevauchements sémantiques.
  • Attention aux associations involontaires créées par le system prompt.
  • Spécifier les formats d'entrée dans input_schema avec des exemples et documenter les edge cases.

Erreurs structurées

  • Toujours retourner isError (champ de la spec) et, en convention applicative encodée dans le bloc text, errorCategory (transient / validation / business / permission) et isRetryable.
  • Distinguer un échec d'accès (timeout) d'un résultat vide valide (zéro correspondance).
  • Les erreurs génériques ("Operation failed") empêchent toute récupération intelligente — c'est l'anti-pattern principal.

Distribution des outils et restrictions d'accès

  • 4 à 5 outils max par agent, pas 18. Chaque agent ne reçoit que les outils pertinents pour son rôle (scoped tool access).
  • Remplacer les outils génériques par des alternatives contraintes (fetch_url → load_document).
  • Outils cross-role scoped : partager des outils (ex. verify_fact) entre agents avec des descriptions précises du contexte d'utilisation.
  • tool_choice : auto (par défaut) / any (garantir un appel) / forced selection (imposer un outil précis).

MCP — primitives et configuration

  • Deux portées : .mcp.json projet (versionné, partagé) pour l'outillage d'équipe ; ~/.claude.json utilisateur (local) pour les serveurs personnels ou expérimentaux. Les deux coexistent, tous les outils sont disponibles simultanément.
  • Substitution de variables d'environnement (${GITHUB_TOKEN}) pour les secrets — jamais de tokens en clair dans le dépôt.
  • Primitives au programme : tools (le modèle exécute une action) et resources (l'application expose des données). Les prompts existent mais ne sont pas testés.
  • resources = « content catalogs » qui réduisent les appels exploratoires en fournissant directement les données de contexte.
  • Préférer les community servers pour les intégrations standards (Jira, GitHub, Slack) ; custom servers pour les workflows spécifiques à l'équipe.
  • Agent qui préfère un outil intégré à un outil MCP plus capable → enrichir la description du serveur MCP (ce qu'il fait, ce qu'il renvoie, ce que l'outil intégré n'a pas). Ni retrait de l'outil intégré, ni couche de routage.

Outils intégrés

  • Glob (fichiers par pattern), Grep (contenu), Read/Write (fichier entier), Edit (modification ciblée), Bash (commandes).
  • Edit échoue → fallback Read + Write.
  • Investigation incrémentale : Grep → Read → Grep usages → Read consommateurs.

7. Questions d'auto-évaluation

Q1 (D2) — Chevauchement sémantique entre deux descriptions

Situation : les requêtes « analyze the uploaded quarterly report » partent vers le web search agent 45 % du temps au lieu du document analysis agent. Les outils sont analyze_content (« analyzes content and extracts key information ») et analyze_document (« analyzes documents and extracts key information »). Comment corriger ?

A) Ajouter un classifieur de pré-routage qui analyse la requête avant chaque tour.

B) Renommer l'outil web search en extract_web_results et réécrire sa description pour la rendre spécifique au web.

C) Ajouter des few-shot examples au coordinateur pour illustrer le bon routage.

D) Enrichir uniquement la description de l'outil document analysis.

Réponse : B) Renommer en extract_web_results et différencier la description

Explication : les deux descriptions sont quasi identiques — le modèle n'a aucun élément pour trancher. Renommer et redécrire élimine le chevauchement fonctionnel à sa source, là où le modèle prend effectivement sa décision.

Pourquoi les autres sont faux :

  • A) Sur-ingénierie : on court-circuite la compréhension du langage naturel au lieu de réparer l'ambiguïté.
  • C) Les few-shot ajoutent du coût en tokens sans supprimer la cause, qui est la description.
  • D) Améliorer un seul côté laisse l'autre description toujours aussi attirante pour les mêmes requêtes.
Q2 (D2) — Outil générique mal employé

Situation : un document analysis subagent dispose d'un outil générique fetch_url. Les logs montrent qu'il télécharge des pages de résultats de moteurs de recherche au lieu de documents. Quel correctif appliquer ?

A) Remplacer fetch_url par load_document, qui valide que l'URL pointe vers un format document.

B) Retirer fetch_url et faire transiter toutes les récupérations par le coordinateur.

C) Ajouter un filtre sur les domaines de moteurs de recherche.

D) Ajouter dans le prompt du subagent l'instruction de ne récupérer que des documents.

Réponse : A) Remplacer fetch_url par load_document, plus contraint

Explication : remplacer un outil générique par une alternative contrainte applique le moindre privilège au niveau de l'interface : l'usage incorrect devient impossible plutôt que déconseillé.

Pourquoi les autres sont faux :

  • B) Ajoute un aller-retour de coordination pour un besoin fréquent et légitime du subagent.
  • C) Une liste de domaines est fragile et ne couvrira jamais tous les cas.
  • D) Une instruction textuelle reste probabiliste, alors que le contrat d'outil est déterministe.
Q3 (D2) — Pourquoi une erreur générique est un anti-pattern

Situation : un outil MCP échoue avec {"isError": true, "content": "Operation failed"}. Pourquoi est-ce un anti-pattern ?

A) L'agent ne peut pas décider s'il faut réessayer, corriger la requête, ou escalader.

B) Le format JSON de la réponse est invalide.

C) isError devrait valoir false puisque l'outil a répondu.

D) Le message est trop court pour être affiché à l'utilisateur.

Réponse : A) L'agent ne peut pas décider de la suite

Explication : une réponse d'erreur uniforme prive l'agent de toute base de décision. Sans catégorie ni indication de caractère rejouable, il ne sait pas distinguer un transient (réessayer), un validation (corriger l'entrée), un business (expliquer au client) et un permission (escalader).

Pourquoi les autres sont faux :

  • B) La forme est effectivement perfectible — content attend un tableau de content blocks — mais reformater ne rendrait pas le message plus exploitable ; ce n'est pas le point testé.
  • C) isError: true est correct : l'opération a bien échoué.
  • D) La longueur n'est pas le problème ; c'est l'absence de métadonnées de décision.
Q4 (D2) — Imposer un outil précis en premier

Situation : vous voulez que Claude appelle toujours extract_metadata avant tout autre traitement d'enrichissement. Quelle valeur de tool_choice utiliser ?

A) {"type": "auto"}

B) {"type": "any"}

C) {"type": "tool", "name": "extract_metadata"}

D) Ajouter « always call this first » dans la description de l'outil.

Réponse : C) {"type": "tool", "name": "extract_metadata"}

Explication : la forced selection impose exactement cet outil sur ce tour. Les étapes suivantes s'enchaînent ensuite dans les tours ultérieurs, une fois les métadonnées disponibles.

Pourquoi les autres sont faux :

  • A) "auto" autorise Claude à n'appeler aucun outil.
  • B) "any" force un appel mais laisse le choix de l'outil — l'ordre n'est pas garanti.
  • D) Une instruction dans la description reste probabiliste là où un paramètre est déterministe.
Q5 (D2) — Contenu d'une réponse d'erreur exploitable (Sélectionne les 2 réponses correctes.)

Situation : vous concevez les réponses d'erreur de vos outils MCP pour que l'agent puisse décider correctement de la suite. Quelles affirmations sont exactes ?

A) Une erreur {"isError": true, "content": "Operation failed"} suffit à l'agent pour décider d'un retry.

B) Une erreur transitoire (timeout, 503) doit porter isRetryable: true encodé dans le bloc text du content.

C) Une erreur de permission doit être escaladée à un humain sans retry, quel que soit le contexte.

D) Les catégories transient, validation, business et permission font partie de la spécification MCP officielle.

E) Un résultat vide valide (zéro correspondance) doit être distingué d'un échec d'accès (timeout) dans la réponse.

Réponses : B, E.

Explication : l'agent a besoin de deux informations pour décider — le caractère rejouable de l'erreur, et la nature de ce qu'il a obtenu. Une requête valide sans résultat est un succès légitime ; un timeout appelle une décision de reprise. Les confondre conduit soit à des retries inutiles, soit à des lacunes silencieuses dans le rapport final.

Pourquoi les autres sont faux :

  • A) C'est exactement l'anti-pattern : une erreur uniforme ne porte aucune base de décision.
  • C) L'escalade est la bonne règle générale (isRetryable: false), mais « quel que soit le contexte » en fait un absolu que la conception ne pose pas.
  • D) Ces catégories sont une convention de conception applicative, encodée dans le texte du content — pas un élément formel de la spec MCP.
Q6 (D2) — Où déclarer deux serveurs MCP

Situation : votre équipe a besoin d'un serveur MCP Jira disponible pour tous les développeurs du projet. Par ailleurs, vous voulez tester chez vous un serveur expérimental qui indexe vos notes personnelles — personne d'autre ne doit l'avoir.

Question : où configurez-vous chacun ?

A) Les deux dans .mcp.json, l'expérimental étant commenté pour les coéquipiers.

B) Les deux dans ~/.claude.json, en demandant à chaque coéquipier d'ajouter l'entrée Jira lui-même.

C) Jira documenté dans CLAUDE.md ; l'expérimental dans .mcp.json.

D) Jira dans .mcp.json à la racine du projet ; l'expérimental dans ~/.claude.json au niveau utilisateur.

Réponse : D) Portée projet pour l'outillage partagé, portée utilisateur pour le personnel

Explication : .mcp.json est la portée projet, versionnée, que tout le monde obtient au clone ; ~/.claude.json est la portée utilisateur, locale à votre machine. Les deux coexistent : les outils de tous les serveurs configurés sont découverts à la connexion et disponibles simultanément.

Pourquoi les autres sont faux :

  • A) Une entrée commentée dans un fichier partagé est une modification qui finira par être décommentée par accident.
  • B) Fait dépendre l'outillage d'équipe d'une configuration manuelle par chacun — exactement ce que la portée projet évite.
  • C) CLAUDE.md ne configure aucun serveur, et les deux portées sont inversées.
Q7 (D2) — Edit échoue faute d'ancre unique

Situation : l'agent doit modifier une instruction return null; dans un fichier de 400 lignes. Edit échoue : la chaîne return null; apparaît onze fois dans ce fichier.

Question : quelle est la solution de repli correcte ?

A) Read le fichier complet, modifier le contenu, puis Write pour le réécrire entièrement.

B) Relancer Edit avec la même ancre jusqu'à ce qu'il tombe sur la bonne occurrence.

C) Utiliser Glob pour localiser la ligne, puis Edit à nouveau.

D) Supprimer le fichier et le recréer depuis zéro avec Write.

Réponse : A) Read puis Write

Explication : quand Edit ne trouve pas de texte d'ancrage unique, charger le fichier entier et le réécrire est le repli documenté. Le contenu complet lève l'ambiguïté que l'ancre ne pouvait pas lever.

Pourquoi les autres sont faux :

  • B) Edit est déterministe : la même ancre ambiguë échoue à l'identique à chaque tentative.
  • C) Glob apparie des chemins de fichiers ; il ne voit pas le contenu et ne localise aucune ligne.
  • D) Supprimer d'abord fait courir le risque de perdre le contenu si l'écriture échoue, sans aucun avantage sur une réécriture en place.
