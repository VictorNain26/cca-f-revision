1. Concevoir des interfaces d'outils claires (Task 2.1)

Le probleme que cela resout

Quand Claude dispose de plusieurs outils aux fonctions proches, il choisit lequel appeler en se basant principalement sur la description de chaque outil. Si deux descriptions se ressemblent trop, Claude confond les outils — c'est le misrouting. Par exemple, si analyze_content est decrit comme "analyzes content and extracts key information" et analyze_document comme "analyzes documents and extracts key information", Claude les confondra dans environ 45 % des cas.

Regle fondamentale : la description d'un outil est le mecanisme principal de selection qu'un LLM utilise pour decider quel outil appeler. Des descriptions vagues ou redondantes entrainent un misrouting systematique.

L'anatomie d'une bonne description

Une description efficace repond a quatre questions :

  • Que fait l'outil et que retourne-t-il ?
  • Quels formats d'entree accepte-t-il ? (avec des valeurs d'exemple dans input_schema)
  • Quels sont les edge cases et les contraintes ?
  • Quand utiliser cet outil plutot qu'un autre similaire ?

Exemple concret

{
  "name": "get_customer",
  "description": "Finds a customer by email or ID. Returns the customer
    profile including name, email, order history, and account status.
    Use this tool BEFORE lookup_order to verify the customer's identity.
    Accepts an email (format: user@domain.com) or a numeric customer_id.",
  "input_schema": {
    "type": "object",
    "properties": {
      "email": {"type": "string", "description": "Customer email"},
      "customer_id": {"type": "integer", "description": "Numeric customer ID"}
    },
    "required": []
  }
}

Comment resoudre le misrouting

ProblemeSolution
Deux outils aux descriptions similaires (chevauchement semantique)Renommer pour lever l'ambiguite : analyze_content → extract_web_results, et mettre a jour la description
Un outil generique utilise hors de son perimetreRemplacer par un outil contraint : fetch_url → load_document (qui valide le format de l'URL)
Un outil « fourre-tout » trop largeDiviser en outils specialises : analyze_document → extract_data_points + summarize_content
Piege courant — system prompt et associations involontaires : le system prompt peut creer des associations non desirees avec les outils. Par exemple, l'instruction "always verify the customer" dans le system prompt pousse Claude a appeler get_customer meme pour des requetes qui ne necessitent pas de verification d'identite. L'examen teste votre capacite a identifier cette cause racine : un wording mal calibre dans le system prompt peut provoquer du misrouting autant que des descriptions vagues.

Outils integres vs outils MCP

Les agents ont tendance a preferer les outils integres (Read, Grep) aux outils MCP offrant des fonctionnalites proches. Pour contrer cette tendance, renforcez les descriptions des outils MCP en soulignant les avantages concrets qu'ils offrent par rapport aux outils integres : donnees exclusives, contexte specifique, ou fonctionnalites que les outils integres ne couvrent pas.

2. Les reponses d'erreur structurees en MCP (Task 2.2)

Le probleme que cela resout

Quand un outil MCP echoue, l'agent doit prendre une decision de recuperation : faut-il faire un retry ? Modifier la requete ? Escalader vers un humain ? Si l'erreur retournee est un simple "Operation failed", l'agent ne dispose d'aucune information pour faire ce choix. Il faut donc des erreurs structurees qui indiquent le type d'erreur, sa cause probable et les actions possibles.

Ce que doit contenir une bonne erreur

{
  "isError": true,
  "content": {
    "errorCategory": "transient",
    "isRetryable": true,
    "message": "Service temporairement indisponible. Timeout sur l'API commandes.",
    "attempted_query": "order_id=12345",
    "partial_results": null
  }
}
Anti-pattern — erreur generique : {"isError": true, "content": "Operation failed"}. L'agent ne peut pas decider s'il doit faire un retry, reformuler la requete ou escalader. Ce type d'erreur generique empeche toute recuperation intelligente. C'est le principal anti-pattern teste a l'examen.

Les quatre categories d'erreurs

errorCategoryExemplesisRetryableAction de l'agent
transientTimeout, erreur 503, panne reseautrueRetry avec backoff exponentiel
validationEntree invalide, champ requis manquanttrue (apres correction)Corriger l'entree et retenter
businessViolation de politique, seuil depassefalseExpliquer a l'utilisateur, proposer une alternative
permissionAcces refuse, privilege insuffisantfalseEscalader a un humain
Distinction fondamentale : un echec d'acces (timeout — le serveur n'a pas repondu) est tres different d'un resultat vide valide (la requete a reussi, mais il n'y a aucune correspondance). Le premier necessite une decision de retry ; le second est une information utile en soi. Les deux doivent etre clairement distingues dans la reponse du tool_use.

3. Distribuer les outils entre agents et configurer tool_choice (Task 2.3)

Le probleme que cela resout

Si vous donnez 18 outils a un seul agent, sa capacite a choisir le bon outil chute significativement. Pire : un agent disposant d'outils hors de sa specialisation aura tendance a les utiliser a mauvais escient. Le principe est simple : chaque agent ne recoit que les outils pertinents pour son role, idealement 4 a 5 maximum, plus un ensemble restreint d'utilitaires transversaux si necessaire.

Scoped tool access et principe du moindre privilege

Chaque subagent dans une architecture hub-and-spoke doit disposer d'un acces limite aux outils (scoped tool access). Cela evite qu'un agent utilise un outil hors de son perimetre. Exemple classique : un document analysis subagent qui dispose d'un outil generique fetch_url finit par telecharger des pages de moteurs de recherche au lieu de documents. La solution : remplacer fetch_url par load_document, un outil contraint qui valide que les URLs pointent vers des formats document.

Principe cle : plutot que de restreindre le comportement via des instructions dans le prompt, remplacez les outils generiques par des alternatives contraintes au niveau de l'interface. Les contraintes au niveau de l'outil sont plus fiables que les instructions textuelles.

Le parametre tool_choice

Ce parametre controle la maniere dont Claude selectionne les outils :

ValeurComportementQuand l'utiliser
{"type": "auto"}Claude decide librement : texte ou appel d'outilMode par defaut, convient a la majorite des cas
{"type": "any"}Claude doit appeler un outil (mais choisit lequel)Pour garantir une sortie structuree quand plusieurs schemas existent
{"type": "tool", "name": "..."}Claude doit appeler un outil precis (forced selection)Pour forcer un ordre d'execution (ex. : extract_metadata avant l'enrichissement)
Pour l'examen : tool_choice avec {"type": "any"} et plusieurs outils d'extraction garantit une sortie structuree tout en laissant Claude choisir le schema le plus adapte. La forced selection ({"type": "tool", "name": "..."}) garantit une premiere action specifique avant le reste du workflow — utile pour imposer un ordre d'execution.

4. Integrer des MCP servers dans Claude Code (Task 2.4)

Le probleme que cela resout

L'approche traditionnelle d'integration d'outils oblige les developpeurs a ecrire manuellement des schemas et des fonctions pour chaque outil. Le Model Context Protocol (MCP) resout ce probleme en deplacant la definition et l'execution des outils vers des serveurs dedies. Quelqu'un d'autre cree les outils, les empaquete dans un MCP server, et votre application s'y connecte automatiquement.

La portee des MCP servers

PorteeFichier de configurationPartageUsage
Projet.mcp.json (a la racine du projet)Versionne dans le VCS, partage avec l'equipeIntegrations standards du projet
Utilisateur~/.claude.jsonPersonnel, non versionneExperimentations, serveurs personnels

La gestion des secrets par substitution de variables d'environnement

Les tokens d'acces ne doivent jamais etre commites dans le depot. Utilisez la substitution de variables d'environnement dans .mcp.json :

{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}

La syntaxe ${VARIABLE_NAME} est resolue au lancement. Chaque developpeur fournit ses propres credentials via ses variables d'environnement locales, ce qui permet de versionner .mcp.json sans exposer de secrets.

Les trois primitives MCP

MCP expose trois types de primitives, chacune controlee par un acteur different :

PrimitiveControlee parObjectifQuand l'utiliser
toolsLe modele (Claude)Ajouter des capacites d'actionClaude doit executer une operation (CRUD, appel API)
resourcesL'applicationFournir des donnees en lectureL'application a besoin de donnees pour l'interface ou le prompt
promptsL'utilisateurDefinir des workflows predefinisL'utilisateur declenche une action (bouton, commande slash)
resources comme « content catalogs » : les resources sont particulierement utiles pour exposer des catalogues de contenu (schemas de base de donnees, listes de taches, hierarchies de navigation). Elles reduisent le nombre d'appels de tools exploratoires en fournissant directement les donnees de contexte dont l'application a besoin.

Les transports MCP

TransportLocalisationBidirectionnelSampling et notifications
StdioMeme machine uniquementOui, completSupport total
StreamableHTTPDistant (via URL)Via SSE (contournement)Selon les flags de configuration
Stateless HTTPDistant, multi-instanceNonDesactives (pas de session)
Piege de deploiement : utilisez le meme transport en developpement et en production. Developper avec Stdio puis deployer en HTTP cause des echecs lies aux differences de communication bidirectionnelle.

Concepts avances

  • Sampling : permet aux MCP servers de demander au client de generer du texte via son LLM, sans que le serveur ait besoin de cles API ni de supporter les couts de tokens. Utile pour les serveurs publics.
  • Roots : fichiers et dossiers auxquels l'utilisateur accorde l'acces au prealable. Ils offrent deux avantages : le controle des permissions (limiter l'acces aux zones autorisees) et la decouverte autonome (Claude navigue dans les roots sans que l'utilisateur fournisse le chemin complet).
Point de securite important : le SDK MCP n'applique pas automatiquement les restrictions de roots. Le developpeur du serveur doit implementer manuellement les verifications d'acces avec une fonction comme is_path_allowed(). Sans cette implementation, les roots sont declaratifs mais pas effectivement appliques. (Source : guide officiel, section Roots.)

Choix entre community servers et custom servers

Pour les integrations standards (Jira, GitHub, Slack), preferez les community servers existants. Ne construisez un custom server que pour les workflows specifiques a votre equipe que personne d'autre n'a implementes. Tous les tools de tous les serveurs connectes sont decouverts a la connexion et disponibles simultanement.

JSON Schema en profondeur (input_schema)

Le input_schema d'un outil utilise la specification JSON Schema draft-07. Au-dela de type, properties et required deja vus en D0, plusieurs constructions avancees apparaissent dans les questions d'examen.

Types complexes (oneOf, anyOf, allOf)

OperateurSemantiqueCas d'usage
oneOfDoit valider exactement un sous-schemaDiscriminated union : email OU id_client, jamais les deux
anyOfDoit valider au moins un sous-schemaAcceptation flexible : string OU array de strings
allOfDoit valider tous les sous-schemasComposition de contraintes (extension de schema de base)
// Exemple oneOf : recherche par email OU par ID, pas les deux
{
  "name": "find_customer",
  "description": "Find a customer by email or numeric ID. Provide exactly one.",
  "input_schema": {
    "type": "object",
    "oneOf": [
      {
        "properties": { "email": { "type": "string", "format": "email" } },
        "required": ["email"]
      },
      {
        "properties": { "customer_id": { "type": "integer", "minimum": 1 } },
        "required": ["customer_id"]
      }
    ]
  }
}

Validation conditionnelle (if/then/else)

// Si type == "refund", alors amount et reason sont obligatoires
{
  "type": "object",
  "properties": {
    "type": { "enum": ["refund", "info_only"] },
    "amount": { "type": "number" },
    "reason": { "type": "string" }
  },
  "required": ["type"],
  "if":   { "properties": { "type": { "const": "refund" } } },
  "then": { "required": ["amount", "reason"] }
}

Contraintes par type

TypeContraintesExemple
stringminLength, maxLength, pattern (regex), format (email, uri, date, date-time, uuid)"format": "email" rejette les strings invalides
number / integerminimum, maximum, exclusiveMinimum, multipleOf"minimum": 0, "maximum": 1000
arrayitems (schema des elements), minItems, maxItems, uniqueItemsListe non vide d'IDs uniques
objectrequired, additionalProperties (false pour rejeter champs inconnus)"additionalProperties": false = strict
EXAM TIP : "additionalProperties": false sur un objet rejette tout champ non declare dans properties. C'est utile pour forcer Claude a ne produire que les champs documentes. Sans cette contrainte, le modele peut ajouter des champs hallucines qui passent la validation syntaxique.

Champs nullable et enums avec fallback (rappel D0 + extension)

{
  "company_name": {
    "type": ["string", "null"],
    "description": "Company name if mentioned, null otherwise"
  },
  "category": {
    "type": "string",
    "enum": ["billing", "technical", "account", "other"]
  },
  "category_detail": {
    "type": ["string", "null"],
    "description": "Free-text detail when category is 'other'"
  },
  "sentiment": {
    "type": "string",
    "enum": ["positive", "negative", "neutral", "unclear"]
  }
}
3 piliers d'un input_schema robuste :
  1. Nullable sur les champs non garantis (au lieu de required) — evite l'hallucination
  2. Enum avec "other" + champ detail — capture les cas inattendus sans perte d'information
  3. Enum avec "unclear" — permet au modele d'exprimer son incertitude honnetement
Ces 3 patterns transforment un schema rigide en interface tolerante a l'incertitude.

Validation cote application (apres reception)

Le tool_use garantit la validite syntaxique du JSON, pas la coherence semantique. Apres reception, valider :

  • Coherence inter-champs : totaux qui s'additionnent, dates dans l'ordre chronologique
  • Existence des references : les IDs pointent vers des entites reelles
  • Plages metier : un montant negatif est syntaxiquement valide mais business-invalide

Voir D4 §4.4 pour le pattern retry-with-feedback : en cas d'echec de validation, renvoyer l'erreur a Claude pour qu'il corrige.

Patterns d'authentification MCP

Les serveurs MCP exposent souvent des donnees protegees (GitHub, Slack, base de donnees). L'authentification est gerable de plusieurs manieres selon le transport et le contexte.

Pattern 1 — Variables d'environnement (stdio, recommande)

Le pattern le plus simple et securise pour les serveurs stdio (sous-processus local). Le serveur lit la variable au demarrage.

// .mcp.json (versionne)
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}

// Le developpeur fournit le token dans son shell
export GITHUB_TOKEN=ghp_xxx
Pourquoi c'est sur : le token n'apparait jamais dans le repository (la variable n'est resolue qu'au runtime). Pour la rotation, chaque developpeur met a jour son env, sans toucher a Git.

Pattern 2 — Headers Authorization (HTTP/StreamableHTTP)

Pour les serveurs MCP distants, le client envoie l'authentification dans les headers HTTP a chaque requete.

// .mcp.json
{
  "mcpServers": {
    "internal-api": {
      "type": "http",
      "url": "https://api.internal.example.com/mcp",
      "headers": {
        "Authorization": "Bearer ${INTERNAL_API_TOKEN}",
        "X-Tenant-ID": "${TENANT_ID}"
      }
    }
  }
}
Schema d'authentificationHeaderCas d'usage
Bearer tokenAuthorization: Bearer <token>API tokens longue duree, JWT
API KeyX-API-Key: <key> ou similaireServices SaaS (Stripe, OpenAI, etc.)
Basic AuthAuthorization: Basic <base64>Legacy, deconseille en production

Pattern 3 — OAuth 2.0 (delegation utilisateur)

Pour les serveurs qui agissent au nom d'un utilisateur (acces a son Google Drive, son Slack personnel), l'authentification ne peut pas etre statique. Le flow OAuth :

  1. Le serveur MCP redirige l'utilisateur vers le provider (Google, Slack)
  2. L'utilisateur s'authentifie et accorde les scopes demandes
  3. Le provider renvoie un authorization_code
  4. Le serveur l'echange contre un access_token (court) + refresh_token (long)
  5. Les requetes ulterieures utilisent l'access_token, refresh quand necessaire
Specificite MCP : la specification MCP definit un flow OAuth 2.1 standardise (oauth/authorize, oauth/token, oauth/register). Le client (Claude Desktop, Claude Code) gere automatiquement le flow et stocke les tokens. Le developpeur du serveur MCP n'a qu'a implementer les endpoints conformes a la spec.

Pattern 4 — Authentification mTLS / certificats

Pour les environnements enterprise sensibles (banques, sante), les certificats clients TLS authentifient le client a chaque connexion. Configuration plus rare, mais a connaitre par son existence.

Tableau decisionnel

SituationPattern recommande
Token API personnel, serveur localVariable d'environnement (stdio + ${VAR})
Service SaaS partage (Stripe, etc.)Header Authorization avec ${VAR}
Acces a des ressources d'un utilisateur (Google, Slack)OAuth 2.1 (geree par le client MCP)
Environnement enterprise haute securitemTLS + audit log
Multi-tenant SaaSOAuth + scope par tenant
Anti-pattern : stocker un token en clair dans .mcp.json versionne. Meme si vous le supprimez plus tard, l'historique Git le conserve indefiniment. Toujours passer par ${VAR} ou par le user-level ~/.claude.json non versionne.
Scenario d'examen : votre equipe deploie un serveur MCP custom pour un outil interne. Chaque developpeur doit acceder a ses propres dossiers. Quel pattern ? OAuth 2.1 — l'authentification se fait par utilisateur, pas par token de service. Un token statique partage reviendrait a donner a tout le monde l'acces aux dossiers de tout le monde.

Cookbook : un serveur MCP custom complet

Cet exemple synthetise tous les concepts MCP de la section dans un serveur Python minimal mais complet : les 3 primitives (tools, resources, prompts), une verification de roots, et un usage de sampling.

// server.py — un serveur MCP "internal-docs" custom
from mcp.server.fastmcp import FastMCP
from pathlib import Path
import json

mcp = FastMCP("internal-docs")

ALLOWED_ROOTS = []  # rempli par on_roots_changed

# ---- ROOTS : verification d'acces ---------------------
@mcp.on_roots_changed
async def on_roots_changed(roots):
    global ALLOWED_ROOTS
    ALLOWED_ROOTS = [Path(r.uri.replace("file://", "")) for r in roots]

def is_path_allowed(path: Path) -> bool:
    """Le SDK MCP n'applique PAS automatiquement les roots — on doit verifier."""
    abs_path = path.resolve()
    return any(abs_path.is_relative_to(r) for r in ALLOWED_ROOTS)

# ---- TOOLS : controles par le modele ------------------
@mcp.tool()
async def search_docs(query: str, max_results: int = 10) -> dict:
    """Search internal documentation. Returns matching documents with
       title, path, and a relevant excerpt. Use this BEFORE read_doc to
       discover what's available."""
    # ... implementation (full-text search) ...
    return {"results": [...]}

@mcp.tool()
async def read_doc(path: str) -> dict:
    """Read the full content of an internal doc. Use after search_docs
       has identified a relevant path."""
    p = Path(path)
    if not is_path_allowed(p):
        return {
            "isError": True,
            "errorCategory": "permission",
            "isRetryable": False,
            "message": f"Path {path} is outside allowed roots."
        }
    return {"content": p.read_text()}

# ---- RESOURCES : controlees par l'application ---------
@mcp.resource("docs://catalog")
async def catalog() -> str:
    """Liste hierarchique des docs disponibles — content catalog
       qui evite les appels search_docs exploratoires."""
    return json.dumps({"sections": [...]})

# ---- PROMPTS : controles par l'utilisateur ------------
@mcp.prompt()
async def summarize_doc(doc_path: str) -> list:
    """Predefined prompt: summarize a doc in 5 bullet points.
       Triggered by user (button, slash command)."""
    return [
        {"role": "user", "content": f"Summarize {doc_path} in 5 bullets."}
    ]

# ---- SAMPLING : le serveur demande au CLIENT de generer
@mcp.tool()
async def classify_query(query: str) -> dict:
    """Classify a query as 'technical' or 'business'.
       Uses sampling to delegate generation to the client's LLM —
       no API key needed on the server side."""
    result = await mcp.sample(
        messages=[{"role": "user", "content": f"Classify: {query}"}],
        system="Reply with one word: 'technical' or 'business'.",
        max_tokens=10
    )
    return {"category": result.content[0].text.strip()}

if __name__ == "__main__":
    mcp.run(transport="stdio")  # ou "streamable-http" pour distant
Ce que cet exemple illustre :
  • tools avec descriptions explicites repondant aux 4 questions (que fait, format input, edge cases, quand utiliser)
  • Erreur structuree (errorCategory: "permission") avec isRetryable: false conforme a §2
  • Roots check explicite via is_path_allowed() — le SDK ne le fait pas tout seul
  • Resource "catalog" = content catalog qui reduit les appels exploratoires
  • Sampling : le serveur n'a pas besoin de cle API, il delegue au client
  • Transport configurable : stdio en local, streamable-http en deploiement distant

Les distracteurs typiques : "deployer directement en prod et observer", "utiliser un debugger Python attache" — pas faux, mais moins canonique.

5. Les outils integres de Claude Code (Task 2.5)

Le probleme que cela resout

Claude Code dispose d'outils integres pour interagir avec le systeme de fichiers et le terminal. Bien les connaitre evite de creer des outils MCP redondants et permet une investigation efficace du code.

Reference de selection

TacheOutilExemple
Trouver des fichiers par nom ou patternGlob**/*.test.tsx, src/components/**/*.ts
Chercher dans le contenu des fichiersGrepUn nom de fonction, un message d'erreur, un import
Lire un fichier en entierReadCharger un fichier pour l'analyser
Creer un nouveau fichierWriteEcrire un fichier depuis zero
Modifier precisement un fichier existantEditRemplacer un extrait via une correspondance de texte unique
Executer une commande shellBashgit, npm, tests, build
Fallback Read + Write : quand Edit echoue parce que le texte a remplacer n'est pas unique dans le fichier, la solution de repli est Read (charger le fichier complet) → modifier le contenu → Write (reecrire le fichier entier).

La strategie d'investigation incrementale

Plutot que de lire tous les fichiers d'un coup, construisez votre comprehension progressivement :

  1. Grep : identifier les points d'entree (definitions de fonctions, exports).
  2. Read : lire les fichiers identifies.
  3. Grep : trouver les usages (imports, appels).
  4. Read : lire les fichiers consommateurs.
  5. Repeter jusqu'a avoir une vue complete.
Pour l'examen : cette strategie incrementale (Grep → Read → Grep → Read) est la methode recommandee pour explorer un codebase inconnu. Elle evite de surcharger le contexte en ne lisant que les fichiers pertinents.

6. Synthese — les points cles

Conception d'outils

  • La description est le mecanisme n° 1 de selection par le LLM. Des descriptions vagues = misrouting.
  • Renommer, diviser ou remplacer les outils pour eliminer les chevauchements semantiques.
  • Attention aux associations involontaires creees par le system prompt.
  • Specifier les formats d'entree dans input_schema avec des exemples et documenter les edge cases.

Erreurs structurees

  • Toujours retourner isError, errorCategory (transient / validation / business / permission) et isRetryable.
  • Distinguer un echec d'acces (timeout) d'un resultat vide valide (zero correspondance).
  • Les erreurs generiques ("Operation failed") empechent toute recuperation intelligente — c'est l'anti-pattern principal.

Distribution et tool_choice

  • 4 a 5 outils max par agent, pas 18. Chaque agent ne recoit que les outils pertinents pour son role (scoped tool access).
  • Remplacer les outils generiques par des alternatives contraintes (fetch_url → load_document).
  • auto (par defaut) / any (garantir un appel d'outil) / forced selection (imposer un outil precis).

MCP

  • .mcp.json pour le projet (versionne dans le VCS), ~/.claude.json pour l'utilisateur (personnel).
  • Substitution de variables d'environnement (${GITHUB_TOKEN}) pour les secrets.
  • Trois primitives : tools (modele), resources (application), prompts (utilisateur).
  • resources = « content catalogs » qui reduisent les appels exploratoires.
  • Preferer les community servers pour les integrations standards ; custom servers pour les workflows specifiques.
  • Roots : le SDK n'applique pas automatiquement les restrictions — implementer is_path_allowed().
  • Transports : stdio (local) / SSE = StreamableHTTP (distant, bidirectionnel) / HTTP stateless (multi-instance).

JSON Schema (input_schema)

  • oneOf (exactement un sous-schema) / anyOf (au moins un) / allOf (tous).
  • Validation conditionnelle if/then/else pour les exigences contextuelles.
  • Contraintes : format (email, uri, uuid), minLength/maxLength, minimum/maximum, pattern (regex).
  • "additionalProperties": false pour rejeter les champs hallucines.
  • 3 piliers anti-hallucination : nullable, enum + "other"/detail, enum + "unclear".
  • Le tool_use garantit la syntaxe ; valider la semantique cote app (retry-with-feedback, voir D4).

Authentification MCP

  • stdio : variables d'env (${TOKEN} dans env) — pattern le plus simple.
  • HTTP : headers Authorization: Bearer, X-API-Key.
  • OAuth 2.1 : delegation par utilisateur — endpoints standardises par la spec MCP.
  • mTLS : enterprise haute securite.
  • Multi-tenant : OAuth + scopes ; token de service partage = anti-pattern.
  • Anti-pattern absolu : token en clair dans .mcp.json versionne (l'historique Git le retient).

Outils integres

  • Glob (fichiers par pattern), Grep (contenu), Read/Write (fichier entier), Edit (modification ciblee), Bash (commandes).
  • Edit echoue → fallback Read + Write.
  • Investigation incrementale : Grep → Read → Grep usages → Read consommateurs.

7. Questions d'auto-evaluation

Q1 : Les logs montrent que les requetes "analyze the uploaded quarterly report" sont routees vers le web-search agent 45 % du temps au lieu du document analysis agent. Les descriptions des outils sont analyze_content ("analyzes content and extracts key information") et analyze_document ("analyzes documents and extracts key information"). Comment corriger ?
A) Ajouter un pre-routing classifier.
B) Renommer le web-search tool en extract_web_results et mettre a jour sa description.
C) Ajouter des few-shot examples au coordinateur.
D) Enrichir seulement la description du document analysis tool.

Reponse : B

Le probleme est un chevauchement semantique entre les deux descriptions. Renommer le web-search tool en extract_web_results avec une description differenciee elimine l'ambiguite a la racine. Les options A et C ajoutent de la complexite sans traiter la cause. L'option D n'elimine pas le chevauchement cote web-search.

Q2 : Un document analysis subagent a un outil generique fetch_url. Les logs montrent qu'il telecharge des pages de moteurs de recherche au lieu de documents. Quel fix appliquer ?
A) Remplacer fetch_url par load_document qui valide les URLs vers des formats document.
B) Retirer fetch_url et router via le coordinateur.
C) Filtrer les domaines de moteurs de recherche.
D) Ajouter des instructions dans le prompt.

Reponse : A

C'est le principe du moindre privilege applique au niveau de l'interface : contraindre l'outil lui-meme plutot que de compter sur des instructions textuelles (option D, peu fiable) ou d'ajouter de la complexite architecturale (option B). L'option C est un filtre fragile qui ne couvre pas tous les cas.

Q3 : Un outil MCP echoue avec {"isError": true, "content": "Operation failed"}. Pourquoi c'est un anti-pattern ?
A) L'agent ne peut pas decider s'il faut faire un retry, modifier la requete, ou escalader.
B) Le format JSON est incorrect.
C) isError devrait etre false.
D) Le message est trop court.

Reponse : A

Une erreur generique ne fournit aucune information pour la prise de decision. Sans errorCategory ni isRetryable, l'agent ne sait pas si l'erreur est transient (retry), validation (corriger l'entree), business (expliquer a l'utilisateur) ou permission (escalader). Le format JSON est valide (B est faux), isError: true est correct (C est faux), et la longueur du message n'est pas le probleme (D est faux).

Q4 : Vous voulez que Claude appelle toujours extract_metadata en premier avant tout autre traitement. Quelle valeur de tool_choice utiliser ?
A) {"type": "auto"}
B) {"type": "any"}
C) {"type": "tool", "name": "extract_metadata"}
D) Ajouter "always call this first" dans la description.

Reponse : C

La forced selection ({"type": "tool", "name": "extract_metadata"}) garantit que Claude appellera exactement cet outil. auto (A) laisse Claude libre de ne pas appeler d'outil. any (B) force un appel mais sans garantir lequel. L'option D repose sur une instruction textuelle dans la description, ce qui est moins fiable qu'une contrainte programmatique.

Q5 : Vous concevez un outil create_refund. La logique metier exige que amount et reason soient obligatoires seulement si type == "refund". Si type == "info_only", ces champs ne servent a rien. Comment exprimer cela proprement dans le input_schema ?
A) Mettre tous les champs dans required.
B) Utiliser if/then : si type == "refund", alors required: ["amount", "reason"].
C) Documenter la regle uniquement dans la description.
D) Creer deux outils separes.

Reponse : B. JSON Schema draft-07 supporte if/then/else pour la validation conditionnelle. C'est le pattern propre quand des champs deviennent obligatoires selon une autre valeur. A force le modele a fournir amount meme pour info_only (et il l'inventera). C deplace la responsabilite sur le modele (peu fiable). D est correct mais ajoute de la complexite et du misrouting potentiel — preferer if/then si la logique est simple.

Q6 : Votre extracteur de metadonnees produit un JSON valide mais Claude ajoute parfois des champs inattendus comme "notes": "..." qui ne sont pas dans votre schema. Comment empecher cela cote schema ?
A) Ajouter "notes" dans properties.
B) Mettre "additionalProperties": false au niveau de l'objet.
C) Lister les champs interdits dans une enum.
D) Utiliser tool_choice: any.

Reponse : B. "additionalProperties": false rejette tout champ non declare dans properties. Le tool_use garantit que la sortie respecte le schema, donc Claude est contraint de ne produire que les champs documentes. A le rendrait acceptable mais ne resout pas la question (le modele continuerait a inventer d'autres champs). C n'a pas de sens semantique. D ne contraint pas la structure du resultat.

Q7 : Votre equipe construit un serveur MCP qui doit acceder aux dossiers Google Drive de chaque developpeur (chacun ses propres fichiers). Quel pattern d'authentification ?
A) Un service account Google partage, token dans .mcp.json.
B) Une cle API par developpeur en variable d'environnement.
C) OAuth 2.1 — chaque utilisateur autorise individuellement, le client MCP gere les tokens.
D) Authentification HTTP Basic.

Reponse : C. Quand l'authentification est par utilisateur (ressources personnelles), seul OAuth 2.1 fournit la delegation propre : chaque dev passe par le flow d'autorisation Google, recoit son propre access_token, et le client MCP le stocke. A est dangereux (un service account partage = tout le monde voit tout). B fonctionnerait pour des cles techniques, mais Google Drive ne distribue pas de cles API par utilisateur — il faut un flow OAuth. D est obsolete et inadapte.
