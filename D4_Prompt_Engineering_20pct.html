1. Des critères explicites plutôt que des instructions vagues (Task 4.1)

Le problème que cela résout

Quand vous demandez à Claude de "vérifier la précision des commentaires de code" ou d'"être conservateur dans ses signalements", il interprète ces instructions vagues de manière inconsistante. Un même pattern sera signalé dans une pull request mais ignoré dans la suivante. Les critères explicites éliminent cette ambiguïté en définissant précisément ce qui constitue un problème.

Mauvais (vague) : "Check code comments for accuracy. Be conservative — report only high-confidence findings."
Bon (critères explicites) :
Signaler un commentaire comme problématique uniquement si :
1. Le commentaire décrit un comportement qui contredit le code réel.
2. Le commentaire référence une fonction ou une variable inexistante.
3. Un TODO/FIXME porte sur un bug déjà corrigé dans le code.

Ne pas signaler : un style simplement daté, des formulations légèrement imprécises, des commentaires manquants (catégorie séparée).

Les deux formulations, côte à côte, sous forme de texte de prompt copiable :

# Prompt vague — ne pas faire
Check code comments for accuracy. Be conservative — report only
high-confidence findings.

# Prompt à critères explicites — à faire
Flag a comment ONLY IF one of these conditions holds:
  1. The comment describes behaviour that contradicts the actual code.
  2. The comment references a function or variable that does not exist.
  3. A TODO/FIXME refers to a bug already fixed in the code.

DO NOT flag:
  - merely dated style or phrasing;
  - slightly imprecise wording that does not contradict the code;
  - missing comments (handled as a separate category).

For each finding, output: file:line, condition number, quoted comment,
and the code fragment that contradicts it.

Les critères de severity

SeverityDéfinitionExemple
CRITICALÉchec à l'exécution pour les utilisateursNullPointerException dans le traitement des paiements
HIGHVulnérabilité de sécuritéSQL injection, XSS, contrôle d'autorisation manquant
MEDIUMBug logique sans impact immédiatTri incorrect, erreur off-by-one
LOWQualité de codeDuplication, algorithme sous-optimal pour de petits volumes

L'effet domino des false positives

Concept clé : des taux élevés de false positives dans certaines catégories (style : 52 %, documentation : 48 %) érodent la confiance des développeurs dans toutes les catégories, y compris les catégories précises (sécurité : 8 %). La solution : désactiver temporairement les catégories à fort taux de false positives, conserver les catégories de haute précision, puis améliorer les prompts des catégories problématiques avant de les réactiver.

2. Le few-shot prompting (Task 4.2)

Le problème que cela résout

Une instruction textuelle comme "sois plus précis" peut être interprétée de dizaines de manières différentes. Un exemple concret, lui, montre exactement le format et la logique de décision attendus. Le modèle généralise ensuite ce pattern à de nouveaux cas, sans se contenter de répéter l'exemple.

Le few-shot prompting est la technique la plus efficace pour obtenir des sorties cohérentes et actionnables. Fournissez 2 à 4 exemples ciblés sur les scénarios ambigus, chacun accompagné du raisonnement qui justifie la décision.

Les cinq types de few-shot examples

1. Scénarios ambigus (avec rationale)

Request: "My order is broken"
Action: Call get_customer → lookup_order → check status.
Rationale: "broken" peut signifier article endommagé ; il faut les détails.

Request: "Get me a manager"
Action: Appeler immédiatement escalate_to_human.
Rationale: Le client demande explicitement un humain. Ne pas tenter de résoudre.

2. Output formatting

{"location": "src/auth/login.ts:42",
 "issue": "SQL injection in username parameter",
 "severity": "critical",
 "suggested_fix": "Use parameterized query"}

3. Code acceptable vs code problématique

// Acceptable (ne pas signaler) :
const items = data.filter(x => x.active);

// Problématique (signaler) :
const items = data.filter(x => x.active == true);  // Utiliser === (strict)

4. Extraction depuis différents formats de documents

Citation inline : "the rate is 42% (Smith, 2023)"
→ {"value": "42%", "source": "Smith, 2023", "type": "inline"}

Référence bibliographique : "The rate is 42%. [1]"
→ {"value": "42%", "source": "reference_1", "type": "bibliography"}

5. Mesures informelles et non standard

(Source : guide officiel, Task 4.2 — « handling informal measurements, varied document structures ».)

Texte : "about two handfuls of rice"
→ {"amount": "~100g", "original_text": "two handfuls", "précision": "approximate"}

Texte : "a pinch of salt"
→ {"amount": "~1g", "original_text": "a pinch", "précision": "approximate"}
Les few-shot examples sont particulièrement efficaces pour l'extraction de mesures informelles et non standard, car ces unités sont trop diverses pour être gérées par des instructions purement textuelles. Le modèle généralise le pattern de conversion à de nouvelles mesures qu'il n'a pas vues dans les exemples.

Les règles de format normalization

Quand vous utilisez des JSON Schema stricts pour la sortie structurée, ajoutez des règles de normalization dans le prompt :

  • Dates : toujours ISO 8601 (YYYY-MM-DD) ; "yesterday" → calculer la date absolue.
  • Monnaie : montant numérique + code devise ; "five bucks" → {"amount": 5, "currency": "USD"}.
  • Pourcentages : fraction décimale ; "half" → 0.5.
Réflexe d'examen : choisissez le few-shot dès que l'énoncé réunit deux signaux — les instructions sont déjà détaillées et la sortie reste inconsistante, et le modèle doit trancher sur des cas non listés à l'avance. C'est le seul levier qui enseigne une distinction généralisable ; tout ce qui énumère échoue sur le cas suivant.

Distracteurs : réécrire les instructions plus fermement (l'énoncé dit qu'elles sont déjà détaillées : le manque est l'illustration, pas l'insistance) ; maintenir une liste blanche des patterns acceptés (ne couvre que ce qui y figure, jamais le pattern qui apparaîtra demain) ; post-traiter la sortie (un filtre aval ne reconstruit pas une décision que le modèle n'a pas produite) ; baisser la sensibilité (supprime les vrais positifs au même rythme que les faux).

3. Les sorties structurées avec tool_use et JSON Schema (Task 4.3)

Le problème que cela résout

Quand vous avez besoin que Claude retourne des données dans un format précis — pour alimenter un pipeline, une API ou un système d'automatisation — le texte libre est insuffisant : il faut un mécanisme qui contraigne la forme de la sortie.

tool_use + JSON Schema est la réponse du référentiel. On définit un outil dont l'input_schema est le schéma de sortie voulu, on force son appel avec tool_choice, et on lit le résultat dans le bloc tool_use. Le guide l'énonce sans réserve : c'est l'approche la plus fiable pour une sortie conforme au schéma, et elle élimine les erreurs de syntaxe JSON.

Ce qu'elle ne garantit pas, et que le guide souligne : la correction sémantique. Les valeurs peuvent être fausses, les totaux peuvent ne pas s'additionner, une donnée peut atterrir dans le mauvais champ. C'est l'objet de la section 4 (validation programmatique).
Le guide fait loi ici. La documentation Anthropic recommande aujourd'hui les Structured Outputs natifs — output_config: {"format": {"type": "json_schema", ...}}, ou client.messages.parse() côté SDK Python. Ce mécanisme n'existe pas dans le guide CCAR-F v1.0 : ne le proposez pas comme réponse à l'examen. Si une option mentionne output_config.format, ce n'est pas celle attendue.

L'exemple travaillé

Le schéma de sortie voulu se déclare comme l'input_schema d'un outil, et l'extraction se lit dans le champ input du bloc retourné — l'outil n'est jamais exécuté.

{
  "tools": [{
    "name": "extract_invoice",
    "description": "Records the fields extracted from an invoice document.",
    "input_schema": {
      "type": "object",
      "properties": {
        "invoice_number": { "type": "string" },
        "issue_date":     { "type": "string", "description": "ISO 8601" },
        "total":          { "type": "number" },
        "company_name":   { "type": ["string", "null"] }
      },
      "required": ["invoice_number", "total"]
    }
  }],
  "tool_choice": { "type": "tool", "name": "extract_invoice" }
}

// La réponse porte un bloc tool_use dont `input` EST l'extraction :
{
  "stop_reason": "tool_use",
  "content": [{
    "type": "tool_use",
    "name": "extract_invoice",
    "input": { "invoice_number": "INV-2024-0912", "issue_date": "2024-09-12",
               "total": 1249.90, "company_name": null }
  }]
}
Distracteurs :
output_config.format / messages.parse() — la méthode de la documentation actuelle, absente du guide : ce n'est pas la réponse attendue à l'examen.
tool_choice: "auto" — laisse au modèle la liberté de répondre en texte ; l'extraction n'est plus garantie.
Demander du JSON en prose, avec le schéma décrit dans le prompt — réintroduit exactement les erreurs de syntaxe que tool_use élimine.
Réparer la sortie à la regex après coup — répare des symptômes au lieu de contraindre la forme à la source.

Le paramètre tool_choice

ValeurComportementCas d'usage
autoClaude décide s'il utilise l'outil ou nonScénarios où l'outil n'est pas toujours pertinent
anyClaude doit utiliser au moins un outil parmi ceux disponiblesForcer une sortie structurée sans imposer un outil précis
Forced (nom spécifique)Claude doit utiliser exactement cet outilExtraction avec un schéma précis et obligatoire
{"type": "none"}Claude ne doit utiliser aucun outilForcer une réponse en texte libre même si des outils sont déclarés

Les règles de conception d'un schéma

RègleDétailRaison
required vs optionalNe marquer un champ comme required que si l'information est toujours disponible.Sinon le modèle fabrique des valeurs pour remplir le champ.
Champs nullableUtiliser "type": ["string", "null"] pour les informations potentiellement absentes.Le modèle peut retourner null au lieu d'halluciner une valeur.
enum + "other" + détailAjouter une valeur "other" accompagnée d'un champ de détail textuel.Évite de perdre les données qui ne rentrent pas dans les catégories prédéfinies.
enum + "unclear"Permettre au modèle d'exprimer son incertitude.Un "unclear" honnête vaut mieux qu'une catégorie incorrecte.

Erreurs syntaxiques vs erreurs sémantiques

TypeExempleComment les traiter
Syntax errorsJSON invalide, mauvais type de champÉliminées par tool_use + JSON Schema
Semantic errorsTotaux incohérents, valeur dans le mauvais champValidation programmatique + retry-with-feedback

4. Validation, retry-with-feedback et self-correction (Task 4.4)

Le problème que cela résout

Même avec un JSON Schema strict, les valeurs extraites peuvent être incorrectes (un total qui ne correspond pas à la somme des lignes, une date dans le mauvais champ). Il faut un mécanisme pour détecter ces semantic errors et guider le modèle vers une correction.

Le pattern retry-with-feedback

  1. Extraire les données du document.
  2. Valider (Pydantic, JSON Schema, règles métier).
  3. En cas d'erreur → relancer avec : le document original + l'extraction incorrecte + les erreurs de validation spécifiques.
Erreur spécifique : "Le champ 'total' vaut 150, mais la somme des
line_items vaut 145. Revérifier les valeurs des line_items."
Le retry-with-feedback fonctionne parce que Claude reçoit un signal d'erreur précis. Un message générique comme "il y a une erreur" est inefficace ; il faut pointer exactement le champ et l'écart observé.

Quand le retry fonctionne — et quand il est inutile

Retry efficaceRetry inutile
Erreurs de format (date dans le mauvais format)L'information est absente du document source
Erreurs structurelles (champ place au mauvais endroit)Le contexte requis se trouve dans un document externe non fourni
Incohérences arithmétiques

La self-correction

Faire extraire à la fois le stated_total (valeur déclarée dans le document) et le calculated_total (somme calculée par le modèle). Si les deux diffèrent, un champ conflict_detected: true permet de gérer l'écart en aval.

{"stated_total": 150,
 "calculated_total": 145,
 "conflict_detected": true,
 "line_items": [...]}

Le champ detected_pattern pour le suivi des false positives

(Source : guide officiel, Task 4.4, Key skill.)

Ajouter un champ detected_pattern dans les résultats structurés pour enregistrer quel pattern de code a déclenché un signalement. Quand les développeurs rejettent un signalement, ce champ permet d'analyser systématiquement les false positives : quels patterns déclenchent des alertes non pertinentes, et comment affiner les prompts en conséquence. 
{"location": "src/auth/login.ts:42",
 "issue": "Potential null pointer",
 "severity": "medium",
 "detected_pattern": "optional chaining absence on user.profile.email",
 "suggested_fix": "Add optional chaining: user?.profile?.email"}

Pydantic comme outil de validation

  • Structural validation : types, champs required, contraintes d'enum.
  • Semantic validation : validateurs personnalisés (somme des lignes = total, date de début < date de fin).
  • Boucles validate-retry : Pydantic valide → en cas d'échec, le message d'erreur est renvoyé au modèle → nouvelle tentative. Ce cycle se répète jusqu'à validation ou limite de retries.
  • Génération de JSON Schema : Pydantic peut générer le schéma utilisé pour tool_use, ce qui crée une source de vérité unique entre la validation et la définition du schéma.

Cookbook : boucle validate-retry production-ready

Voici l'implémentation de référence d'un pipeline d'extraction avec retry-with-feedback. Le code est volontairement minimaliste pour mettre en évidence les 5 éléments clés : schéma unique source-of-truth, tool_use, structural validation, semantic validation, retry avec contexte de l'erreur.

from pydantic import BaseModel, Field, model_validator
from anthropic import Anthropic
from typing import Optional

# 1. SCHEMA UNIQUE — source de vérité pour tool_use ET validation
class LineItem(BaseModel):
    description: str
    quantity: int = Field(ge=1)
    unit_price: float = Field(ge=0)
    line_total: float = Field(ge=0)

class Invoice(BaseModel):
    invoice_number: str
    issue_date: str = Field(pattern=r"^\d{4}-\d{2}-\d{2}$")  # ISO 8601
    company_name: Optional[str] = None  # nullable contre l'hallucination
    currency: str = Field(pattern=r"^[A-Z]{3}$")  # ISO 4217
    line_items: list[LineItem]
    stated_total: float
    calculated_total: float

    @model_validator(mode="after")
    def check_total_consistency(self):
        """Semantic validation : la somme des lignes doit égaler stated_total."""
        computed = sum(li.line_total for li in self.line_items)
        if abs(computed - self.calculated_total) > 0.01:
            raise ValueError(
                f"calculated_total ({self.calculated_total}) ne correspond pas "
                f"à la somme des line_items ({computed:.2f})"
            )
        if abs(self.stated_total - self.calculated_total) > 0.01:
            # Tolère : on signale via un champ side-channel plutôt qu'un raise
            pass  # le caller décidera quoi faire avec stated vs calculated
        return self

# 2. PIPELINE avec retry-with-feedback
def extract_invoice(document_text: str, max_retries: int = 3) -> Invoice:
    client = Anthropic()
    messages = [
        {"role": "user", "content": f"Extract structured data from:\n{document_text}"}
    ]

    for attempt in range(max_retries):
        response = client.messages.create(
            model="claude-sonnet-5",
            max_tokens=2048,
            tools=[{
                "name": "submit_invoice",
                "description": "Submit extracted invoice data.",
                "input_schema": Invoice.model_json_schema()  # 3. SCHEMA AUTO-GÉNÉRÉ
            }],
            tool_choice={"type": "tool", "name": "submit_invoice"},  # 4. FORCED tool_use
            messages=messages
        )

        # Récupérer le tool_use block
        tool_use = next(b for b in response.content if b.type == "tool_use")

        try:
            # 5. VALIDATION (structurelle + sémantique en une passe)
            invoice = Invoice.model_validate(tool_use.input)
            return invoice

        except Exception as e:
            # RETRY-WITH-FEEDBACK : on renvoie l'erreur à Claude
            messages.append({"role": "assistant", "content": response.content})
            messages.append({
                "role": "user",
                "content": [{
                    "type": "tool_result",
                    "tool_use_id": tool_use.id,
                    "is_error": True,
                    "content": (
                        f"Validation failed: {e}\n"
                        f"Please fix the specific issue and resubmit."
                    )
                }]
            })

    raise RuntimeError(f"Échec d'extraction après {max_retries} tentatives")
Les 5 éléments de robustesse :
  1. Schema unique : Pydantic génère le JSON Schema injecté dans input_schema via .model_json_schema(). Pas de divergence possible entre validation et tool definition.
  2. Forced tool_use : tool_choice: {"type": "tool", "name": "..."} garantit que Claude appelle le tool — pas de texte libre.
  3. Structural validation : types, contraintes (ge, pattern), Optional nullable.
  4. Semantic validation : @model_validator vérifie la cohérence inter-champs (totaux, dates).
  5. Retry-with-feedback : l'erreur Pydantic est renvoyée à Claude via tool_result avec is_error: true. Claude voit son erreur précise et corrige.
EXAM TIP : sur les questions de scénario Structured Data Extraction, le pattern "boucle validate-retry avec Pydantic comme source de vérité" est la réponse canonique. Les distracteurs typiques : "ajouter plus de few-shot examples" (peut aider en amont mais ne résout pas la validation runtime), "post-processer avec un parser custom" (réimplémente ce que Pydantic fait déjà), "augmenter max_tokens" (sans rapport).

5. Le traitement par lots — Message Batches API (Task 4.5)

Le problème que cela résout

Certains traitements (audits de sécurité hebdomadaires, rapports de dette technique, génération de tests nocturne) ne nécessitent pas de réponse immédiate. La Message Batches API permet de les exécuter avec une réduction de coût de 50 %, en échange d'un délai de traitement pouvant aller jusqu'à 24 heures.

Paramètres clés de la Message Batches API

ParamètreValeur
Réduction de coût50 %
Fenêtre de traitementLa plupart des batchs terminent en moins d'1 heure, jusqu'à 24 heures maximum
SLA de latenceAucun garanti
Limites de taille100 000 requêtes ou 256 Mo par batch (la limite atteinte en premier s'applique)
Conservation des résultats29 jours
Ordre des résultatsNon ordonné — matcher chaque réponse par custom_id, jamais par position
Boucle d'outils interactiveNon supportée : pas de boucle d'outils interactive, une passe, une réponse
Correlation requête/réponseVia le champ custom_id
Piège d'examen : la Message Batches API n'a pas de boucle d'outils interactive : une passe, une réponse. Si votre workflow nécessite que Claude demande des fichiers supplémentaires via des appels d'outils itératifs, la Message Batches API est fondamentalement incompatible. Chaque requête du batch produit une seule réponse, sans possibilité d'échanges supplémentaires.

Quand utiliser chaque API

TâcheAPIPourquoi
Vérification pre-merge (bloquante)SynchroneLe développeur attend ; un délai de 24 h est inacceptable.
Rapport de dette technique (overnight)BatchLe résultat est attendu pour le lendemain matin ; 50 % d'économies.
Audit de sécurité hebdomadaireBatchPas urgent, économies significatives sur de gros volumes.
Revue de code interactiveSynchroneRéponse immédiate requise pour le développeur.

L'exemple travaillé

Chaque requête porte son custom_id ; c'est lui, et non la position, qui rattache la réponse au document source.

POST /v1/messages/batches
{
  "requests": [
    { "custom_id": "order-10231",
      "params": { "model": "claude-sonnet-5", "max_tokens": 1024,
                  "messages": [{ "role": "user", "content": "Extract: ..." }] } },
    { "custom_id": "order-10232",
      "params": { "model": "claude-sonnet-5", "max_tokens": 1024,
                  "messages": [{ "role": "user", "content": "Extract: ..." }] } }
  ]
}

// Résultats : ordre non garanti, on apparie par custom_id.
{ "custom_id": "order-10232", "result": { "type": "succeeded", "message": { ... } } }
{ "custom_id": "order-10231", "result": { "type": "errored",   "error": { ... } } }
// → ne resoumettre que order-10231.
Distracteurs :
Basculer un contrôle bloquant pré-merge sur le Batches API — les 50 % d'économie séduisent, mais il n'existe aucune garantie de latence et un développeur attend.
Le rendre acceptable en ajoutant du polling de statut — « souvent plus rapide » n'est pas un engagement.
Tout garder en synchrone pour éviter les problèmes d'ordre — méprise : custom_id corrèle les réponses, l'ordre n'est pas un problème.
Batch avec repli temporisé vers le synchrone — deux chemins de code pour un problème qui disparaît en appariant chaque API à sa charge.

Planification du SLA avec la Message Batches API

La borne arithmétique. Dans le pire cas, le délai total vu par le livrable est temps d'attente en file + temps de traitement. Avec un plafond de traitement de 24 heures et un engagement de 30 heures :
30 h − 24 h = 6 heures de file au maximum.
Ces 6 h sont le maximum théorique : une soumission qui tomberait pile à 6 h épuise exactement le budget et ne laisse rien pour un batch qui traite au plafond, ni pour re-soumettre un document échoué.

Le chiffre du guide. Sur ce même couple 30 h / 24 h, l'exemple officiel du référentiel (Task 4.5) retient des fenêtres de 4 heures — soit 2 h de marge sous la borne. C'est ce chiffre qu'il faut retenir pour l'examen : on soumet un batch au moins toutes les 4 heures pour tenir un engagement de 30 heures.
Réflexe d'examen : sur une question de cadence de soumission, ne rendez jamais la borne théorique — on garde une marge sous l'engagement. Posez le calcul (engagement − plafond de traitement) pour obtenir le maximum, puis descendez en dessous.

Distracteur : la valeur qui épuise exactement le budget — ici 6 heures pour un SLA de 30 h. Elle est arithmétiquement juste et c'est ce qui la rend séduisante, mais elle ne laisse aucune marge pour un batch traité au plafond ni pour une re-soumission. Le guide répond 4 heures.

La gestion des échecs

  • Correlation via custom_id : chaque requête du batch a un custom_id unique qui permet de relier chaque réponse au document source.
  • Re-soumettre uniquement les documents échoués : identifier les échecs par leur custom_id, ne pas relancer tout le batch.
  • Adapter la stratégie pour les échecs (ex. : découper les documents trop longs en morceaux).
  • Affiner les prompts sur un échantillon avant de lancer un traitement de masse.

6. La revue multi-instance et multi-pass review (Task 4.6)

Le problème que cela résout

Quand Claude génère du code puis le relit dans la même session, il conserve son contexte de raisonnement et est moins susceptible de questionner ses propres décisions. C'est le biais fondamental de la self-review : le modèle retient son reasoning et est donc moins enclin à remettre en cause ses propres choix.

Une instance de review indépendante (sans accès au contexte de génération) détecte mieux les problèmes subtils. C'est le même principe que la peer review en développement logiciel : une perspective externe, sans biais de confirmation.

Pourquoi la self-review est limitée

Limitation clé : le modèle qui a généré le code conserve son reasoning. Il a déjà considéré et rejeté certaines alternatives. Lors de la relecture, il a tendance à confirmer ses décisions initiales plutôt qu'à les challenger. Une instance indépendante, qui ne voit que le code (sans le contexte de génération), détecte les problèmes que le générateur a rationalisés.

La multi-pass review pour les grosses pull requests

Quand une pull request modifie plus de 10 fichiers, une seule passe produit des résultats inconsistants. La solution :

PassePérimètreCe qu'elle détecte
per-file passChaque fichier analysé individuellementBugs locaux, qualité, vulnérabilités
intégration passRelations entre les fichiersTypes incohérents, dépendances circulaires, flux de données cassés
# Passe 1 — per-file, une invocation par fichier
for file in $(git diff --name-only main...HEAD); do
  review --scope="$file" \
         --prompt="Local issues only: bugs, security, quality in THIS file."
done

# Passe 2 — intégration, une seule invocation sur les signatures et les appels
review --scope="$(git diff --name-only main...HEAD)" \
       --prompt="Cross-file only: type mismatches across module boundaries,
                 circular dependencies, broken data flow. Ignore local issues."
Réflexe d'examen : quand l'énoncé décrit une revue contradictoire d'un fichier à l'autre — un pattern signalé ici, le même approuvé là, dans la même PR — nommez la cause : dilution de l'attention, pas manque de contexte. Toute option qui donne plus de contexte au lieu de réduire le périmètre de chaque passe est fausse.

Distracteurs : passer à un modèle à fenêtre plus large (confond capacité de contexte et qualité d'attention) ; trois passes complètes avec vote de consensus (exiger 2 détections sur 3 supprime les vrais bugs qui ne sont vus qu'une fois) ; demander aux développeurs de découper leurs PR en lots de 3-4 fichiers (déplace la charge sur les humains sans améliorer le système).

Verification pass avec confidence self-report

Un troisième skill de review Task 4.6 : demander au modèle de produire, pour chaque finding, un score de confidence explicite qui l'accompagne. Ce signal sert à router la revue (haute confidence → validation rapide ou auto-approuvé ; basse confidence → revue humaine approfondie) et à calibrer les seuils de revue au fil du temps.

Voir aussi : D1, section 4 pour le détail de la multi-pass review dans le contexte de la décomposition de tâches.

7. Synthèse — les points clés

Critères et few-shot

  • Les critères explicites battent les instructions vagues ("be conservative" ne fonctionne pas de manière fiable).
  • Les false positives élevées dans une catégorie érodent la confiance dans toutes les catégories.
  • Le few-shot prompting est la technique la plus efficace pour la cohérence. Fournir 2 à 4 exemples ciblés avec le raisonnement.
  • Cinq types de few-shot examples : scénarios ambigus, output formatting, code acceptable vs problématique, formats de documents, mesures informelles.
  • Règles de format normalization : dates → ISO 8601, monnaie → montant + code, pourcentages → décimal.

Sorties structurées

  • tool_use + JSON Schema = la méthode la plus fiable. Garantit la syntaxe, pas la sémantique.
  • tool_choice : auto (le modèle décide), any (au moins un outil), forced (outil spécifique).
  • Champs nullable pour éviter la fabrication de valeurs. enum avec "other" + détail et "unclear" pour l'extensibilité.
  • Le champ detected_pattern dans les résultats permet le suivi systématique des false positives.

Validation et retry-with-feedback

  • Pattern retry-with-feedback : document original + extraction incorrecte + erreur spécifique.
  • Les retries sont efficaces pour les erreurs de format, structurelles et arithmétiques.
  • Les retries sont inutiles quand l'information est absente du document source ou nécessite un contexte externe.
  • Self-correction via stated_total / calculated_total + conflict_detected.
  • detected_pattern pour tracer les false positives et affiner les prompts.
  • Pydantic : structural validation, semantic validation, boucles validate-retry, génération de JSON Schema.

Message Batches API

  • 50 % d'économies, jusqu'à 24 h de traitement, pas de SLA de latence.
  • Pas de multi-turn tool calling : une requête = une réponse.
  • Batch pour les traitements overnight et hebdomadaires. Synchrone pour tout ce qui bloque un développeur.
  • Planification SLA : engagement − plafond de traitement = borne maximale (30 h − 24 h = 6 h), mais on garde une marge — l'exemple du guide retient des fenêtres de 4 h pour un SLA de 30 h.
  • Correlation via custom_id. Re-soumettre uniquement les documents échoués.

Revue

  • La self-review est moins efficace qu'une instance indépendante (le modèle retient son reasoning et ne remet pas en cause ses décisions).
  • Instance de review indépendante sans accès au contexte de génération → meilleure détection des problèmes subtils.
  • multi-pass review : per-file pass (issues locales) + intégration pass (relations inter-fichiers).
  • Verification pass : le modèle auto-reporte une confidence par finding, pour router/calibrer la revue.

8. Auto-évaluation (7 questions)

Questions de révision — Domain 4

Q1 (D4) — A rule the reviewer reads differently every run

Scenario: A reviewer inspects database migration scripts under the instruction "flag risky migrations, and be careful". The same DROP COLUMN statement is flagged on Monday and approved on Thursday.

Question: What change makes the verdicts stable?

A) Add few-shot examples of migrations the team called risky, letting the reviewer infer the threshold.

B) Spell out the criteria: a dropped column, an in-place table rewrite, or an unbatched backfill.

C) Run the check twice and keep the findings both runs agree on, taking agreement for stability.

D) Restrict the check to migrations touching production schemas, where an inconsistent verdict actually costs something.

Answer: replace the adjective with named, testable conditions

Why: "risky" carries no operational meaning, so every run reinvents the threshold. Named conditions — flag a migration only when it drops a column, rewrites a table in place, or backfills rows without batching — turn a matter of taste into something the model applies the same way twice.

Why the others are wrong:

  • Illustrates a rule that still has not been defined.
  • Intersecting two unstable verdicts drops genuine findings.
  • Shrinks the volume without making any remaining decision consistent.
Q2 (D4) — A nightly job's clock, borrowed by a live feature

Scenario: A retailer re-translates its whole product catalog every night through the Message Batches API, and the job has come back within twenty minutes every night this quarter. A product manager cites that record to move the storefront's live "translate this review" button onto the same endpoint.

Question: Where does the argument break?

A) A live button submits one request at a time, and the endpoint prices a submission as a unit rather than per token, so a batch holding a single review would forfeit the discount that motivates the move.

B) The nightly run clears in twenty minutes because it lands in the emptiest hours of the queue, while the button would submit all day long, when the same endpoint runs slower.

C) Twenty minutes is an observation, not a commitment: this endpoint publishes no latency guarantee at all, and the twenty-four hours it quotes bound how long processing may run rather than promise when any one submission will be handed back.

D) The endpoint draws no line between a scheduled caller and an interactive one, so the button is entitled to whatever treatment the nightly job already gets.

Answer: a measured time is not a service commitment

Why: no latency is promised here at all. The twenty-four hours describe how long processing may run, not what a given run will take, and last quarter's twenty minutes records the queue those particular nights happened to meet. A shopper waiting in front of a button needs a bound this endpoint never offers.

Why the others are wrong:

  • The discount applies per token, so a submission of one still earns it.
  • Makes the flaw a matter of which hour it is, when no hour comes with a promised turnaround.
  • True of the endpoint, and beside the point: the requirement lives in the workload.
Q3 (D4) — Cases graded by whoever invented them

Scenario: A pipeline invents synthetic test cases for a billing rules engine, then asks the same conversation to mark which ones actually break the stated rule. The marking comes back almost entirely clean, yet a QA engineer opens the file and finds cases that break nothing at all.

Question: What restores the marking?

A) Score each generated case for confidence, and review only the weak ones.

B) Keep the marking in the same conversation, but restate the rule in a fresh turn before the model decides, so it judges against the wording rather than its memory.

C) Hand the rule and the bare cases to a second instance that never saw the generation turn.

D) Ask for the marking inline, one verdict written under each case as it is produced, so no case is judged far from the rule that prompted it.

Answer: a second instance carrying none of the generation context

Why: the generator still holds the reasoning that produced each case, so rereading confirms those choices instead of testing them. An instance handed only the rule and the artifact reads them the way an outside grader would.

Why the others are wrong:

  • Confidence reported from inside the same context inherits the same blind spot.
  • Restating the rule leaves the anchoring transcript exactly where it was.
  • Ties the verdict tighter still to the moment of generation.
Q4 (D4) — A gift with no price on it

Scenario: A museum catalogs donation paperwork into a schema where acquisition_price is a compulsory string. Many pieces arrive as gifts and carry no amount anywhere on the paperwork, yet those records come back with tidy round figures nobody can trace.

Question: What should change?

A) Fill the field with zero when the paperwork names no amount, so every record can satisfy the schema without invention.

B) Let the field accept null and take it out of the compulsory set.

C) Split the intake in two: route gift paperwork to a second schema without the field, and keep purchases on the current one.

D) Have the model report how sure it is of each amount, so catalogers can set aside the values it is least sure of.

Answer: let absence be a legal value, and stop demanding one

Why: as long as the field is compulsory, the model chooses between breaking the schema and producing an amount, and it produces one. A field the source may leave empty needs a representation for empty; a gift then comes back with no price instead of a convincing one.

Why the others are wrong:

  • Zero is an amount, and downstream nothing separates a gift from a bargain.
  • Whoever routes the paperwork faces the same missing information first.
  • The invented figure stays in the catalog, and the field still demands one.
Q5 (D4) — Hours that do not add up (Select the 2 correct answers.)

Scenario: A payroll extractor returns a timesheet whose reported_hours reads 38, while the daily entries sum to 41. The payload parses and matches the schema.

Question: Which two statements fit this situation?

A) It is a syntax error; enforcing the tool schema more strictly makes the payload conform.

B) It is a semantic error; validate programmatically and resubmit on failure with the exact discrepancy named.

C) It is a syntax error; a few more worked examples keep the arithmetic from drifting.

D) It is a semantic error; carry computed_hours beside reported_hours with a conflict_detected flag.

E) It is a syntax error; a higher output token cap leaves room to finish the arithmetic.

Answers: a semantic error, handled by a validate-retry loop and by an explicit conflict flag

Why: a forced tool call guarantees the shape of the payload, never the truth of its values. The retry carries the document, the rejected extraction and the named gap, which lets the model correct itself; carrying both figures plus a flag keeps the conflict visible to downstream code.

Why the others are wrong:

  • Schema enforcement removes malformed payloads, not disagreement between fields.
  • Confuses shape with meaning; examples do not repair a systematic arithmetic gap.
  • The token cap bounds output length, not the correctness of a sum.
Q6 (D4) — What the batch endpoint will and will not do (Select the 2 correct answers.)

Scenario: A media team scores the sentiment of 40,000 archived reviews every Sunday night through the Message Batches API.

Question: Which two statements about that run are correct?

A) Results come back in submission order, so a response position is a safe key to its review.

B) Results come back unordered, so each one is paired with its request through the custom_id the team set.

C) A batch request buys one pass and one answer, so a multi-turn tool loop does not fit.

D) The endpoint halves latency along with price, so the weekly job finishes well inside its window.

E) Results are discarded once the batch completes, so the run must stream them out as they land.

Answers: pair results by their correlation key, and expect a single pass per request

Why: the two structural facts that decide whether a workload fits. The correlation key ties each response to its document and lets the team resubmit only the failures; a batch request buys one turn, so a step whose code must execute a tool and hand the result back to the model has nowhere to run.

Why the others are wrong:

  • Position is exactly what must not be trusted; results are unordered.
  • Confuses price with latency: the discount is real, the latency is not guaranteed.
  • Results stay retrievable for 29 days; no streaming workaround is needed.
Q7 (D4) — Quantities nobody can enumerate

Scenario: A recipe importer turns ingredient lines into structured quantities. Informal amounts such as "a couple of handfuls" or "a splash" come back empty or wildly wrong, and fresh phrasings appear with every new import.

Question: What is the most effective fix?

A) Lower the extractor's sensitivity so it reports fewer questionable quantities and the wildest values disappear.

B) Keep a lookup table mapping every informal phrase to a quantity, extended by hand as new phrasings appear in the imports.

C) Show two to four worked examples, each one carrying the reasoning that takes an informal phrase to a converted amount rather than the amount alone.

D) Reject ingredient lines carrying no explicit unit and route them to manual entry, so no invented quantity ever reaches a published recipe.

Answer: worked examples that teach the conversion, not a dictionary of phrases

Why: two to four targeted examples are enough, and the reasoning each one carries is what does the teaching: the model reads how the phrase was resolved, not merely what it was resolved to. A rationale shown inside the example teaches a transferable rule, so the model generalizes to phrasings it has never seen — which is what a space nobody can enumerate demands. Written instructions cannot describe this mapping; examples demonstrate it.

Why the others are wrong:

  • Suppresses good extractions at the same rate as bad ones.
  • Covers only what is listed, and the scenario says the list is never complete.
  • Buys correctness by refusing to do the work: every informal line becomes a manual task, and informal lines are most of the corpus.
